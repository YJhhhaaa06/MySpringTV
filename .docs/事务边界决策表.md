## 〇、旧事务模型的两个硬约束（理解差异的起点）

```java
// util/TransactionTemplate.java:26-33
public <T> T execute(TransactionAction<T> action) {
    Connection conn = MyConnectionPool.getConnection();   // ← 每次都是新连接
    conn.setAutoCommit(false);
    T result = action.execute(conn);                       // ← conn 手工穿透到 DAO
    conn.commit();
    ...
}
```

| 约束 | 后果 |
|------|------|
| **每次 `execute` 取新连接** | 无传播语义：内层事务与外层互不可见，**组合操作无法原子化** |
| **无事务同步回调** | "提交后动作"（缓存失效/MQ 投递）只能靠代码行序 + 注释纪律 |

**Spring 带来的变化**：`@Transactional` 默认 `REQUIRED` 传播 + `TransactionSynchronization` 回调。
**风险点**：这两个变化都会**静默改变语义**——把旧的两个独立事务合成一个原子事务，或让副作用时机改变。
所以下表是**必须**的，不是可选文档。

### U-1 `registerAndLogin` —— 注册与自动登录是两个独立事务

**位置**：`user/service/UserService.java:100-120`

**旧行为**（原始注释即规格说明）：

> 注册并自动登录（池 U-16 兜底）：**注册成功即视为成功**。
> 自动登录失败时不再向上抛异常，而是返回 `token == null` 的 `LoginVO`，由调用方提示"注册成功，请手动登录"。
> **不重试、不补登：注册与自动登录仍是两个独立事务（注册事务先提交，再做登录查询）**。

代码结构：

```java
public LoginVO registerAndLogin(RegisterCommand rc) {
    long id = registerAsUser(rc);          // 事务 1：校验占用 + 插入，提交
    try {
        return login(id, rc.getPassword()); // 事务 2：查用户 + 校验密码
    } catch (BusinessException e) {
        // 注册已提交 ⇒ 不能把自动登录失败报成注册失败
        LOGGER.log(Level.WARNING, "注册后自动登录失败, userId=" + id + ", 改为提示手动登录");
        return new LoginVO(id, rc.getUsername(), null);   // token = null
    }
}
```

**决策**：✅ **保持**（拆分是刻意的，不是妥协）

**新实现**：

```java
// 编排方法：本身不加 @Transactional，保持"注册已提交"这一事实
public LoginVO registerAndLogin(RegisterCommand rc) {
    long id = registerAsUser(rc);          // 内部 @Transactional(REQUIRED)，独立提交
    try {
        return login(id, rc.getPassword());
    } catch (BusinessException e) {
        log.warn("注册后自动登录失败, userId={}, 改为提示手动登录", id);
        return new LoginVO(id, rc.getUsername(), null);
    }
}

@Transactional
public long registerAsUser(RegisterCommand rc) { ... }
```

> ⚠️ **反模式警告**：若把 `registerAndLogin` 整体标 `@Transactional`（"看起来更原子"），
> 自动登录失败会**回滚注册**——直接违反产品语义（用户以为注册失败，实际也没注册成功，
> 而旧行为是注册成功、提示手动登录）。这是本次迁移**最容易误改**的一处。

**迁移时必须固化的测试**：
- 正常注册 → 返回含 token 的 `LoginVO`
- 注册成功但随后登录失败 → **用户行仍存在**（不被回滚）+ `token == null`
- 手机号/用户名占用 → 抛 `DuplicatePhoneException` / `ConflictException`（不被兜底吞掉）

**位置**：`user/service/UserService.java:128-145`

**旧行为**：同一 `execute` 内先 `isPhoneUsed` / `isUsernameUsed`，再 `addUser`。

> 转成与 `ConflictException` 一致的对外响应——**这是新增的映射点，勿漏**。
>
> ---
>
> ## ⚠️⚠️ U-2 附注（S2 执行期实测发现，**本行声明的那条原子性当前并未真正生效**）
>
> **发现方式（实测，非推断）**：S2 期间为确认"`@Transactional` 是否真的在跑"，
> 用一个临时探针 spy `PlatformTransactionManager` 数 `getTransaction` 的调用次数，
> 分别测两条进入路径（探针用完已删，证据如下）：
>
> | 进入路径 | `getTransaction` 调用次数 | 结论 |
> |---------|------------------------|------|
> | 外部直调 `userService.registerAsUser(...)`（必经代理）| **1** | 事务生效（对照通过）|
> | 经 `userService.registerAndLogin(...)` 内部 `this.registerAsUser(...)` | **0** | **事务未开启** |
>
> 失败断言原文：`[PROBE-待判：registerAndLogin → this.registerAsUser 是否也开启事务（U-2 的原意）] expected: 1 but was: 0`
>
> **根因**：Spring AOP 的**自调用**——`registerAndLogin` 与 `registerAsUser` 同在一个类内，
> 内部调用用的是 `this`（目标对象），**不经过代理**，故 `@Transactional` 被静默跳过。
> 不报错、不留日志，只有把事务管理器当探针才看得见。
>
> **影响评估（据实，不夸大）**：线上路径是 Controller → `registerAndLogin`
> ⇒ 生产环境里 `registerAsUser` 实际**跑在无事务的自动提交连接上**。
> 唯一键 `uk_users_phone` 仍兜住并发竞态，**对外可观察行为（占用 → 409）不受影响**，
> 故属"声明与事实不符"，不是可见缺陷。丢掉的只是"两次占用检查 + 插入"的快照一致性，
> 而这一致性本由唯一键覆盖。
>
> **为什么 U-2 没被测出来**：`TransactionBoundaryTests.注册失败必须回滚且不被吞掉`
> 调的是 `registerAsUser` **本身**（外部直调，必经代理）——恰好是探针里"生效"的那条路径。
> 也就是说：**测试选错了进入路径，把一条不生效的路径照成了绿灯**。
> 这是"测试迎合"的变体——不是跟着实现改测试，而是测了一条与生产不同的路径。
>
> **推荐修法（待拍板，本切片不动 slice 0）**——目标是同时满足 U-1 与 U-2：
> 1. 把编排逻辑 `registerAndLogin` 抽到**独立 bean**（如 `UserRegistrationService`，注入 `UserService`），
>    使"注册"与"自动登录"天然是两次跨 bean 调用；或
> 2. 在 `UserService` 内自注入代理（`@Lazy UserService self`）再调 `self.registerAsUser(...)`。
> 方案 1 分层更清晰（编排 vs 领域），方案 2 改动最小。
> ⚠️ **不要**用"给 `registerAndLogin` 加 `@Transactional`"来修——那会违反 U-1（见上方反模式警告）。
>
> **修完后必须补的测试**：一条断言"经 `registerAndLogin` 进入时 `registerAsUser` 处于事务中"
> 的回归用例（即把本次探针保留下来），否则同样的问题会再次静默复现。

### C-1 `grabCoupon` —— 扣库存与插订单必须原子（✅ 保持单事务）

**位置**：`coupon/service/CouponService.java:33`（方法 32-58）

**旧行为**：一个 `transactionTemplate.execute` 内包住两步写：

```java
int rows = couponDao.deductStock(conn, couponId);        // ① 原子扣库存（条件全在 SQL 内）
if (rows == 0) throw new ConflictException("库存不足或活动未开始/已结束");
couponDao.insertOrder(conn, couponId, userId, code);     // ② 插订单（1062 → ConflictException("您已抢过该优惠券")）
```

原注释只说明了日志纪律（T11-B"包装点即源头"），**未写明事务理由**——但语义是显然的：
"扣了库存却没有订单"= 白扣，"有订单却没扣库存"= 超发。二者都必须排除。

**关键机制**：两处异常都在 lambda **内部**抛出，`TransactionTemplate` 的
`catch (BusinessException) → rollbackQuietly(conn) → throw e`（`util/TransactionTemplate.java:34-36`）
把它们变成**回滚**。所以旧实现里"重复抢券"实际上**不会**把库存扣掉——
这不是巧合，是 C-1 最需要固化的行为。

**决策**：✅ **保持**（本来就是单事务）

**新实现**：`@Transactional`（`REQUIRED` 传播）。差异点两处，逐条表态：

1. **删掉 `e.getErrorCode() == 1062` 判断**（《切片计划》§一 明确要求）。
   MyBatis + Spring 的异常翻译把 1062 变成 `DuplicateKeyException`（`DataAccessException` 子类），
   经 `GlobalExceptionHandler.handleDuplicateKey` 统一映射为 409——正是 U-2 补注预告的映射点。
   > ⚠️ **契约差异（有意，勿当缺陷修）**：重复抢券的 `msg` 由 `"您已抢过该优惠券"`
   > 变为 `ErrorCode.CONFLICT.getMessage()` = `"操作冲突"`。
   > **HTTP 状态码与 body `code` 仍是 409，未变**；DoD #5 冻结的是"路径 / 信封 / 状态码"，`msg` 不在冻结范围。
   > 若要保住旧 msg，就得在异常出口按约束名 `uk_coupon_user` 反查语义——那是把 DB 细节泄露到出口层，
   > 且与"删掉错误码判断"的决策直接冲突。**取决策，不取 msg。**
2. **`deductStock` 的 `rows == 0` 分支原样保留**——它仍然是"库存不足 / 未开始 / 已结束"三合一的唯一判定点。

> ⚠️ **两条反模式警告**（后来者最容易"顺手优化"掉的地方）：
> 1. **不得把时间窗判断从 SQL 挪到 Java**。`begin_time <= NOW() AND end_time >= NOW()` 在 `UPDATE` 的
>    `WHERE` 里，与 `stock > 0` 是**同一条原子语句**的一部分；拆成"先 SELECT 判断时间窗、再 UPDATE"
>    会引入 TOCTOU 窗口（并发下判定与扣减之间活动可能刚开始/刚结束）。
> 2. **不得把 `insertOrder` 移出事务**（例如为了"减少锁持有"改成先插订单再扣库存、
>    或把扣库存改成非事务的 `UPDATE`）。这会破坏"库存只扣一次、失败必回滚"。

**迁移时必须固化的测试**：

- 抢券成功 → 200；`coupon_order` 新增 1 行、`coupon.stock` 减 1（**独立 oracle 直接查列**，不信任接口回显）；
  `data` 恰为 16 位 `[0-9A-Z]{16}` 券码
- 库存为 0 → 409，且**不产生订单行**、**库存不为负**
- 活动未开始 / 已结束 → 409（时间窗判定在 SQL 内，Service 层不可区分这三者）
- **同一用户重复抢 → 409，且库存只扣一次**（★核心：证明 `@Transactional` 回滚确实生效，
  而不是"扣了库存才发现重复"）
- **并发**：N 个线程抢库存 1 的券 → 恰好 1 成功、`stock == 0`、`coupon_order` 恰 1 行
- 未登录抢券 → 401（`@RequiresLogin`）

### C-3 `listMyCoupons` —— 只读，事务只是"取连接的手段"（⚠️ 有意改进）

**位置**：`coupon/service/CouponService.java:73`（方法 72-82）

**旧行为**：同 C-2，`transactionTemplate.execute` 包住一条 `SELECT ... JOIN`，**纯读**。

**决策**：⚠️ **有意改进**——去掉事务包装（同 U-3 / U-4）

### CM-1 `addComment` —— 插入评论 + 楼中楼归一化 + 跨表计数联动（✅ 保持单事务）

**位置**：`comment/service/CommentService.java:179`（方法 162-225）

**旧行为**：一个 `transactionTemplate.execute` 内完成 6 步，顺序即语义：

```java
if (!contentDao.isContentExist(conn, contentId)) throw new NotFoundException("被评论的内容不存在");   // ① 404
if (parentId != null && parentId != 0) {                                                              // ② 归一化
    if (!commentDao.isCommentExist(conn, parentId)) throw new ConflictException("被回复评论不存在或已删除");
    CommentCacheDTO parent = commentDao.findCommentById(conn, parentId);
    if (parent.getContentId() != contentId) throw new ConflictException("被回复评论不属于该视频或动态");
```

原注释（楼中楼口径，即规格说明）：

> 楼中楼：{@code parentId} 一律指向主楼。被回复评论本身是回复时，上溯挂到其主楼 id，

1. **校验顺序逐条保留**——它决定客户端拿到 404 还是 409，是契约的一部分，不是可有可无的细节。
2. **去掉 `Long[] effectiveParentId` 数组技巧**。旧代码用数组是因为要在 lambda 内改写被捕获变量
   （Java 编译约束）；新实现没有 lambda，直接用局部变量。
   **但"归一化后的 effectiveParentId 要活到事务外"这一事实必须保留**——旧代码用它决定
   提交后该失效哪个缓存（见 CM-4）。
3. **评论区开关改读 DB**：旧代码是 `contentCache.getContent(contentId)`，读的是**缓存**
   （cache-aside，miss 才回源 `loadContentFromDb`，其查询带 `is_deleted = 0`）。
   新实现直读 `SELECT comment_enabled FROM content WHERE id = ? AND is_deleted = 0`。
   > ⚠️ **有意改进（非事务边界，一并记录）**：直读 DB 消除了旧实现的**缓存陈旧窗口**——
   > 旧代码靠 `notifyCommentEnabledChanged` 失效 + TTL 自愈，作者刚关评论区时缓存可能仍是"开"。
   > 语义上不放松（关闭后仍不可发），只是**更即时**。补回位置：S5 接入 ContentCache 时，
   > 此处可改回缓存读（届时需一并考虑该窗口）。

**迁移时必须固化的测试**：

- 发主楼评论 → 200；`comment` 新增 1 行且 `parent_id IS NULL`；`content.comment_count` +1（**独立 oracle 直查列**）

### CM-2 `doDeleteComment` —— 软删除 + 计数回减（✅ 保持单事务）

**位置**：`comment/service/CommentService.java:240`（方法 239-287，入口 `deleteCommentByUser` / `deleteCommentByAdmin`）

**旧行为**：单事务内 ① `isCommentExist`（已删/不存在 → 404）② 取评论 ③ 权限

⑥ 主楼 → 整栋软删，回复 → 只删自己 ⑦ `content.comment_count -= deletedCount`
⑧ 删回复时主楼 `reply_count -1`。

原注释（**必须保留的顺序约束**）：

> 必须先计数再软删：{@code countFloorReplies} 过滤 {@code is_deleted=0}，若先软删会数到 0 导致计数少扣

配套口径（`CommentDao.countFloorReplies` 原注释）：

> 单删回复时 {@code comment_count} 已 -1；删主楼时再扣 "1(主楼) + 剩余未删回复数"，
> 与递增口径对称，**避免对已单删回复二次扣减导致负数**

**决策**：✅ **保持单事务**

**新实现**：`@Transactional`。三条**不得"顺手优化"**的地方：

1. **"先计数再软删"的顺序**——理由写在旧注释里，改了就会静默少扣计数。
2. **删主楼不扣 `reply_count`**（`if (!isMain && rootId != null)` 的 `!isMain` 是有意的：
   主楼已整栋删掉，其 `reply_count` 无意义）。
3. **`updateReplyCount` 的防负守卫**
   （`WHERE comment_id = ? AND reply_count + ? >= 0`）保留——它同时承担"防负"与"是否命中"两种作用。

**已知并接受的旧实现尖锐处**（**不修**，以旧实现为准）：`content.comment_count` 列类型是
`int unsigned`，而 `updateCommentCount` 无防负守卫（对比 `reply_count` 有）。
若评论存在但 `comment_count` 已是 0（数据不一致），删除会因 UNSIGNED 下溢报错 → 500。

> **已实测复现（S2 执行期，非推测）**：
> `Data truncation: BIGINT UNSIGNED value is out of range in '(\`tvdatabase\`.\`content\`.\`comment_count\` + -(1))'`
> —— 由 `content.comment_count = 0` 时执行 -1 触发，经 `DataAccessException` 出口变 500。
> 触发场景是**数据本身不自洽**（评论行存在但计数为 0），正常路径不会走到。
> 这是 TV 既有行为，本切片**原样保留**；修它（加 `GREATEST(...)` 或 `WHERE comment_count >= 1` 守卫）
> 属于行为改动，需单独立项，且要让 DoD 明确"这是改进不是回归"。
> 注：S2 的测试夹具必须让 `comment_count` 与评论行数自洽——否则会把这条尖锐处
> 误当成被测逻辑的缺陷（S2 期间踩过一次，已修夹具）。

**鉴权**：`deleteCommentByUser` 走 `/comment/delete`（TV `PROTECTED_EXACT` 含它 ⇒ 需登录）。
`deleteCommentByAdmin` 由 admin 模块调用（本批不搬 admin），故**本切片无端点暴露**，
但**要搬并测试**——它是 `doDeleteComment` 的 `isAdmin` 分支唯一入口，砍掉等于砍掉该分支语义，
且 admin 切片补回时会引入未测路径。

**迁移时必须固化的测试**：

- 删自己的主楼 → 主楼 + 楼内回复**整栋** `is_deleted=1`；`comment_count` 减
  **1 + 剩余未删回复数**；该主楼 `reply_count` **不动**
- 删自己的回复 → 仅该行 `is_deleted=1`；`comment_count` -1；主楼 `reply_count` -1
- ★**先单删一条回复，再删主楼** → 主楼删除时只扣 `1 + 剩余未删回复数`
  （这是 `countFloorReplies` 口径的核心回归点：**不得对已单删的回复二次扣减**）
- 删**别人**的评论 → **403**，且该行**未被软删**（失败不留副作用）

```java
commentCache.invalidateRoots(contentId) 或 commentCache.invalidateReplyUnder(...);   // 失效 comment 两键组
```

> 需回到 `CommentService.addComment` / `doDeleteComment`，把这三行副作用改为
> `@TransactionalEventListener(phase = AFTER_COMMIT)`（决策表 §三 模式 A）。
> 旧注释已写明为什么必须在**提交后**：事务内先失效会留窗口，并发读者按旧计数回填缓存，
> 表现为计数短暂陈旧（T34/U-22 的修复结论）。

### L-5 `LikeCacheService` 的 3 处 loader 事务 —— ⚠️ **有意改进：去掉事务**

**位置**：`like/service/LikeCacheService.java:326`（`loadUserLikeIds`）、`:344`（`loadLikeCount`）、
`:362`（`queryLikedIds`）

**旧行为**：三个 loader 各自用 `transactionTemplate.execute(conn -> ...)` 包住**一条纯读语句**
（成员全量 SELECT / `COUNT(*)` / `IN` 批量 SELECT），再手工 `catch (SQLException)` 包成 `ServerException`。

**决策**：⚠️ **有意改进 —— 去掉事务包装**（同 U-3/U-4、C-2/C-3）。纯读无原子性需求，
旧事务只是"取连接的手段"。

**★ 这同时回答了《决策表》§三 模式 B 的第 1 个待定项：「回填是否需要在事务内？」→ 否。**
理由：回填只读一条语句，无多语句一致性需求；而且 loader 是在**缓存层内部**被调用的，
给它加事务会把"读缓存"这件事也拖进事务边界，反而**扩大**事务范围（缓存本不该有事务语义）。

**★ 第 2 个待定项「回填失败是否要影响读结果（降级 vs 报错）」→ 必须区分两种失败，
这是 TV 的核心设计，逐字保留：**

| 失败 | 处置 | 理由 |
|------|------|------|
| **Redis 失败** | 降级直查 DB，**不影响结果** | 缓存是加速器，挂掉不能让点赞接口 500（TV NEEDS 4.2 / H5） |
| **DB 失败** | **上抛**（500） | "无答案可答"——降级成空值会把"读不到"伪装成"没有"，是更坏的语义 |

**新实现**：loader 变成普通的方法调用（无事务注解），DB 异常照旧上抛
（由 `GlobalExceptionHandler` 的 `DataAccessException` 分支转 500 并记堆栈——
TV 手写的 `ServerException` 包装退役）。

### L-6 提交后副作用：`@TransactionalEventListener(AFTER_COMMIT)` —— ⚠️ 有意改进（**本切片核心**）

**位置**：`LikeService.java:72-75`（内容点赞）、`:96-98`（取消）、`:131-133`（评论点赞）、`:154-156`（取消）

**旧行为**：事务 lambda **之后**紧跟 2 行副作用，靠**注释纪律**维系：

```java
// 缓存更新放在事务提交后
cache.likeContent(userId, contentId);
contentCache.notifyLikeCountChanged(contentId);
```

《迁移参照系》§2.4 已定性这是【妥协】：写错位置就是"事务回滚但缓存已改"，
只能靠评审兜住。

**决策**：⚠️ **有意改进 —— 改为 `@TransactionalEventListener(phase = AFTER_COMMIT)`**
（《决策表》§三 模式 A 的落地）

**★ 为什么这里不能像 S2 那样"裁剪"**：S2 裁剪失效是因为**当前不存在读缓存**（失效是空操作）；
S3 **恰恰就是引入读缓存的那一片**，缓存更新是这个切片的交付内容本身。
所以 AFTER_COMMIT 机制必须在这里真正落地——否则 S3 的核心价值
（把"提交后"从注释纪律变成**类型保证**）就丢了。

**新实现**：`LikeService` 在事务内发布事件（内容 id / 用户 id / 方向），
`@TransactionalEventListener(AFTER_COMMIT)` 监听器调用 `LikeCache`。
框架保证"事务没提交就不触发"，无需再靠代码行序 + 注释。

> ⚠️ **同步记录一处裁剪**：旧代码那两行里的**第二行**（`contentCache.notifyLikeCountChanged` /
> `commentCache.notifyCommentLikeChanged`）在本切片**无法交付**——`ContentCache` / `CommentCache`
> 属 **S5**，当前没有内容/评论读缓存可失效 ⇒ 该动作是空操作。
> 与 S2 的裁剪同性质、同纪律：**不为尚不存在的缓存预埋失效逻辑**。
> **补回位置**：S5 接入两个 Cache 后，在同一个 `AFTER_COMMIT` 监听器里补上这两次失效。

**迁移时必须固化的测试**（本切片最有价值的测试，旧代码靠注释维系、最易写错处）：

- ★ **事务回滚后缓存未被污染**：用 `@MockitoSpyBean` 让 `updateLikeCount` 抛异常
  ⇒ 事务回滚 ⇒ 断言 **Redis 里那个 count key / set key 根本不存在**
  （因为没有提交 ⇒ AFTER_COMMIT 监听器不触发）。**这是 AFTER_COMMIT 机制的存在证明**：
  若有人把它改回"事务内更新缓存"或"写在方法体末尾"，此用例立刻失败。
- ★ **反向对照**：正常点赞提交后 ⇒ 断言两个 key 确实被建立/更新（否则上一个测试可能是"永远不写"而误过）
- 缓存 key 形状断言：`user:likeSet:{userId}` 含该 contentId、`content:likeCount:{id}` 值正确
- ★ **Redis 不可用时降级**：读路径在 Redis 故障下仍返回 DB 正确答案，且**不抛**
- ★ **DB 失败仍旧上抛**：loader 的 DB 异常不被降级吞掉（区分两种失败）

### L-7 S3 缓存层的保真度表态（模式 B 的逐项落地）

**背景**：`LikeCacheService` 依赖 TV `cache` 包的 **2,528 行 / 12 文件**
（`CacheAside` 624、`SetCache` 397、`CacheKeys` 296、`CacheStats` 130、`RedisAccess` 90
+ `SingleFlight`/`CacheResult`/`JacksonCodec`/`CacheStatus`/`CacheDomain`/`ZSetCache`/`RedisCircuitBreaker`）。

**决策：⚠️ 有意改进——按决策⑤做「显式封装层」的精简版（约 250 行，放 `like/cache/`），
不搬 TV 的 cache 包。**

**为什么不"完整搬"（实测结论，不是偏好）**：该基建**不能开箱即用**，搬它等于先做一次基建重构——
要改 10 类东西，其中 5 类本就在**不迁移清单**或**已判给框架**：

| 要改的 | 证据 | 归属 |
|--------|------|------|
| 连接池 `MyRedisPool` → Spring JedisPool | `RedisAccess` 唯一依赖 | **不迁移清单** |
| `RedisCircuitBreaker` → Resilience4j | `RedisAccess` **硬依赖**它（141 行） | 决策⑤，留后 |
| `CacheStats` 打点 → Actuator/Micrometer | 平行机制 | **不迁移清单** |
| `AppConfig.getLikeTtlSeconds()` → `@ConfigurationProperties` | `AppConfig` 847 行覆盖链 | **不迁移清单（整体退役）** |
| Jackson 2 → 3（`JacksonCodec`） | `com.fasterxml.jackson.databind` + `JavaTimeModule`（J3 已内置） | SOP 坑 1 |
| Jedis `Pipeline`/`Response` 原生 API（3 文件） | 直接调 Jedis | 需改写或暴露原生连接 |
| `@Component`/`@InjectConstructor`（8/4 文件） | 自研 IoC | 机械替换 |
| `LogUtil`（5 文件） | 自研日志 | 不迁移 |
| `TransactionTemplate` + `Connection conn` | loader 形态 | 管道删除 |
| `CacheKeys` 296 行里 like 只用 5 个工厂 | content/comment/follow/feed 的 key | 搬进来 90% 是无主代码 |

**保留（骨架 + 低成本高价值）**

1. **DB 是唯一真理源**：读 miss → 回源 DB → 回填；写先落 DB，**提交后**才碰缓存（L-6）
2. **两个 key 族**（T4 反转后的**用户维度**，与 TV 现状一致）：
   `content:likeCount:{id}` / `comment:likeCount:{id}`（String 整数）、
   `user:likeSet:{userId}` / `user:commentLikeSet:{userId}`（Set&lt;id&gt;）
3. ★ **条件写防"残缺缓存"**：只在 key **已存在**时才 `INCR/DECR/SADD/SREM`；冷 key 不创建半套数据。
   **用 Lua 一趟原子执行**（`DefaultRedisScript`）——保住 TV 的 N7 修复，
   不退回"探存在→再写"的竞态窗口
4. ★ **失败降级不抛**：Redis 异常 → 读直查 DB、写失效 key 让读自愈；点赞接口不因 Redis 挂掉 500
5. **TTL 与命中续期**：key 带 TTL，由 `video.cache.like-ttl` 给出（替代 `AppConfig`，TV 原值 15 分钟）
6. **批量状态**：Redis 侧单 set 多成员；DB 侧 `IN (...)` 用 `<foreach>`（《迁移参照系》§2.1 的"白赚"项）
7. **三态读**：hit-data / miss→回填 / 异常→降级 DB
8. **区分 Redis 失败与 DB 失败**（见 L-5 的表）

**有意去掉（逐条记录影响，不是默默省）**

| 去掉的 | 影响 | 严重度 |
|--------|------|--------|
| **单飞 SingleFlight（防击穿）** | 同一 key 并发 miss 各打一次 DB（N 次而非 1 次）。结果仍来自 DB，**正确性不变**；且进程内单飞在多实例下本就只挡一部分 | 低 |
| **空标记 `empty:...`（防穿透）** | **从未点赞过的用户**每次读状态都回源 DB（常见路径，读放大最明显的一条） | **中** |
| **`CacheStats` 打点** | 失去缓存命中率指标；参照系本就要它收敛到 Actuator（尚未接） | 低 |
| **`RedisCircuitBreaker` 熔断** | Redis 整体故障时每请求要等 Jedis 超时（已配 1000ms）而非快速失败 | 中 |
| **`CacheAside`/`SetCache` 通用框架层** | 不搬泛型三态/codec/多域 key 工厂；like 形态直接写在 like 的缓存类里。**等 S5 出现第二个使用方再抽公共层**（rule of three——避免 S2 那种"为尚不存在的东西预埋抽象"） | — |

> **补回位置（逐项）**：
> - 空标记 / 单飞 → 若 S5 的读路径感到读放大或击穿，回到 `LikeCache` 的两个读方法补
> - 熔断 → 接 Resilience4j 时（决策⑤留后）在缓存读写外层加
> - 打点 → 接 Actuator/Micrometer 时
> - 通用框架层 → S5 搬 `ContentCache`/`CommentCache` 时，与 like 的形态一起抽 `common/cache`

**一处顺带的简化（有理由，非偷懒）**：TV 在**冷 miss 批量**时打两次 DB
（`findLikedContentIds` 的 IN 子查询出答案 + `findLikedContentIdsByUser` 全量 loader 回填）。
因"miss 必然回填"，那次 IN 查询是**冗余**的 ⇒ 新实现冷 miss 只用全量 loader（1 次）。
但 **`findLikedContentIds`（IN + `<foreach>`）仍搬并测试**——它服务**降级路径**：
Redis 挂掉时按请求的 id 批量作答，不该为 3 个 id 去拉用户全量点赞史。

```java
if (alreadyFollowed) throw new ConflictException("已关注，不可重复操作");

userDao.updateFollowCount(conn, userId, 1);
userDao.updateFollowerCount(conn, followedUserId, 1);
return autoBigVState.evaluate(conn, followedUserId);      // 同事务、同 conn（fail-atomic）
```

`deleteFollow` + 两个计数 `-1` + `evaluate`。

**决策**：✅ **保持单事务**（"关系行"与"两侧计数"必须同进同退；否则计数漂移）

**新实现**：`@Transactional`（`REQUIRED`）。要点四条，逐条表态：

1. **校验顺序逐条保留**（决定 409 / 200 的分支）：
   - 自我关注 / 自我取关的**文案不同**（`"不能关注自己"` / `"不能取关自己"`），**保留不一致**（同 L-3 的纪律）。

     可观察行为不变（异常都在写操作之前抛出）。

   - 取关未关注 → `"未关注，不可取消"`。
2. **并发仍靠唯一键兜底**：`follow.uk_user_follow(user_id, followed_user_id)`
   ⇒ 并发重复关注撞键抛 `DuplicateKeyException` → 全局出口 409（同 C-1 / U-2 / L-1 的映射点）。
3. **`autoBigVState.evaluate` 留在事务内**（同 conn、计数之后）——见盘点 B 的裁定。
4. ⚠️ **已知并接受的旧实现尖锐处（不修）**：`users.follow_count` / `follower_count` 是

### F-6 `AutoBigVStateService.evaluate` —— 事务内新增语句（✅ 保持，见盘点 B 的裁定）

**位置**：`user/service/AutoBigVStateService.java:89-109`；调用点 `FollowService.java:77` / `:234`

**旧行为**：滞回判定——`粉丝数 >= threshold` ⇒ `INSERT IGNORE auto_bigv`（返回 affected==1 即 UPGRADED）；
`粉丝数 < ratio × threshold` ⇒ `DELETE auto_bigv`（affected==1 即 DOWNGRADED）；带内 ⇒ 不动。
**affected rows 即 edge 信号**（刻意不用"比较 before/after"，并发下会重复触发）。

**决策**：✅ **保持**——留在**调用方事务内、同一 conn**（fail-atomic：判定输入是刚写入的计数真值；
失败则整体回滚，不给"计数已变但状态没跟上"的中间态）。原注释已写明理由，不重复论证。

**新实现**：
- 搬 `AutoBigVStateService` + `UserDao` 的两个幂等 SQL（`insert ignore into auto_bigv(user_id) values(?)` /
  `delete from auto_bigv where user_id=?`，**affected rows 语义必须在 Mapper 层保住返回值**）。
- 阈值 / 系数改由 `BigVProperties`（`video.bigv.*`）提供，替代 `FeedBigVConfig.current()` 快照。
- 配置非法（ratio ∉ (0,1]）**照旧向上抛**（fail-fast，不静默降级）。
- `@Transactional` 在该方法上**不能标**——它必须在**调用方事务内**跑；
  标了会因 `REQUIRED` 传播而**并进**已有事务（行为恰好一致），但语义上它是"事务内的一段逻辑"，
  且标了会掩盖"它必须被事务内调用"这一约束 ⇒ **不标**，由 `FollowService` 的 `@Transactional` 覆盖。

**迁移时必须固化的测试**：

- 关注使粉丝数达线 ⇒ `auto_bigv` **新增 1 行**；再次达线 ⇒ 不重复新增（幂等 `INSERT IGNORE`）
- 取关使粉丝数跌破降级线 ⇒ `auto_bigv` 行**被删**；带内 ⇒ **不动**（滞回：已升者不掉回）
- `evaluate` 抛异常 ⇒ **整个关注事务回滚**（关系行与计数一并回滚）
- ⚠️ 阈值默认 10000 ⇒ **必须用低阈值覆盖的独立测试上下文**才能触发（见测试类说明）

> **为什么这条要"搬"而 notifier 要"裁"**：`evaluate` 在**事务内**（改的是事务的语句集与失败面），
> notifier 在**事务后**（是下游异步投递）。前者砍掉 = 静默少写一张表；后者砍掉 = 下游尚未存在。

> **★ 关于去掉 `partial` 标记（T11-C）——这是本切片最需要解释的一条**
>
> TV 的 T11-C 把"集合不变量"从「数据 key 存在 ⇒ 完整」放宽为「**无 partial 标记 ⇒ 完整**」，
> 以便"百万粉丝的博主分页时只装载前缀"。其代价是**四处特判**：① 单条/批量判定在部分态下
> **未命中要回落 DB**；② 全量读要**先补齐**；③ 写路径遇部分态一律**双 DEL**；④ `total` 在部分态改走**计数口径**。
>
> **本切片回到 T11-C 之前（T7）的口径：key 存在 ⇒ 完整。** 理由是**可观察行为完全一致**而复杂度显著更低：
> - 返回的 ids 与 total 逐字节一致（部分态下 `total` 走 `users.follow_count`，完整态走 `ZCARD`；两值由 F-1 同事务维护，恒等）；
> - 顺序口径一致（均为升序）；
> - 唯一差别是**装载量**：miss 时全量装载（**大列表会退化为 U-18 的"百万行装载"**），且需要
>   `getAllFollowedUserIds` / `getFollowerUserIds` 两个全量 loader（后者自 T11-C 起在 TV 里已是**零调用**）。
> - 当前无生产数据、无规模压力 ⇒ 收益为 0、风险不为 0（四处特判，每处写错都"不报错"）。
>
> **补回位置**：接入压测或真实规模数据时，回到 `FollowCache` 的窗口读加回"前缀装载 + partial 标记"，
> **以 TV 的 `ZSetCache` 为参照**；届时四处特判需一并回补，并补"部分态下判定未命中必须回落 DB"的测试。
>
> **另一处顺带的简化（有理由，非偷懒）**：TV 用**独立的计数缓存** `user:followCount:{id}` /
> `user:followerCount:{id}`（`CacheAside` 三态读 + 写后 Lua 条件 INCRBY）。去掉 `partial` 后，
> 该计数缓存在本切片的**唯一用途**只剩"降级路径的 total"——直查 DB 一列即可，**不值得为它建一族 key**。
> 故本切片**不建计数缓存**，降级路径的 total 走 `userDao.getFollowCountById` / `getFollowerCountById`。

### G-1 内容写路径 4 处 —— ✅ 保持单事务

**位置**：`ContentService` `:265`（开关）/ `:319`（删媒体）/ `:353`（改文案）/ `:374`（删作品）

**旧行为**：各自一个 `transactionTemplate.execute` 包住"校验 + 多条写"。`deleteContent` 是**最宽的一条**：

```java
findOwnedContent(conn, contentId, userId);                 // ① 存在 + 所有权
contentMediaDao.findMedia(conn, contentId);                // ② 取全部 url（返回值要交给调用方清理文件）
contentDao.softDeleteContent(conn, contentId);             // ③ 软删内容
commentDao.softDeleteByContentId(conn, contentId);         // ④ 级联软删评论
contentLikeDao.deleteByContentId(conn, contentId);         // ⑤ 物理删点赞记录
contentMediaDao.deleteByContentId(conn, contentId);        // ⑥ 物理删媒体记录
```

**决策**：✅ **保持单事务**。③④⑤⑥ 必须同进同退：任一步失败而其余已落库，会留下
"内容已软删但评论/点赞/媒体仍在"或反之的**不可自愈的不一致**（且没有补偿机制）。
`deleteMedia` 的"删一行 + 重排 sort"同理（重排失败会让 `sort` 出现空洞，前端 `index+1` 定位失准）。

**新实现**：`@Transactional`（`REQUIRED`）。要点：

1. **校验顺序逐条保留**：存在性 → 所有权（`NotFoundException("内容不存在")` /
   `ForbiddenException("只能操作自己的作品")`）；`deleteMedia` 的 `type != 2` 前置校验
   （`ParamException("仅支持删除图片")`）在**事务外**（TV 亦在事务外，`updateContentInfo` 的三条
   校验同理在事务外）——保留"参数错不占事务"的性质。
2. **`content:index` 的剔除与 `comment:comments:*` 的失效在提交后**（G-3）。
3. **⚠️ 已知并接受的旧实现尖锐处（不修）**：`deleteMedia` 只做 `content:index` + 内容 key 的刷新，
   **不失效 `content_media` 层面的任何缓存**（TV 亦无此类缓存）——不是缺陷。
4. **物理文件清理：本切片裁剪**（范围裁定 1）。

**迁移时必须固化的测试**（每条含独立 oracle）：

- 开关：作者本人 → 200；非作者 → **403** + `comment_enabled` 列**未变**；内容不存在 → **404**
- 编辑：标题空 → 400、标题 >50 → 400、简介 >5000 → 400（**且不产生任何写**）；非作者 → 403
- 删媒体：非图片 type → 400；删除后 `content_media` **行数 −1** 且剩余图片 `sort` **连续 1..n**（直查列）
- 删作品：`content.is_deleted=1`、`comment.is_deleted=1`（全部）、`content_like` **行数 0**、
  `content_media` **行数 0**（四条独立 oracle）；且 Redis 里 `content:{id}` / `content:comments:*` **均不存在**

### G-2 `ContentService.search` —— ⚠️ 有意改进：去事务

**位置**：`ContentService.java:88`（方法 86-113）

**旧行为**：事务回调**只**承载两条 DB 查询（`countKeywordSearch` + `keywordSearchInBrief`），
**查完即提交归还连接**，再在事务外做缓存批量读（TV 的 T12 专门这么改的，注释写明
"消除外层事务持连接 + miss 装载再取新连接"）。

**决策**：⚠️ **有意改进——去掉事务包装**（同 U-3/U-4、C-2/C-3、L-5、F-3）。两条**纯读**无原子性需求；
TV 的事务只是"取连接的手段"。**去掉后与 TV 的对外行为完全一致**——事务本来就已经在缓存读之前结束了；
去掉只是少了 BEGIN/COMMIT 两次往返。

**新实现**：直调 Mapper，**不加事务注解**。SQL 原样保留（含
`ORDER BY c.create_time DESC, c.id DESC`——T15 的 tie-breaker 修复，两条分支都有）。
分页口径**归一到域级常量**（`page<1→1`；`pageSize` 缺省/≤0/超上限 → **100**；
非法值回落缺省而非 500）——**与 follow 一样照搬旧口径**，因为旧 pytest 对它有逐字断言。

**迁移时必须固化的测试**：见 G-2 末尾（T19 契约）。

- 缺省 == 显式 `page=1&pageSize=100` 响应**逐字节一致**（非空列表比对）
- `pageSize=999 → 100`；`pageSize=51` **原样回显**；`pageSize=abc` → **200 且回落 100**（旧 500 坑）
- ★ **同秒内容的页间顺序 = id 降序**（T15）：把 N 行 `create_time` 钉到同一秒 → `pageSize=1` 逐页取
  → 断言 `id 降序` 且页间不重不漏（单字符 `LIKE` 与多字符 `MATCH` **两条分支都要测**）
- 关键词空白 → **400**（`"输入不能为空"`）

### G-3 提交后副作用 —— ⚠️ 有意改进（模式 A 的第 3 次落地，且**首次跨两个 Cache**）

**旧形态**（事务 lambda 之后紧跟缓存动作，靠注释纪律）：

| 位置 | 提交后动作 |
|------|-----------|
| `ContentService.setCommentEnabled:282` | `contentCache.updateCommentEnabled(contentId)` |
| `ContentService.updateContentInfo:363` / `deleteMedia:333` | `contentCache.refreshContent(contentId)` |
| `ContentService.deleteContent:399-403` | `contentCache.removeContent` + `commentCache.invalidateComments` + `likeService.deleteContentLike` |
| `LikeService.likeContent/…`（S3 已落地）| `contentCache.notifyLikeCountChanged(contentId)` / `commentCache.notifyCommentLikeChanged(commentId)`——**S5 补回**（见 L-6 的裁剪说明） |
| `CommentService.addComment:215-224`（CM-3 要求补回）| `contentCache.notifyCommentCountChanged` + `commentCache.invalidateRoots/invalidateReplyUnder` |
| `CommentService.doDeleteComment:275-286`（同上）| 同上 |

**决策**：⚠️ **有意改进——统一改为 `@TransactionalEventListener(phase = AFTER_COMMIT)`**
（S3 的 L-6 首个实例、S4 的 F-4 第 2 次落地；S5 是第 3、4 次，并**首次出现"一次事件驱动两个 Cache"**）。

**新实现**：`content/event/{ContentCacheChangedEvent,ContentCacheChangedListener}` 承载**失效语义**
（`REFRESH` / `REMOVE` / `COMMENT_ENABLED` / `INVALIDATE_COMMENTS` 四种意图），
`comment/event/{CommentCacheChangedEvent,CommentCacheChangedListener}` 承载评论侧失效
（`INVALIDATE_ROOTS` / `INVALIDATE_REPLY_UNDER` / `INVALIDATE_COMMENTS`）。
`LikeChangedListener` 内补上两行（L-6 的补回位置），`CommentService` 两处写路径改为**发事件**。

> **为什么把"失效"也做成事件，而不是"直接在 Service 里调 Cache"**：
> 失效必须在**提交后**（事务内先失效会留窗口：并发读者按旧值回填，表现为计数短暂陈旧——TV 的 T34/U-22 结论）。
> 直接调用就要么把它写在 `@Transactional` 方法体末尾（**一旦有人调整顺序就静默坏掉**），
> 要么在 Service 里手工注册 `TransactionSynchronization`（重复样板）。事件把时序变成**类型保证**。

**测试（本切片最有价值的一条之一）**：

- ★ **事务回滚后缓存未被污染**：`@MockitoSpyBean` 让事务内某一步抛 `DataAccessException`
  ⇒ 回滚 ⇒ 断言相关 key **根本不存在**（或保持预热原值）。**这是 AFTER_COMMIT 的存在证明。**
- ★ **反向对照**：正常提交 ⇒ 断言 key 确实被刷新/删除（排除"永不写缓存"的假绿）。
- ★ **删作品的"两个 Cache 都被失效"**：只证明其中一个被失效不足以证明链路完整。

### G-4 `ContentCache` / `CommentCache` 的 13 处 loader 事务 —— ⚠️ 有意改进：去事务

**位置**：`ContentCache` 4 处（`:250` `:391` `:440` `:725`）、`CommentCache` 8 处
（`:124` `:249` `:321` `:338` `:371` `:483` `:551` `:637`）

**旧行为**：每个 loader 用 `transactionTemplate.execute(conn -> ...)` 包住**一条或一小组纯读语句**
（`CommentCache:249` 是"窗口查询 + 首装 COUNT"，`loadContentsFromDb` 是"批量内容 + 批量媒体"，
仍属**同一读快照内的多条 SELECT**，无写操作）。

**决策**：⚠️ **有意改进——全部去掉事务包装**（同 L-5 / F-5）。理由三条，逐条表态：

1. **纯读无原子性需求**（无写语句 ⇒ 不存在"部分落库"）。
2. 且 loader 是在**缓存层内部**被调用，给它加事务会把"读缓存"拖进事务边界，
   **反而扩大**事务范围（缓存本不该有事务语义）；
3. `@Transactional` 标在"会被**同类内部调用**"的方法上会有**自调用失效**的风险（坑 12）——
   TV 的 `transactionTemplate` 是显式传参，没有这个陷阱；换成注解就**会**有。
   故**不标**，从源头避开。

> ⚠️ 一处**必须注意**的差异：`CommentCache` 的 loader 会被 `@Transactional` 的**外部**调用方间接触发吗？
> 不会——两个 Cache 只被 `ContentService`/`CommentService`/`ProfileService` 的**读**方法调用，
> 而那些读方法**无事务**（G-2/G-3/G-5）。故 loader 在无事务上下文执行，SQL 各自独立提交（只读，无影响）。

**★ 两种失败必须区分（TV 的核心设计，逐字保留）**：

| 失败 | 处置 | 理由 |
|------|------|------|
| **Redis 失败**（`CacheUnavailableException`）| 降级直查 DB，**不影响结果** | 缓存是加速器，挂掉不能让内容/评论接口 500 |
| **DB 失败**（`DataAccessException`）| **上抛**（500）| "无答案可答"——降级成空值会把"读不到"伪装成"没有" |

实现上沿用 S3/S4 的手法：**只 catch 自己的异常类型**（`CacheUnavailableException` 只从 `*RedisOps` 冒出）。

**测试**：每个 Cache 至少"Redis 失败降级 + DB 失败上抛"各一条（S3/S4 已有同款，S5 沿用形态）。

**有意去掉（逐条记录影响，不是默默省）**

| 去掉的 | 影响 | 严重度 |
|--------|------|--------|
| **单飞 SingleFlight（防击穿）** | 同 key 并发 miss 各打一次 DB（N 次而非 1 次）。结果仍来自 DB，**正确性不变** | 低 |

| **`CacheDomain` / `CacheResult` / `CacheStatus` / `SetCache` / `ZSetCache`** 通用框架层 | 各域自持精简实现 | — |

> **★ 关于不搬 `ContentCache.init()` —— 这是本切片最需要解释的一条**
>
> TV 的 `init()` 在应用启动时 `findAllContent` **全表 + 全量媒体**装载进 Redis，并重建全部索引。
> **本切片不搬**，理由是**可观察行为完全一致而收益为负**：
> - `init()` 的产物只有两样：内容 key 集合、`content:index:*` 索引。前者**有懒回填**（miss 即回源），
>   后者**有懒重建**（`ensureIndex` 发现 key 缺失即从 DB 重建）⇒ **两条都有自愈路径**，
>   `init()` 只是"预热"，不承载正确性。
> - 而它的代价是真实的：启动时全表扫描（TV 侧 `findAllContent` + `findMediaByContentIds` 是**无上限**查询），
>   数据量一大就是启动期的一次长事务；且 `loadBuildableFromDb` 里有"单个内容媒体损坏则跳过该内容"
>   的分支，需要连带搬 `buildContentMedia` 的异常语义。
> - **当前无生产数据 ⇒ 收益为 0**；接入压测/真实数据时按需回补（实现参照 TV 的三期 T5 两阶段：
>   事务内只读装载、提交后再写 Redis）。
> - **补回位置**：`ContentCache` 增加 `@PostConstruct`（或 `ApplicationRunner`）调用两阶段重建；
>   参考 TV `ContentCache.init()` / `loadBuildableFromDb` / `rebuildRedis`。
>
> **★ 关于去掉索引重建冷却退避**
>
> TV 用 10 秒进程内冷却，把"停机期间每请求一次全表重建"收敛为"每冷却窗口一次"。
> 本切片去掉（与 L-7/F-7 去掉熔断同口径：**当前无规模压力，收益为 0**）。区别是它**有**正确性含义——
> 去掉后 DB 故障 + 索引缺失的组合下会产生重试放大。
> **影响与补回位置**：`ContentCache.ensureIndex` 内加回 `volatile long lastFailedAtMillis` + 窗口判定
> （TV `inIndexRebuildCooldown()` 同款），TTL 值走 `video.cache.content-index-rebuild-cooldown`。

## 三、模式库：已知会重复出现的三类边界

在 user 切片之外，同类模式会大量重复（见 §四 统计）。先定模式，切片时套用：

### 模式 A：写操作 + 缓存失效（最高频）

**旧形态**（`LikeService.java:54-76`、`ContentService.java:211-219`、`FollowService.java:60-92`）：

```java
transactionTemplate.execute(conn -> { ...写库... });
cache.xxx(...);                       // 提交后，靠注释维系
contentCache.notifyLikeCountChanged(contentId);
```

**决策**：⚠️ **有意改进** —— 副作用改用 `@TransactionalEventListener(phase = AFTER_COMMIT)`

**理由**：旧写法"写错位置就是事务回滚但副作用已发出"，靠评审兜住（踩坑清单 §5）。
框架机制把"提交后"变成**类型保证**而非注释纪律。

> **已落地**：**S3 = like**（首个实例，见 §二·D **L-6**）。落地时确认了两件事：
> ① AFTER_COMMIT 必须真的在 S3 用上（S3 正是引入读缓存的那一片，不能像 S2 那样裁剪）；
> ② 配套测试"**事务回滚后缓存未被污染**"是该机制的存在证明——改回"事务内更新缓存"即失败。

**判定规则**：事务 lambda 之后紧跟的每一行副作用，逐个表态：
| 副作用 | 机制 |
|--------|------|
| 缓存失效 | `AFTER_COMMIT` 事件 |
| 缓存写入（非失效） | `AFTER_COMMIT` 事件（避免回滚后留下脏缓存） |
| MQ 投递 | `AFTER_COMMIT` + `@Async` |
| 纯日志 | 留在原地 |

### 模式 B：cache-aside miss 回填（`*Cache` 类，20 处事务）

**旧形态**：缓存未命中 → 回源 DB → **可能写库**（见《迁移参照系》§一 警告）。

**决策**：🔴 **待决策**（按决策⑤的"显式封装层"承接，**不用** `@Cacheable`）

**待定项**：回填是否需要在事务内？回填失败是否要影响读结果（降级 vs 报错）？——**每个 Cache 类都要单独表态**。

> **首个实例已表态**：`LikeCacheService`（S3，见 §二·D **L-5 / L-7**）。两个待定项的答案：
> ① **回填不需要事务**（单条 SELECT；且给缓存层加事务会反而扩大事务范围）；
> ② **必须区分两种失败**——Redis 失败 → 降级 DB 不影响结果；DB 失败 → 上抛（"无答案可答"，
> 降级成空值会把"读不到"伪装成"没有"）。
> 同时 S3 对"搬多少基建"做了保真度表态（不搬 TV `cache` 包 2,528 行，改做 ~250 行显式封装层，逐项记录去掉的机制与影响）。
>
> **仍待各自表态**（在 S5 及其后）：`ContentCache`（5 处事务）、`CommentCache`（8 处）、
> `FollowCache`（4 处）、`FeedInbox*`（2 处）等。**不要照抄 S3 的结论**——
> 它们做的是"内容详情三态读 / 评论树 / 计数"等不同形态，且 S5 起才可能抽公共层。

### 模式 C：组合业务跨 Service（踩坑清单 §4 的核心痛点）

**旧形态**：跨 Service 组合要么塞进一个大 lambda，要么拆成多个独立事务（原子性丢失）。

**决策**：🔴 **逐个表态** —— 这正是 `REQUIRED` 传播能**真正改进**的地方。
但注意 U-1 的反例：**并非所有"拆开"都是缺陷**，有的是产品语义。判定顺序：
1. 先问"旧行为是不是刻意设计的"（查原注释——旧项目注释质量很高，常直接写明理由）
2. 再看"合成原子是否违反产品语义"
3. 两者都不明确 → 🔴 挂起，向人确认，**不要自行决定**
