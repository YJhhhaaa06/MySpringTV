# 事务边界决策表

> 生成时间：2026-10-01
> 用途：迁移时**每一个事务边界都要显式表态**——旧行为是什么、新设计怎么写、差异是否有意。
> 存在的理由：旧代码的事务模型在语义上就是**残缺的**（无传播、无嵌套、无同步回调，见踩坑清单 §4/§5）。
> 迁移时必然遇到"这里本该原子但当年拆成了两个事务"。这类地方**既不能静默改，也不能静默保留**——
> 本表让"改进"变成经过拍板的记录，可 `git blame` 追溯（解报告 D2 债）。
> 关联：《迁移参照系.md》《TV-Spring迁移选型决策记录.md》

## 〇、旧事务模型的两个硬约束（理解差异的起点）

```java
// util/TransactionTemplate.java:26-33
public <T> T execute(TransactionAction<T> action) {
    Connection conn = MyConnectionPool.getConnection();   // ← 每次都是新连接
    conn.setAutoCommit(false);
    T result = action.execute(conn);                       // ← conn 手工穿透到 DAO
    conn.commit();
    ...
}
```

| 约束 | 后果 |
|------|------|
| **每次 `execute` 取新连接** | 无传播语义：内层事务与外层互不可见，**组合操作无法原子化** |
| **无事务同步回调** | "提交后动作"（缓存失效/MQ 投递）只能靠代码行序 + 注释纪律 |

**Spring 带来的变化**：`@Transactional` 默认 `REQUIRED` 传播 + `TransactionSynchronization` 回调。
**风险点**：这两个变化都会**静默改变语义**——把旧的两个独立事务合成一个原子事务，或让副作用时机改变。
所以下表是**必须**的，不是可选文档。

### U-1 `registerAndLogin` —— 注册与自动登录是两个独立事务

**位置**：`user/service/UserService.java:100-120`

**旧行为**（原始注释即规格说明）：

> 注册并自动登录（池 U-16 兜底）：**注册成功即视为成功**。
> 自动登录失败时不再向上抛异常，而是返回 `token == null` 的 `LoginVO`，由调用方提示"注册成功，请手动登录"。
> **不重试、不补登：注册与自动登录仍是两个独立事务（注册事务先提交，再做登录查询）**。

代码结构：

```java
public LoginVO registerAndLogin(RegisterCommand rc) {
    long id = registerAsUser(rc);          // 事务 1：校验占用 + 插入，提交
    try {
        return login(id, rc.getPassword()); // 事务 2：查用户 + 校验密码
    } catch (BusinessException e) {
        // 注册已提交 ⇒ 不能把自动登录失败报成注册失败
        LOGGER.log(Level.WARNING, "注册后自动登录失败, userId=" + id + ", 改为提示手动登录");
        return new LoginVO(id, rc.getUsername(), null);   // token = null
    }
}
```

**决策**：✅ **保持**（拆分是刻意的，不是妥协）

**新实现**：

```java
// 编排方法：本身不加 @Transactional，保持"注册已提交"这一事实
public LoginVO registerAndLogin(RegisterCommand rc) {
    long id = registerAsUser(rc);          // 内部 @Transactional(REQUIRED)，独立提交
    try {
        return login(id, rc.getPassword());
    } catch (BusinessException e) {
        log.warn("注册后自动登录失败, userId={}, 改为提示手动登录", id);
        return new LoginVO(id, rc.getUsername(), null);
    }
}

@Transactional
public long registerAsUser(RegisterCommand rc) { ... }
```

> ⚠️ **反模式警告**：若把 `registerAndLogin` 整体标 `@Transactional`（"看起来更原子"），
> 自动登录失败会**回滚注册**——直接违反产品语义（用户以为注册失败，实际也没注册成功，
> 而旧行为是注册成功、提示手动登录）。这是本次迁移**最容易误改**的一处。

**迁移时必须固化的测试**：
- 正常注册 → 返回含 token 的 `LoginVO`
- 注册成功但随后登录失败 → **用户行仍存在**（不被回滚）+ `token == null`
- 手机号/用户名占用 → 抛 `DuplicatePhoneException` / `ConflictException`（不被兜底吞掉）

>
> ---
>
> ## ⚠️⚠️ U-2 附注（S2 执行期实测发现，**本行声明的那条原子性当前并未真正生效**）
>
> **发现方式（实测，非推断）**：S2 期间为确认"`@Transactional` 是否真的在跑"，
> 用一个临时探针 spy `PlatformTransactionManager` 数 `getTransaction` 的调用次数，
> 分别测两条进入路径（探针用完已删，证据如下）：
>
> | 进入路径 | `getTransaction` 调用次数 | 结论 |
> |---------|------------------------|------|
> | 外部直调 `userService.registerAsUser(...)`（必经代理）| **1** | 事务生效（对照通过）|
> | 经 `userService.registerAndLogin(...)` 内部 `this.registerAsUser(...)` | **0** | **事务未开启** |
>
> 失败断言原文：`[PROBE-待判：registerAndLogin → this.registerAsUser 是否也开启事务（U-2 的原意）] expected: 1 but was: 0`
>
> **根因**：Spring AOP 的**自调用**——`registerAndLogin` 与 `registerAsUser` 同在一个类内，
> 内部调用用的是 `this`（目标对象），**不经过代理**，故 `@Transactional` 被静默跳过。
> 不报错、不留日志，只有把事务管理器当探针才看得见。
>
> **影响评估（据实，不夸大）**：线上路径是 Controller → `registerAndLogin`
> ⇒ 生产环境里 `registerAsUser` 实际**跑在无事务的自动提交连接上**。
> 唯一键 `uk_users_phone` 仍兜住并发竞态，**对外可观察行为（占用 → 409）不受影响**，
> 故属"声明与事实不符"，不是可见缺陷。丢掉的只是"两次占用检查 + 插入"的快照一致性，
> 而这一致性本由唯一键覆盖。
>
> **为什么 U-2 没被测出来**：`TransactionBoundaryTests.注册失败必须回滚且不被吞掉`
> 调的是 `registerAsUser` **本身**（外部直调，必经代理）——恰好是探针里"生效"的那条路径。
> 也就是说：**测试选错了进入路径，把一条不生效的路径照成了绿灯**。
> 这是"测试迎合"的变体——不是跟着实现改测试，而是测了一条与生产不同的路径。
>
> **推荐修法（待拍板，本切片不动 slice 0）**——目标是同时满足 U-1 与 U-2：
> 1. 把编排逻辑 `registerAndLogin` 抽到**独立 bean**（如 `UserRegistrationService`，注入 `UserService`），
>    使"注册"与"自动登录"天然是两次跨 bean 调用；或
> 2. 在 `UserService` 内自注入代理（`@Lazy UserService self`）再调 `self.registerAsUser(...)`。
> 方案 1 分层更清晰（编排 vs 领域），方案 2 改动最小。
> ⚠️ **不要**用"给 `registerAndLogin` 加 `@Transactional`"来修——那会违反 U-1（见上方反模式警告）。
>
> **修完后必须补的测试**：一条断言"经 `registerAndLogin` 进入时 `registerAsUser` 处于事务中"
> 的回归用例（即把本次探针保留下来），否则同样的问题会再次静默复现。

### C-1 `grabCoupon` —— 扣库存与插订单必须原子（✅ 保持单事务）

**位置**：`coupon/service/CouponService.java:33`（方法 32-58）

**旧行为**：一个 `transactionTemplate.execute` 内包住两步写：

```java
int rows = couponDao.deductStock(conn, couponId);        // ① 原子扣库存（条件全在 SQL 内）
if (rows == 0) throw new ConflictException("库存不足或活动未开始/已结束");
couponDao.insertOrder(conn, couponId, userId, code);     // ② 插订单（1062 → ConflictException("您已抢过该优惠券")）
```

原注释只说明了日志纪律（T11-B"包装点即源头"），**未写明事务理由**——但语义是显然的：
"扣了库存却没有订单"= 白扣，"有订单却没扣库存"= 超发。二者都必须排除。

**关键机制**：两处异常都在 lambda **内部**抛出，`TransactionTemplate` 的
`catch (BusinessException) → rollbackQuietly(conn) → throw e`（`util/TransactionTemplate.java:34-36`）
把它们变成**回滚**。所以旧实现里"重复抢券"实际上**不会**把库存扣掉——
这不是巧合，是 C-1 最需要固化的行为。

**决策**：✅ **保持**（本来就是单事务）

**新实现**：`@Transactional`（`REQUIRED` 传播）。差异点两处，逐条表态：

1. **删掉 `e.getErrorCode() == 1062` 判断**（《切片计划》§一 明确要求）。
   MyBatis + Spring 的异常翻译把 1062 变成 `DuplicateKeyException`（`DataAccessException` 子类），
   经 `GlobalExceptionHandler.handleDuplicateKey` 统一映射为 409——正是 U-2 补注预告的映射点。
   > ⚠️ **契约差异（有意，勿当缺陷修）**：重复抢券的 `msg` 由 `"您已抢过该优惠券"`
   > 变为 `ErrorCode.CONFLICT.getMessage()` = `"操作冲突"`。
   > **HTTP 状态码与 body `code` 仍是 409，未变**；DoD #5 冻结的是"路径 / 信封 / 状态码"，`msg` 不在冻结范围。
   > 若要保住旧 msg，就得在异常出口按约束名 `uk_coupon_user` 反查语义——那是把 DB 细节泄露到出口层，
   > 且与"删掉错误码判断"的决策直接冲突。**取决策，不取 msg。**
2. **`deductStock` 的 `rows == 0` 分支原样保留**——它仍然是"库存不足 / 未开始 / 已结束"三合一的唯一判定点。

> ⚠️ **两条反模式警告**（后来者最容易"顺手优化"掉的地方）：
> 1. **不得把时间窗判断从 SQL 挪到 Java**。`begin_time <= NOW() AND end_time >= NOW()` 在 `UPDATE` 的
>    `WHERE` 里，与 `stock > 0` 是**同一条原子语句**的一部分；拆成"先 SELECT 判断时间窗、再 UPDATE"
>    会引入 TOCTOU 窗口（并发下判定与扣减之间活动可能刚开始/刚结束）。
> 2. **不得把 `insertOrder` 移出事务**（例如为了"减少锁持有"改成先插订单再扣库存、
>    或把扣库存改成非事务的 `UPDATE`）。这会破坏"库存只扣一次、失败必回滚"。

**迁移时必须固化的测试**：

- 抢券成功 → 200；`coupon_order` 新增 1 行、`coupon.stock` 减 1（**独立 oracle 直接查列**，不信任接口回显）；
  `data` 恰为 16 位 `[0-9A-Z]{16}` 券码
- 库存为 0 → 409，且**不产生订单行**、**库存不为负**
- 活动未开始 / 已结束 → 409（时间窗判定在 SQL 内，Service 层不可区分这三者）
- **同一用户重复抢 → 409，且库存只扣一次**（★核心：证明 `@Transactional` 回滚确实生效，
  而不是"扣了库存才发现重复"）
- **并发**：N 个线程抢库存 1 的券 → 恰好 1 成功、`stock == 0`、`coupon_order` 恰 1 行
- 未登录抢券 → 401（`@RequiresLogin`）

### CM-1 `addComment` —— 插入评论 + 楼中楼归一化 + 跨表计数联动（✅ 保持单事务）

**位置**：`comment/service/CommentService.java:179`（方法 162-225）

**旧行为**：一个 `transactionTemplate.execute` 内完成 6 步，顺序即语义：

```java
if (!contentDao.isContentExist(conn, contentId)) throw new NotFoundException("被评论的内容不存在");   // ① 404
if (parentId != null && parentId != 0) {                                                              // ② 归一化
    if (!commentDao.isCommentExist(conn, parentId)) throw new ConflictException("被回复评论不存在或已删除");
    CommentCacheDTO parent = commentDao.findCommentById(conn, parentId);
    if (parent.getContentId() != contentId) throw new ConflictException("被回复评论不属于该视频或动态");
    if (parent.getParentId() != null && parent.getParentId() != 0) {   // 被回复的是楼内回复 → 上溯挂主楼
        effectiveParentId = parent.getParentId();                     //   @ 目标 = 该回复作者
        replyToUserId     = parent.getUserId();
    }
}
long commentId = commentDao.addComment(...);                          // ③
if (effectiveParentId != null) commentDao.updateReplyCount(effectiveParentId, +1);  // ④
contentDao.updateCommentCount(conn, contentId, +1);                   // ⑤ 跨表
return commentDao.findCommentById(conn, commentId);                   // ⑥
```

原注释（楼中楼口径，即规格说明）：

> 楼中楼：{@code parentId} 一律指向主楼。被回复评论本身是回复时，上溯挂到其主楼 id，
> 并记录被回复评论作者（{@code replyToUserId}，用于楼中楼「回复 @xxx」展示）

**决策**：✅ **保持**（本来就单事务；且**必须**单事务——否则会出现"评论插入成功但计数没加"
这类静默脏数据，而计数是列表排序/展示的输入）

**新实现**：`@Transactional`（`REQUIRED`）。三处要点：

1. **校验顺序逐条保留**——它决定客户端拿到 404 还是 409，是契约的一部分，不是可有可无的细节。
2. **去掉 `Long[] effectiveParentId` 数组技巧**。旧代码用数组是因为要在 lambda 内改写被捕获变量
   （Java 编译约束）；新实现没有 lambda，直接用局部变量。
   **但"归一化后的 effectiveParentId 要活到事务外"这一事实必须保留**——旧代码用它决定
   提交后该失效哪个缓存（见 CM-4）。
3. **评论区开关改读 DB**：旧代码是 `contentCache.getContent(contentId)`，读的是**缓存**
   （cache-aside，miss 才回源 `loadContentFromDb`，其查询带 `is_deleted = 0`）。
   新实现直读 `SELECT comment_enabled FROM content WHERE id = ? AND is_deleted = 0`。
   > ⚠️ **有意改进（非事务边界，一并记录）**：直读 DB 消除了旧实现的**缓存陈旧窗口**——
   > 旧代码靠 `notifyCommentEnabledChanged` 失效 + TTL 自愈，作者刚关评论区时缓存可能仍是"开"。
   > 语义上不放松（关闭后仍不可发），只是**更即时**。补回位置：S5 接入 ContentCache 时，
   > 此处可改回缓存读（届时需一并考虑该窗口）。

**迁移时必须固化的测试**：

- 发主楼评论 → 200；`comment` 新增 1 行且 `parent_id IS NULL`；`content.comment_count` +1（**独立 oracle 直查列**）
- 发回复（`parentId` = 主楼）→ 新行 `parent_id` = 主楼、`reply_to_user_id` 为 **NULL**、
  主楼 `reply_count` +1、`content.comment_count` +1
- ★**回复一条"回复"** → 归一化：新行 `parent_id` = **主楼 id**（不是被回复的那条回复 id）、
  `reply_to_user_id` = 被回复回复的**作者 id**（CM-1 的核心语义）
- `contentId` 对应内容不存在 → **404**，且**不产生评论行**、`comment_count` 不变
- ★内容**已软删**（`content.is_deleted=1`）→ 404（content-thin 的 `isContentExist` 带 `is_deleted = 0`，
  已读旧代码确认，非推断）
- 被回复评论不存在/已软删 → **409**
- 被回复评论属于**另一条内容** → **409**
- 评论区已关闭（`comment_enabled = 0`）→ **409**，且**不产生评论行**
- `message` 缺失/空白 → **400**；`message` 超 1000 字 → **400**；`contentId` 缺失或 0 → **400**
  （口径来自旧 `CommandConverter.commentToCommand`，被 pytest `E-03` 固化）
- 未登录 → **401**

### CM-2 `doDeleteComment` —— 软删除 + 计数回减（✅ 保持单事务）

**位置**：`comment/service/CommentService.java:240`（方法 239-287，入口 `deleteCommentByUser` / `deleteCommentByAdmin`）

**旧行为**：单事务内 ① `isCommentExist`（已删/不存在 → 404）② 取评论 ③ 权限
（非 admin 且 `author != operator` → 403）④ 判是否主楼 ⑤ 定位 rootId（删回复时沿 parent 链上溯）
⑥ 主楼 → 整栋软删，回复 → 只删自己 ⑦ `content.comment_count -= deletedCount`
⑧ 删回复时主楼 `reply_count -1`。

原注释（**必须保留的顺序约束**）：

> 必须先计数再软删：{@code countFloorReplies} 过滤 {@code is_deleted=0}，若先软删会数到 0 导致计数少扣

配套口径（`CommentDao.countFloorReplies` 原注释）：

> 单删回复时 {@code comment_count} 已 -1；删主楼时再扣 "1(主楼) + 剩余未删回复数"，
> 与递增口径对称，**避免对已单删回复二次扣减导致负数**

**决策**：✅ **保持单事务**

**新实现**：`@Transactional`。三条**不得"顺手优化"**的地方：

1. **"先计数再软删"的顺序**——理由写在旧注释里，改了就会静默少扣计数。
2. **删主楼不扣 `reply_count`**（`if (!isMain && rootId != null)` 的 `!isMain` 是有意的：
   主楼已整栋删掉，其 `reply_count` 无意义）。
3. **`updateReplyCount` 的防负守卫**
   （`WHERE comment_id = ? AND reply_count + ? >= 0`）保留——它同时承担"防负"与"是否命中"两种作用。

**已知并接受的旧实现尖锐处**（**不修**，以旧实现为准）：`content.comment_count` 列类型是
`int unsigned`，而 `updateCommentCount` 无防负守卫（对比 `reply_count` 有）。
若评论存在但 `comment_count` 已是 0（数据不一致），删除会因 UNSIGNED 下溢报错 → 500。

> **已实测复现（S2 执行期，非推测）**：
> `Data truncation: BIGINT UNSIGNED value is out of range in '(\`tvdatabase\`.\`content\`.\`comment_count\` + -(1))'`
> —— 由 `content.comment_count = 0` 时执行 -1 触发，经 `DataAccessException` 出口变 500。
> 触发场景是**数据本身不自洽**（评论行存在但计数为 0），正常路径不会走到。
> 这是 TV 既有行为，本切片**原样保留**；修它（加 `GREATEST(...)` 或 `WHERE comment_count >= 1` 守卫）
> 属于行为改动，需单独立项，且要让 DoD 明确"这是改进不是回归"。
> 注：S2 的测试夹具必须让 `comment_count` 与评论行数自洽——否则会把这条尖锐处
> 误当成被测逻辑的缺陷（S2 期间踩过一次，已修夹具）。

**鉴权**：`deleteCommentByUser` 走 `/comment/delete`（TV `PROTECTED_EXACT` 含它 ⇒ 需登录）。
`deleteCommentByAdmin` 由 admin 模块调用（本批不搬 admin），故**本切片无端点暴露**，
但**要搬并测试**——它是 `doDeleteComment` 的 `isAdmin` 分支唯一入口，砍掉等于砍掉该分支语义，
且 admin 切片补回时会引入未测路径。

**迁移时必须固化的测试**：

- 删自己的主楼 → 主楼 + 楼内回复**整栋** `is_deleted=1`；`comment_count` 减
  **1 + 剩余未删回复数**；该主楼 `reply_count` **不动**
- 删自己的回复 → 仅该行 `is_deleted=1`；`comment_count` -1；主楼 `reply_count` -1
- ★**先单删一条回复，再删主楼** → 主楼删除时只扣 `1 + 剩余未删回复数`
  （这是 `countFloorReplies` 口径的核心回归点：**不得对已单删的回复二次扣减**）
- 删**别人**的评论 → **403**，且该行**未被软删**（失败不留副作用）
- 删不存在/已软删的评论 → **404**
- 管理员删任意评论 → 放行（service 级测试，无端点）
- `reply_count` 为 0 时删回复 → **不得变成 -1**（防负守卫）
- 未登录 → **401**；`commentId` 缺失/非数字 → **400**

### CM-3 `getRepliesForRoot` 的 2 处读事务 —— ⏭ **划归 S5**（不在 S2 范围）

**位置**：`comment/service/CommentService.java:102`、`:115`（方法 98-139）

**旧行为**：两处 `transactionTemplate.execute` 各包一条**纯读**
（`findMainById` 查主楼、`getRepliesInTreeByRoot` 查展开页），纯读无原子性需求。

**决策**：⏭ **不在 S2 交付，划归 S5**。理由（SOP 步骤 1「以能力闭环为单位」+ 步骤 3「盘点跨模块依赖」）：

| 端点 | 旧实现入口 | 拖入的依赖 |
|------|-----------|-----------|
| `GET /comment/replies` | `CommentService.getRepliesForRoot` | `LikeService.batchIsCommentLiked`（**S3**）拿点赞态 |
| `GET /comment/show` | **`ContentService.getCommentsForContent`**（注意：不是 CommentService） | `CommentCache`（**8 处事务**的两键组 Redis 设计）+ `ContentCache` + `LikeService` + `PageResult`/`CommentVO`（content 域） |

即"comment 完整模块"= 把 S3 与 S5 的一部分吞进 S2，规模从 ~930 行涨到 3000+ 行，
正好违反《切片计划》§〇「content 必须拆薄、不要让某模块成为所有下游的阻塞源」的初衷。

**佐证：S2 的验收要点本身全是写路径**——《切片计划》§二 列的 6 条
（发评论计数 +1 / 楼中楼字段与 reply_count / 软删除与计数减少 / 不存在或已删内容拒绝 /
未登录 401 / 评论区开关）**没有一条依赖读路径**。用独立 oracle 直接查库即可验收，无需 HTTP 读回。

**提交后副作用（模式 A）—— ⚠️ 有意裁剪，必须显式留痕（对应 S4 notifier 裁剪的同款纪律）**

旧代码在事务 lambda **之后**紧跟 3 行缓存失效：

```java
contentCache.notifyCommentCountChanged(contentId);                                  // 失效 content key
commentCache.invalidateRoots(contentId) 或 commentCache.invalidateReplyUnder(...);   // 失效 comment 两键组
```

**S2 裁剪它们**，理由是**当前不存在任何读缓存**：`ContentCache` / `CommentCache` 都随读路径留在 S5，
新项目里没有缓存可失效 ⇒ 失效动作是**空操作**，裁剪不产生可观察差异
（这属"缺什么补什么"，不是投机抽象：**不为尚不存在的缓存预埋事件总线**）。

> **补回位置（feed/后来者按此查）**：S5 接入 `ContentCache` / `CommentCache` 时，
> 需回到 `CommentService.addComment` / `doDeleteComment`，把这三行副作用改为
> `@TransactionalEventListener(phase = AFTER_COMMIT)`（决策表 §三 模式 A）。
> 旧注释已写明为什么必须在**提交后**：事务内先失效会留窗口，并发读者按旧计数回填缓存，
> 表现为计数短暂陈旧（T34/U-22 的修复结论）。
> **在那之前，任何"评论后计数不即时更新"的现象都属预期**——原因是缓存不存在，而不是漏了失效。


## 三、模式库：已知会重复出现的三类边界

在 user 切片之外，同类模式会大量重复（见 §四 统计）。先定模式，切片时套用：

### 模式 A：写操作 + 缓存失效（最高频）

**旧形态**（`LikeService.java:54-76`、`ContentService.java:211-219`、`FollowService.java:60-92`）：

```java
transactionTemplate.execute(conn -> { ...写库... });
cache.xxx(...);                       // 提交后，靠注释维系
contentCache.notifyLikeCountChanged(contentId);
```

**决策**：⚠️ **有意改进** —— 副作用改用 `@TransactionalEventListener(phase = AFTER_COMMIT)`

**理由**：旧写法"写错位置就是事务回滚但副作用已发出"，靠评审兜住（踩坑清单 §5）。
框架机制把"提交后"变成**类型保证**而非注释纪律。

**判定规则**：事务 lambda 之后紧跟的每一行副作用，逐个表态：
| 副作用 | 机制 |
|--------|------|
| 缓存失效 | `AFTER_COMMIT` 事件 |
| 缓存写入（非失效） | `AFTER_COMMIT` 事件（避免回滚后留下脏缓存） |
| MQ 投递 | `AFTER_COMMIT` + `@Async` |
| 纯日志 | 留在原地 |

### 模式 B：cache-aside miss 回填（`*Cache` 类，20 处事务）

**旧形态**：缓存未命中 → 回源 DB → **可能写库**（见《迁移参照系》§一 警告）。

**决策**：🔴 **待决策**（按决策⑤的"显式封装层"承接，**不用** `@Cacheable`）

**待定项**：回填是否需要在事务内？回填失败是否要影响读结果（降级 vs 报错）？——**每个 Cache 类都要单独表态**。

### 模式 C：组合业务跨 Service（踩坑清单 §4 的核心痛点）

**旧形态**：跨 Service 组合要么塞进一个大 lambda，要么拆成多个独立事务（原子性丢失）。

**决策**：🔴 **逐个表态** —— 这正是 `REQUIRED` 传播能**真正改进**的地方。
但注意 U-1 的反例：**并非所有"拆开"都是缺陷**，有的是产品语义。判定顺序：
1. 先问"旧行为是不是刻意设计的"（查原注释——旧项目注释质量很高，常直接写明理由）
2. 再看"合成原子是否违反产品语义"
3. 两者都不明确 → 🔴 挂起，向人确认，**不要自行决定**
