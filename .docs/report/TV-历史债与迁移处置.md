# TV 历史债与迁移处置

> 生成时间：2026-09-30（调查窗口产出，未改动业务代码）
> 与《TV-无Spring踩坑清单.md》互补：那份记"框架能力缺口"，本份记"工程实践债/弯路"。
> 处置口径（三选一）：**【避免重演】**= 新仓库不要重演这种模式；**【不迁移】**= TV 里的这套东西不要带过去；**【迁移后改掉】**= 带过去但有明确改造点。

## 〇、规模事实（本债的物理量级）

| 项 | 数据 |
|----|------|
| .docs 文档 | **406 个文件 / 3.6 MB**（主代码仅 16,944 行） |
| 关键文档体量 | BUSINESS_FLOW 1,451 行；CURRENT_ARCHITECTURE 878 行；TEST_AUTOMATION 515 行；NEXT_CYCLE_TASKS 326 行 |
| 测试代码 | JUnit 15,132 行 + pytest 7,145 行 ≈ **1.3 倍主代码量** |
| 工具脚本 | tools/ 14 个脚本（含 tv.py 包装层与环境系统）；temp_script/ 13 项一次性探针残留 |
| 不追踪清单 | `.gitignore:71-72` 覆盖 `/.docs/目标与任务`、`/.docs/archive`（+temp/DBbackups/报告） |
| 归档结构 | archive 下整树复制四套体系（报告/常青/目标与任务/说明书 + DBbackups） |

**总纲洞察**：你列的三个弯路（文档、流程、测试）不是孤立的三件事，而是一个自我强化的循环——
**手写基建 → 行为无框架默认 → 用文档纪律对冲 → 规范层层加码 → 流程变重、决策变慢 → 测试被迫补偿 → 更多妥协登记**。
迁移的本质，是把这个循环的源头（手写基建）换掉，然后**主动拆掉为对冲它而长出来的全部制度**。

## 一、文档体系

### D1. 文档规模失控、职责叠装【避免重演】

- 现象：3.6 MB 文档；INDEX 仅 62 行却用超长段落承担"导航 + 项目史 + 现状 + 决策索引"四重职责；同一事实在多份文档同步维护（改动要"同步 x 处"）；归档 = 复制整棵文档树，产生长期双份维护。
- 证据：`.docs/INDEX.md`（长段落）；`.docs/archive/` 顶层四套体系；AGENTS.md 的"同步维护"约定。
- 弯路在哪：文档密度曾是协作（人 + AI）的资产，但已越过边际收益点——维护成本开始吃掉它带来的可追溯性。
- 处置：新仓库立"少而分层"的文档规范：单一事实源、现状与历史分离（历史交给 git）、INDEX 只做导航不做史书、归档用 git tag 不做文档树复制。

### D2. 决策记录不入 git = 决策不可追溯【迁移后改掉】

- 现象：决策（R 系列）与任务清单存于 `目标与任务/`，而该目录与 `archive/` 均被 .gitignore 排除；部分决策靠 commit 正文承载（COMMIT_CONVENTION 要求正文写"git diff 看不见的决策"）。
- 证据：`.gitignore:71-72`；`.docs/说明书/COMMIT_CONVENTION.md:8-49`。
- 弯路在哪：**"决策错误不容易发现"的根因之一**——决策演进无法 `git log/blame` 回溯，只能看到文档"现状快照"，错了也找不到"何时、为什么这样决的"。
- 处置：新仓库把决策收进 git（ADR 目录或 decisions/，一条决策一条记录），与代码变更同一历史线。

### D3. 多字母编号体系 + 手工归档【不迁移】

- 现象：G/R/N/T/U 五套编号并存，编号本身成为维护对象（"编号不悬空"规则、去向登记）；归档靠人工复制文档树。
- 证据：`.docs/目标与任务/UNPLANNED_ISSUES.md`（U 系列去向登记）；`.docs/INDEX.md`（G/R/N/T/U 混用）。
- 处置：新仓库用 issue/PR + 标签替代字母编号；周期/里程碑交给 git branch/tag。

## 二、工程流程

### P1. 单人项目跑"大厂流程"【避免重演】

- 现象：立项结构化问答 → 门禁（G 系列）→ 留证跑 → **每题独立评审**（"独立评审 = 有条件通过（无🔴）、N🟡 + M🟢 已全部处置"在 INDEX 高频出现）→ 归档结转。一个人同时扮演 PM / 架构 / 评审 / QA。
- 证据：`.docs/INDEX.md` 各任务记录；`.docs/目标与任务/周期模板_TASKS.md`（任务四要素+评审栏）。
- 弯路在哪：在"学大型工程流程"目标下它曾是学习内容，但已明显拖慢代码产出，精力从"写系统"转移到"跑流程"。
- 处置：新仓库压到最小集——commit 规范 + 关键决策记录 + 测试；评审按需触发，不设默认环节。

### P2. 用"文档纪律"对冲"手写基建的不确定性"【迁移后改掉】

- 现象：LOG_CONVENTION 163 行（定栈规则/脱敏/级别判据）、COMMIT_CONVENTION 81 行、TEST_AUTOMATION 515 行——大量纪律条文的存在前提是"框架零默认行为，一切靠人守约定"。
- 证据：`.docs/说明书/LOG_CONVENTION.md`、`COMMIT_CONVENTION.md`、`TEST_AUTOMATION.md`。
- 弯路在哪：纪律文档不可自动校验，越长越难守；AI/人都靠"记得"。
- 处置：迁移后把能固化的约定全部下沉为框架配置/代码/注解，纪律文档只留"真正需要人判断"的部分。

### P3. "红线 + 例外审批"制度成本【避免重演】

- 现象：web.xml 里有"唯一获批红线例外"的正式注释；任务里出现"红线禁止 fanout 删 / 定期任务"这类制度性约束，例外要登记与豁免。
- 证据：`src/main/webapp/WEB-INF/web.xml:7-9`；`UNPLANNED_ISSUES.md` U-36。
- 弯路在哪：红线随复杂度增长，登记与豁免变成固定流程成本，且无自动校验（靠人记得）。
- 处置：新仓库红线保持个位数，且每条红线必须能被测试/检查脚本自动校验。

## 三、测试体系

### T1. 测试环境重资产、不可携带【迁移后改掉】

- 现象：跑全量测试依赖——外部 Tomcat 18080 + Docker MySQL 3307 + Redis 6379 + RabbitMQ 5672 + Maven 离线仓 + pytest 依赖目录 + 项目内构建重定向。
- 证据：`.docs/说明书/TEST_AUTOMATION.md:18-20、106-132`；`tools/run_tests.py:86-111、177-190`（端口预检）；`pom.xml:15-21`（stage8.buildDir）。
- 处置：Spring Boot Test + Testcontainers（或 CI 服务容器）；目标 = "一条命令拉起全部依赖"，环境不再是"本机手工资产"。

### T2. 端到端测试的妥协矩阵【避免重演】

- 现象：skip 守卫三种风格并存；同一场景要按 `FEED_BIGV_THRESHOLD=1` 双模式分别跑；U-35 存在稳定假失败；"并发重复投递 e2e 侧无法可靠构造 → 交给 JUnit"。
- 证据：`src/test/python/test_feed_read.py:22-31`、`test_feed_push.py:21-33`、`test_feed_rebuild.py:24-35`；`UNPLANNED_ISSUES.md` U-35。
- 弯路在哪：可测性没有前置设计，导致 e2e 断言因环境/时序不可靠而系统性降级为"守卫 + 双模式 + 跳过"。
- 处置：新仓库把可测性前置：外部依赖可注入/可替换、消息确认与时钟可注入、关键交互用契约测试锁定；e2e 只留"跨组件主链路"。

### T3. 种子数据与真实库强耦合【迁移后改掉】

- 现象：TEST_SEED 固定基线（管理员/楼中楼回复者/固定券/过期券/`sample_comment_id`）；测试中断会残留 `comment_like`，要 `check_integrity.py --fix` 修；重复 init 需幂等设计。
- 证据：`.docs/说明书/TEST_SEED.md:6-29、30-47`。
- 弯路在哪：造数 = 长期维护一套会演化的库状态；测试之间通过"共享库状态"隐性耦合。
- 处置：每测试自建数据（fixture builder）+ 隔离（事务回滚或容器重建），废除"全局种子库"模式。

### T4. 自研测试工具链已成"产品"【不迁移（大部分）】

- 现象：tools/ 14 个脚本：run_tests 全家（含报告）、gen_coverage_map（手工解析 controller/filter + 守卫前缀对齐的覆盖率地图）、log_report、check_integrity、cleanup_*、media_paths、db_config、backup、tv.py（包装层 + test/prod 双环境 + DB_* 注入护栏，注释里还记录过"环境注入事故"）。
- 证据：`tools/tv.py:2-29、173-190`；`tools/gen_coverage_map.py:1-11`；`tools/run_tests.py`。
- 弯路在哪：工具链本身精度依赖人工口径对齐（如守卫前缀语义），成为又一层要维护和测试的"产品"。
- 处置：迁移后用生态标准替代（Surefire/Spring Boot Test/JaCoCo 报告直接消费；覆盖率交给 IDE/CI）；只保留 1-2 个真正业务定制的（如需要，feed 核对工具重写为可测试模块）。

## 四、环境与工具链

### E1. 离线仓/版本钉死 hack【不迁移】

- 现象：byte-buddy 因离线仓缺版本被钉 1.17.7→1.17.8；Jacoco 需同步离线仓并写 `>aliyun=` 标记；构建目录被 `-Dstage8.buildDir` 重定向进项目内。
- 证据：`pom.xml:69-107、15-21`。
- 处置：新仓库用正常联网仓库 + 标准版本管理；不把离线仓 hack 与产物重定向带过去。

### E2. 本机 Docker 依赖被当作架构假设【迁移后改掉】

- 现象：生产/测试都依赖本机容器（Redis/RabbitMQ/MySQL 双实例）；测试媒体、备份目录等散落项目内外；tv.py 注释记录过"DB_* 注入但 JDBC URL 仍指向 3306 导致 Access denied"的环境事故。
- 证据：`src/main/resources/app.properties:27-38`；`tools/tv.py:173-190`；`tools/feed_shadow_check.py:218-229`（docker exec）。
- 处置：容器编排（compose/CI services）入库成为资产；环境假设写进 README 与 CI 定义。

### E3. 一次性探针残留【避免重演】

- 现象：temp_script/ 残留 13 项（t28a_*、t29_*、t30_* 探针、fixtures、snapshots、nodecheck 等），大部分是"一次性调查脚本用完即弃"。
- 证据：`temp_script/` 目录清单。
- 处置：新仓库立约定——探针脚本随任务清理（或统一 gitignore 一个 scratch 目录）；能沉淀的才进 tools/。

## 五、架构演进

### A1. feed 三期可靠性机制堆叠（对单实例手写实现）【部分不迁移 / 部分重写】

- 现象：为 feed 推拉结合三期堆了——大V三路并集（名单/状态表/粉丝数）+ 分块批量 + fail-open 降级（FeedBigVRouter）；Redis 熔断状态机（CLOSED/HALF_OPEN）；去抖/补偿/DLQ TTL/清池；外加影子核对工具与多个探针脚本。
- 证据：`feed/service/FeedBigVRouter.java:20-68`；`cache/RedisCircuitBreaker.java:10-29、75-126`；`.docs/INDEX.md`（feed 三期记录）。
- 辨析（重要）：
  - **保留**：业务语义（幂等、重建三步序、降级口径、投递序）——这些在类 B 站里是真实需要的，且是学习资产。
  - **重写**：为"单实例、无调度、无 AOP"手工实现的可靠性机制——迁移后由生态组件（重试/熔断/调度/异步）承接。
  - **不迁移**：研究型脚手架（影子核对、一次性探针）——它们是"手写体系的验证工具"，随体系一起淘汰。
- 处置：迁移时按上述三分法过一遍 feed 代码，避免整块照搬。

### A2. 平行机制纵生（每个横切需求自造一套）【迁移后改掉】

- 现象：日志、审计、重试、调度、指标、限流预备……每个横切需求都自造一套小机制，彼此之间靠文档对齐（如"定栈规则""脱敏出口""结果码三处收口"）。
- 证据：`util/LogContext.java`、`util/AuditLog.java`、`cache/CacheStats.java` 等各自独立的机制化实现。
- 处置：迁移后收敛为"生态组件的单一实现线"（logback/MDC、Spring AOP、@Scheduled、Actuator、spring-retry），不再允许同类机制多套并存。
