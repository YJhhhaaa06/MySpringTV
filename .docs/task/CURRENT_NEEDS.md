# 当期需求（Current Needs）

> **定位**：登记**当期要做、以及新发现待消化**的需求 / 痛点 / 方向，是「这一期做什么」的**决策唯一源（Why）**。
> **工作流**：登记（N# / R-##）→ 评审拍板（纳入 / 留池 / 废弃）→ 拆任务（进 `CURRENT_TASKS.md` 的 T#）。
> **与任务文件的关系**：本文件只回答**要不要做、为什么**；怎么做在 `CURRENT_TASKS.md`。
> 单向引用：本文件 N# / R-## → 任务 T#，任务回写时引用本文件编号。
> **膨胀控制**：处理完即流转状态（已纳入 T# / 留池 / 废弃）；跨期未决项保留编号结转。
>
> **边界（不在这里登记的）**：执行中遇到的问题 → `CURRENT_ISSUES.md`；本期不解决的 → `FURTHER_ISSUES.md`；
> 迁移期遗留与上线准备度 → `FURTHER_ISSUES.md`（**F-01 / F-02**；`archive/migration/遗留台账.md` 已归档不再维护）。

| R-03 | **夹内列表遇到 `is_deleted != 0` 的内容怎么办** | N1 / 2026-10-08 | ✅ **已拍板：脱敏占位**（不是"返回原标题 + 打标"） | 用户 2026-10-08 按 B 站口径拍板：条目仍占位置，但**只给一张没有封面、标题位写「内容已失效」的灰卡片 —— 不返回原标题 / 封面 / 作者**。⚠️ 若 VO 里带着标题，第三方客户端就能捞出作者已删的内容。另：本仓 `is_deleted` 有 **0 正常 / 1 作者删除 / 2 管理员下架** 三态，判定须覆盖 1 和 2；且**不要照搬 `/profile` 的「跳过、total 不变」口径**（`ProfileService.java:109`，那会让分页出空洞）。★ **适用范围 2026-10-09 扩展**：失效口径放宽为「**装载不出来即失效**」（"看不了 ≈ 失效"），见 **R-11** |
| R-04 | **已失效内容的媒体资源要不要拦** | R-03 / 2026-10-08 | ✅ **已拍板：一期不做** | B 站"已失效 = 拿不到媒体资源"；本仓媒体走 `common/config/WebMvcConfig.java:56` `addResourceHandlers` **静态直出**，`is_deleted` 完全不参与访问控制 ⇒ 已软删内容的 URL **仍可直连下载**。加闸属**内容域**议题，不该由收藏域背 ⇒ 转 `FURTHER_ISSUES.md` **F-10** |
| R-05 | **公开 / 私密 放在哪一期** | N1 / 2026-10-08 | ✅ **已拍板：一期就给** | 原分期把它排在后一期。推翻理由：① `is_private` 列在 V2 建表时顺手加 = **零成本**，之后补要 V3 + 存量回填；② "默认公开"一旦上线即成对外契约，再改是 breaking change |
| R-06 | **`favorite_count` 一期怎么出** | N1 / 2026-10-08 | ✅ **已拍板：一期实时 `COUNT(DISTINCT user_id)`，二期才上冗余列** | 列在 V2 就加（零成本）但一期**不读不写**。收益：实时值是**唯一事实源**，二期上增量维护时它就是**现成的验收 oracle**（不变量 `favorite_count == COUNT(DISTINCT user_id)`），把"最易假绿的一条"变成有独立 oracle 的普通切片 |
| R-07 | **失效条目的计数与操作口径**（R-03 的衍生） | R-03 / 2026-10-08 | ✅ **已拍板**（**用户 B 站实测**） | ① **计入**：B 站把失效视频算进收藏夹视频数（分页同理，占一条返一条占位）② **可移出、不可移入 / 移动** ③ **算**（`favorite_count` 仍计；实际不可观察 —— 内容页已打不开）。★ **实现根因**：`remove` **不校验内容存在性** ⇒ 移得掉；`add`/`move` 校验（`isContentExist` 带 `is_deleted=0`）⇒ 自然被拒。⚠️ **`remove` 绝不能顺手加存在性校验**，一加用户就永远清不掉占位条目 |
| R-08 | ★ **「私密」一期有没有可观察落点** | R-05 / 2026-10-08 | ✅ **已拍板：新增 `GET /favorite/folder/public?userId=X`** | R-05 拍了"一期就给私密"，但**私密只有在"他人视角"下才有可观察行为**（自己的私密夹自己照样看得见），否则 `is_private` 就是**用户看不到任何变化的死开关**。落点 = 个人空间页的「收藏夹」模块（需求篇 §二）。★ **拆成两个端点**而不是给 `folder/list` 加可选 `userId`：① 安全 —— "他人视角"是一条**独立且危险的路径**，才能单独写"去掉 `is_private=0` 就变红"的契约测试；混在一个端点靠"传没传 userId"分流，分支写错即**直接泄露私密夹**；② 依赖方向 —— 塞进 `/profile` 会让 `content` 域白新增一条指向 `favorite` 的依赖边；③ 前端不多一跳 —— 被查看者 `userId` 在个人空间页本来就有，**不需要"先拿收藏夹 ID"**。⚠️ 一期只给"名称 + 视频数"，封面归三期 |
| R-09 | **默认夹"每用户至多一个"怎么落地**（R-01 的衍生：懒建的并发重复靠什么兜） | R-01 / 2026-10-08（T1 执行期） | ✅ **已拍板：VIRTUAL 生成列 `default_uniq` + `UNIQUE uk_user_default (user_id, default_uniq)`**（**执行者自行决断**，非用户拍板；见 G13） | ① **必须靠唯一键**：`INSERT ... WHERE NOT EXISTS` 兜不住 —— 两个事务都能查到"默认夹不存在"。② **但 `UNIQUE (user_id, is_default)` 会连坐自建夹**（它们都是 `is_default = 0` ⇒ 一个用户只能有一条自建夹）。③ **落地形态**：加一列生成列 `default_uniq = IF(is_default = 1, 1, NULL)` 并把唯一键挂它 —— 靠"唯一索引不约束 NULL"让自建夹可多条、默认夹至多一条；比"把 `is_default` 改成 `1/NULL`"稳（后者会让下游的 `is_default = 0` 全部查空）。④ **为什么在 T1 而不是 T2**：schema 级的东西必须**一次到位**（分期篇 §一 错位 2），留到 T2 就得 V3 + 改活库；且这正是 T2 红线"并发重复建夹必须靠唯一键兜住"**所依赖的那个键**。⑤ **可逆性**：V2 只落在 dev 与测试容器上，否决即改 V2 一行并回退（步骤见 T1 回写） |
| R-10 | ★ **「详情页内联 `isFavorited`」要不要做**（一期-5「收藏状态」的取数形态） | R-06 / T5 / 2026-10-09（T5 开工前讨论） | ⏸ **待拍板 —— 用户 2026-10-09 决定「简单登记，真要排任务时再调查复核」**；T5 按**独立端点**（形如"方案 A"）执行，本项**未采纳** | 用户提出：把「是否已收藏」**内联进内容详情响应**、只把「在哪些夹」留给独立端点，则**登录用户浏览内容页的收藏域请求从 2 降到 1** —— 因为 R-06 逼着收藏数必须单独请求（一期不写 `favorite_count` 列 ⇒ 进不了内容缓存），故省的是 **2→1**（常见情形：没收藏、不用开弹窗）；且它与详情页既有 `isLiked`/`isFollowed` 的内联形态一致。**未采纳的理由**（用户已认可推迟）：收益落在"请求数"，而**一期判据 ③ 明写"不看 QPS"**；且它会把 **content 域拉进 T5**（改 `ContentDetailVO` 键集 + `ContentStatusFiller` + content 契约测试 + 模块边界 §六 表态）。⚠️ **待复核要点（真要排任务时先查这几条）**：① `favorite → content.dao.isContentExist` 已存在，内联会让 `content ⇄ favorite` **成环** —— 须按 `模块边界与依赖.md` §六「有意保留的双向依赖」逐条表态（与 `content ⇄ like` 同形）；② 后补该字段是**纯加字段、对客户端不 breaking** ⇒ 属"纯优化可推迟"，**不是** `is_private` 那种 schema 级「必须一次到位」；③ 代价是给热路径加一条跨域窄查询（登录态才发，匿名 `userId == null` 短路，同 `ContentStatusFiller`）；④ 若采纳，`ContentDetailVO` 键集须补契约测试（其类注释目前写死"键集 = 父类全部键 + isLiked/isFollowed"）。 |
| R-11 | ★ **夹内列表失效口径扩展**（R-03 的适用范围："看不了 ≈ 失效"） | T6 残留 / 2026-10-09（**用户拍板**） | ✅ **已拍板**：不存在 / 已删下架 / **媒体损坏（视频行缺失）/ 未知 type** 统一折叠为失效 ⇒ 占位；判定整体走 content 装载契约 `ContentService.loadContentVOs`（**"取不到"即失效**） | 收益：favorite 不再自持 content 域的封面规则副本与 URL 前缀第二份实现，**一并吃到 content 缓存与失效链**（根治 I-07 ①②③）。**已知代价（接受）**：数据损坏态（`is_deleted = 0` 但装不出来）下列表占位、而 `add`/`move`（`isContentExist` 只看 `is_deleted`）仍收得进 —— 该态无 API 可达（发布必插视频行、删只允许 type=2 图片、换源只改 url），属边缘态取舍；结构性媒体损坏的巡检缺口另议（属内容域 / 运维） |
