# 当期需求（Current Needs）

> **定位**：登记**当期要做、以及新发现待消化**的需求 / 痛点 / 方向，是「这一期做什么」的**决策唯一源（Why）**。
> **工作流**：登记（N# / R-##）→ 评审拍板（纳入 / 留池 / 废弃）→ 拆任务（进 `CURRENT_TASKS.md` 的 T#）。
> **与任务文件的关系**：本文件只回答**要不要做、为什么**；怎么做在 `CURRENT_TASKS.md`。
> **边界（不在这里登记的）**：执行中遇到的问题 → `CURRENT_ISSUES.md`；本期不解决的 → `FURTHER_ISSUES.md`。
>
> ★ **膨胀控制**：**已拍板并交付的 R-## 在期收尾时清出** —— 结论 / 理由 / 归宿收编进该功能的
> **活速查**（落点见 §三 末）与 git 历史。跨期未决项保留编号结转。**编号不回收**。

|---|---|---|---|
| **R-19** | 播放记录**服务端上报缓冲**（`/report` 先进 Redis，退出信号 / 空闲兜底才落库）—— 曾按 `F-27`「想过但否决」 | ★ **做**。**语义重新定位（这是推翻原否决的唯一依据）**：正常用户发"退出/保存"信号 ⇒ **同步 flush，可见性延迟 0**；轮询**只兜"没正常上报退出"的用户**（崩溃 / 断网），**不是**降频手段 ⇒ 原否决理由"与客户端节流在写次数/新鲜度/丢包窗口上等价"不再成立。收益 = **每次观看会话 1 次写库**（而非每条心跳 1 次）。五条契约：① 缓冲与缓存**共用同一 Redis**，前提是未设 `maxmemory`（本仓已核）+ 启动自检 `maxmemory-policy`；② `HSET` + `ZADD` **必须同一个 Lua**（否则"在 hash 不在 dirty"的孤儿数据永不被 flush）；③ flush 粒度 = **按 userId 全量**（不是按 contentId）；④ `/position` **读缓冲优先**（优于"读触发 flush"：读比读触发写便宜，且崩溃用户重开能拿到新值）；⑤ 同步 flush 失败**返回 200**，数据留 Redis 等兜底（不返 5xx：客户端重试无益且放大流量） | `T51-1` / `T51-2` / `T51-3` —— ✅ **已交付（2026-10-22，全量 800/800 绿）** |

| **R-20** | `/history/position` 是否继续**读上报缓冲**（推翻 `R-19` 契约④）—— 2026-10-22 复核 6 项性能候选时提出 | ★ **改：只点查 DB**（用户 2026-10-22 拍板）。**依据**：① `/flush` 成功后 `ACK_LUA` 的 `HLEN == 0` 分支会 `DEL` 该用户 hash ⇒ **正常路径本端点必然 miss** ⇒ 读缓冲是**纯多一趟 `HGET`**，收益只存在于异常路径；② B站 实测：手机在播时电脑刷新看不到进度、停止播放才可见 ⇒ 跨设备"实时续播"不是行业预期，本仓不必用"服务端缓冲"去超出它；③ 由此带来的"多设备 + 双方都未正常退出 ⇒ 旧值覆盖新值"判为**极低频已知代价**（上报缓冲 §七 #7）。**配套**：崩溃续播改由客户端 `history:pending` 承载 —— 初始化取 `max(服务端值, 本地值)` 定位播放头（客户端契约 §6.2 重写），否则补报改不了已定位的播放头。**不动**：`R-19` 的写路径（缓冲 / flush / 轮询 / 503）一字未改 | `T52` —— ✅ **已交付（2026-10-22）** |
