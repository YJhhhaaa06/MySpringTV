> **定位**：登记**当期要做、以及新发现待消化**的需求 / 痛点 / 方向，是「这一期做什么」的**决策唯一源（Why）**。

### N4 明细：重试即非幂等的写端点（2026-10-24 盘点，39 写端点全扫）

判据分两层：**效果层**（DB 终态）/ **响应层**（客户端能否判定成功）。两层都幂等才算幂等。

**A. 效果层不幂等 —— 6 条（本次改造的真缺口）**

| 端点 | 重试后多出什么 | 根因 | 证据 |
|---|---|---|---|
| `POST /api/v1/comments` | 一条评论；`comment_count` 再 +1（若是回复，主楼 `reply_count` 再 +1） | 表上无任何自然键，正文重复本身合法 | `CommentService.java:164,170` |
| `POST /api/v1/contents/videos` | 一条 content + 2 条 media + 2 个新 UUID 文件 + **一次多余的 feed 投递** | 内容 id 自增、文件名 UUID，都不带业务唯一性 | `ContentService.java:504`、`UploadController.java:104` |
| `POST /api/v1/contents/posts` | 同上，每张图各多一份 | 同上 | `ContentService.java:531`、`UploadController.java:142` |
| `POST /api/v1/favorite-folders` | 一个**同名**夹（`T16` 明定允许重名），吃掉自建夹 20 名额之一 | 刻意无 `(user,name)` 唯一键 | `FavoriteService.java:275` |
| `POST /api/v1/contents/{id}/coins` | `count=1` 时**真的再扣**：投币人 −1 枚、作者 +0.1 枚、`coin_count` +1；`count=2` 第二次才 409 | `amount + delta <= 2` 是**业务封顶，不是去重键** | `CoinService.java:165,179` |
| `DELETE /api/v1/contents/{id}/media?type=2&sort=N` | **删掉下一张图**：首删后 `compactImageSort` 把 `sort>N` 前移，重试的 `sort=N` 命中原第 N+1 张，仍回 204 | 用**可变位置** `(type,sort)` 定位，且删除后重排 | `ContentService.java:383`、`ContentMediaMapper.xml:55` |

★ 最后一条是全站唯一**"重试破坏另一个对象"**的面（其余 5 条只是重复自己那份），也正好是接口契约 §2.4"重复 DELETE = 204"的**反例** —— 入账时要单列。

**B. 效果层幂等、响应层不可判 —— 8 条**

| 端点 | 重试响应 | 备注 |
|---|---|---|
| `POST /api/v1/coupons/{id}/claims` | 409 `SYSTEM_DUPLICATE_KEY` | 库存已回滚不超发，但**券码只在首次响应给过一次** ⇒ 只能靠 `GET /users/me/coupons` 找回（`I-25`） |
| `POST /api/v1/favorites` | 409 撞 `uk_folder_content` | 首次可能已懒建默认夹，重试者看不到这个事实 |
| `POST /api/v1/users` | 409 手机号 / 用户名已占用 | 与"被第三方占用"**不可区分** |
| `PUT /api/v1/users/me/password` | 401 旧密码错 | 接口契约 §2.4② 已冻结：前端不得自动重试 |
| 4 条资源型删除（`/comments/{id}`、`/contents/{id}`、`/favorite-folders/{id}`、`/admin/comments/{id}`） | 404 | 接口契约 §2.4① 已冻结："已删亦视为不存在" |

**C. 两层都达标 —— 25 条（不重复改造）**：`T59` 那批（点赞 4 / 关注 2 / 稍后再看 2 / 收藏移动 / 改名 / 下架恢复）、
有唯一键或条件写（`/play`、签到、`/progress`、4 条覆盖类）、无持久副作用（登录、`/history/flush`、
`/admin/media/scan`、`PUT /admin/media/{id}`）、批量移出 2 条。

**D. 灰色区（`f(f(x)) ≠ f(x)` 但无业务错，先别当缺陷）**：`PUT /watch-later/{id}`（每次刷 `create_time`
⇒ 等同"再点一次加入"）、`PUT /contents/{id}/media`（每次写新文件、删上一次的；并发重试留孤儿）、
`PUT /contents/{id}/progress`（LWW，**旧请求晚到会回退进度**）、`PUT /contents/{id}` 与
`POST /admin/media/scan`（只刷 `update_time` / `last_verify_time`）。

**E. 三个"假幂等"陷阱（决定了方案必须分线）**

1. **有唯一键 ≠ 幂等**：券是"撞键 + 生成随机券码"，撞键只能报错，换不来"把上次结果还给你"。
2. **有封顶 ≠ 幂等**：投币 2 枚上限让 `count=1` 的重试正好落进合法区间 —— 抽检 `count=2` 会通过。
3. **复合参数定位删除 ≠ 幂等**：`sort` 是位置不是身份，且删除后会被重排。

**F. 缺口按性质分三类（方案不能一刀切）**

1. **真缺自然键**：`POST /comments`、`POST /contents/{videos,posts}`（`favorite-folders` 也缺键，但那是**刻意**的
   —— 重名合法，加键就破业务）；
2. **有键但语义是"加"不是"设"**：`POST /coins` —— `uk_user_content` 表达累计枚数，不是请求标识
   ⇒ **只能靠请求标识去重**；改"目标累计量（set）"的方案**已否决**（实测见 §G）。
3. **键里含可变位置**：`DELETE /contents/{id}/media` —— `sort` 删除后被重排。

**G. 处置结论（2026-10-24 讨论）**

**口径先定**：目标是**客户端"自动重试"幂等**。防双击由客户端短期冻结按钮承担（请求根本没发出），
脚本刷屏由限流层承担 —— 两者都不进本议题，**不为它们加机制**。

| 处置 | 落点 | 状态 |
|---|---|---|
| 删图改按**稳定标识**定位（取 `url` 而非 `mediaId`：详情媒体形状不必破坏性改造，判据与推翻条件见 `T63`）；`sort` 只用于展示排序 | P0-1 | **已纳入 `T63`** |
| 券：先查 `(coupon,user)` 有订单则返回**原券码**；并发撞键后回查（不猜键） | P0-3 | **已纳入 `T64`** |
| 收藏 add 重复 `409` → `200`（与 `T59` 的 like/follow 同款） | P0-4 | **已纳入 `T65`** |
| 投币改"目标累计量（set）" | P0-2 | ❌ **已否决**（见下） |
| 通用客户端幂等键（`Idempotency-Key`）覆盖 评论 / 视频 / 图文 / 投币 | P1 | **待拍板**（`R-24`），**不在本期** |
| 收藏夹重名 | P2 | 留池（可删可改，重复影响小） |

★ **P0-2 为何否决（业务语义有外部锚点，不是实现偏好）**：B站实测 —— 两台设备对同一视频**各投 1 枚，
最终累计 2 枚**。⇒ "投币"是**累加**（每次调用是一次独立意图），不是"把状态设到 N"。
set 语义会把"合法的第二次独立投币"误判成重复（两台设备各投 1 只留下 1 枚），**改变业务行为**。
同理 B站 客户端状态陈旧时也只能靠"封顶 2"拒绝、做不到请求级去重 ⇒ **封顶兜底是它的水平，不是本仓该抄的答案**。
⇒ 投币缺的是**请求标识**，与评论/发布同类，只能进 P1。

| 号 | 议题 | 状态 / 决策点 | 落地 |
|---|---|---|---|
| **R-24** | **通用客户端幂等键（`Idempotency-Key`）：载体 / 存储 / 严格性**（`T59` 开工时提出；`N4` 是证据基础） | **待拍板**。**范围已定**（`N4` §G）：只覆盖 **4 个端点** —— 评论 / 视频 / 图文 / 投币（P0 三条已用结构性修复解决，收藏夹重名留池）。**决策点**：① **载体** —— header（body 字段覆盖不了 multipart，且逐 DTO 加字段 = 污染；★ 现有 `X-Request-Id` 是**服务端生成的 trace id**，不能复用）；② **存储与严格性** —— Redis 响应快照（通用、不动 schema，但"业务提交→写快照"之间有窗口，**不是 exactly-once**）vs DB 业务列+唯一键（严格、同事务，但破"不动 schema"，且投币是累计行**无处落列**）；③ **处理器位置** —— 必须在鉴权与限流**之后**（否则被限流 429 的请求会留下 PENDING 污染），上传类必须**早于 multipart 解析**（否则第二次的文件已落盘）；④ 同 key 不同载荷（非 multipart 校验 body 指纹，multipart 无法算指纹 ⇒ 跳过并登记）；⑤ PENDING 态的返回（建议 409 + `Retry-After`，**客户端须当"可重试"**）；⑥ 只缓存 **2xx** 快照（失败不固化）。**不做**：分片上传 / 先领 ticket 再发布的两步式（本仓无此流程，收益不抵改造）。**推翻条件**：前端重制不做自动重试；或"提交→快照"窗口真的造成重复 | 未纳入任务；`T59` 不加死字段（只加字段不上机制 = 死字段） |
