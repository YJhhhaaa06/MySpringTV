> **定位**：本篇只记 **「分几期、每期大致做成什么样」** 与 **骨架级设计**（数据模型 / 端点 / 计数口径 / 模块边界）。

> **用户看得到的功能需求 → `收藏功能-需求.md`**（唯一事实源，本篇不复述）。

## 一、分期（预告）

| 期 | 主题 | 目标 | 完成判据（可复算） |
|---|---|---|---|
| **一期** | **有无** | 功能**存在且行为正确**：`收藏功能-需求.md` 里标「纳入」的每一项都能用 | ① 需求篇「纳入」项逐条可演示；② 回归基线全绿；③ **不看 QPS** |
| **二期** | **性能** | 在一期契约**不变**的前提下换实现（缓存 + 冗余计数） | ① **先有一期的基线数字**（无基线不得宣称"优化生效"）；② 不变量 `content.favorite_count == COUNT(DISTINCT user_id)` 成立；③ 一期的测试**不许改** |
| **三期** | **周边** | 需求篇标「待定」的周边能力，按价值排序逐项立项 | 逐项单独立项，不绑成一批 |

### ★ 为什么按「有无 → 性能」切，而不是按功能广度切

旧分期（P0 核心 / P1 私密+整理 / P2 周边）按**功能广度**切，会把两件性质不同的事混进同一期：

| 错位 | 具体 | 处置 |
|---|---|---|
| 一期里塞了性能工作 | 域骨架带 cache、冗余计数增量维护、批量读 | **推迟到二期** |
| 后期里混了"必须一次到位"的东西 | 公开/私密要 `is_private` 列、简介要 `description` 列 —— **建表时顺手加是零成本，之后再加要 V3 + 存量回填**；且"默认公开"一旦上线就是对外契约，再改即 breaking change | **提前到一期** |
| 周边被绑成一期 | 稍后再看 / 订阅他人夹是**新功能**，失效占位 / 容量 / 连播是**展示或治理**，都不是性能 | 拆到三期，按价值排序 |

> 🔑 **判据：这是"性能"还是"有无"？** 看**去掉它功能还在不在** —— 去掉缓存功能照样能用（只是慢），
> 去掉 `is_private` 列功能就缺一块（且后期补要付 schema 代价）。

## 二、一期包含的能力（预告，**不是任务清单**）

> 任务四要素与执行态在 `CURRENT_TASKS.md`；这里的编号只是速记用的序号，不是任务号。

| 编号 | 能力 | 一句话 |
|---|---|---|
| 一期-1 | V2 建表 | `favorite_folder` + `favorite_item` + `content.favorite_count` 列（**列先加、一期不依赖**） |
| 一期-2 | 收藏夹 CRUD | 新建 / 改名 / 删除（**默认夹拒绝删除**）+ 我的夹列表（含每夹条目数） |
| 一期-3 | 公开 / 私密 | 建表即带 `is_private`；**可观察落点 = `GET /favorite/folder/public?userId=X`**（他人视角只返回公开夹，2026-10-08 拍板） |
| 一期-4 | 收藏 / 取消 | 指定夹收藏、从指定夹移出、移动到其他夹、批量移出 |
| 一期-5 | 收藏状态 | 我对某内容是否已收藏 + **收在哪些夹** |
| 一期-6 | 收藏数 | `COUNT(DISTINCT user_id)` **实时算**（按人去重；二期才上冗余列） |
| 一期-7 | 夹内列表 | 收藏时间倒序分页；`is_deleted != 0` 的条目返回**脱敏占位**（无封面 / 标题位「内容已失效」/ **不给原标题与作者**），仍占分页位置、仍可移出 |
| 一期-8 | 前端点亮 | `data-nav="star"` 摘掉 `disabled`；同步 `static/js/api.js` |
| 一期-9 | 契约测试 | 默认夹不可删、按人去重、**私密夹不在 `/folder/public` 出现**、**失效条目不含原标题 / 封面 / 作者**、**失效条目能移出**、取消收藏边界 |

> ⚠️ **「收藏不进 feed」不是契约测试，是设计红线**（见 §3.4）：它捕获的是"将来有人误把收藏接到 feed 上"，
> 而**没有任何实现可去掉** ⇒ 写测试只会得到一条永远绿的假绿（纪律④判据：去掉那行实现会红吗？）。
> 真要写，必须**先注入缺陷**（临时在收藏路径加一行 `FeedDelivery.deliver`）证明它会红，否则删掉。

> ⚠️ **一期的反面**（同等重要）：**不上缓存**、**不做冗余计数增量维护**、**不改媒体访问控制**、
> 不做订阅他人夹 / 稍后再看 / 容量上限 / 连播。逐条去向见 `FURTHER_ISSUES.md`。

## 三、骨架设计（跨期稳定）

### 3.1 数据模型

```
favorite_folder                     favorite_item
  id              bigint PK           id           bigint PK
  user_id         bigint 归属         folder_id    bigint → 收藏夹
  name            varchar(100)        user_id      bigint 冗余（查去重用）
  description     varchar(255) 简介   content_id   bigint
  is_private      tinyint 私密        create_time  datetime
  is_default      tinyint 默认夹      UNIQUE uk_folder_content (folder_id, content_id)
  create_time     datetime            KEY idx_user_content (user_id, content_id)
  update_time     datetime            KEY idx_folder_time (folder_id, create_time)
```

- ⚠️ `is_private` / `description` **必须在 V2 就带上**（见 §一 错位 2）。
- ⚠️ `content.favorite_count` **列在 V2 加**（零成本），但**一期不读不写**，二期才启用 ——
  启用时需**存量回填**（V2 落地时该列全是 0）。
- `favorite_item.user_id` 与 `folder_id` **冗余**：判"同一人是否收藏过"要按 `(user_id, content_id)`，
  不能按夹判（同一内容可进多夹，但收藏数只算 1）。

### 3.2 计数口径（跨两期，判据不变）

> 口径本身见 `收藏功能-需求.md` §六（**按人去重**）；这里只写**分两期怎么落地**。

| 期 | 收藏数怎么出 | 说明 |
|---|---|---|
| 一期 | `SELECT COUNT(DISTINCT user_id) FROM favorite_item WHERE content_id = ?` | 唯一事实源，**不会漂移** |
| 二期 | 增量维护 `content.favorite_count` | 冗余列，**唯一价值是快** |

🔑 **白捡的收益**：一期的"笨办法"直接就是**二期的验收 oracle** ——
二期上线后必须满足 `content.favorite_count == COUNT(DISTINCT user_id)`。
等于把"最容易写成假绿的一条"变成有独立 oracle 的普通切片。

增量维护的三条路径（**二期**）必须走**同一条判据**，否则计数漂移：

- **加收藏**：插入前查有无行 → **无** 则 `+1`
- **取消收藏**：删除后查有无剩余 → **无** 则 `-1`
- **删夹**（已拍板"删除条目"）：批量删后，对受影响的每个 `(user_id, content_id)` 逐个判剩余

### 3.3 端点草图（对齐 `/like/*` 命名风格）

```
POST   /favorite/folder/add          新建收藏夹
POST   /favorite/folder/update       改名 / 简介 / 私密开关（部分更新）
POST   /favorite/folder/remove       删除（默认夹拒绝）
GET    /favorite/folder/list         我的收藏夹列表（含每夹视频数）—— 需登录，返回**全部含私密**
GET    /favorite/folder/public       看他人公开夹 ?userId=X —— 匿名可访问，**只返回公开**
POST   /favorite/add                 收藏到指定夹
POST   /favorite/remove              从指定夹移出（支持批量）
POST   /favorite/move                移动到其他夹
GET    /favorite/status              我对某内容是否已收藏（含所在夹）
GET    /favorite/count               某内容的收藏数
GET    /favorite/list                夹内内容分页
```

> ⚠️ **端点形状是契约**：一期定下的路径、参数形态、分页语义（page/size）**二期不许改**
> （游标优化是二期**内部实现**，对外仍是 page/size）。

🔑 **为什么"我的"和"他人的"拆成两个端点，而不是给 `folder/list` 加可选 `userId`**：

1. **安全**：把"他人视角"做成**一条独立且危险的路径**，才能单独给它写
   "去掉 `is_private = 0` 就变红"的契约测试；混在一个端点里靠"传没传 userId"分流，
   分支一写错就是**直接泄露私密夹**。
2. **依赖方向**：若把收藏夹塞进 `/profile`，`ProfileService` 就要调 favorite 的 Service 契约，
   白白新增一条 `content → favorite` 的跨域依赖边；独立端点则 `content` 域**完全不依赖** `favorite` 域。
3. **前端不多一跳**：被查看者的 `userId` 在个人空间页本来就有（URL 参数），
   直接 `GET /favorite/folder/public?userId=X` 即可，**不需要"先拿收藏夹 ID"**。

### 3.4 模块边界与依赖

- 新域 `favorite`：**必须登记进 `ArchitectureTests.DOMAINS`**，否则规则 1/2/3 根本不覆盖它 ——
  该文件注释原话：新域不登记就会成为"**没有任何规则约束的空洞**"。
  ⚠️ 因此"ArchUnit 规则通过"**不是有效验收**（永远绿）；有效验收是"`DOMAINS` 含 `favorite`"。
- 跨域只走 Service 契约或事件。
- 🚫 **红线：收藏不得接 feed** —— `FavoriteService` **不得**调用 `FeedDelivery.deliver`、**不得**发
  `ContentPublishedEvent`（feed 关注流的唯一驱动源是 `ContentService.addVideo/addPost` 发的该事件）。
  ⚠️ 这是**给实现者的约束，靠 review 不靠测试**：它是"不要做某事"，没有实现可去掉 ⇒ 写成测试必假绿。

### 3.5 失效条目的 VO 形态（**易踩坑**）

> 口径见 `收藏功能-需求.md` §六「失效条目里能看到什么」；这里只写落地的坑。

- 后端**只给占位**：`invalid = true`、`cover = null`、`title` = 固定文案「内容已失效」、`author = null`；
  **保留条目 id / contentId**（供移出 —— 失效条目**可以移出**）。
- 🔑 **分页单位是 `favorite_item` 行，不是"内容"**：`LIMIT/OFFSET` 作用在收藏记录上，失效记录**占一条、返回一条占位**。
  ⚠️ **一张信封被失效条目占满也要照常返回**（用户 2026-10-08 实测确认 B 站如此），
  否则用户看不到、也就**永远清不掉**这些条目。
- 🔑 联结用 **LEFT JOIN content**，失效判据 = **`c.id IS NULL OR c.is_deleted != 0`**：
  `c.id IS NULL` 覆盖"内容行真没了"（本仓目前只有逻辑删除，但 INNER JOIN 一旦丢行同样造成分页空洞）。
- ⚠️ **不要照搬 `/profile` 的口径**：`ProfileService.java:109` 对已删内容是**「跳过，total 不变」**
  （TV 原样语义 ⇒ 分页出空洞）；收藏夹按 B 站是**返回占位条目**（条数连续）。两者不同，**别复用同一段填充逻辑**。
- 计数：夹内视频数与分页 `total` **包含**失效条目（B 站实测，占位即占位）。

**★「可移出但不可移入」的根因是存在性校验，不需要专门写分支**：

| 端点 | 校验内容存在性？ | 失效条目的结果 |
|---|---|---|
| `remove`（移出） | **不校验** —— 直接按 `(folder_id, content_id)` 删行 | **移得掉** ✅ |
| `add` / `move`（移入 / 移动） | 校验（`isContentExist` 的 SQL 带 `is_deleted = 0`） | **自然被拒** ✅ |

🚫 **因此 `remove` 绝不能"顺手"加上存在性校验** —— 一加，用户就永远清不掉占位条目了。
这与 `/like/*` 写路径「先校验存在性」的既有惯例**刻意不同**，必须在任务里点名。

## 四、已拍板结论（**索引**）

> 拍板过程与理由在 `CURRENT_NEEDS.md` **R-##**（本篇不复制理由，只留结论供设计时查阅）。

| 决策 | 结论 | 详见 |
|---|---|---|
| 默认夹创建时机 | **懒建**（首次收藏时）；夹列表需能返回空态 | `CURRENT_NEEDS.md` R-01 |
| 删除自建夹时的条目 | **一并删除**，逐个判剩余以维护计数 | R-02 |
| 失效内容（`is_deleted != 0`） | **占位保留并标记已失效**，不自动清理（B 站口径） | R-03 |
| 已失效内容的媒体可否下载 | **一期不做媒体闸** —— 本仓媒体静态直出，与 B 站不一致，属内容域议题 | R-04 / `FURTHER_ISSUES.md` **F-10** |
| 公开 / 私密 | **一期就给** | R-05 |
| `favorite_count` | 一期**实时算**，二期上冗余列 | R-06 |
| 失效条目的计数与操作口径 | ✅ **已拍板**（实测）：占位**计入**视频数 / **可移出、不可移入** / 收藏数仍算 | R-07 |
| 「私密」一期的**可观察落点** | ✅ **已拍板**：新增 `GET /favorite/folder/public?userId=X`（他人视角只返回公开夹） | R-08 |
