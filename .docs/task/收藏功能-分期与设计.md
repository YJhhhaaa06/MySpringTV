### ★ 为什么按「有无 → 性能」切，而不是按功能广度切

旧分期（P0 核心 / P1 私密+整理 / P2 周边）按**功能广度**切，会把两件性质不同的事混进同一期：

| 错位 | 具体 | 处置 |
|---|---|---|
| 一期里塞了性能工作 | 域骨架带 cache、冗余计数增量维护、批量读 | **推迟到二期** |
| 后期里混了"必须一次到位"的东西 | 公开/私密要 `is_private` 列、简介要 `description` 列 —— **建表时顺手加是零成本，之后再加要 V3 + 存量回填**；且"默认公开"一旦上线就是对外契约，再改即 breaking change | **提前到一期** |
| 周边被绑成一期 | 稍后再看 / 订阅他人夹是**新功能**，失效占位 / 容量 / 连播是**展示或治理**，都不是性能 | 拆到三期，按价值排序 |

> 🔑 **判据：这是"性能"还是"有无"？** 看**去掉它功能还在不在** —— 去掉缓存功能照样能用（只是慢），
> 去掉 `is_private` 列功能就缺一块（且后期补要付 schema 代价）。

## 三、骨架设计（跨期稳定）

### 3.1 数据模型

```
favorite_folder                                   favorite_item
  id              bigint PK                         id           bigint PK
  user_id         bigint 归属                       folder_id    bigint → 收藏夹
  name            varchar(100)                      user_id      bigint 冗余（查去重用）
  description     varchar(255) 简介                 content_id   bigint
  is_private      tinyint 私密                      create_time  datetime
  is_default      tinyint 默认夹                    UNIQUE uk_folder_content (folder_id, content_id)
  default_uniq    tinyint VIRTUAL 生成列            KEY idx_user_content (user_id, content_id)
  create_time     datetime                          KEY idx_folder_time (folder_id, create_time)
  update_time     datetime
  UNIQUE uk_user_default (user_id, default_uniq)    ← 每用户至多一个默认夹
```

- ⚠️ `is_private` / `description` **必须在 V2 就带上**（见 §一 错位 2）。
- ⚠️ `content.favorite_count` **列在 V2 加**（零成本），但**一期不读不写**，二期才启用 ——
  启用时需**存量回填**（V2 落地时该列全是 0）。
- `favorite_item.user_id` 与 `folder_id` **冗余**：判"同一人是否收藏过"要按 `(user_id, content_id)`，
  不能按夹判（同一内容可进多夹，但收藏数只算 1）。
- ★ `uk_user_default (user_id, default_uniq)` —— `default_uniq` 是 **VIRTUAL 生成列**
  （默认夹 `1` / 自建夹 `NULL`）：MySQL 唯一索引**不约束 NULL**，故"同一用户多条自建夹、
  至多一条默认夹"能用一个键表达。**它是 R-01 懒建在并发下唯一的防重复手段**
  （`INSERT ... WHERE NOT EXISTS` 兜不住：两个事务都能查到"不存在"）。
  建表时（2026-10-08，T1）落地，理由见[收藏功能-编号索引.md](收藏功能-编号索引.md)**A.2**（R-09）。
- ⚠️ `favorite_item` **刻意不加 `content_id` 前导索引**：一期收藏数走
  `COUNT(DISTINCT user_id) WHERE content_id = ?`，它的耗时基线是二期优化的对照
  （★ **T5 已实测记录**，见 §3.2）。

### 3.2 计数口径（跨两期，判据不变）

> 口径本身见 `收藏功能-需求.md` §六（**按人去重**）；这里只写**分两期怎么落地**。

| 期 | 收藏数怎么出 | 说明 |
|---|---|---|
| 一期 | `SELECT COUNT(DISTINCT user_id) FROM favorite_item WHERE content_id = ?` | 唯一事实源，**不会漂移** |
| 二期 | 读 `content.favorite_count`；**写路径用「事务内批量重算」维护该列** | 冗余列，**唯一价值是快** |

★ **一期耗时基线（T5 实测，2026-10-09；二期优化的对照）**：测试容器 MySQL 8.4 上造
**2 万行、目标内容 2000 个不同 user**（`user_id` 全不同、`content_id` 在 10 个值间轮转 ⇒
该 content 上 `COUNT(DISTINCT user_id)` = 2000）：

- `EXPLAIN` = `type=range`、`key=idx_user_content`、`key_len=16`、
  `Extra="Using where; Using index for group-by (scanning)"`；
- `EXPLAIN ANALYZE` 实际 ≈ **17 ms**；同一查询 20 次实测 **best ≈ 14 ms / avg ≈ 19 ms**。

⚠️ **别按"没有 `content_id` 前导索引 ⇒ 全表扫"去推断访问计划** —— 实测**推翻**了该假设：
本查询形态（`COUNT(DISTINCT user_id)`）恰好能被 `idx_user_content (user_id, content_id)` 的
**loose index scan** 接住（`DISTINCT` 列 `user_id` 恰是索引最左前缀；`Extra` 里的 `(scanning)`
是它的一个变体）。⚠️ 措辞别混：MySQL 的 `INDEX_SKIP_SCAN`（`Using index for skip scan`）官方
**不含** GROUP BY / DISTINCT —— 本条**不是** skip scan。

二期建 `content_id` 前导索引或上冗余列时，**重新实测**再与上面这组数字比。

🔑 **白捡的收益**：一期的"笨办法"直接就是**二期的验收 oracle** ——
二期上线后必须满足 `content.favorite_count == COUNT(DISTINCT user_id)`。
等于把"最容易写成假绿的一条"变成有独立 oracle 的普通切片。

#### ★ 二期的维护口径 =「**事务内批量重算**」，**不是**增量（2026-10-11 拍板方向）

> 方案取舍与排除理由见[收藏功能-编号索引.md](收藏功能-编号索引.md)**A.2 R-10**（2026-10-12 二期收尾时从 `CURRENT_NEEDS.md` 迁入）。此处只留骨架。

| 写路径 | 重算范围 |
|---|---|
| `add` / `remove`（单内容） | 该 `contentId` |
| `deleteFolder`（批量删条目） | **受影响的全部 contentId** |

统一入口 `recountFavoriteCounts(Set<Long> contentIds)`：

1. **一条** `SELECT content_id, COUNT(DISTINCT user_id) FROM favorite_item WHERE content_id IN (...) GROUP BY content_id`
   —— **一次聚合**，而不是"对受影响的每个 `(user_id, content_id)` 逐个判剩余"的 **N 次往返**；
2. 批量 `UPDATE content SET favorite_count = ? …`。

★ **它一次消掉四件事**：判"第一次收藏"、判"移出最后一个夹"、**并发漂移**、"需要同维唯一键"。

- ⚠️ **为什么不能用增量**：`favorite_item` 的唯一键是 `uk_folder_content (folder_id, content_id)`
  —— **"夹内唯一"，与判定的 `(user_id, content_id)` 维度不重合** ⇒ 同一用户**并发往两个不同夹**收同一内容时，
  两个事务都判"无行"、都 `+1`、撞不到唯一键 ⇒ **计数偏大**。
  （对照 like 域：它的判定维度与唯一键同在 `content_like (user_id, content_id)` 上，故增量安全。）
- ⚠️ **`SELECT … FOR UPDATE` 也不可用**：判"**不存在**"时 **RC 下不加锁**（形同虚设）、
  **RR 下 gap lock 共享** ⇒ 双方都过判定、随后 INSERT 互等 ⇒ **死锁**；
  且本仓是"唯一键 + 409"的**乐观并发**风格，**没有取锁顺序规范**。

#### ★ T12 落地（2026-10-12）——实测数字、残留窗口与口径修订

**⏳→✅ 实测（测试容器 MySQL 8.4，与上方 T5 基线**同构造数**：2 万行、content_id 在 10 个值间轮转、
每条 2000 个不同 user、user 全不同；探针为一次性、不入库，报告见 git）**：

| 查询 | EXPLAIN | EXPLAIN ANALYZE |
|---|---|---|
| 一期单内容实时 `COUNT(DISTINCT)`（**复测**，该查询已随 T12 退役） | 与 T5 记录一致：`type=range`、`key=idx_user_content`、`Extra="Using where; Using index for group-by (scanning)"` | ≈15 / 15.4 / 14.6 ms —— 与 T5 基线（≈17ms）同量级，**基线成立** |
| **T12 批量**：`GROUP BY content_id` + `IN (10 id)` | `type=index`、`key=idx_user_content`、`Extra="Using where; Using index; Using filesort"` —— ⚠️ **不是** loose index scan：IN 多值让优化器放弃该变体，改为**全索引扫描**（覆盖索引，免回表）+ GROUP BY 排序 | 首趟 9.5→12ms（冷），稳态 ≈ 4.2~6.5ms |

**对照结论**：同样 2 万行规模，批量**一趟** ≈6ms，逐条 10 次单内容 ≈150ms —— "1 次 GROUP BY + 1 次批量 UPDATE、绝不逐条"的价值被实测坐实。两个如实登记的特征：① 批量版是**全索引扫描**（成本 ∝ 表总行数，不是受影响内容的行数；覆盖索引免回表，本仓规模下 ≈6ms）；② 它不是 loose index scan —— 别拿一期的"scanning"措辞套在本条上。列读启用后该查询只在**写路径**（低频）上运行，读路径已降为主键点查。

**★ 残留并发窗口（如实登记，G14）**：重算消掉的是"增量判错方向"那类漂移（本节上方两段）；两个**不同用户**并发首次收藏同一内容时，两个事务的聚合各自读提交前快照，**后提交者把陈旧绝对值写回**（content 行锁只保证写串行、不保证值新鲜）⇒ 列短暂偏小，直到该内容下次被任何写路径波及（重算幂等 ⇒ 自愈）。这是"拍板重算制 + 排除 `FOR UPDATE`"下的固有代价，接受。

**★ 判据③ 的第二个例外（G8 第二例外，用户 2026-10-12 拍板）**：读切列使 T5 一期计数测试的**直插 DB 夹具**不可见（列只由写路径的事务内重算维护）⇒ T5 夹具改走真实写路径（**业务断言一字未改**）；幽灵内容（内容行不存在）的 count 期望值 1 → 0（列只能存在于 content 行上，该态无 API 可达；"无行回退实时聚合"的混合方案会重开匿名端点的 17ms 聚合口子，刻意不做）。登记见本文**附录 A.3 I-12**。

**落地形态**：`recountFavoriteCounts(Set<Long>)` 收在 `FavoriteService`（私有，运行在调用方事务里）；
聚合 = `FavoriteItemDao.countDistinctUsersByContentIds`（1 趟 GROUP BY）+ 写回 = `ContentDao.updateFavoriteCounts`
（1 趟 CASE-WHEN 批量 UPDATE，跨域 DAO 薄依赖，与 like 的 `updateLikeCount` 同构）；列读 = `ContentDao.findFavoriteCountById`
（`COALESCE` 标量子查询保恒一行；域边界读例外登记见《模块边界与依赖》§六）。接入路径 = **四条**（add / remove / **move** / deleteFolder
—— move 为 I-12 拍板补入，理由见该条）；`addItem`/`removeItems` 随之升级 `@Transactional`（两写同进同退），
事务口径变更见《事务边界》§1.1；机制判别力 = `FavoriteCountMaintenanceTests`（10 例：四路径不变量 oracle、
清零补 0、绝对值自愈、读切换证明、最后一步打桩回滚 ×2、批量单趟 verify）。

### 3.3 端点草图（对齐 `/like/*` 命名风格）

```
POST   /favorite/folder/add          新建收藏夹
POST   /favorite/folder/update       改名 / 简介 / 私密开关（部分更新）
POST   /favorite/folder/remove       删除（默认夹拒绝）
GET    /favorite/folder/list         我的收藏夹列表（含每夹视频数）—— 需登录，返回**全部含私密**
GET    /favorite/folder/public       看他人公开夹 ?userId=X —— 匿名可访问，**只返回公开**
POST   /favorite/add                 收藏到指定夹
POST   /favorite/remove              从指定夹移出（支持批量）
POST   /favorite/move                移动到其他夹
GET    /favorite/status              我对某内容是否已收藏（含所在夹）
GET    /favorite/count               某内容的收藏数
GET    /favorite/list                夹内内容分页
```

> ⚠️ **端点形状是契约**：一期定下的路径、参数形态、分页语义**二期不许改**
> （游标优化是二期**内部实现**，对外仍是 page/pageSize）。
> 📌 **分页参数名是 {@code page} + {@code pageSize}**（T6 落地时定）：与 {@code PageResult.pageSize}
> 及全项目其余分页端点（{@code /start}、{@code /profile}、{@code /search}、{@code /feed}、{@code /comment/*}）
> 一致；早期草稿里速记的 {@code size} **不采用** —— 两个名字表达同一件事会让契约分裂。

> ⚠️ **二期会给「内容详情」的响应加一个内嵌子对象**（`interaction`）—— 那是**内容域**的响应形态变化，
> **不是新端点**，见 **§3.6**（`/search/IdSearch` 路径不变）。

🔑 **为什么"我的"和"他人的"拆成两个端点，而不是给 `folder/list` 加可选 `userId`**：

1. **安全**：把"他人视角"做成**一条独立且危险的路径**，才能单独给它写
   "去掉 `is_private = 0` 就变红"的契约测试；混在一个端点里靠"传没传 userId"分流，
   分支一写错就是**直接泄露私密夹**。
2. **依赖方向**：若把收藏夹塞进 `/profile`，`ProfileService` 就要调 favorite 的 Service 契约，
   白白新增一条 `content → favorite` 的跨域依赖边；独立端点则 `content` 域**完全不依赖** `favorite` 域。
3. **前端不多一跳**：被查看者的 `userId` 在个人空间页本来就有（URL 参数），
   直接 `GET /favorite/folder/public?userId=X` 即可，**不需要"先拿收藏夹 ID"**。

### 3.4 模块边界与依赖

- 新域 `favorite`：**必须登记进 `ArchitectureTests.DOMAINS`**，否则规则 1/2/3 根本不覆盖它 ——
  该文件注释原话：新域不登记就会成为"**没有任何规则约束的空洞**"。
  ⚠️ 因此"ArchUnit 规则通过"**不是有效验收**（永远绿）；有效验收是"`DOMAINS` 含 `favorite`"。

  它的三条不可省的约束（**单条 + 批量契约**、**不得依赖 content**、**边界排除评论点赞**）见 **§3.6**。

### 3.5 失效条目的 VO 形态（**易踩坑**）

> 口径见 `收藏功能-需求.md` §六「失效条目里能看到什么」；这里只写落地的坑。

- 后端**只给占位**：`invalid = true`、`cover = null`、`title` = 固定文案「内容已失效」、`author = null`；
  **保留条目 id / contentId**（供移出 —— 失效条目**可以移出**）。
- 🔑 **分页单位是 `favorite_item` 行，不是"内容"**：`LIMIT/OFFSET` 作用在收藏记录上，失效记录**占一条、返回一条占位**。
  ⚠️ **一张信封被失效条目占满也要照常返回**（用户 2026-10-08 实测确认 B 站如此），
  否则用户看不到、也就**永远清不掉**这些条目。
- 🔑 失效判据 = **content 装载契约"取不到"**（T6-5 残留提交 2026-10-09 更新；口径 **R-11**「看不了 ≈ 失效」）：
  列表经 `ContentService.loadContentVOs` 批量取展示字段，**不存在 / 已删下架 / 媒体损坏 / 未知 type 统一当失效**；
  本域 SQL 只查 `favorite_item` 三列。⚠️ 原"**LEFT JOIN content** + `c.id IS NULL OR c.is_deleted != 0`"写法
  已被取代（它测不出"视频行缺失 / 未知 type"），favorite 也不再直连他域表（I-07 ③ 已根治）。
- ⚠️ **不要照搬 `/profile` 的口径**：`ProfileService.java:109` 对已删内容是**「跳过，total 不变」**
  （TV 原样语义 ⇒ 分页出空洞）；收藏夹按 B 站是**返回占位条目**（条数连续）。两者不同，**别复用同一段填充逻辑**。
- 计数：夹内视频数与分页 `total` **包含**失效条目（B 站实测，占位即占位）。

**★「可移出但不可移入」的根因是存在性校验，不需要专门写分支**：

| 端点 | 校验内容存在性？ | 失效条目的结果 |
|---|---|---|
| `remove`（移出） | **不校验** —— 直接按 `(folder_id, content_id)` 删行 | **移得掉** ✅ |
| `add` / `move`（移入 / 移动） | 校验（`isContentExist` 的 SQL 带 `is_deleted = 0`） | **自然被拒** ✅ |

⚠️ R-11 之后"列表失效集" ⊋ "`add`/`move` 拒收集"：数据损坏态（`is_deleted = 0` 但装不出来）
列表占位、而 `add`/`move` 仍收得进 —— 属**已拍板接受**的边缘态（生产写路径造不出该态），
详见[收藏功能-编号索引.md](收藏功能-编号索引.md)**A.2**（R-11）。

🚫 **因此 `remove` 绝不能"顺手"加上存在性校验** —— 一加，用户就永远清不掉占位条目了。
这与 `/like/*` 写路径「先校验存在性」的既有惯例**刻意不同**，必须在任务里点名。

### 3.7 收藏侧的缓存边界（**二期**，与 R-10 同期定；细节形态与 like 域同构）

| 读 | 频率 | 怎么取 |
|---|---|---|
| 我是否收藏过（`isFavorited`） | **高频**（详情 / feed / 列表） | **Redis `Set` + `SISMEMBER`**（`user:favoriteSet:{userId}`） |
| 收藏数（`count`） | 高频（详情页展示） | **Redis `String`**（`content:favoriteCount:{id}`）；miss 回源 **主键点查**（二期有冗余列后） |
| **收在哪些夹（`folders`）** | **低频**（只在开收藏弹窗） | **直查 DB**，且 **`SISMEMBER` 为 false 时短路**（未收藏**连库都不查**） |

★ **`folders` 刻意不缓存**（2026-10-11 拍板）：它**低频**且"未收藏时短路"⇒ 正常路径下 DB 查询**几乎不发生**；
若给它加缓存，失效点有 **add / remove / move / 删夹 / 改名**五个，收益只是"省一次**亚毫秒**索引点查" ⇒ **不划算**。
（缓存第一原则：只为"**高频 × 昂贵**"加缓存 —— `folders` 两者都不满足。）

⚠️ **防护归属 = 限流，不是缓存**：脚本刷"自己已收藏内容的 `folders`"虽 1:1 打 DB，但**需登录**
（`/favorite/status` 是 `@RequiresLogin`）、**只能查自己的夹**（无越权 / 无泄露）、单次 **亚毫秒 ~ 1–2ms**
—— 属**任何登录接口的常态**。⚠️ 而本仓**限流目前缺失**（2026-10-13 补登记为 `FURTHER_ISSUES.md` **F-22**；
F-01 / F-02 是 **Spring Security 迁移**，属同一"上线准备度"专项但不是限流本身）
⇒ **"限流在场"是本设计可接受的前提条件**。
⚠️ **真正该防的是 `/favorite/count`**：**匿名**（不需要账号）+ 回源 **17ms 聚合** ⇒ 它的解是
**冗余列（把回源降为主键点查）+ 缓存**。

★ **2026-10-13 补充（F-17 收口时）**：上面两句要**分开读** —— ① **"前提"针对的是"可放大的点"**；
② 而**最尖锐的那个点（匿名 + `17ms` 聚合）已由 T12 消除**（回源降为**主键点查**），且那个点的解**本来就是
"冗余列 + 缓存"、不是限流**。⇒ 剩余风险只有"**任何登录接口的常态**"（本段自己的判断）
⇒ **"限流在场"作为前提的强度已下降**，且**不因"保留计数缓存"（F-17 ② 的结论）重新变紧急**。
