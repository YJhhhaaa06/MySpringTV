## 一、总纲：两个记账主体、两个桶、一条非对称规则

| 概念 | 定义 |
|---|---|
| **用户桶** | per-key 配额。key = 登录态 `user:{userId}`，匿名态 `anon:{ip}` |
| **服务器桶** | 全局单桶。代表"单实例整体还能接多少活" |
| **记账主体 · 请求** | 过闸：用户桶 + 服务器桶都参与 |
| **记账主体 · 任务** | 不过闸：只在执行处扣服务器桶（§三） |

**核心规则（非对称扣减，用户 2026-10-16 拍板）**：

- **用户桶：无条件扣**。请求到达即扣一笔"询问费"，**被拒也扣**——否则被拒的请求是**免费探路**，
  刷子可以用被拒请求零成本试探。扣的是"打折后的询问费"，不是全款（见 §二 `reject-discount`）。
- **服务器桶：条件扣**。只在**确定放行**时扣。被拒的请求没有消耗服务器资源（它在闸门处就被拦了）
  ⇒ 服务器桶不该为它记账。

> ★ **这条非对称规则顺手消掉了本设计最难的一块**：两个桶**不需要"同时扣"的原子操作**。
> 用户桶先扣、服务器桶后判后扣，天然分两阶段 ⇒ 不必跨 key 做分布式事务，也不必把"两桶都够"变成一个
> 不可分割的判定。副作用是"服务器忙时用户桶已扣不返还"——由 §二 的折扣把这一刀削钝。

## 二、请求主体：账本时序

```
key  = 登录 ? "user:" + userId : "anon:" + clientIp
cost = cost.base(路由) × cost.miss-multiplier        // 信号① × 信号②

一次 Lua（KEYS = [userKey, serverKey]），惰性补充写在脚本内（§五）：

① user.refill()                            // tokens = min(cap, tokens + elapsed × rate)
   user.tokens -= cost × reject-discount   // 询问费：无条件扣（可为负 ⇒ 欠账累积）

② 闸门：
     user.tokens ≥ cost × (1 − reject-discount)      // 付得起尾款吗
  且 server.tokens ≥ cost                            // 服务器桶够吗
   否 ⇒ 429（只扣了询问费；服务器桶完全不动），带 Retry-After
   是 ⇒ user.tokens -= cost × (1 − reject-discount)
        server.tokens -= cost
        ⇒ 放行
```

> ★ **T26 修订注（落地修正）**：上面的 `cost = cost.base(路由) × cost.miss-multiplier` 是
> **请求总成本**的简写——信号②（缓存 miss）是**本请求运行期事实**，门时取不到 ⇒ 实现拆两阶段：
> **门时按 `base` 扣、请求收尾按差额 `base × (multiplier − 1)` 补扣**（仅"门放行过"的请求、
> 两桶同扣、fail-open；登记 `I-20`）。落地形态（二值标记 / 线程封闭 / 清理点）与"不计数"的
> 已否决论证见 `architecture/tech/限流.md` §四 与本文 §12.2。

**`reject-discount` 是本设计唯一的连续旋钮**（默认 0.3，见 §九）：

| 取值 | 被拒时的代价 | 边界含义 |
|---|---|---|
| `0` | 完全不扣 | 被拒 = **免费探路**（防刷最弱） |
| `1` | 扣全款 | 用户为"服务器过载"**全额买单**（易误伤正常用户） |
| `(0,1)` | 扣打折后的一笔 | 刷子有成本、正常用户只受轻伤 |

## 三、异步任务主体：无条件扣服务器桶

```
任务执行处：server.tokens -= server.task-cost      // 无条件、可为负；不碰任何用户桶
```

**为什么任务不碰用户桶**：被去抖合并的异步任务（"多个用户一起点赞、热度表只重建一次"）
其成本**不属于任何一个用户**——摊给"触发者"＝第 100 个人替前 99 个人买单；摊给所有人＝传递所有人的 id，复杂度高。

**为什么不需要传 `userId`**：异步任务跑在 MQ 消费线程上，与请求线程**不是同一个执行上下文**，
`ThreadLocal` / `MDC` 都不会跟过去。要靠显式传参就等于**跨层回传信号**

**第一个落点 = `FeedRebuildService`**（feed 收件箱重建，跑在 MQ 消费线程）——**现成就有**，不必等未来。
**立规**：新增昂贵后台任务（如将来的评论热度表重建）一律在**执行处**接同一扣减入口。

> ★ **T27 落地修订注（2026-10-17）**：扣减点 = **重建锁成功之后、真正重建之前**——
> "锁跳过（并发去重 / Redis 降级）= 没干活 = 不扣"；重复执行（跨去抖窗口的重复消息）= 重复计费，
> 是"谁干活谁付费"的想要的语义（容器重试只发生在"载荷非法"出口，到不了扣减点）；
> DB 失败**不退钱**（已过锁、已计费，"试图干活"即扣）。扣减自带**独立失败边界**（fail-open）——
> 不许复用重建主 try 的兜底（那会把语义变成"扣减失败让任务失败"）。
> **演进方向（登记，暂不做）**：本节"摊给触发者＝第 100 个人买单"的反面做法——
> 去抖合并后把成本按触发用户分摊回用户桶——等真实需要再论证（已写进 `architecture/tech/限流.md` §四③）。

## 四、成本信号：三条来源

| 信号 | 来源 | 形态 | 覆盖什么 |
|---|---|---|---|
| **① 端点权重** | 配置表 | 静态 `cost.base(方法 + 路径模式)`，未登记 ⇒ `default-base` | 不同端点的量级差异 |
| **② 缓存命中系数** | **本请求运行期事实** | 乘数 `miss-multiplier`（miss 更贵） | "这一次查询有没有命中缓存" |
| **③ 任务成本** | 任务自身 | 常量 `server.task-cost`，记在任务主体上 | "写的时候是否触发了昂贵异步活" |

### 4.1 明确不做：全事后结算（预扣 + 按实际多退少补）

| 否办理由 | 说明 |
|---|---|
| 信号归因不到请求线程 | 昂贵异步活在 MQ 消费线程跑，请求早已返回 ⇒ **永远归因不到"这一次请求"** |
| 换算函数本身也是拍的 | "耗时 → 令牌数"这个函数同样没有依据 ⇒ 只是把"拍"从端点级挪到实测级，精确是幻觉 |
| 二次写把原子性请回来 | 补扣 / 返还是又一次跨桶写 ⇒ 需要幂等 + 原子性，而 §一 刚把这块消掉 |
| 结算点被污染 | "耗时"包含排队时间——服务器忙的时候本来就慢，会把负载误当成成本 |

⇒ **用"记账主体扩成请求 + 任务"替代"事后结算"**：不需要新机制，只是多记一类账。

## 五、状态结构：惰性补充，**没有定时任务**（★ 本节回答"Redis 压力"问题）

**先推翻一个隐含假设**：标准令牌桶**不存在"每隔一段时间给所有人加令牌"这件事**。
没有任何定时任务、没有全量扫描、没有 ZSet 轮询。补充是**惰性**的：

```
桶里只存两个字段：tokens、lastRefillMs
每次请求到达（在 Lua 脚本内）：
    elapsed = now − lastRefillMs
    tokens  = min(capacity, tokens + elapsed × refillPerSec)
    lastRefillMs = now
```

- **补充的写与"扣减的写"是同一次写** ⇒ **零额外 Redis 压力**。
- 全量扫描是 O(N) 灾难（活跃用户桶数 = key 数）——惰性补充从结构上排除了这条路。

**key 回收靠 TTL，不靠 GC**：

```
TTL = ceil(capacity / refillPerSec)      // = 把空桶补满所需时间
```

★ **自证性质（这条让 TTL 取值不需要论证）**：能被 TTL 淘汰的桶，说明它**空闲时长 > 满桶时间**
⇒ 按惰性公式，它此刻**本来就该是满的** ⇒ "淘汰后下次从满桶起算"与"公式算出来的值"**完全一致**，
**无损**。

**其余结构口径**：

| 项 | 口径 |
|---|---|
| 每桶一个 key | 含 `tokens` 与 `lastRefillMs` 两个字段（编码形态——`HASH` 或紧凑字符串——在实现任务里定） |
| 单请求往返 | **1 次**（`KEYS = [userKey, serverKey]`，一次 Lua 覆盖 §二 的 ①②③） |
| 任务侧扣减 | 单独一次 Lua（`KEYS = [serverKey]`） |
| 实例 | 服务器桶与用户桶**同一 Redis 实例**（本仓单实例部署） |
| ⚠️ 留池 | Redis Cluster 下多 key 跨 slot 需要 `{tag}`——本仓单实例不涉及，登记为推翻条件 |

## 六、接线：过滤器链位置 + 复用既有熔断

**位置（用户 2026-10-16 拍板 A：先鉴权后扣费）**——限流器排在 `JwtAuthFilter` 之**内**侧：

```
RequestIdFilter ─► AccessLogFilter ─► Security 链 ─► JwtAuthFilter ─► ★限流器 ─► DispatcherServlet
```

- 直接读请求属性里的 `userId`（`JwtAuthFilter.ATTR_USER_ID`）；
  401 / 403 短路发生在它**之前** ⇒ 被鉴权拒绝的请求**不浪费令牌**。
- ⚠️ `JwtAuthFilter` 目前**无 `@Order`**（最低优先级）、限流器若要排在它之内侧就必须**显式定序**
  ⇒ 本任务要给两者补 `@Order`，并**同步** [安全与鉴权](../architecture/tech/安全与鉴权.md) §2.1 的链序表。
- ⚠️ 迁 Spring Security（`F-01` / `F-02`）时这条链序要**再挪一次**；**算法 / 规则 / 契约不重写**。

**降级与熔断：复用 `RedisOps.guarded`，零新增机制**

本仓全仓的 Redis 访问收在 `RedisOps.guarded`（[韧性](../architecture/tech/韧性.md) §八 第 1 条：
"新增 Redis 访问一律经 `RedisOps.guarded`"），它已经提供两件事：

```
熔断 OPEN ⇒ tryAcquire() 返回 false ⇒ 不访问 Redis、直接抛 CacheUnavailableException（快速失败）
放行      ⇒ 真发命令 → 成功记 success / 失败记 failure
```

⇒ 限流器只要经它发 Lua，就**白拿**"告诉下游 redis 挂了别再查"这条能力。限流器自己只做一步：

```
catch (CacheUnavailableException) ⇒ 放行（fail-open）
```

⚠️ **fail-open 的副作用（必须钉住）**：限流器**自身的缺陷**（Lua 脚本写错、返回值解析失败）
也会被归一成 `CacheUnavailableException` ⇒ **静默放行**，看起来像"Redis 挂了"，实际是**限流消失**。
两条兜底：① Lua 脚本被**契约测试钉住**（改脚本去掉某行必须变红）；② 日志把"Redis 不可达"与
"脚本 / 返回异常"分开（WARN vs **ERROR**）。

## 七、覆盖范围

| 项 | 口径 | 理由 |
|---|---|---|
| **过闸** | 所有到达 `DispatcherServlet` 的请求，**含匿名读接口、未映射路径（404 扫描流）、`/api/admin`** | 404 扫描流正是要防的对象之一 |
| **跳过** | `/`、`/index.html`、`/favicon.ico`、`/static/**`、`/actuator/**` | 静态资源不是业务成本；一起过闸会拖慢首屏、甚至 429 掉 CSS（前端 18 文件在 `static/`） |
| **白名单** | **无**（含管理员） | 管理端人工操作、流量极小，不值得开一个"绕过口" |
| **权重表未登记路由** | 落到 `cost.default-base`（**不是 0**） | 防"漏配 = 不限" |

## 八、429 契约

| 项 | 口径 |
|---|---|
| HTTP 状态 | **429** |
| 业务码 | ★ `ErrorCode` 现在**没有 429** ⇒ 新增 `RATE_LIMITED(429, "请求过于频繁")`，沿用"code 与 HTTP 对齐"的既有规则 |
| 响应头 | **`Retry-After`**（秒，向上取整）——令牌桶**天生知道自己何时补齐**（`ceil((cost − tokens) / rate)`），这是它相对固定窗口的卖点，值得暴露 |
| 出口形态 | 与 `JwtAuthFilter` 同款：过滤器**自写 `ApiResponse`** ＋ 写 `AccessLogFilter.ATTR_BUSINESS_CODE`（否则访问日志三态塌成两态） |
| 区分桶 | **不区分**是哪个桶挡的，响应体统一 |

## 九、配置与参数结构（`video.rate-limit.*`）

沿用本仓既有范式：`@ConfigurationProperties` 记录 + **绑定期校验**（非法即拒绝启动，
同 `RedisBreakerProperties` / `FavoriteLimitProperties`）+ 环境变量可覆盖（测试注入用）。

```
video.rate-limit:
  server:   capacity / refill-per-sec / task-cost
  user:
    authed: capacity / refill-per-sec
    anon:   capacity / refill-per-sec      # 匿名独立一套（IP 共享 ⇒ 更宽），且必须可被测试覆盖
  cost:
    base: Map<方法 + 路径模式, 权重> / default-base     # 如 "POST /favorite/add"（Spring 路由模式，非具体 id）
    miss-multiplier        # 信号②，默认 1.0 = 关闭（显式给 >1 才生效，沿用本仓"0/1 = 关闭"惯例）
    reject-discount        # §二 的折扣，默认 0.3
```

### 9.1 ★ 首版数值：**全是拍的**

> 下表用途是让口径**可复算、可替换**，**不是让数值可信**。每项登记「推导锚点」与「推翻条件」。

| 参数 | 首版值 | 推导锚点（拍依据） | 推翻条件 |
|---|---|---|---|
| `server.capacity` | 200 | 量级锚点 = 容器默认最大工作线程数（"瞬时在途请求上限"） | 出现真实并发基线 |
| `server.refill-per-sec` | 50 | capacity / 4（空桶 4 秒补满 ⇒ 稳态吞吐上界） | 同上 |
| `server.task-cost` | 10 | "一次收件箱重建 ≈ 十次普通读" | 有异步任务实测耗时 |
| `user.authed.capacity` / `refill` | 20 / 2 | "正常人远达不到每分钟 120 次" | 有真实用户行为分布 |
| `user.anon.capacity` / `refill` | 60 / 6 | IP 共享（NAT / 内网）⇒ 比登录桶放宽 3 倍 | 有真实匿名请求分布 |
| `cost.default-base` | 1 | 未登记端点的兜底单位 | — |
| `cost.base` | 登录 / 注册 5；上传 10；写路径（like / comment / favorite / follow 的 add / remove）3；读 1 | 按"是否触达 DB 写 + 是否重活"排序 | 有按端点的实测成本 |
| `cost.miss-multiplier` | 3.0 | "miss 一次 ≈ 三次命中"（凭"DB 远慢于 Redis"的量级差） | 有命中 / 未命中的实测耗时比 |
| `cost.reject-discount` | 0.3 | "被拒 = 打三折"，既不免费也不全款 | 出现正常用户被误伤的证据 |

⚠️ **本表的"来源 = 拍"要在实现里写进配置注释**——本仓已有先例（`video.favorite.*` 的注释明写
"数字是刻意砍小的演示值"）。

## 十、可观测

| 面 | 口径 |
|---|---|
| 指标 | Micrometer：`rate.limit.decisions{scope=server\|user, result=allowed\|rejected}` 计数 ＋ 限流器自身耗时 |
| 拒绝日志 | **WARN 结论行、不持栈**（对齐 MQ 口径"一条故障只留一条诊断"） |
| Redis 不可达（放行） | WARN 结论行 |
| **脚本 / 返回解析异常** | **ERROR**（§六 的兜底②） |
| ★ 拒绝日志**不记原始 key** | 登录记 `userId`（仓内已有此惯例）；**匿名不落盘 IP**——[可观测](../architecture/tech/可观测.md) §三 的脱敏面**只认手机号**，IP 要脱敏得先扩脱敏；当前无排查需求，**建议不落盘** |

> ★ **T28 落地注（2026-10-17）**：`scope` 标签在实现层**没有取值来源**——§八 的"不区分桶"是响应体口径，
> 而 Lua 只返回联合结论，被拒时无法反推哪一侧挡的（两侧可能都不够）⇒ 返回值扩成
> `allowed:retrySeconds:uPass:sPass`，指标按**逐桶判定**记两条样本（登记 `I-21`；**响应体形状一字未改**）。
> **`fail-open` 计数（`failopen{reason}`）刻意不做**：本表没有这一族，fail-open 的出口只有日志
> （用户 2026-10-17 拍板；口径见 `architecture/tech/限流.md` §五「刻意不做」）。

|---|---|---|
| D-1 | **数值全是拍的** | 无真实流量；靠"来源 + 推翻条件"登记而不是靠数值可信 |
| D-2 | **后台任务忙 ⇒ 前台更容易被限** | 任务无条件扣服务器桶的直接后果；也是"服务器确实忙"的**诚实信号** |
| D-3 | **测试 / 压测环境匿名桶退化成全局限流** | MockMvc / 本机压测 IP 全同；用"测试覆盖阈值"对冲 |
| D-4 | **Redis 从"可降级加速器"变成关键路径依赖** | 选 Redis 做限流的必然结果；用 fail-open ＋ E2E 既有熔断对冲 |
| D-5 | **fail-open 期间等于没有限流** | 可用性优先（本仓既有口径"缓存不可用不许 500"） |
| D-6 | **服务器桶可为负**（欠账） | 欠账要靠恢复补回来 ⇒ 后台密集期会延长前台拒绝窗口 |
| D-7 | 反代 / NAT / 校园网下的 IP 语义未处理 | 本仓尚无反代（同 `F-01` / `F-02` 的"上线准备度"） |

### 12.2 已否决的方案（留痕，防重复论证）

| 被否决 | 为什么 |
|---|---|
| **全事后结算**（预扣 + 实测多退少补） | §4.1 四条 |
| **任务也过闸**（不足则延迟 / 重试） | 本仓 `default-requeue-rejected=false` ⇒ "消费侧拒绝"**直接进 DLQ** ⇒ 会**把任务丢掉**；且 push ＋ `prefetch=1` 下"取任务前判"这个动作**不存在** |
| **消费侧背压**（按令牌暂停消费者） | 方向正确但收益边际（任务已被 `InboxRebuildDebouncer` 去抖限频）；恢复时补跑堆积任务会形成尖峰；且需新增"读令牌 → 调容器"控制面 |
| **匿名不单独建桶**（只吃服务器桶） | 失去"防单个 IP 刷"的能力；改按 IP ＋ 宽桶后代价可控（D-3 / D-7 已登记） |
| **管理员白名单** | 管理端人工、流量极小，不值得开"绕过口" |
| **多维度令牌**（网络 / 磁盘 IO / CPU / 缓存 / DB 时间） | 用户 2026-10-16 拍板：**不区分维度**，按请求折算 |
| **次数加权**（回传 miss 次数、按次数定系数） | T26 否决（2026-10-16）：① "次"的单位随实现漂移（按调用 / 按 key / 按条目？批量装载与页大小会静默改价）；② "次数 → 系数"是又一个拍的函数、还得再拍封顶值——"换算函数本身也是拍的"（§4.1 同一理由）；③ 冷启动 / 深翻会把正常用户 ×(3n) 误伤。**取二值**（任一 miss 乘一次）：接线位置不变，升级 = 调用点改累计 + 差额公式改函数 |
| **拉高查询端点基础价**（用"平均值"代替运行期信号） | T26 否决（2026-10-16）：只把命中价与 miss 价**同涨**（比值仍 1:3），不解决"多 miss vs 单 miss"的刻画；且与 §4.1 同一立场——"平均价"与那里的"换算函数"一样都是拍的（"把不确定性烘进常量"，见 §4.1「换算函数本身也是拍的」）。读端点维持 `default-base = 1` |
