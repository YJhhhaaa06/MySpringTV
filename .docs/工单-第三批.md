### 顺序理由（**不是按台账编号排的**）

1. **T1 必须最先**——它同时是"观测线"与 T2–T5 的**验收工具**。
   没有它，后面每个任务的"注入故障 → 看是否变红"都没法演示（故障注入测试不能进默认回归集，
   否则回归集永远红 ⇒ 必须能按组选跑）。
2. **T2 在 T3/T5 之前**——故障注入的**观察手段**就是日志与打点。
   先把"看得见"建好，再补"扛得住"；否则 T3/T5 补完**无法证明有效**（这正是 B 类
   "全部不会让测试变红"的老问题）。
3. **T3 内部分三步（B6 → B4 → B1）**：B6 有明确正确性含义（DB 故障 + 索引缺失
   ⇒ **每请求一次全表重建**），代价最大、最该先做；B4 熔断是 B6 的同类（Redis 故障
   每请求等 1000ms 超时）；B1 单飞是纯优化、风险最低。
4. **T5 放最后**——正确性含义最强（B9 会**永久丢消息**），但也最依赖 T1+T2，
   且需要 broker 断连注入（比停 Redis 更麻烦）。
5. **T6 与 T1–T5 无依赖**——前端只碰 `src/main/resources/static/`，可与后端并行。

## T1：`tools/run_tests.py`（独立工具任务）

> **本任务不含任何业务代码**，纯工具。它是本批其余任务的**验收工具**，所以排在第一位。
> 老项目已有正确范式可参考：`old-project/TVhomework1/tools/run_tests_report.py`
> （其 docstring 的三条设计约定——完整输出落盘 / 机器可读结果 / stdout 只回显摘要——直接沿用）。

### 它要承载什么功能（**需求清单，实现自由**）

**① 一键运行**

- 默认跑**全量**：`mvnw.cmd -B clean verify`（⚠️ **必须带 `clean`**：`target/classes` 留着
  上一轮 class 时增量编译会跳过重编，"源码编译不过"会被旧 class 掩盖而测试照样绿）。
- 支持**按组选跑**（`--group <tag>`）：这是**故障注入的前提**——故障注入测试不能进默认回归集。
  机制用 JUnit 5 `@Tag` + Maven 过滤（`-Dgroups=...`）。
- 支持**按类选跑**（`--test <Class>`），供单任务开发期用。

**② 完整报告落盘**

| 产物 | 内容 |
|------|------|
| `target/test-reports/run-<时间戳>.log` | 完整控制台输出（**不截断**，供事后排查） |
| `target/test-reports/latest.json` | 机器可读：exit code / 用例数 / 失败清单 / 各阶段耗时 / 日志路径 |
| `target/test-reports/report-<时间戳>.md` | 人类可读：按测试类汇总 + **失败用例逐条列 + 失败栈摘要** |

**③ stdout 只输出摘要**

- 常态**约 10 行**：总数 / 通过 / 失败 / 跳过 / 耗时 / 报告路径。
- 有失败时**额外列出失败用例名**（一屏内可读），并给出"去哪看完整栈"的路径。
- **目的**：避免测试输出灌进主会话上下文（老项目原话）。

### ⚠️ 三条实现口径（**避开老做法的坑**）

1. **数据源用 surefire XML，不要解析控制台**：`target/surefire-reports/TEST-*.xml` 是结构化结果，
   含每个用例的名字/耗时/失败栈。**正则解析控制台会在日志里出现 "Tests run" 字样时误判**
   （老项目 `parse_pytest_summary` 就是这么干的，因为它没有 XML 可依赖；新项目有）。
2. **必须拿到"全部失败"而不是第一条**：Maven 默认遇失败即停 ⇒ 需 `-Dmaven.test.failure.ignore=true`，
   然后由脚本按 XML 判定退出码并**透传**（失败仍须 `exit != 0`，否则 CI 形同虚设）。
3. **报告目录放 `target/`**（已在 `.gitignore`），不污染仓库；脚本本身**只读**，
   不改任何源码或配置（`tools/README.md` §3.4）。

### 交付物与验收

- **交付**：`tools/run_tests.py`（Python，遵守 `tools/README.md` §三：UTF-8 强制 / 路径从仓库根解析 /
  `--help` / 默认只预演——本脚本不改文件故无 `--apply`）；`tools/README.md` 补一行说明。
- **验收**：
  1. `python tools/run_tests.py` → 全量绿，stdout ≤ 15 行，三个产物齐备；
  2. **故意造一个失败用例** → stdout 列出该用例名、`latest.json` 里计数正确、**退出码非 0**、
     `report-*.md` 能看到失败栈摘要；
  3. `--group <某个 tag>` 能只跑该组；
  4. 用 `python tools/run_tests.py --help` 自证用法（不要把用法只写在文档里）。

> ✅ **已完成（2026-10-04）**：B8/B9 两条均闭合（见《遗留台账》**D26/D27**、《决策留痕表》**J 类**）。

> 去掉不可达窗口 / 注掉定时调度）。
> ⚠️ **同时更正了 C-7 / B-21 的前提**："不启用 publisher-confirm ⇒ 天然不阻塞 Web 线程"只在
> broker **可达**时成立；不可达时会等一次连接超时，而那笔等待原就在 Web 线程上（这才是 B8 的真正理由）。

> **正确性含义最强的一条**：B9 的代价是"MQ 不可用窗口内投递的消息**永久丢失**"。

| 账 | 缺的能力 | 补回位置 |
|----|---------|---------|
| **B8** | `MqDeliveryDispatcher`（异步投递线程池，把"发布+等 confirm"挪离 Web 线程） | 若"发布线程阻塞"成实测痛点，回 `feed.mq.FeedPublisher` 外层加 `@Async`/专用执行器 |
| **B9** | `MqDeliveryBuffer`（内存补偿缓冲：MQ 不可用时暂存、恢复后重放） | 回 `FeedPublisher`：连接确定不可用时入有界队列 + 定时/连接回调重放 |

**注入什么 → 观察什么**（⚠️ **以下为原设想；实际做法见本节末"关于'停 broker'"一段**）：
- 停 broker（`containers.stop()` / `GenericContainer` 暂停）→ 发布路径**不阻塞**（B8 的判据）；
- broker 恢复后 → 窗口内投递的消息**被重放**（B9 的判据；当前行为是**永久丢失**）。
- 若决定**不补**：必须把"丢失窗口"与"靠未同步 ⇒ 回退纯拉自愈"的口径**写成测试断言**
  （证明"丢了也能自愈"），否则这条账就永远是"没人验证过的假设"。

**前置**：T1 + T2。**验收**：故障注入测试 + 台账 B8/B9 → D 类（或明确记录"有意不补 + 自愈证明"）。
**→ 结论（2026-10-04）：选"补"**，两条都补。B9 那条"不补"的备选（把"丢失窗口 + 纯拉自愈"写成断言）
**不成立**：自愈是**部分**的——收件箱一旦有同步行（`feed_inbox_sync`），读侧就走窗口路径，
丢掉的写扩散消息要等该用户下一次关注 / 取关触发重建才可见，不是"丢了也能自愈"。
故按"补"处置，判据与反向验证见上文。

**⚠️ 关于"停 broker"这条注入手段（实际做法与工单原设想不同，如实记录）**：
不用 `containers.stop()` / `pause()`——测试 broker 是 `Containers` 的**进程级单例**，
停机波及其它测试类（与 `RedisCircuitBreakerTests` 对测试 Redis 的处置同款）。
实际注入面：**B8** = 把投递体做成"会长时间阻塞"的任务（同步执行则提交线程被卡住）；
**B9** = mock `FeedPublisher` 返回三态里的 `UNAVAILABLE` / `SENT`。两手都 deterministic，
且不污染共享容器。真实 broker 的通路由既有 `FeedMqTests`（拓扑声明 / 端到端写扩散 /
