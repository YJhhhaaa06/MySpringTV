## 〇、总原则：三层三套命运

用户常见提法是"整份复制再改"或"从零重写"。两者都不对——**可移植性按层相反**，必须分层定策：

| 层 | 迁移性质 | 判据 |
|----|---------|------|
| **SQL 语句** | **复制** | 全部 `?` 占位符手写 SQL，MyBatis XML 可近乎原样承接 |
| **业务语义** | **对照重写** | 校验顺序/异常类型/幂等/失效时机——学语义，不抄骨架 |
| **连接与事务管道** | **删除** | 一切 `Connection conn` 参数、`throws SQLException`、`transactionTemplate.execute` |
| **IoC 注解** | **机械替换** | 一对一映射，正交于业务逻辑 |
| **手写基建** | **不迁移** | IocContainer / MyConnectionPool / TransactionTemplate / Mq* / 手写路由 |

**一句话**：SQL 复制、语义重写、管道删掉。

### ⚠️ 关键测量发现：`cache` 包不是纯缓存层

**含义**：这些类在做 **cache-aside 的 miss 回填**——缓存未命中时**回源 DB 并可能写库**。所以迁移时**不能**把它们当"加个 `@Cacheable` 就完事"的缓存层。决策⑤要求的"显式封装层"正是为这类语义准备的，迁移时按**读路径服务**处理，不是按注解缓存处理。

## 二、逐层搬运规则

### 2.1 DAO 层 —— SQL 复制，签名重写

**旧形态**（`like/dao/ContentLikeDao.java:18-25`）：

```java
public int addLike(Connection conn, long userId, long contentId) throws SQLException {
    String sql = "INSERT INTO content_like (user_id, content_id) VALUES (?, ?)";
    try (PreparedStatement pstmt = conn.prepareStatement(sql)) {
        pstmt.setLong(1, userId);
        pstmt.setLong(2, contentId);
        return pstmt.executeUpdate();
    }
}
```

**新形态**（Mapper 接口 + XML）：

```xml
<insert id="addLike">
    INSERT INTO content_like (user_id, content_id) VALUES (#{userId}, #{contentId})
</insert>
```

**改动清单**（106 个方法，逐项机械执行）：

| 旧 | 新 |
|----|-----|
| `Connection conn` 首参 | **删掉**（连接由 Spring 绑定） |
| `throws SQLException` | **删掉**（`DataAccessException` 接管） |
| `?` 占位符 + `setLong(n, x)` | `#{param}` 命名参数 |
| `ResultSet` 手工遍历 | `<resultMap>` 或 `resultType` |
| `StringBuilder` 拼 `IN (?, ?, ...)` | `<foreach>` 动态标签 |
| `@Component` | `@Mapper`（或 `@MapperScan` 统一扫描） |

**保留不动**：SQL 文本本身、表名、列名、`COUNT(*)` 口径、索引使用方式。

> 注：`IN` 动态拼接这类"手写负担"在 MyBatis 里天然消失（`ContentLikeDao.java:66-71` 的 StringBuilder 循环 → 一行 `<foreach>`）。这是**白赚**，不是重写成本。

### 2.2 Service 层 —— 学语义，重写骨架

以 `like/service/LikeService.java:54-76` 为标本：

```java
// 旧：事务模板 + conn 穿透 + 手写异常包装 + 事后副作用
public void likeContent(long userId, long contentId) {
    transactionTemplate.execute(conn -> {
        if (!contentDao.isContentExist(conn, contentId)) throw new NotFoundException("内容不存在");
        if (contentLikeDao.isLiked(conn, userId, contentId)) throw new ConflictException("不可重复点赞");
        try {
            contentLikeDao.addLike(conn, userId, contentId);
            contentDao.updateLikeCount(conn, contentId, 1);
            return null;
        } catch (SQLException e) { ...throw new ServerException(...); }
    });
    cache.likeContent(userId, contentId);                 // 提交后
    contentCache.notifyLikeCountChanged(contentId);       // 提交后
}
```

**搬什么（语义清单）**：

- 校验**顺序**：先"内容存在"→ 再"未重复点赞"（决定返回哪个错误码）
- 异常**类型**：`NotFoundException` / `ConflictException`（映射到 HTTP 状态与 body 码）
- 幂等口径：重复点赞靠唯一键 `uk_user_content` 兜底
- 计数增减：`updateLikeCount(±1)` 与点赞记录同事务
- 副作用**时机**：缓存更新必须在**提交后**

**怎么改（骨架）**：

```java
@Transactional
public void likeContent(long userId, long contentId) {
    if (!contentDao.isContentExist(contentId)) throw new NotFoundException("内容不存在");
    if (contentLikeDao.isLiked(userId, contentId)) throw new ConflictException("不可重复点赞");
    contentLikeDao.addLike(userId, contentId);
    contentDao.updateLikeCount(contentId, 1);
    // 提交后副作用 —— 见 2.4
}
```

**删掉**：`transactionTemplate.execute` 包装、`conn` 参数、`catch (SQLException)` 手工包装、`ServerException`（`SQLException` 已由 `DataAccessException` 承接，由 `@ControllerAdvice` 统一出口）。

### 2.3 IoC 注解 —— 一对一机械替换

| 旧 | 新 | 备注 |
|----|-----|------|
| `@Component` | `@Service` / `@Repository` / `@Component` | 按语义选，非功能差异 |
| `@InjectConstructor` + 构造器 | `@Autowired`（单构造器可省） | 旧项目**已是构造器注入**，这点很干净 |
| `@Inject`（字段） | 删注解，改构造器注入 | 旧项目仅 Filter/Controller 用字段注入 |
| `@PostConstruct`（自研） | `jakarta.annotation.PostConstruct` | 直接换 import |
| `Disposable` / 反射 `shutdown()` | `@PreDestroy` / `DisposableBean` | 见踩坑清单 §3 |
| `IocContainer.getBean(X.class)` | 构造器注入 | `AuthFilter.java:58` 的"现取现用"要改掉 |

**这一层可以整体一次提交完成**（见决策记录 §三）。

### 2.4 "提交后副作用" —— 必须用框架机制承接

旧项目靠**注释纪律**维系（`LikeService.java:72` "缓存更新放在事务提交后"），踩坑清单 §5 已标记为【妥协】。

新写法二选一：

| 场景 | 机制 |
|------|------|
| 缓存失效 | `@TransactionalEventListener(phase = AFTER_COMMIT)` |
| 投递 MQ | `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async` |
| 轻量、无需解耦 | 仍写在 `@Transactional` 方法**之后**（调用方），但需注释说明 |

**判定规则**：凡旧代码里"事务 lambda 之后紧跟的副作用行"，迁移时**每一处都要显式决策**用哪种机制，不允许默默照原样写。

## 四、首切片建议：`user` 模块

**选它的理由**（不是"最简单"，而是"闭环最完整"）：

1. 引入 Security + JWT（决策③），是后续一切鉴权的基础
2. 事务边界清晰且**已有一个真实的语义决策点**（见《事务边界决策表》U-1）
3. 规模小（14 文件 1,087 行），7 处事务
4. 已有 `PasswordUtil`（BCrypt）+ `JwtUtil` 可直接搬
5. 闭环含"注册 → 登录 → 带 token 访问受保护接口"，端到端可验
