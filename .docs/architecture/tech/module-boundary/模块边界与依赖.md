# 模块边界与依赖

> 定位（先读这一句）：**`common` 不依赖任何业务域；跨域只走"对方的 Service 契约 / DAO 薄依赖 / 领域事件"三条合法通道。**
> 本篇只讲包结构与依赖方向、`common` 约束与窄端口、合法 vs 非法通道、ArchUnit 规则、以及**有意保留**的双向依赖。
> 事件订阅的形态与"禁止代发"去 [领域事件与解耦](../events/领域事件与解耦.md)；缓存三态 / 失效口径去 [缓存与数据一致性](../cache/缓存与数据一致性.md)
> ——本篇对二者**只写一句话边界 + 链接**，不复制。
> 文末 [§八 边界与去向](#八边界与去向机制外链) 列全部外链。

## 一、分层与包结构

一句话总则：**依赖只能"业务域 → `common`"，或"业务域 → 业务域（且只走 §三 的三条合法通道）"；`common` 永不反向依赖业务域。**

```
io.github.yjhhhaaa06.videoweb
├── common/                横切基建（不得依赖任何业务域，见 §二）
│   ├── cache/             CacheAside / CacheKeys / RedisOps / SingleFlight /
│   │                      RedisCircuitBreaker / CacheMetrics
│   ├── config/            各类 *Properties
│   ├── log/               RequestIdFilter / AccessLogFilter / LogMasker / AuditLog
│   ├── security/          JwtAuthFilter / JwtService / AdminChecker / @RequiresLogin / @CurrentUserId
│   ├── web/               ApiResponse / GlobalExceptionHandler / PageParams / BusinessCodeAdvice
│   ├── exception/         业务异常族 + ErrorCode
│   └── model/             PageResult 等通用模型
└── 业务域（13 个）
    user / content / comment / like / follow / feed / coupon / upload / admin / favorite / interaction
    / coin / history
```

> 📌 **域名清单必须与 `ArchitectureTests.DOMAINS` 逐字一致**（T47 实测：本清单此前漏了 `coin`，
> 现补 `coin` + `history` ⇒ 12 → 13）。清单漏一个域，读者就会以为规则覆盖了它；
> 实际是"规则根本没扫它"（见 §五 开头那句警告）。

业务域**内部按需分层**（并非每个域都有全部子包）：

| 子包 | 职责 | 实际出现的域 |
|---|---|---|
| `controller` | HTTP 入口（唯一注入本域 Service） | 除 `interaction` 外的 12 个（`interaction` 刻意**不建 Controller**：不拆 HTTP 接口，R-10 §3.6，T9） |
| `service` | 业务逻辑 + **对外 Service 契约** | 13 个（全部） |
| `dao` | SQL / Mapper | user / content / comment / like / follow / feed / coupon / favorite / coin / history（`interaction` **不建**：聚合器，不是数据所有者，T9） |
| `model` | `entity` / `vo` / `dto` / `cache` DTO 等载体 | 除 like / history 外的 11 个（`history` 到目前为止**没有** `model` 子包：写路径只吞吐标量、没有 VO；读面的 VO 随下一批建。favorite 的载体由**收藏一期 T2 起按需建**：`entity/FavoriteFolder` + `vo/FavoriteFolderVO`；**T3** 增 `vo/PublicFavoriteFolderVO`
（他人视角与"我的"**刻意不同形状**，见该类注释）；**T5** 增 `vo/FavoriteStatusVO` + `vo/FavoriteFolderBriefVO`
（brief 只给 id + name，刻意不复用 `FavoriteFolderVO`）；**T6** 增 `vo/FavoriteItemVO`（夹内条目：
正常卡片与**失效占位**同一形状，靠 `invalid` 区分）；`interaction` 由**收藏二期 T9** 建
`model/vo/InteractionStatusVO` + `model/InteractionTarget`） |
| `cache` | 本域缓存实现（**私有**，见 §四） | content / comment / like / follow / feed / favorite / coin（**收藏二期 T11 落地**：`FavoriteCache` + `FavoriteRedisOps`；收藏**一期刻意没有**缓存 —— G7。`interaction` 不建——无自有数据，T9。★ `history` **刻意不建**：私有 + 写多读少 + 每次上报都变 ⇒ 缓存必然"写后就废"（`history.md` §七.1，推翻条件 = 出现真实读放大） |
| `event` | 事件类型 + 监听器（订阅落点，见 §三） | user / content / comment / like / follow / feed / coin / history（favorite **不该有**：收藏不是"别人要响应的事实"；`interaction` 同款**不该有**：只聚合读，无自己的事实，T9。`history` 的 `PlayCountChangedEvent` 预定由 **content 域**的 `PlayCountChangedListener` 消费（下一批交付；订阅落在订阅方自己的 `event` 包，规则 3） |
| `mq` | 生产者 / 消费者 | 仅 feed |

> 📌 本篇出现的 `T#` / `I-##` 编号见 [favorite.md 附录「编号速查」](../../domain/favorite/favorite.md)（编号的**活**查证入口；逐条论证在 `archive/favorite-2026-10-15/收藏功能-编号索引.md`）。

> 结构不靠"约定"靠"测试"：§五 的 ArchUnit 用例把每条依赖方向断言成**会失败的构建**；
> 任何"我以后会注意"都不是机制。

## 二、`common` 不得依赖任何业务模块（窄端口模式）

**规则**：`common` 是所有业务域的公共底座，**不得 import 任何 `videoweb.<domain>.*`**。业务 → 基建合法，基建 → 业务一律非法。

**历史倒挂**：`common.security.JwtAuthFilter` 曾直接注入 `user.service.UserService` 来判管理员
（`/api/admin` 前缀需 `role == 1`），形成"基建反向依赖业务"的边。

**正解 = 依赖倒置（窄端口）**：把接口 `common.security.AdminChecker`（只含 `boolean isAdmin(long)`）放在基建，
实现由业务域提供（`user.service.UserService implements AdminChecker`）：

```
  改前： common.security.JwtAuthFilter ──► user.service.UserService            ❌ 倒挂
  改后： common.security.JwtAuthFilter ──► common.security.AdminChecker ◄── UserService
                                             （接口在基建）           （实现由 user 提供）
```

依赖方向由"基建 → 业务"变成"业务 → 基建"，与其余所有模块一致。

**为什么只抽一个方法**：端口宽度以**真实使用面**为准——`JwtAuthFilter` 只问"这个 id 是不是管理员"这一个问题。
不要因为"user 域还有别的能力"就把它们一并塞进端口；那只是把倒挂换个地方。
也**不能**把 `isAdmin` 做成 `boolean` 参数或配置：它是**运行期查库**的判断（读 `users.role`），必须走 Service。

**强制**：ArchUnit 规则 1（§五），对全部 13 个域逐一断言 `common.*` 不依赖 `videoweb.<domain>.*`。

> 正面旁证：`common.security.RequestMappingLookup`（读 `@RequiresLogin` 注解）依赖的 `RequiresLogin` / `HandlerMapping`
> 都属基建或框架，**不触碰任何业务域**——基建只依赖基建。

## 三、跨域交互：合法通道 vs 非法通道

判据只有三条合法通道，其余一律非法。**"读状态 → 走对方 Service 公开方法；同事务改计数/级联 → 允许 DAO 薄依赖；响应别人发生的事 → 订阅事件。"**

| 通道 | 合法形态 | 源码实证 | 由哪条规则把关 |
|---|---|---|---|
| ✅ **对方的 Service 契约** | 只调对方 Service 的**公开方法**（查询 / 命令） | feed→`ContentService.loadContentVOs`、`FollowService.getFollowingIds`、`InteractionService.batchGetStatus`（T13 起）；favorite→`ContentService.loadContentVOs`（夹内列表，T6-5）；content→`InteractionService.batchGetStatus` / `getStatus`（详情 / 列表取互动态，T10）；✅ `ProfileService`（主页维度）→`FollowService.getFollowerCount` / `getFollowCount` / `isFollowing`；★ **内容条目的互动态自 T13 起也走 `InteractionService`**（原 **I-09 例外**已随 `F-16` 核销）；comment→`LikeService.batchIsCommentLiked`、`ContentService.isCommentReadable`；interaction→`LikeService` / `FavoriteService` / `FollowService`（互动域组装，T9） | — |
| ✅ **跨域 DAO 薄依赖** | 同事务内的**必要联动**：改对方的冗余计数列、级联软删 / 物理删 | content→`comment.dao.CommentDao`（`softDeleteByContentId` 级联软删评论）、`like.dao.ContentLikeDao`（`deleteByContentId`）；like→`content.dao.ContentDao` / `comment.dao.CommentDao`（`updateLikeCount` ±1）；comment→`content.dao.ContentDao`（`isContentExist` / `updateCommentCount`）；feed→`content.dao.ContentDao`、`follow.dao.FollowDao`、`user.dao.UserDao` | 规则 4 只禁 service/model/cache，**不禁 dao** |
| ✅ **领域事件** | 在**自己**的 `X.event` 包订阅 `Y.event.XxxEvent`，动作只作用于**自己的**资源 | `content.event.CommentCacheChangedContentListener`←`comment.event.CommentCacheChangedEvent`；`comment.event.ContentRemovedCommentListener`←`content.event.ContentCacheChangedEvent`；`comment.event.LikeChangedCommentListener`←`like.event.LikeChangedEvent`（★ T43 删掉内容侧的 `LikeChangedContentListener`：点赞数独立成 key 后，点赞不再失效内容载荷） | 规则 3（落点必须在 `event` 包） |
| ❌ **触碰他域的 `cache` 包** | `X` import `Y.cache.*` | 历史：`ContentService`→`comment.cache.CommentCache`；`ContentStatusFiller` / `ProfileService`→`follow.cache.FollowCache`；`LikeChangedListener`→`content.cache`+`comment.cache` | 规则 2 |
| ❌ **直接依赖他域实现** | `X` import `Y.service` / `Y.model` / `Y.cache` | 历史：`content`→`comment.service` / `comment.model`（`content⇄comment` 双向环） | 规则 4 |
| ❌ **在非 `event` 包引用别域事件** | service / controller 直接 import 别域事件类型，或"替别域发事件" | 历史：`CommentService` 发 `ContentCacheChangedEvent` | 规则 3 |
| ❌ **`common` 依赖业务域** | `common` import 任意 `videoweb.<domain>.*` | 历史：`JwtAuthFilter`→`UserService` | 规则 1 |

> 注意两处"允许但需克制"：
> ① **DAO 薄依赖**的合法性来自"同事务原子性"（计数与关系行同进同退、删内容级联删评论）；
> 若只是"读点数据"，应改走对方 Service 契约，而不是顺手 import 对方的 DAO。
> ② 跨域 `service` 依赖只允许调**公开方法**，不得读其实现细节（否则又把实现变成 API，等价于规则 2 想治的病——见 §四）。

## 四、缓存是模块的私有实现细节

**每个域的 `cache` 包只被本域 import**：`ContentCache` / `FollowCache` / `LikeCache` / `CommentCache` / `FeedCache`
（外加各域 `*RedisOps`）。它们是本域的**私有实现细节**——方法签名、降级语义、要不要建空标记，都不是别的域该跟着走的东西。

**下游要跨域状态时，只能走对方 Service 的公开方法**：

| 下游想知道的 | 走哪个 Service 契约（而非 Cache） |
|---|---|
| 我对内容的互动态（赞 / 藏 / 关注作者） | `InteractionService.getStatus` / `batchGetStatus`（R-10：content→互动域，T10；三份数据仍归各自域） |
| 我是否关注了作者（主页维度） | `FollowService.isFollowing` / `batchIsFollowing`（互动域内部同样走它） |
| 我关注的全体（feed 用） | `FollowService.getFollowingIds` |
| 某用户的关注数 / 粉丝数 | `FollowService.getFollowCount` / `getFollowerCount` |
| 我是否点过赞（评论 / feed 单维） | `LikeService.batchIsCommentLiked`；★ feed 与各列表面自 **T13** 起经 `InteractionService.batchGetStatus`按维度取（不直连 `LikeService`） |
| 该页 id → 内容 VO | `ContentService.loadContentVOs` |

**两条必须守住的契约点**：

- **批量语义原样透传**，不是"循环调单条"。现锚点是 `InteractionService.batchGetStatus`
  （"三维各一趟"）与 content 侧薄壳 `ContentStatusFiller`："一次列表请求只打一次缓存/DB（批量而非逐条）"
  ——100 条推荐页若逐条判关注态就是 100 次往返。故 `FollowService.batchIsFollowing` 是**原样透传**批量语义。
- **下游对缓存实现无感**：缓存换实现、加空标记、改降级路径（详见 [缓存与数据一致性](../cache/缓存与数据一致性.md)），
  下游一概不必知道——因为它依赖的是 Service 契约，不是缓存 API。

**由来（用户原始痛点）**：S6 之前缓存类被大量跨域 import，缓存**变成了跨域 API**；
正解即"跨域只走服务契约或事件"，并由 ArchUnit 规则 2 变成会失败的测试。

## 五、ArchUnit 规则

**位置**：`src/test/java/io/github/yjhhhaaa06/videoweb/ArchitectureTests.java`（**共 5 条规则 = 5 个 `@Test`**）。

**实现方式**：只引 ArchUnit **核心包**（`ClassFileImporter` + `ArchRuleDefinition.noClasses()`），
类文件全项目扫描**导入一次**、五个用例共享；**不用** `archunit-junit5` 引擎
（本项目跑 JUnit Platform 6，该引擎是给 Platform 1.x 写的）。域集合由常量 `DOMAINS` 给出：
`{user, content, comment, like, follow, coupon, upload, admin, feed, favorite, interaction, coin, history}`——**新域必须登记**，否则新域会成为一个"没有任何规则约束的空洞"。
（`favorite` 由收藏一期 T1 登记：迁移收口后的第一个新域；`interaction` 由收藏二期 T9 登记；
`coin` 由投币专项 T36 登记；`history` 由播放记录专项 T47 登记。）

| # | 规则（测试方法） | 意图 | 违规长什么样（断言形式） |
|---|---|---|---|
| 1 | `common_不得依赖任何业务模块()` | `common` 是公共底座，不能倒挂依赖业务域 | `..videoweb.common..` → `..videoweb.<domain>..`，对 13 个域逐一 `noClasses` |
| 2 | `任何模块都不得触碰别的模块的缓存实现()` | 缓存是本域私有；跨域只能走 Service 契约或事件 | `..videoweb.<X>..` → `..videoweb.<Y>.cache..`，对全部 `X ≠ Y` 有序对 |
| 3 | `跨域事件只能由自己的event包消费()` | "谁订阅谁"在包结构上一眼可见 | `..videoweb.<X>..`（排除 `.<X>.event..`）→ `..videoweb.<Y>.event..`，对全部 `X ≠ Y` |
| 4 | `content不得依赖comment的服务与模型()` | content 对 comment 只留 `content-thin` 的 DAO 薄依赖 | `..videoweb.content..` → `..videoweb.comment.service..` / `.model..` / `.cache..` |
| 5 | `任何域都不得依赖feed()` | feed 是纯下游聚合域（S9 §八）；他域 → feed 倒灌 = 把 S9 消掉的 `content⇄feed` 环接回去 | `..videoweb.<X>..` → `..videoweb.feed..`，对 10 个域（`X ≠ feed`）逐一 `noClasses` |

**每条治什么病（由来）**：

- **规则 1**：治 `JwtAuthFilter` 直接注入 `UserService` 的倒挂（§二）。需要业务能力时，在 `common` 声明窄端口。
- **规则 2**：治"缓存变跨域 API"这一用户原始痛点（§四）。
- **规则 3**：治"评论域去发内容域的事件"——`CommentService` 曾 `publishEvent(ContentCacheChangedEvent.invalidate(...))`，
  只为了失效内容的 key，让两个域的编译期耦合加深且从包结构上完全看不出。正解是"只声明自己发生了什么，需要的人自己订阅"
  （订阅机制详见 [领域事件与解耦](../events/领域事件与解耦.md)）。
- **规则 4**：治 `content⇄comment` 双向环——`ContentService` 曾承载 `/comment/show` 读路径，被迫 import 评论域的
  cache / DAO / VO / Service 四类东西。S6-B2d 把门禁收敛成 `ContentService.isCommentReadable`（一条返回 `boolean` 的窄查询），
  此后 `content → comment` **只剩 `comment.dao`**。故本规则**只禁 service/model/cache，不禁 dao**——"按现实划线"。
- **规则 5**：治 `content⇄feed` 双向环——S9 把 `/feed` 编排从 content 迁到 feed 域消掉的环，当时**只靠约定**守住
  （遗留台账 C1 2026-10-03 补记"无规则禁止重新引入"；登记 `FURTHER_ISSUES.md` F-03，T35 落钉）。
  通知 feed 的正道 = 发领域事件（`ContentPublishedEvent` / `FollowChangedEvent`）、`feed.event` 订阅；
  任何域直连 feed 的 service / mq / cache 即违规。from 取**全部其余 10 域**（不止 content）：
  feed.md §八 的不变式是"全链路无包环"，只禁 content 会漏掉别的倒灌边（如 `comment → feed` 会经
  `feed → content.dao → comment.dao` 传出传递三环）；落地时实测无任何域 import feed ⇒ 零误伤。
  ⚠️ feed 今天**不发布领域事件** ⇒ 暂无规则 3 同款的 event 落点豁口；若将来发布且他域需消费，
  先给规则 5 开"仅限 event 落点"的口子（推翻条件已写进测试注释）。

**自检**：

```bash
.\mvnw.cmd -B test -Dtest=ArchitectureTests
```

## 六、有意保留的双向依赖（为什么不做"全局无环"断言）

本仓的 ArchUnit **刻意不写"全局无环"断言**：它只禁**已经证明有害**的那几条边（缓存实现、跨域发事件、`common` 倒挂），
**不假装架构比现实更干净**。原因是存在若干**真实业务需要**的双向依赖——强行消环只能靠合并域或引入异步，代价远大于收益：

| 方向对 | 一条边 | 另一条边（反向） | 为什么保留 |
|---|---|---|---|
| `content ⇄ like` | content → `like.dao.ContentLikeDao`（删内容清点赞记录）+ `resetLikeCount`（T44-1：同事务把 `like_count` 归零）；★ **原 `ProfileService` → `like.service.LikeService` 的例外已随 T13 消除**（**I-09 / F-16 已核销**） | like → `content.dao.ContentDao`：**写** = `updateLikeCount`（同事务改计数列，T34 守卫）；**读** = `findLikeCountById`（T44-1：`content:likeCount` 缓存 miss 回源读 `like_count` 列，主键点查） | 点赞要**同事务**改对方的计数列（content-thin）；计数回源读列与 favorite/coin 同构（T12 先例）；主页列表要显示"我点过赞吗" |
| `content ⇄ favorite`（T12 登记） | content →（**无直连**；传递闭包环见下一行 `content ⇄ interaction`） | favorite → `content.dao.ContentDao`：**写** = `updateFavoriteCounts`（T12 事务内批量重算 `favorite_count`，与 like 的 `updateLikeCount` 同构）；**读** = `findFavoriteCountById`（`/favorite/count` 缓存 miss 回源的**主键点查**） | ★ 写边有明确合法通道（"同事务改计数"）。⚠️ **读边是对 §三"读状态走对方 Service"判据的显式登记例外**：回源点在 `FavoriteCache` 内部（域内实现细节），为它开一条 Service 契约 = 把"读自己缓存 miss 该怎么回源"变成对外的公共 API，契约面倒贴；该读是**主键点查**、不读 content 的任何业务语义（连 `is_deleted` 都不看），与 `isContentExist` 同一"窄到不构成耦合"的形态。经"缓存回源点唯一"（`FavoriteCache#loadFavoriteCount`）钉住扩散面 |

## 七、新代码检查清单

写新代码前逐条自检（命中哪条就按哪条做）：

1. **新增业务域** → 把域名加进 `ArchitectureTests.DOMAINS`。否则新域是"没有规则约束的空洞"。
2. **`common` 里需要业务能力** → 在 `common` 声明**窄端口接口**（如 `AdminChecker`），由业务域实现；
   **不要**注入业务 Service；端口只放真实用到的方法（§二）。
3. **跨域读对方状态** → 调对方 Service 的**公开方法**；**不要** import 对方 `cache` 包（规则 2，§四）。
4. **响应"别人发生了什么"** → 在**自己**的 `X.event` 包订阅 `Y.event.XxxEvent` 并只动自己的资源；
   service / controller **不要** import 别域事件；也**不要替别域发事件**（规则 3）。
5. **`content` 想用评论能力** → 只允许 `comment.dao`（薄依赖）；service/model/cache 一律不行（规则 4）；
   需要"评论能否被读"时走 `ContentService.isCommentReadable`。
6. **新增跨域 `dao` 依赖** → 先确证它是"**同事务内的必要联动**"（改冗余计数 / 级联删），否则改走 Service 契约。
7. **新增跨域 `service` 依赖** → 只调公开方法，不读其实现细节。
8. **想通知 feed**（发布 / 关注变化要进时间线）→ 在**自己域**发领域事件
   （content 的 `ContentPublishedEvent` / follow 的 `FollowChangedEvent`），由 `feed.event` 订阅；
   **不要**直连 feed 的任何类——feed 是纯下游，任何域 → feed 都被规则 5 拦下。

**改完自检**：

.\mvnw.cmd -B test -Dtest=ArchitectureTests
