# 韧性（Redis 故障 / 惊群 / 降级）

> 定位（先读这一句）：**Redis 挂掉不许让接口 500，热 key 过期不许把并发全砸到 DB**。
> 本篇只讲**三层防护机制**（熔断 / 单飞 / 冷却退避）与**降级链的接线边界**。
> 缓存三态 / 空标记 / 键命名 / 写后失效**不在本篇**，去向见文末
> [§九 边界与去向](#九边界与去向机制外链)。

---

## 一、三层防护各治什么

一句话：**三个机制治三个不同的病，谁都不替代谁**。

| 机制 | 治什么 | 触发场景 | 落点（唯一收口） | 实现 |
|---|---|---|---|---|
| **熔断** | Redis 整体不可达时，**每请求一次连接/读取超时**（故障放大） | Redis 宕机、网络断 | `RedisOps.guarded`（协议层） | `RedisCircuitBreaker` + Resilience4j |
| **单飞** | 同一热 key 过期/被清的**瞬间**，并发请求各打一次 DB（缓存击穿） | 热 key miss 的风口 | 各域**读路径**的 miss 回填处 | `SingleFlight`（进程内） |
| **冷却退避** | DB 故障 + 索引缺失时，**每请求一次无上限全表重建**（串行重复昂贵动作） | `findAllContent()` 装载失败 | `ContentCache.ensureIndex` | `volatile` 时间戳 + 窗口判定 |

三者**互补**（正交，不是替代）：

```
Redis 不可达 ──► 熔断：快速失败，一个冷却窗口内只放 1 个探针 ──► 降级走 DB
热 key 过期 ──► 单飞：同 key 并发只回源一次 ─────────────────► 其余线程共享结果
DB 故障 + 索引缺失 ──► 冷却退避：把"每请求一次全表重建"收敛为"每窗口一次" ──► 降级空推荐
```

- **熔断**把"故障期"整体收敛，治的是 **时间轴上的重复**（每个请求都要等超时）；
- **单飞**把"同一瞬间的重复"收敛，治的是 **并发轴上的重复**（同一 key 的并发 miss）；
- **冷却退避**把"失败后的重复昂贵动作"收敛，治的是 **串行轴上的重复**（上一次失败后下一个请求又来一次）。

> ⚠️ 三者**不覆盖**彼此：熔断打开时单飞照常生效（降级路径仍可能经单飞）；单飞不阻止"不同 key"的并发
> 回源；冷却退避只管 `ensureIndex` 这一处昂贵动作。各自的**局限与代价**在各节如实登记。

## 二、熔断：为什么接在协议层收口

### 2.1 收口点 = `RedisOps.guarded`（唯一）

全仓**所有** Redis 访问都经过 `RedisOps.guarded`：like / follow / content / comment / feed 五域命令层
各自 `extends RedisOps`，共享的 `CacheAside` 也 `extends RedisOps`。因此熔断只需在这一处生效。

**为什么不接在"各域三态机"里**：

| 若接在域内 | 后果 |
|---|---|
| N 个域各自持一份状态机 | 状态口径漂移；同一 Redis 实例宕机却各自计数，探针流量 × N |
| 域内若漏接一处 | 该处仍每请求等一次 Jedis 超时，故障放大照旧 |
| 域内 catch 点分散 | "快速失败未访问 Redis"这条性质无法用一个收口保证 |

接在协议层则**新增任何 Redis 访问都自动被覆盖**（见 §八 检查清单第 1 条）——与"从命令出口收口"同构。

### 2.2 熔断打开即抛 `CacheUnavailableException`（**未访问 Redis**）

```java
protected <T> T guarded(Supplier<T> action) {
    if (!breaker.tryAcquire()) {                    // OPEN：不访问 Redis
        throw new CacheUnavailableException("Redis 熔断开启中，快速失败（未访问 Redis）");
    }
    try {
        T result = action.get();                    // 真正触达 Redis
        breaker.recordSuccess();
        return result;
    } catch (CacheUnavailableException e) {         // Redis 起源失败
        breaker.recordFailure();
        throw e;
    } catch (RuntimeException e) {                  // 其它 Redis 层异常 → 归一化
        breaker.recordFailure();
        throw new CacheUnavailableException("Redis 访问失败: " + e.getMessage(), e);
    }
}
```

**"未访问 Redis"是关键收益**：Jedis connect/socket 超时（dev 各 1000ms）不再被每请求各撞一次——
下游各域 `*Cache` 早已 `catch (CacheUnavailableException)` 并降级直查 DB，于是熔断期间
**接口仍返回正确结果，只是不读缓存**。

### 2.3 失败计数只记**真正访问过 Redis** 的调用

计数发生在 `action.get()` **之后**的 catch 里。被 `tryAcquire()` 拦下的调用**直接抛、不计数**。

**为什么必须这样**：Resilience4j 的 `COUNT_BASED` 滑动窗口按"调用样本"计算失败率；若把"被熔断拦下"也
计入，则 OPEN 期间每个被拒请求都往窗口里塞一个样本，**窗口被不断续期**，永远凑不满"冷却期满"的
条件 ⇒ 永不进入 `HALF_OPEN` 探针 ⇒ 熔断无法自愈。故"只记真正触达 Redis 的调用"是**正确性要求**，
不是优化。

### 2.4 代价（如实登记）

- **全局单熔断，无按域隔离**：一个 `@Bean` 单例，单 Redis 实例宕机影响所有域（这也是选全局的理由——
  单实例宕机本就影响全域，按域熔断只增加探针流量）。代价：无法"只熔断某个高频域"。
- **OPEN 期间的真实尝试量不进样本**：由 §2.3，熔断器样本读不到"被拦下的降级请求有多少"。要看这个量
  得靠 Micrometer 打点（见《可观测》），不从熔断器状态取。
- **记录失败用哨兵异常**：`recordFailure()` 传固定实例 `REDIS_FAILURE`（一个 `CacheUnavailableException`），
  其**具体信息对判定无影响**——`recordExceptions` 谓词只看类型（见 §三）。

## 三、选型：Resilience4j 核心库 + 手工 `@Bean`

### 3.1 只引**核心库**，不引 starter

`pom.xml` 只声明 `io.github.resilience4j:resilience4j-circuitbreaker`（显式版本 `2.3.0`，
Boot 父 POM 不托管）。**不引** `resilience4j-spring-boot3` 一类的 starter，理由：

- 核心库是**纯 Java、无 Spring 版本耦合** ⇒ 规避 starter 对 Boot 4.x 的适配风险；
- 熔断器以**手工 `@Bean`** 装配（`RedisBreakerConfig`），只用 `CircuitBreakerConfig.custom()` 一处表达全部口径，
  比 starter 的"约定 + 自动配置"更**可审计**（所有参数在一个文件里能读完）。

装配类：`RedisBreakerConfig`，熔断器名 `RedisBreakerConfig.REDIS_BREAKER_NAME = "redis"`（全局唯一）。

### 3.2 状态机三处刻意口径

| 口径 | 取值 | 理由 |
|---|---|---|
| 滑动窗口类型 | `COUNT_BASED`（**硬编码**，不可配） | 与"连续失败计数"最接近；样本量小、判定确定 |
| OPEN 冷却 | `wait-duration-in-open-state` 默认 **10s** | 期满由**同步**转换完成 OPEN→HALF_OPEN |
| OPEN→HALF_OPEN 自动转换 | `automaticTransitionFromOpenToHalfOpenEnabled(false)`（**硬编码**） | 由 `tryAcquirePermission()` 在冷却期满时**同步**完成转换并放行探针——**不依赖后台调度线程**，对测试确定 |
| HALF_OPEN 探针数 | `permitted-number-of-calls-in-half-open-state` 默认 **1** | **单探针**：放 1 个请求去探；成功即闭合，失败即重开并重置冷却 |

状态流转（`RedisCircuitBreaker.stateName()` 可明文观测）：

```
CLOSED ──窗口失败率≥阈值 且 样本≥最小调用数──► OPEN
  ▲                                              │ 冷却期满，放行单个探针
  │ 探针成功                                      ▼
  └──────────────────────────────────────── HALF_OPEN
                                                 │ 探针失败
                                                 └──► OPEN（重置冷却）
```

### 3.3 失败谓词**显式收窄**为 `CacheUnavailableException`

```java
.recordExceptions(CacheUnavailableException.class)
```

**为什么收窄**：协议层已把**所有 Redis 起源异常**归一为 `CacheUnavailableException`（DB 异常不经过协议层），
故谓词只认这一个类型。收益：**业务回调里的意外异常不会被误计入熔断**——否则一次业务 bug 就可能把
健康的 Redis 熔断掉。这是"熔断只对缓存依赖负责"的边界。

### 3.4 参数一览（`video.cache.redis-breaker`，绑定期即校验）

| 键 | 默认 | 含义 |
|---|---|---|
| `video.cache.redis-breaker.failure-rate-threshold` | `50` | 失败率阈值（百分比，须在 `(0,100]`） |
| `video.cache.redis-breaker.sliding-window-size` | `10` | 滑动窗口样本数（`COUNT_BASED`，须 ≥ 1） |
| `video.cache.redis-breaker.minimum-number-of-calls` | `5` | 触发判定前最少调用数（须在 `[1, sliding-window-size]`） |
| `video.cache.redis-breaker.wait-duration-in-open-state` | `10s` | OPEN 冷却时长（须为正 `Duration`，**必须带单位**） |
| `video.cache.redis-breaker.permitted-number-of-calls-in-half-open-state` | `1` | HALF_OPEN 探针数（须 ≥ 1） |

> `RedisBreakerProperties`（`record`，前缀 `video.cache.redis-breaker`）在**构造期**校验上述约束：
> 任一越界 ⇒ **启动即拒**（不是运行期才发现）。`minimum-number-of-calls ≤ sliding-window-size` 是最容易写错的一条。

## 四、单飞：接线边界

`SingleFlight.get(key, loader)`：`FutureTask` + `ConcurrentHashMap.putIfAbsent`。leader 执行 loader，
follower 拿同一 `FutureTask` 等结果。两条约束（失败不得被固化）：

- **loader 失败必须 remove** ⇒ 否则把失败结果缓存给后续请求；
- **无论成败都清理在飞项** ⇒ 否则 key 无限增长（内存泄漏）。

### 4.1 接在哪

| 接线点 | 单飞 key | 负载 |
|---|---|---|
| `CacheAside.get`（内容详情三态读）miss 回填 | 数据 key | 单 key loader |
| `CacheAside.get` 的**单 key 降级** | 数据 key | 同一 loader（降级也复用，同 key 负载相同） |
| `LikeCache` 单条 / **批量**读的 miss 回填 | 数据 key（用户维度 set） | 该用户全量点赞 |
| `FollowCache` 单条 / 批量 / **窗口**读的 miss 回填 | 数据 key；窗口用**窗口指纹** `dataKey@offset+count` | 见下 |
| `FollowCache.degradeWindow`（窗口降级） | 窗口指纹 | 同一页 DB 窗口查询 |
| `ContentCache.ensureIndex`（索引懒重建） | `content:index:rebuild`（进程内字面量） | 全表重建 |

**窗口为什么用指纹 key**：前缀装载的负载**与页位置相关**（第 1 页装 10 条、第 5 页装 50 条）；
若共用裸数据 key，第 5 页会**共享第 1 页的装载结果**（越界补齐白做、甚至把前缀当页返回）。
空标记 / 全量读仍用裸数据 key（负载与页无关）。

### 4.2 降级**批量**不接（理由）

`LikeCache` / `FollowCache` 的**批量状态**降级路径（`catch` 后按请求 id 子集作答）**不接**单飞：

> 批量降级是**按请求 id 子集**作答（`IN (...)`），而单飞 key 若取**数据 key**，会让不同 id 子集
> **串结果**——A 请求问 3 个 id、B 请求问另外 5 个 id，却共享同一次装载。故这一类降级直接查 DB，
> 不用单飞（单条/按需查询更省）。

> 注意 `SingleFlight` 类注释里"降级路径不接"这句的**范围就是这类批量状态降级**；`FollowCache` 的
> **窗口降级**另有单飞（用窗口指纹 key，同一页负载相同），二者不矛盾。

### 4.3 `CacheAside.getBatch` 不接（理由）

批量读（`getBatch`）的 miss **不逐 key 单飞**：它**一趟批量装载**
（`pipeline` 拉全部 key + 一次 `batchLoader`），已经消除"逐 key 往返"，无需再逐 key 单飞。
逐 key 单飞会把它退化回逐 key 装载，反而放大。

### 4.4 `getFollowingIds` 返回**防御性拷贝**的原因

`FollowCache.getFollowingIds` 在 miss / 部分态经单飞拿到的 `List` 是**并发者共享的同一实例**：
leader 的 loader 结果会返回给所有 follower。调用方（如 feed 域）若**原地改动**该 List，会**互相影响**。
故返回前 `new ArrayList<>(all)` 拷贝一份，切断共享。

### 4.5 代价（如实登记）

- **进程内锁，只对单实例有效**：多实例部署时不共享在飞表 ⇒ 击穿防护退化为"每实例各一次 loader"；
  真正跨实例防击穿需分布式锁（当前单实例够用，不过度设计）。
- **单飞不覆盖的场景**：`FeedCache`（feed 读缓存）与 `CommentCache` **不接**单飞；
  `CacheAside.getBatch` 不接；like / follow 的**批量状态降级**不接（见 §4.2）。
  这些场景各自有"批量装载 / 域内口径"的理由，不接是**有意**而非遗漏。
- **单飞只治"同一瞬间"**：它不缩短 TTL、不替代空标记、不改变失效策略——那些属《缓存与数据一致性》。

## 五、冷却退避与单飞互补

`ContentCache.ensureIndex` 在索引 key 缺失时会触发一次 **无上限全表重建**（`findAllContent()`）。
若 DB 恰好不可用，装载失败会"跳过重建、保留旧索引"，但**每次请求**都会再试一次 ⇒
**每请求一次全表重建**。冷却退避把它收敛为"每冷却窗口一次"。

```
ensureIndex(indexKey):
  ① if (inIndexRebuildCooldown()) return;        // 入口冷却判定
  ② keyExists? → 回来（有索引）
  ③ singleFlight.get("content:index:rebuild", () -> {
          ★ if (inIndexRebuildCooldown()) return; // ← 双检
          loaded = findAllContent()               // DB 失败 ⇒ 记失败时刻、保留旧索引
          rebuild…（成功 ⇒ 清除冷却 / 失败 ⇒ 记失败时刻）
     })
```

**两者互补**（同处一层，治不同轴）：

| 机制 | 治 | 触发轴 |
|---|---|---|
| 冷却退避 | "**串行**重复"：停机期间每个请求各触发一次全表重建 | 时间轴（上一次失败 → 下一次请求） |
| 单飞 | "**并发**重叠"：同一瞬间多个请求同时触发重建（惊群） | 并发轴（同一 key 的并发 miss） |

**双检的必要性**：并发线程在"通过入口冷却判定"与"抢到 leader"之间，可能已有他者失败并进入冷却。
loader 内**重读**冷却状态，避免"刚入冷却又被重新重建一次"。

**参数**：`video.cache.content-index-rebuild-cooldown` 默认 **10s**；**0 = 关闭退避**（与既有口径一致，
测试注入大值即等效关闭）。缓存窗口由 `volatile long lastFailedRebuildAtMillis` 承载（写发生在请求线程、
读跨线程）。

**代价（如实登记）**：退避只治 `ContentCache` 索引重建这**一处**昂贵动作；状态是**进程内 `volatile`**，
**多实例不共享**（每实例各自退避）；它是"把每请求一次收敛为每窗口一次"，**不是**"重建不再尝试"
（冷却期满会自动重试）。

## 六、降级链：`CacheUnavailableException` → 各域既有 catch → DB 直查

**熔断接在协议层，所以各域读代码一行未改**——它们只 catch `CacheUnavailableException`：

```
Redis 失败 / 熔断打开
      │ throw CacheUnavailableException（协议层唯一出口）
      ▼
各域 *Cache 既有的 catch (CacheUnavailableException)
      │ 记 WARN（不带栈或带栈由各处定）
      ▼
降级直查 DB（正确结果，不 500）；写路径则"失效 key 让读自愈"
```

| 域 | catch 落点 | 降级动作 |
|---|---|---|
| content 详情 | `CacheAside.get` | 调 loader 直查 DB，**不写回** |
| like | `LikeCache` 单条 / 批量 | 单条 `checker` / 批量按请求 id 子集 DB 作答 |
| follow | `FollowCache` 单条 / 批量 / 窗口 | DB 判定 / DB 窗口直查（不装载、不写回） |
| comment | `CommentCache.prepareRoots` 等 | `loadRootsFromDb` / `loadRepliesFromDb`（不写回） |
| feed 收件箱腿 | `FeedCache.readInbox` | `descending(dbLoader.get())` |
| feed 大V腿 | `FeedCache.readOutbox` | 全量 DB 回源（fail-open，见《缓存与数据一致性》的失败面口径） |

**两类失败必须可区分**：`CacheUnavailableException`（Redis）降级；DB 的 `DataAccessException`
**原样上抛**（→ 500）。实现上靠**只 catch 自己的异常类型**——协议层只冒 `CacheUnavailableException`，
DB 异常不经过它。这一区分保证"降级成空值把读不到伪装成没有"不会被引入。
（各域逐处失败面明细属各域与《缓存与数据一致性》，本篇只保"降级链的接线"这一句。）

## 七、测试：`resilience` 组不进默认回归集

**为什么**：本批的验收门禁是"每条能力必须能在故障注入下变红"。故障注入测试若进默认回归集，
**回归集永远是红的** ⇒ 必须有"按组选跑"。

机制在 `tools/run_tests.py`：

- 常量 `DEFAULT_EXCLUDED_GROUPS = ("resilience",)` ⇒ 默认命令生成 `-DexcludedGroups=resilience`
  （即 `mvnw -B clean verify -Dmaven.test.failure.ignore=true -DexcludedGroups=resilience`）；
- 函数 `effective_excluded_groups()` 会把**显式 `--group` 的 tag 从排除集里剔除**——
  否则 `--group resilience` 会同时生成 `-Dgroups=resilience` 与 `-DexcludedGroups=resilience`，
  两者交叠 ⇒ **零用例**（这正是默认集含 `resilience` 时会踩的坑）；
- **零命中不放行**：指定了 `--group`/`--test` 却 0 用例被执行 ⇒ 退出码非 0（静默绿灯是最危险的失败模式）。

**显式跑法**：

```bash
python tools/run_tests.py --group resilience      # 只跑 @Tag("resilience")
python tools/run_tests.py --group resilience --test RedisCircuitBreakerTests   # 叠加类名
```

**组内测试类**（均 `@Tag("resilience")`）：

| 测试类 | 覆盖 |
|---|---|
| `RedisCircuitBreakerTests` | 熔断打开后**不再访问 Redis**；未达最小调用数不误熔断；探针成功自动闭合；探针失败重开并重置冷却（反向验证：去掉 `tryAcquire` 判定即变红） |
| `SingleFlightTests` | 同 key 并发只执行一次 loader；失败移除条目；DB 异常原样重抛；不同 key 互不阻塞 |
| `SingleFlightCacheTests` | 内容详情 / 索引懒重建 / 点赞 / 关注的并发 miss 只回源一次 |
| `ContentIndexCooldownTests` | 冷却窗口内重复读只重建一次；冷却期满自动重试；成功不进冷却；Redis 写失败同样进冷却（反向验证：删掉入口冷却判定即变红） |

## 八、新代码检查清单

1. **新增 Redis 访问一律经 `RedisOps.guarded`**（或继承 `RedisOps`）——否则熔断不覆盖它，"快速失败"失效。
2. **只 catch `CacheUnavailableException`**；DB 的 `DataAccessException` **原样上抛**（别宽 catch 吞掉）。
3. **缓存不可用不得让接口 500**：读路径降级直查 DB；写路径**失效 key 让读自愈**。
4. **贵的 miss 回源接单飞**，单飞 key 用**数据 key**；若同一 key 存在**不同负载**（不同页 / 不同 id 子集），
   必须加**指纹**（如 `dataKey@offset+count`），否则会串结果。
5. **批量状态降级不要用数据 key 做单飞 key**（会串 id 子集）；批量读已有批量装载，**不逐 key 单飞**。
6. **共享返回给并发者的集合要做防御性拷贝**（单飞 follower 共享同一实例）。
7. **失败后仍会被重复触发的昂贵 DB 动作**，考虑**进程内冷却退避**，并注明 `0 = 关闭`；同时意识到它
   **多实例不共享**。
8. **新接线的故障注入测试打 `@Tag("resilience")`**（不进默认回归集），并提供"去掉该能力即变红"的反向验证。
