# 写接口幂等（Idempotency-Key）

> 定位（先读这一句）：幂等 = **同一个客户端请求标识（`Idempotency-Key`）重发 N 次，副作用只发生一次，
> 且每次都拿回第一次的 2xx 响应**。它是"**响应快照 + 占位状态机**"，不是锁，也不是分布式事务。
>
> **本篇是幂等的活事实源**（设计与边界）。测试口径与对外契约在
> [写接口幂等-测试与契约](写接口幂等-测试与契约.md)。实现落点 = `common/idempotency/`。
>
> **读者假设**：没参与过设计讨论。所以本篇保留"为什么不做 X"的结论 —— 它们不是过程，
> 而是**防止同一个问题被反复推翻**的护栏（每条都给了判据，不是偏好）。

---

## 一、目标与判据

**一句话**：客户端"收不到 2xx"时用同一 key 重发，服务端**不产生第二次副作用**，并**返回第一次的响应**。

两层判据缺一不可：

| 层 | 要求 | 只有效果层会怎样 |
|---|---|---|
| 效果层 | DB 终态与单次调用一致 | —— |
| 响应层 | 重发返回与首次**逐字节相同**的 2xx body | 客户端拿不到新对象 id，只能重拉列表 |

**为什么响应层是硬要求**：客户端断网重试时往往已丢上下文（页面刷新过）。若重放只回 `{}` 或 `409`，
它无法定位"刚创建的是哪一条"，后续操作（给自己刚发的评论点赞、删评）没有入口。

★ **由此可以判定：Redis 分布式锁不是幂等机制**（这是最常被提出的替代方案）。
锁的生命周期是"请求处理期间"，重发到达时锁早已释放 ⇒ 顺利拿锁、**再执行一遍**，
正好制造出要防的那种重复。锁保证的是"同一时刻只有一个执行者"，幂等要求的是
"后来的调用能拿回第一次的结果"——后者只能靠**持久化的结果**，锁本身不产出结果。
本仓的状态机里 `SET NX` 兼作占位，那是"让并发同 key 的第二个请求看到有人在做"，
不是"用锁实现幂等"。

## 二、不解决什么（三个相邻问题各归谁）

| 问题 | 归属 | 说明 |
|---|---|---|
| **双击** | 客户端短期冻结按钮 | 两次点击是两个不同 key，服务端视为两次独立意图，**不应合并** |
| **脚本刷屏** | 限流（[限流](../rate-limit/限流.md)） | 幂等不承担频率控制 |
| **跨资源一致性**（如"发内容 + 落文件"） | 各自的补偿/清理 | 文件系统不在事务里，见 §十二 |

## 三、覆盖范围

只覆盖"**效果层非幂等、且客户端需要判定成功**"的端点。四条：

| 路由模式 | slug | 请求体 | 指纹 | 2xx 的 `data` |
|---|---|---|---|---|
| `POST /api/v1/comments` | `comment` | JSON | 可算 | `{}`（★） |
| `POST /api/v1/contents/videos` | `video` | multipart | 不可算 | `{"contentId": N}` |
| `POST /api/v1/contents/posts` | `post` | multipart | 不可算 | `{"contentId": N}` |
| `POST /api/v1/contents/{id}/coins` | `coin` | JSON | 可算 | `{"balance": "x.y"}` |

★ **评论的 2xx 目前是空 `data`**（`CommentController#add`）⇒ 它只满足**效果层**判据：
重放能保证"不重复写"，但只能告诉客户端"成功过"，不能告诉它"成功的是哪一条"。
响应层补齐属**需求侧**，不在本篇范围（架构文档只描述机制，不承载待办）。

**不在范围**（每条都有承担者，不是遗漏）：

- **领券**：已由"先回查、返原券码"结构性修复（`CouponService` 编排层），且响应层已可判。
- **自建收藏夹重名**：重名合法是业务规则，加唯一键会改业务行为；影响只是多吃一个名额。
- **"效果层幂等、仅响应层不可判"的端点**（重复收藏撞 `uk_folder_content`、注册撞手机号、改密、资源型 DELETE）：
  对外契约已冻结为"已删亦视为不存在"/"前端不得自动重试"，不做请求级去重。
- **两层都达标的写端点**（点赞、关注、签到、`/play`、`/progress`、覆盖类、无持久副作用类）：
  只需在注册表登记 `NATURAL`，实现不动。
- **GET / HEAD / OPTIONS / TRACE**：天然幂等，注册表不覆盖（与限流权重表同一跳过口径）。

## 四、位置：独立过滤器，不进限流层

```
RequestIdFilter(MIN) → AccessLogFilter(MIN+1) → Security 链(-100)
    → JwtAuthFilter(0)          ← 401 / 403 在此短路，写 ATTR_USER_ID
    → RateLimitFilter(10)       ← 429 在此短路
    → IdempotencyFilter(20)     ← 占位 / 重放 / CAS 收尾
    → DispatcherServlet         ← multipart 解析在这里
    → Controller
```

`@Order` 用 `RateLimitFilter.RATE_LIMIT_ORDER + 10` 表达，把"必须在鉴权与限流之后"这条结构约束
钉进常量本身（与 `RateLimitFilter` 用"鉴权序 + 10"同一手法）。

**三个收益都来自位置本身，不需要额外代码**：

1. **429 的请求到不了这里** ⇒ 不会留下 PENDING 残留。否则客户端按 `Retry-After` 重试时，
   命中的正是自己上次留下的占位，越限流越拿不到结果。
2. **`ATTR_USER_ID` 已由 `JwtAuthFilter` 放好** ⇒ 不需要二次解析 token。
3. **天然早于 `DispatcherServlet`** ⇒ 占位早于 multipart 解析，**第二个请求的文件根本不会落盘**。
   这一条决定了它不能放 Controller / AOP / `@Transactional` 附近。

**为什么不合并进 `RateLimitFilter`**（会被当作"省一次往返"的优化反复提出）：

- **fail-open 分不了档**：限流不可用时"放行"是已接受的代价；幂等不可用时"放行"意味着**重试会重复写**。
  两种风险等级不同的降级被同一个 `catch` 吃掉，日志上再也分不清。
- **故障域合并**：Lua 一坏两条机制一起失灵，而限流侧正是靠"脚本异常 = ERROR"来区分
  "外部依赖故障"与"自身缺陷"的。
- 收益面只有**少数端点**，成本面却是全部端点的公共路径；
  而合并只省一次 Redis 往返（约 0.1 ms），且限流收尾本来就还有第二次命令。

## 五、状态机

**存储键**：`idem:{slug}:{uid}:{clientKey}`（HASH，字段见 §十）。

| 事件 | 迁移 | 谁写 · 时机 | TTL |
|---|---|---|---|
| 首次 / 重发时无记录 | ∅ → `PENDING`(owner) | filter，进 chain 前 | 30 s（`video` / `post` 120 s） |
| 业务 2xx | `PENDING` → `DONE`（快照 + fp） | filter，chain 返回后、**响应 flush 前**，CAS owner | 180 s |
| 非 2xx / 异常 / 断连 | `PENDING` → `FAILED` | filter，`finally`，CAS owner | 5 s |
| 命中 `DONE` | 重放快照 + `Idempotent-Replayed: true` | filter | 不续期 |
| 命中 `PENDING` | 短轮询 2×100 ms，仍 PENDING ⇒ 409 | filter | — |
| 命中 `FAILED` | 视为无记录，重新占位 | filter | 重置 |

### 5.1 顺序约束（本设计唯一不可调的实现细节）

快照必须落在**响应体 flush 之前**：

```
校验 key / 查表 → [轮询] ACQUIRE → PENDING
  ├ 命中 DONE     → 重放快照（status + body + Content-Type）→ return
  └ 命中 PENDING  → sleep 100ms 重试 2 次 → 仍 PENDING ⇒ 409 + Retry-After: 1
  ↓
try {
    chain.doFilter(包装后的 request, ContentCachingResponseWrapper)
    if (2xx) COMPLETE(owner, fp, status, body, ctype)   // ★ 先写快照
} finally {
    if (!completed) RELEASE(owner)                      // CAS；state=DONE 时自然失败
    wrapper.copyBodyToResponse()                        // ★ 后 flush
}
```

由此得到一条可依赖的性质：**客户端收到 2xx ⇒ 快照已写**。它同时覆盖两个场景：

- 服务端成功、响应在网络上丢了（最常见的成因）；
- **flush 时客户端已断开**：那时快照已在盘上，客户端重连重发会命中 `DONE`。

### 5.2 `FAILED` 不是状态，是墓碑

命中 `FAILED` 的行为**完全等同"无记录"**（重新占位执行）⇒ 它不承载任何分支。
存在理由只有两个：指标（"失败后重发"的频次）与排障（能看见"刚才失败过"）。
★ **不要往它身上加逻辑**：它的语义到此为止。若嫌多余，可退化为"CAS DEL + 一条指标"。

### 5.3 owner CAS 是防串扰的唯一手段

每个请求生成随机 `owner`。`COMPLETE` / `RELEASE` 只在
`state == PENDING && owner == 本请求 owner` 时生效。防的是这段竞态：

```
A 处理超时（PENDING TTL 到期）→ B 占位 PENDING(ownerB)
→ A 的 finally 若无条件写 FAILED，会打掉 B 的占位 → C 又能占位 ⇒ 三重执行
```

手法与 `FeedRedisOps#releaseLock` 的 Lua CAS 同源。

## 六、请求头与 key

**请求头**：`Idempotency-Key`。
★ **不能复用 `X-Request-Id`** —— 那是服务端生成的 trace id（`RequestIdFilter`），
语义是"这一次网络请求"；客户端拿它做幂等 = 每次都不同 = 永远不命中，且会让排障时两个概念混为一谈。

**校验**：`[A-Za-z0-9._-]{1,64}`。字符集排除 `:` 与 `/`，所以 `idem:{slug}:{uid}:{clientKey}`
的边界**唯一可解析**。

★ **不需要定长补零，也不需要哈希**：拼接有分隔符，不存在歧义
（只有"无分隔符拼接后再哈希"才需要长度前缀）；明文 key 让 `redis-cli` 一眼看出是谁的哪个端点。

**`slug` 由注册表提供**，不在产码点硬编码。

## 七、缺 key 与非法 key

| 情况 | 处置 | 理由 |
|---|---|---|
| 没传 key | **放行、不占位**、WARN（按端点 5 min 节流）+ 指标 | 见下 |
| 传了但不合法（超长 / 字符集） | **400** `IDEMPOTENCY_KEY_INVALID` | 客户端 bug；假装成功等于骗它"你有幂等保护" |
| 非 KEYED 端点传了 key | 忽略，不报错 | 宽容；契约写明"只对 4 条生效" |

**"没传就放行"的正当理由不是兼容**（旧网页前端已废弃、App 从未存在过，没有要兼容的对象），
而是**不给测试与 curl 制造摩擦**：`Idempotency-Key` 是**可选增强**，不带就退化为普通请求，
既有全部用例、临时验证、健康检查一行都不用改。

⇒ **不做 `require-key` 开关**：少一个配置项、少一组参数化用例、少一个错误码，
也少一处"开关翻没翻都说得通"的模糊地带。代价见 §十三 第 6 条。

## 八、端点注册表

```java
// common/idempotency/IdempotencyScope.java
public enum Scope { KEYED, NATURAL }
public record Entry(Scope scope, String slug, int pendingTtlSeconds) {}

private static final Map<String, Entry> TABLE = Map.ofEntries(
    entry("POST /api/v1/comments",            KEYED, "comment", 30),
    entry("POST /api/v1/contents/videos",     KEYED, "video",  120),
    entry("POST /api/v1/contents/posts",      KEYED, "post",   120),
    entry("POST /api/v1/contents/{id}/coins", KEYED, "coin",    30),
    entry("PUT /api/v1/contents/{id}/like",   NATURAL, null, 0),
    /* … 其余非 GET 端点全部显式登记 … */
);
```

**键形态与限流权重表同形**：`"<方法> <路由模式>"`，路径取
`HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`，**不是原始 URI**。
用原始 URI 查表时 `{id}` 端点会静默落"未登记"（限流那张表踩过这个坑）。

**放代码不放 yaml**：权重是**调参**（运行时改有意义）；幂等类别是**契约**
（改了必须走 review + 编译 + diff，改一条登记不留任何信号就是错的介质）。

**`NATURAL` 的判据**：**重试不改变 DB 终态，且响应可判**。**不设第三档**。
★ **备注只写灰色地带**（如"每次刷 `update_time`"、"LWW 旧请求晚到会回退进度"），其余条目留空 ——
二十多条逐条写理由，读的人会自动跳过，等于没写。

## 九、指纹（同 key 不同载荷）

**为什么必须有**：客户端 bug 复用同一个 key 却改了内容时，若只按 key 命中就重放，
会把 A 的结果当 B 的返回 —— **比重复更坏（数据错乱）**。

三个阶段的口径（**不要合成一条**）：

| 阶段 | 比对？ | 原因 |
|---|---|---|
| 首次（∅ → `PENDING`） | **不比对** | 没有可比对象。因此 `PENDING` **不带 fp**，占位可以放心早于 multipart 解析 |
| 写 `DONE` | 写 fp | 此时 handler 已读完 body，从 `ContentCachingRequestWrapper` 的缓存算 |
| 命中 `DONE` | 算本次 fp 并比对 | 不同 ⇒ 422 `IDEMPOTENCY_KEY_CONFLICT`；这条路径**不进 chain**，读坏请求流无副作用 |

**范围与上限**：

- 只对 `Content-Type: application/json` 包装 request；**multipart 不包装**（避免把文件读进内存），
  登记为"上传类不做指纹校验"。
- 请求缓存上限 **8 KB**：超过则视为无 fp（**不可用截断后的 body 算指纹**），记 WARN。
- 响应快照上限 **64 KB**：超过则不写 `DONE`（降级为不幂等）并记 ERROR —— 业务已提交，响应照常 2xx。

## 十、存储与原子操作

```
KEY   idem:{slug}:{uid}:{clientKey}
TYPE  HASH
FIELD state   PENDING | DONE | FAILED
FIELD owner   随机 token（CAS 用）
FIELD fp      SHA-256(body)，仅 JSON 端点、仅 DONE
FIELD code    首次响应的 HTTP status
FIELD body    首次响应的 body（≤64 KB）
FIELD ctype   Content-Type
TTL   见 §五
```

**选 HASH 而非 JSON 字符串**：`COMPLETE` 要写 4 个字段、`RELEASE` 只改 `state`；
字符串形态下两者都得先读再整体写回，Hash 可以直接改字段。`HGETALL` 一次取全。

三个 Lua（放 `IdempotencyRedisOps extends RedisOps`，**不裸用 `RedisOps`**）：

| 脚本 | 逻辑 | 返回 |
|---|---|---|
| `ACQUIRE` | 不存在 **或** `state=FAILED` ⇒ 写 `PENDING` + owner + TTL；否则不动 | 当前状态 |
| `COMPLETE` | `state=PENDING && owner==ARGV.owner` ⇒ 写 `DONE` + 快照，TTL 改 180 s | 1 / 0 |
| `RELEASE` | 同上条件 ⇒ 写 `FAILED`，TTL 改 5 s | 1 / 0 |

**配置**（`application.yaml`，前缀 `video.idempotency`）：`ttl.done-seconds`(180) ·
`ttl.failed-seconds`(5) · `poll.attempts`(2) · `poll.interval-millis`(100) ·
`limits.fingerprint-bytes`(8192) · `limits.snapshot-bytes`(65536)。
**端点级 `PENDING` TTL 不放配置**：它是"该端点业务耗时"的属性，跟着注册表走。

## 十一、失败处置与降级

所有 Redis 操作经 `RedisOps` 基类（熔断 + 异常归一），口径与缓存层一致：**缓存不可用不许 500**。

| 失败 | 处置 | 日志 |
|---|---|---|
| Redis 不可达 / 熔断打开 | **放行**（不幂等），不抛 500 | WARN |
| 脚本 / 返回值解析异常 | **放行**，但同时是缺陷 | **ERROR**（持栈） |
| 写 `DONE` 失败 | 响应仍 2xx（业务已提交，不能骗客户端失败） | ERROR |
| `copyBodyToResponse` 抛 `IOException` | 快照已在盘上；`finally` 的 CAS 因 `state=DONE` 自动失效 | DEBUG（断连是常态） |

⚠️ 最后两行是同一个坑的两面：**`RELEASE` 必须走 CAS**。若写成"无条件 HSET FAILED"，
一次客户端断连就会把刚写好的 `DONE` 覆盖成 `FAILED`，下一次重发重新执行 ⇒ 重复写。

**可观测**：指标 `idempotency.decisions{result=miss|hit|pending|conflict|missing_key|invalid_key|degraded}`，
一次请求记一条（判定结果互斥）。日志三档沿用"外部故障 WARN / 自身缺陷 ERROR / 业务拒绝 WARN 结论行"。
**不记** `clientKey` 原文与快照 body。

## 十二、严格性边界（**不是 exactly-once**）

"客户端收不到 2xx"有几种成因，覆盖程度不同 —— 这是选型时必须摊开看的账：

| 成因 | 覆盖 | 依据 |
|---|---|---|
| ① 服务端成功，响应在网络上丢了 | **严密** | §5.1"2xx ⇒ 快照已写" |
| ② 服务端 500 / 业务回滚 | **严密** | 失败不固化；重发命中无记录或 `FAILED` ⇒ 重新执行 |
| ③ 业务已提交、快照写入前进程崩溃 | **不覆盖**（毫秒级） | Redis 方案关不掉 |
| ④ Redis 整体不可用 | **不覆盖** | fail-open，那段时间不幂等 |
| ⑤ 处理时长超过 `PENDING` TTL | **不覆盖** | 第二个请求能重新占位 ⇒ 双执行（靠 TTL 定够长来压） |

**"非 2xx 可安全重试"的前提**：被覆盖的端点各自只有**一条事务边界**
（`CommentService#addComment`、`CoinService#add`、`ContentService#addVideo` / `#addPost`），
不存在"编排层两步、第一步已提交第二步失败"。
⚠️ 若某个端点改成多事务编排，它**立即失去这个前提** —— 不要再给它登记 `KEYED`，先解决事务边界。

⚠️ **术语纠正**（容易被想错）：不存在"回滚失败留下副作用"——`ROLLBACK` 是本地操作、不走网络，
会话断开时未提交事务会被 InnoDB 自动回滚。真正的洞是 **`COMMIT` 已发出但 ACK 丢失**。

### 12.1 为什么不用 DB 幂等记录表

`idempotency_record(user_id, endpoint, client_key, …)` + 唯一键、与业务同事务，对 ①②③ 全严密。
**没选它**：

- 上传类端点的**文件系统不在事务里**，仍然覆盖不了 ⇒ 最终退化成"两套机制 + 两套测试 + 两套文档"。
- 本仓无真实流量，毫秒级窗口的收益抵不过认知成本。
- 保留这个对照的意义是：**知道窗口在哪、为什么接受**，而不是假装没有。

### 12.2 为什么不引入 `UNKNOWN`（提交结果未知）状态

1. **拿不到**：事务边界在 Service，filter 执行时 `TransactionSynchronization` 尚未 active、注册不上。
   Spring 本身有 `STATUS_UNKNOWN` 语义，但它传不到 filter。
2. **消解不了**：`UNKNOWN` 只能"阻塞"（409），不能"消解"。消解需要"按业务自然键查上一次成没成"，
   而评论与投币**没有自然键**，本仓也没有对账作业。它换来的是"用户彻底发不出去"，不是"少一条重复"。
3. **代价方向反了**：评论重复了用户能自己删；发不出去是功能故障。可用性优先。

---

## 十三、已知代价（已拍板接受，不修）

1. **不是 exactly-once**：窗口见 §十二 ③④⑤。
2. **重放也消耗限流令牌**：幂等在限流内侧。好处是不用改链序；代价是狂重试会先撞 429。
3. **上传类无指纹保护**：同 key 换文件不会被识别（multipart 无法算指纹）。
4. **`PENDING` TTL 是估的**：进程崩溃后该 key 在 TTL 内全 409，TTL 到期才自愈。
5. **快照只存"重放所需最小集"**：都是 KB 级（发布类含新 id、投币含余额）。明文落 Redis，TTL 180 s，未加密。
6. **服务端分不清"忘了带 key"与"选择不带"**：不做强制开关的直接代价，只能靠 `missing_key` 指标观测。
7. **`openapi.yaml` 本期不声明 `Idempotency-Key`**：需改 `OperationCustomizer`，前端重制时一并补。
8. **DB 幂等记录表方案被放弃**：换取"一套机制 + 覆盖上传"，代价是 §十二 ③ 的毫秒窗口。

---

## 十四、推翻条件

出现以下任一条，本设计必须回来重估（不是"可以顺便看看"）：

| 触发 | 影响 |
|---|---|
| 前端重制时**不做自动重试** | 整套机制收益为 0（只剩接口能力） |
| 前端只对 5xx 重试、**不对网络超时重试** | ① 永不触发，最主要的场景失效 |
| 前端重试窗口 **> 3 min** | `DONE` TTL 必须跟着加长，否则保护失效 |
| 某覆盖端点变成**多事务编排** | 失去 §十二 的前提 |
| 出现**业务自然键 + 对账作业** | `UNKNOWN` 才有价值（可从"阻塞"变"消解"） |
| 需要**跨设备/跨会话**去重（同一意图在两台设备重发） | 当前 key 由单端生成，不覆盖此场景 |
