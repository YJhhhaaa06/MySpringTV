## 一、三条总决策（`R-21`，2026-10-22）

### 1.1 错误信息两层：HTTP status 表类别，body `code` 表原因

- **HTTP status** = 类别（400 / 401 / 403 / 404 / 409 / 415 / 429 / 5xx），前端据此做**通用**处理
  （401 清登录态、403 显示无权限、429 退避、5xx 报障）。
- **body `code`** = **稳定字符串枚举**（`<域>_<原因>`，如 `AUTH_PASSWORD_WRONG`、`COIN_ALREADY_FULL`），
  前端拿它**翻字典**做精细化反馈；`msg` 降级为"服务端兜底文案"，前端可覆盖。
- **推翻条件**：前端需要"带参数的错误文案"（如"还需 2 枚硬币"）⇒ 加 `params` 对象，
  **不改 code 的语义**；若真要改，须先登记 `R-##` 再动。

> 现状为什么不行（§三 #1）：`code` 就是 HTTP 状态码本身（`HttpStatus.resolve(code)`），
> 两层信息完全重复 ⇒ 前端唯一可判别的东西是中文 `msg`。

### 1.2 硬切，不做双轨

- 旧路径 / 旧码一律替换，**不保留 `deprecated` 副本**，不出现 `/v2` 新老并存。
- 依据：① 前端本来就**同期重制**（`F-27` 已确认前端存在但播放器等要重写）；② 仓外无调用方
  （无第三方集成 / 无移动端）；③ 双轨会让**每个端点写两遍**，与"学习项目要讲清取舍"的目标相反。
- **推翻条件**：出现无法同期升级的仓外调用方 ⇒ 届时按"版本前缀 + 一个版本窗口"重开 `R-##`。

### 1.4 前端不跟随（`R-23`，2026-10-23 用户裁决）

- **旧 SPA 视为一次性资产**：本专项的用途是"给前端重制准备契约"，重制时 `static/` 会被**整体删除重写**
  ⇒ `T58` / `T59` **只改后端**，不同步 `static/js` 的调用点。
- **代价（已知、接受）**：迁移期间旧 SPA 在已改的域上必然 404 —— 它本来就要被删，
  为它做适配是**给将死的代码续命**（与 `T58` 原红线"必须同批改前端"相反，此处以本条为准）。
- **连带**：`T61`（前端适配层）的原目标"旧 SPA 不挂"随之失效；它是否改成"重制前的消费样例"由重制期重定
  （登记台已改【搁置】）。`T60` 的 OpenAPI 反而更重要 —— 重制方就是照 spec 写，而不是照代码猜。

### 1.3 资源化 REST + 统一前缀 `/api/v1`

- 路径表达**资源**，HTTP 方法表达**动作**；非 CRUD 动作用**资源子路径 + POST**
  （`POST /api/v1/contents/{id}/play`），不把动词堆在顶层（`/like/content/remove` 这种形态退役）。
- 统一前缀 `/api/v1`（含原 `/api/admin`、`/api/upload` 一并归入）。
- **推翻条件**：某动作无法用"资源 + 方法"表达、且子路径读起来明显更糟 ⇒ 记入 §二.4 的**例外清单**
  （逐条写理由），**不许逐个端点破例**。

> 本节只定**规则**；具体码表取值由 `T55` 填、端点定性与路径由 `T58` 改、载荷细节由 `T59` 兑现。

### 2.1 状态码用法

| status | 何时 | 备注 |
|---|---|---|
| 200 | 读 / 改 成功（有 body） | 体 = 统一信封 |
| 201 | 创建成功 | ★ **当前全站未使用**（创建类仍回 200，见下方注） |
| 204 | 删除 / 取消成功 | **无 body**（前端必须能处理空响应） |
| 400 | 参数缺失 / 格式错 / 校验失败 / **配额不足** | 带 `errors[]`（§2.5）；配额口径见 400/409 注 |
| 401 | 未认证 / 令牌失效 / **凭证不对** | ★ **不能一律清登录态**，见下方注 |
| 403 | 已认证但无权限 | 与 401 **不得混用** |
| 404 | 资源不存在 / **未映射路径** | 未映射 = `SYSTEM_ENDPOINT_NOT_FOUND`（见 §三 #6 · `T56`）；静态资源与媒体缺文件 = 404 **无体**，见下方注 |
| 405 | 路径存在但 HTTP 方法不支持 | 带 `Allow`；码 `PARAM_METHOD_NOT_ALLOWED`（`T56` 前落 500） |
| 409 | 状态冲突（**唯一性占用 / 资源状态不允许 / 动作前置条件**） | 例：手机号/用户名占用、重复收藏、管理员下架已删内容、评论区已关、重复领券；与 400 的边界见下方注 |
| 415 | Content-Type 不支持 | 带 `Accept`；码 `PARAM_MEDIA_TYPE_UNSUPPORTED`（`T56` 前落 **500**，不是 400） |
| 429 | 限流 | 带 `Retry-After` |
| 5xx | 未预期 / 依赖不可用 | 503 可重试（带 `Retry-After`） |

- **成功体**：`{code:"OK", msg:"success", data}`；`data` 为空时**不出现**（沿用 `NON_NULL`），
  **不许**用`"操作成功"` / `"删除成功"` 这类文案充当 `data`。
- **失败体**：`{code:"<域>_<原因>", msg, errors?}`；`data` 不出现。
- ★ **消费判据（前端唯一正确姿势）**：HTTP status 做**通用**分支（403/404/409/429/5xx），
  **401 一律按 `code` 再判一次**，`msg` 只在"字典里没这个码"时兜底展示。

> ★ **201 为什么定而不做**（`T59-4` 裁决，登记 `I-24` 同批）：表里保留 201 的语义，
> 但 `T59` **不**给创建类端点（注册 / 登录 / 评论 / 收藏 / 领券 / 发布）加 201 + `Location`。
> 理由：① 大多数创建端点在响应里已经给了新 id（`LoginVO` / `ContentCreatedVO`），`Location`
> 没有消费方；② 改状态码会让 `T59` 从"载荷面"扩成状态面（`T55` 已定稿），
> 且前端目前按 200 处理 —— 属**已知代价**而非缺陷。推翻条件 = 前端重制明确要求按 201 建资源
> 或 OpenAPI 消费方按 201 生成代码 ⇒ 届时统一改并同批更新登记簿。
>
> ★ **400 与 409 的边界（`T59-4` 裁决 `I-24`）**：**配额类**（收藏夹已满 / 稍后再看已满 /
> 夹数超限 / 硬币不足）在本仓是 **400**，不是 409 —— 这是**域文档冻结的契约**
> （`coin.md` §五.1 拒因表第 6 条、`favorite.md` §八），语义上把"资源容量/余额不足"
> 与"参数不合法"同归"用户侧修正"；而 409 只留给**唯一性占用与资源状态不允许**
> （手机号/用户名占用、重复收藏、管理员下架已删内容、评论区已关、重复领券）。
> 已知代价：严格按 HTTP 语义，"夹已满"更像 409；前端若需要把"配额"与"字段错误"
> 分流展示（不同引导文案），仍要靠 `code`（`FAVORITE_FOLDER_FULL` / `COIN_INSUFFICIENT`）
> 再判一次。推翻条件 = 前端明确要求按 status 分流配额 ⇒ **一次改实现 + 域文档 + 测试**，
> 不许只改一边（`I-24` 的原话）。

> ★★ **401 不是「清态」的同义词**（`T55` 拆码后暴露的坑）：401 里只有
> `AUTH_UNAUTHORIZED`（没带/伪造令牌）、`AUTH_TOKEN_EXPIRED`（过期）、`AUTH_USER_NOT_FOUND`
> （令牌有效但账号已删）该清登录态；**`AUTH_BAD_CREDENTIALS`（登录失败）与
> `AUTH_OLD_PASSWORD_WRONG`（改密时原密码错）绝不清态** —— 前者在登录页（清了也没意义、还会闪一下），
> 后者是登录用户打错了原密码，按 status 清态会把人无故踢下线。T55 前这条规则成立是因为当时所有 401
> 语义相同；现在不成立了。
> ⚠️ 顺带记一条**冻结契约**：改密表单里「手机号不匹配」是 400、「原密码错」是 401，
> 两者在**同一个表单**里分属不同类别（手机号比对严格先于旧密码比对，`UserService#changePassword`），
> 前端只能靠 `code` 把错误挂到字段上，不能靠 status 分流。

> ★ **失败体的唯一形状**（`T56`）：`{code,msg}`，校验失败再带 `errors[]`（`T57`，口径见 **§2.5.1**），
> 由 `common/web/ApiErrorWriter` **一处**产出，
> 控制器层（advice）、`JwtAuthFilter`（401/403）、`RateLimitFilter`（429）三条出口共用。
> 合的是**产物**不是**时机** —— 401/403 仍必须在过滤器内短路（过滤器在 `DispatcherServlet` 之前，
> advice 物理上覆盖不到，见 `tech/rate-limit/限流.md`）。契约钉在
> `ApiErrorExitContractTests`（三出口骨架一致 + `X-Request-Id`）与 `FrameworkErrorContractTests`（404/405/415）。

> ★ **唯一"无信封"的错误响应：静态资源与媒体 404**（`T56`）。`/upload/**`（媒体）、`/static/**`（样式脚本）
> 与 `/`、`/index.html`、`/favicon.ico` 缺文件 ⇒ **只回 404 状态、空体**：消费方是 `<img>` / `<video>`，
> 不看 body；给一段 JSON 只会让排查者误以为那是业务错误。未映射的**业务路径**仍回 404 信封。
> 副作用（有意）：这类响应不产业务信封 ⇒ 访问日志记 `code=0`（"从未产生业务信封"哨兵仍有存在意义）。

> ⚠️ **已知代价（`T56` 如实登记）**：
> ① **405 匿名可见、415 不可见** —— 差别在**时机**：`RequestMappingLookup` 对"路径命中、方法不匹配"
> 直接抛异常 ⇒ 按未映射放行 ⇒ 匿名也能看到 405；而 415 发生在处理器解析**之后**（读 body 时才找转换器）
> ⇒ 受保护端点仍先 401。泄露面仅"这条路径存在、接受什么方法"。契约由
> `FrameworkErrorContractTests#受保护端点的415仍先401` 反向钉住。
> ② **容器级 `/error` dispatch（`BasicErrorController`）不在三出口内** —— `GET /error` 本身是一个
> `@Controller` 端点（匿名先被判 401），且客户端 `Accept` 不接受 JSON 时写出会失败、退回默认错误体。
> 故"信封覆盖一切"不成立，前端一律显式 `Accept: application/json`。
> ③ **静态/媒体的"无信封"判定只能是路径清单** —— 静态缺文件与未映射走**同一个** `/**` 资源处理器
> （这正是未映射一度变 500 的原因），异常层无从区分。新增资产目录必须同步 `GlobalExceptionHandler`
> 的清单，**漂移不会自己变红**。

### 2.2 码表命名与粒度

- 形态正则 `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)+$`（**至少两段**，纯单词码不合格）。
- **前缀白名单**（`T55` 补齐两项，见 `R-22`）：`AUTH` `USER` `CONTENT` `COMMENT` `LIKE` `FAVORITE`
  `FOLLOW` `WATCHLATER` `COIN` `HISTORY` `COUPON` `UPLOAD` `ADMIN` `RATE` `SYSTEM` `PARAM`。
  新域先加白名单，再造码。★ `PARAM` 是**横切命名空间**（不是业务域）；
  `FOLLOW` 是**定稿表当时的遗漏**（既有域却未列入），由 `ErrorCodeContractTests` 第一次跑出来。
- **基础设施类码**（判据 ③：运维按码统计才看得出问题）：`SYSTEM_ENDPOINT_NOT_FOUND`（404，未映射接口 ——
  能看出前端/扫描器在打哪些不存在的路径）、`PARAM_METHOD_NOT_ALLOWED`（405）、
  `PARAM_MEDIA_TYPE_UNSUPPORTED`（415）。
- **码表只此一份**（`ErrorCode`），四个取值点（advice / `JwtAuthFilter` / `RateLimitFilter` / 访问日志）
  都从这里取；状态也由枚举携带（不再 `HttpStatus.resolve(code)`）。

**★ 粒度判据（`T55`，用户 2026-10-22 裁决）** —— 「不同原因必须不同码」里的"不同"指**前端会不会做出不同决定**，
不是"每个校验文案一个码"。三条任一成立才独立成码：

| # | 判据 | 例 |
|---|---|---|
| ① | 前端要**改流程**：清登录态 / 跳登录页 / 重拉资源 / 隐藏入口 / 按 `Retry-After` 退避 / 提示"去签到" | `AUTH_TOKEN_EXPIRED` · `COIN_ALREADY_FULL` · `COIN_INSUFFICIENT` · `COMMENT_DISABLED` |
| ② | 前端要**定位目标**（哪个资源没了） | `CONTENT_NOT_FOUND` vs `COMMENT_NOT_FOUND` vs `FAVORITE_FOLDER_NOT_FOUND` |
| ③ | **运维 / 审计要按码统计** | `RATE_LIMITED` · `SYSTEM_UNAVAILABLE` · `SYSTEM_DUPLICATE_KEY` |

> 只是"同一个 toast 换一句中文"的差异 ⇒ **同码**，差异进 `msg`（`T57` 起进 `errors[]`）。
> 例：「标题不能为空」「简介不超过 5000 字」「enabled 格式错误」全部落 `PARAM_INVALID`；
> 「内容已删除无法下架 / 无法恢复」全部落 `CONTENT_STATUS_CONFLICT`（处置都是"重拉列表再判断"）。
> ★ `T59` 起"已下架 / 未下架"不再产生该码：重复 PUT / DELETE 是幂等 no-op（200 / 204）。
> ⚠️ 这条判据**推翻条件**：前端出现"同 toast 但需要不同埋点/统计"的需求 ⇒ 按判据 ③ 重新分码。

**★ 唯一的安全例外：登录失败只有一个码**（`T55`，用户裁决）

- 「账号不存在」与「密码错误」**必须**同码同文案（`AUTH_BAD_CREDENTIALS` / "账号或密码错误"）。
  分开回答 = 给出「这个手机号注册过没有」的探测口，一个脚本就能批量筛出全站已注册手机号。
  这与收藏域「收藏夹不存在 / 收藏夹不公开 ⇒ 同 404 同文案」是同一条原则，**不是漏改**。
- **同耗时也是契约的一部分**：账号不存在时也要对一个假哈希跑一次 BCrypt（`UserService#doLogin`）。
  只统一 code 与 msg、留着 50–100ms 的时间差，等于没统一。
- 与之对照，以下两处**保留**可区分：`AUTH_OLD_PASSWORD_WRONG`（改密时操作者已用令牌证明身份）、
  `AUTH_USER_NOT_FOUND`（令牌有效但账号已删，只用于"查自己"）。
- **已知代价（如实登记）**：注册接口的 `USER_PHONE_TAKEN`（409「手机号已被使用」）与
  `USER_NAME_TAKEN`（409「用户名已被占用」）仍如实回答 —— 注册流程必须告知，否则用户无法完成注册。
  ⇒ **手机号 / 用户名的占用探测面在注册口依然存在**（限流按 IP、不按账号）。
  真正的收口手段是注册前置短信验证，本期不做；推翻条件 = 出现真实的批量注册/探测攻击。
- **已知代价（第二例：DB 唯一键兜底只能回基础设施码）**：`POST /api/v1/coupons/{id}/claims` 重复领取撞
  `uk_coupon_user` ⇒ 出口只能回 `SYSTEM_DUPLICATE_KEY`（409「数据已存在」），拿不到「您已抢过该优惠券」——
  因为出口**分不清**撞的是 `uk_coupon_user` 还是 `uk_coupon_code`，硬猜会报反；要精确就得在 Service 里
  catch 再翻译，那会推翻优惠券域 C-1「不判 1062」（`CouponService` 类注释）。⇒ 只登记、不擅自改（`I-25`）。
- **另一条口径（避免与收藏域"不给探测口"打架）**：**用户 id 的存在性不视为探测面** ——
  `GET /api/v1/users/{id}` 对不存在的 id 回 404 `USER_NOT_FOUND`（资源化 REST 必需，且 id 不是秘密）；
  收藏域刻意用「200 + `[]`」隐藏的是**收藏夹的存在性与私密性**，不是用户。两者不矛盾，
  但下一个人容易按"收藏域更严格"去改 `GET /api/v1/users/{id}`，故在此写明。

**★ 不许有死码**：每个码在 `src/main` 至少有一个产码点（`ErrorCodeContractTests#无死码` 扫源码钉住）。
当前 **41 项**；历次增删（`T55` 清死码、`T56` +3、`T59` −4）的明细在 git，
**结论只有一条**：泛码（`NOT_FOUND` / `CONFLICT` / `PARAM_ERROR`）不许存在 —— 每个抛出点必须指名原因。

### 2.3 路径

- 形态：`/api/v1/<资源复数>[/{id}][/<子资源>]`，层级 ≤ 3（不含 `/api/v1`）。
- 全小写；多词用连字符；**禁止** PascalCase / camelCase 段（`IdSearch`、`signIn` 退役）。
- 路径参数统一写 `{id}`；**禁止**在路径里出现动词。
- **例外清单**（`T58` 定稿；判据 = "动作不是对该资源的 CRUD，且表达成改某字段会丢语义"）：

  | 端点 | 为什么是例外 |
  |---|---|
  | `POST /api/v1/contents/{id}/play` | 播放事件：非幂等、无自然键（"看了一次"不是可枚举资源），服务端只记首播 |
  | `POST /api/v1/history/flush` | 退出信号：粒度是 userId **全量**，没有可指的单个资源 |
  | `POST /api/v1/admin/media/scan` | 运维动作：同步全盘扫描、无持久化产物；POST 形态只为把它计成重活（权重 10） |
  | `POST /api/v1/users/me/check-ins` | 按日签到：自然键 =（用户，当天），客户端给不出 id；重复请求返回已存在（`credited=false`） |

  **逐条写理由，不许逐端点破例。** ⚠️ 反例：`/history/report`（进度 LWW 覆盖）**不是**例外
  ⇒ 落 `PUT /contents/{id}/progress`（`T58` 已按此落地）。
- **资源清单**（`T58` 定稿）：`users` · `sessions` · `contents` · `comments` · `favorites` ·
  `favorite-folders` · `watch-later` · `follows` · `coupons` · `media` · `history` · `feed` · `admin`。
  不可数名词（`history` / `feed` / `media` / `watch-later`）**不加 s** —— 造 `histories` 只增噪音。
- **计数是标量投影**：用平级段 `-count`，**不用** `likes/count` —— 后者会造出第 4 级（破"≤3 级"），
  且暗示"该端点返回集合"，与事实不符。当前全站 3 条：

  | 完整路径 | 含义 | 返回 |
  |---|---|---|
  | `GET /api/v1/contents/{id}/like-count` | 该**内容**被点赞的次数 | `Integer` |
  | `GET /api/v1/comments/{id}/like-count` | 该**评论**被点赞的次数 | `Integer` |
  | `GET /api/v1/contents/{id}/favorite-count` | 该**内容**被收藏的次数 | `Long` |

  **读法钉死**：`<资源>/{id}/<关系>-count` 的主语是**被计数的资源**（不是"我的 X 有几个"）。
  与单例关系读端点靠末段区分、不撞路由：
  `GET /contents/{id}/like`（**我**赞没赞 → `Boolean`） vs `GET /contents/{id}/like-count`（**它**被赞几次 → 数字）。
  歧义面已排查：`{id}` 在前、`like-count` 是字面量末段 ⇒ 路由不互相命中；`/contents/like-count` 会落
  `GET /contents/{id}` 并按非法 id 回 400（不存在"计数集合"端点）；唯一要防的是**中文口述**把
  `favorite-count` 说成"收藏夹数量"——故上表把主语写死。

- **路径变量**：统一写 `{id}`（Java 侧 `@PathVariable("id") long contentId`，语义名留在形参上）。
  ★ id 从 query/form 进路径后，**"缺 id" = 404**（请求根本不匹配路由），**非法 id = 400**
  （`参数类型不正确`，`field=id`）。这条区分是 `T58` 的契约变更，`T59` 不改。
- **逐切片的迁移记录**（旧路径根 → 新路径根）**已清出**：过程在 git（`T58-1…T58-10`），
  当前形态以 `spec` 与登记簿为准。执行期裁决（`R-23`）保留一句：迁移期间旧 SPA 在已改域上 404 是**接受**的已知代价。

### 2.4 方法判据

| 方法 | 判据 |
|---|---|
| GET | 无副作用、可缓存、可重试 |
| POST | 创建（非幂等）**或** §2.3 例外清单里的动作 |
| PUT | **幂等替换 / 幂等设置**：改密码、改用户名、改内容、换源、评论开关、进度覆盖 |
| DELETE | **取消 / 删除**（取消点赞、取关、移出收藏、删内容）——必须幂等 |
| PATCH | ★ **不用**（定稿）：本仓"局部修改"的字段都少，PUT 整体替换已足够；少一套方法少一套约定 |

- **判据优先级**：无副作用 → GET；"从集合移除 / 删资源" → DELETE；"幂等设置" → PUT；其余 → POST。
- 幂等口径写死：**重复 DELETE = 204**（不报 409）；**同值重复 PUT = 200**（不报冲突）。
  ★ **落地归属**：方法由 `T58` 定，**幂等行为与 204 由 `T59` 同批落地** —— `T59-1` 已交付：
  点赞/关注（内容/评论/关注）改 `INSERT IGNORE` + 受影响行数（0 行不扣计数、不发事件）；
  收藏移动 / 稍后再看移入收藏夹幂等；管理员下架/恢复幂等；四个冲突码删除（见 §2.2）。
  ★ **边界（必须知道）**：
  ① **"重复 DELETE = 204"只覆盖关系型取消与状态型取消**（赞 / 关注 / 收藏 / 稍后再看 / 管理员恢复）。
     **资源型删除**（评论 / 内容 / 媒体 / 收藏夹 / 管理员删评论）成功 = 204，但**第二次仍是 404**
     —— "已软删亦视为不存在"是既有冻结契约，硬删资源也无法区分"从未存在"与"已删除"；
     改成 204 会给"id 打错"开一个静默成功口。
  ② **不适用"同值 PUT = 200"的两类**：**改密码**（旧密码已失效，重试必然 401，前端不得自动重试）、
     **上传类换源**（`PUT /contents/{id}/media`、`PUT /admin/media/{id}` 是文件动作，重复执行会再写一次文件）。
  ★ **访问日志**：204 无信封但属业务成功 ⇒ `code=OK`（不是 `0`）；静态资源不会返回 204，不污染 `0` 判据。
- **`T58` 定性结果**：39 个原 POST 全部重新定性，当前分布 = **GET 28 / POST 13 / PUT 15 / DELETE 11**
  （逐条归属见 `spec` 的 method 与 §2.4 判据；`T59-1` 已把"幂等行为 / 204"落地）。
  ★ 验收口径不变：**0 个 POST 承担"取消 / 删除 / 幂等替换"语义**。

### 2.5 载荷

- 入参：写操作统一 **JSON body**；GET 用 query。
- ★ **multipart 的落点**（`T59` 更正，原写 `/api/v1/uploads` 是漂移）：只有上传类四条 ——
  `POST /api/v1/contents/videos`、`POST /api/v1/contents/posts`（表单字段 + 文件 part）、
  `PUT /api/v1/contents/{id}/media`、`PUT /api/v1/admin/media/{id}`（文件 part + 选择参数）。
  这些端点的**非文件字段**仍按表单/query 传（multipart 无法同时是 JSON body）。
- ★ **DELETE 一律不带 body**（`T59` 例外清单，1 条）：批量/选择参数走 query ——
  `DELETE /api/v1/favorites?folderId=&contentIds=`、`DELETE /api/v1/watch-later?contentIds=`、
  `DELETE /api/v1/contents/{id}/media?type=&url=`（`T63`：选择参数由 `sort` 改为稳定标识 `url`，
  见 §2.4① "重复删除 = 404" —— 位置型参数重试会删到下一张）。
  理由：DELETE + body 在 HTTP 语义与客户端支持上都不稳定（代理/缓存可能丢弃 body），
  而这几条的动作对象（集合/内容）在路径上、**选择范围是参数**。
- 真类型：布尔用 `true/false`；枚举用**语义化字符串**（如 `type=VIDEO|POST`），不用裸数字 `1|2|3`。
  ⚠️ **已知宽松**：Jackson 默认标量强制会接受字符串 `"true"/"false"` 当布尔。
  **对外契约只承诺 JSON 布尔**（前端按布尔传）；服务端宽容不视为契约、也不得依赖
  （`FavoritePrivacyTests` 已注明）。
- 出参：`ApiResponse<T>`，其中 T **不得**是 `?` / `Map<String,Object>` / 裸 `String`；
  `Void` 仅用于"成功但无数据"（如改密码 / 各写端点成功）。
- 删除 / 取消：`204`，**不**返回 `String` 文案。
- `T59` 兑现的具名出参：上传 → `ContentCreatedVO` / `MediaReplacedVO`；领券 → `CouponClaimVO`；
  评论列表 → `PageResult<CommentVO>`。

#### 2.5.1 校验失败体（`T57` 定稿，本节即验收依据）

形状：`400` + `{"code":"PARAM_INVALID","msg":"<摘要>","errors":[{"field","code","message"}]}`

- **出现范围只此六类**（都属"输入不合法"，与业务拒绝严格区分）：
  ① `@Valid` 请求体失败；② 缺必填 `@RequestParam`；③ 缺 multipart part；
  ④ 参数类型 / 取值不可转换；⑤ 请求体整体不可解析（空体 / 报文残缺）；
  ⑥ 标在控制器方法参数上的约束（`HandlerMethodValidationException`，如 `@RequestParam @NotBlank`）。
  ⚠️ `T59-2` 起 `src/main` 已无此类约束（入参统一到请求体 DTO）⇒ 本类目**当前无产码点**；
  分支保留（未来若加参数约束仍走同一出口），新增时必须同批补契约用例（`I-29` 已登记）。
  它们都是**声明式机制**的产物；Service 里的手写校验不在此列（见下"业务拒绝"）。
- `field` = **请求里的字段名**（JSON 键 / query 参数名 / multipart part 名），不是 Java 属性名。
  ★ **定位不到时省略 `field`**（不编一个名字）：请求体整体不可解析、类级（跨字段）约束失败。
  此时该条只有 `code` + `message`，`msg` 也就只有 `message`（没有 `field: ` 前缀）。
  ⚠️ 今天"JSON 键 = 属性名"的前提成立（全仓无 `@JsonProperty` 改名字段、无 `@JsonNaming`、
  无 `spring.jackson` 命名策略、无 `@RequestParam("alias")` 别名）——**任何一项出现，都必须回来改这里的口径**
  （`HandlerMethodValidationException` 分支已按"注解别名优先"实现，请求体分支仍依赖"同名"）。
- `code` = 码表里的**族码**，当前恒 `PARAM_INVALID`。依据 §2.2 粒度判据：字段级定位已由 `field` 承担，
  给每条约束造一个码只会让字典膨胀。保留 `code` 是**形状守恒** —— 将来真出现"某字段要不同处置"
  （判据①/③），只换码、不改形状。
- `message` = **稳定中文文案**，两个来源：
  ① 约束注解上的 `message`（源码里的契约文案）。★ **本仓约定：约束注解必须写 `message`** ——
     默认文案随 Locale 变（本机中文、CI 英文），不能进对外 body；
  ② 框架异常的**固定文案表**（异常自带 message 一律不进 body）：

| 触发 | `message` |
|---|---|
| 缺 `@RequestParam` | `缺少必填参数` |
| 缺 `@RequestPart`（multipart part） | `缺少必填部分` |
| 参数类型不匹配（query 参数 / 请求体字段类型不对；本仓无 `@PathVariable`） | `参数类型不正确` |
| 请求体里某个值不可转换（非法枚举字面量、数字字面量等） | `参数取值不合法` |
| 请求体解析层失败（空体 / 报文残缺 / 根层类型不符） | `请求体缺失或格式错误` |
| 控制器参数上的约束（方法校验） | 该注解的 `message`；缺失时 `参数不合法` |

  ★ "解析层失败"与"某字段值不对"的区别是**失败层**，不是能否回收字段名：
  报文在字段值处被截断时字段名仍可回收（照给 `field` 便于排查），但文案仍是
  `请求体缺失或格式错误`——说"类型不正确"会把"报文断了"误报成"用户填错"。
- ★ **禁止把异常 message 写进 body**：`MethodArgumentTypeMismatchException`（`for value [xxx]`）、
  `MethodArgumentNotValidException`（`RegisterRequest[... password=verysecret ...]`）都会**回显入参**，
  那是 PII 出口。异常对象只进日志。
  ⚠️ 日志侧脱敏**只覆盖已登记形态**（手机号，见 `common/log/LogMasker`）：密码等仍明文落盘
  —— "只进日志"≠"日志里看不见"。
- `msg` = 人读摘要：有 `field` 的写成 `field: message`，没有的只写 `message`；多条用 `"; "` 拼接。
  **与 `errors[]` 同源**（`ApiErrorWriter#summary`）—— 保留它只为旧前端与不翻字典的调用方兜底。
- 同一字段可能有多条（Bean Validation 是"每条违反一条"）⇒ **不合并**：合并要选"哪条算第一条"，
  那是不可解释的隐式策略，且会丢掉"还违反了另一条"的信息。前端按 `field` 分组、展示第一条。
- **业务拒绝不产 `errors[]`**：Service 内手写校验（`ParamException`，如"标题不能为空"/"输入不能为空"）
  仍只有 `msg`。这是 `T57` 的**有意边界**（已登记 `I-26`）：那些校验是 fail-fast 单条，
  要迁到声明式得先解决 multipart 表单绑定，时机归载荷面（`T59`）与重制期。
- 落点与护栏：`common/web/ApiFieldError`（元素，构造即校验三条不变量）/ `ApiResponse#errors` /
  `ApiErrorWriter`（唯一写出点 + `summary`）/ `GlobalExceptionHandler`；契约由
  `ValidationErrorContractTests`（11 例）+ `ApiErrorExitContractTests`（失败体骨架 = `{code,msg}`
  或 `{code,msg,errors}`，元素只允许 `{field?,code,message}`）+ `UploadFlowTests#缺必填part为400` 钉住。
- **降级分支（理论，今天不可达）**：Bean Validation 报"校验失败"却拿不到任何原因时退回 `{code,msg}`
  不带 `errors`（`errors:[]` 被 `ApiResponse#error` 直接拒绝——宁可少一个字段，也不产出"我失败了但列不出原因"）。
  写在这里是为了让"六类必带 `errors[]`"的例外可查。
- ⚠️ **已知代价**：
  ① `errors[].message` 是**自由文本**（不在码表里）⇒ 前端**不许**按它做分支或匹配中文，
     要分支就用 `code` + `field`。文案改动不视为契约破坏（这正是把它放在 `message` 而不是 `code` 的原因）。
  ② "约束注解必须写 `message`"只是**约定**，没有机械守卫（漏写会落到兜底文案 `非法值` / `参数不合法`，
     不会变红）—— 靠 review，与"码表死码护栏"不同级别。
  ③ **上传超限 / 畸形 multipart 仍是 500**（`MaxUploadSizeExceededException` 落 catch-all）：
     它属"输入不合法"，但补它要新增 413 类别（§2.1 状态表没有），属规则变更 ⇒ 已登记 `I-27` 待裁决，
     不在 `T57` 内自行放宽。

### 2.6 分页

- 默认 offset 信封 `{list,total,page,pageSize,totalPages}`；
  keyset `{list,total,pageSize,nextCursor}` **仅**用于"按单调键深翻且 offset 成本不可接受"（当前只有评论回复）。
- **同一端点只许一种形状**；不得"带了参数就换信封"。
  ★ `T59` 落地：`GET /api/v1/contents/{id}/comments` 的"缺省全量数组 / 带参信封"两态退役，
  恒为 `PageResult<CommentVO>`（缺省 = `page=1&pageSize=200`，与显式传参逐字节一致）。
- 参数统一 `page` / `pageSize`（1 起）；上限各域自持并写进下方清单。
- **非数字 / ≤0 静默归一**（既有冻结契约），**不**返 400 —— 与本条目的"参数错误"区分开。
- ★ **各域 pageSize 清单**（`T59` 补，缺省 / 上限；常量各自持在 Controller）：

  | `GET /api/v1/users/{id}`（主页 `contentPage`） | 100 | 100 |
  | `GET /api/v1/feed` | 100 | 100 |
  | `GET /api/v1/users/{id}/following` · `/followers` | 100 | 100 |
  | `GET /api/v1/favorites` · `/api/v1/favorite-folders/{id}/items` | 100 | 100 |

### 2.7 时间与 ID

- 时间：ISO-8601 **本地时间** `yyyy-MM-ddTHH:mm:ss`，语义时区 **Asia/Shanghai**（库与 JVM 同区）；
  **不引入偏移**。推翻条件 = 出现跨时区客户端或跨区排序需求。
- ID：**保持 JSON number**。依据：自增 id 远小于 2^53，改字符串是零收益的返工；
  推翻条件 = 改雪花 id / 引入外部 id ⇒ 届时全站一次改完。
- ★ **计数**（`T59`）：**标量计数端点**的 Java 出参统一 `Long`（OpenAPI 因此统一 `int64`）；
  VO 内嵌计数字段沿用实体类型（JSON 层一律 number，无 int/long 之分）。
  根因与修正：like 侧曾是 `int`（`Integer.parseInt` + DAO `COUNT` 返回 int），
  favorite 侧是 `long`（DAO `COUNT` 直接映射 long）⇒ 同类计数器两个宽度；
  `T59` 把 like 计数链（DAO / mapper / cache / service / controller）一并改 `long`，
  并删掉聚合回填处的 `Math.toIntExact`（那是 `int` 宽度留下的转换点）。
- 两者由 `T59` 用跨 VO 断言钉住：`PayloadShapeContractTests`（时间逐字 / ID 是 number / 计数是 number）
  + `ApiContractInventoryTests#计数端点出参统一为long`（`T59` 前这些只是 Boot 默认行为，无人显式断言）。

### 2.8 一物一名（接口术语）

| 词 | 用于 | 不要叫 |
|---|---|---|
| `remove` | 从集合里移除**关系**（收藏夹条目、稍后再看） | `delete` / `cancel` |
| `delete` | 删除**资源本体**（评论、内容、媒体） | `remove` / `mediaDelete` |
| `cancel` | 撤销一个**动作 / 状态**（取消点赞、取消关注） | ★ `unlike` / `dislike` |

- ★ **`unlike` 全站退役**：本仓**没有"点踩"**，对外只说"取消点赞"（旧 `POST /like/.../remove` 的
  语义就是 cancel，不是"取消踩"）。Java 方法名已由 `T58` 改为 `cancelContentLike` / `cancelCommentLike`
  （Controller / Service / Cache / Listener 四层同批），否则下一个人会照着抄。
- **`T58` 补充词条**（路径段一律 kebab-case，动词命名退役）：

  | 词 | 用于 | 不要叫 |
  |---|---|---|
  | `session` | 登录产物（会话凭据） | `login`（动词） |
  | `check-in` | 每日签到（`users/me/check-ins`） | `signIn` / `sign-in`（与"登录"混淆）★ |
  | `like` | 当前用户与目标的**单例**赞关系 | `unlike`（退役） |
  | `like-count` | 赞数（标量投影） | `count`（无归属） |
  | `favorite` | 收藏关系（集合 `favorites`；单例读 `contents/{id}/favorite`） | `collect` |
  | `favorite-folder` | 收藏夹 | `folder`（脱离域上下文） |
  | `follow` | 关注关系（`follows/{id}` = 我关注谁） | `subscribe` |
  | `claim` | 领券（创建领取记录） | `grab`（动词） |
  | `hidden` | 内容的隐藏状态（管理员视角，PUT 设 / DELETE 撤） | `hide` / `unhide`（动词） |
  | `progress` | 播放进度（GET 读 / PUT 覆盖） | `position` / `report` |
  | `media` | 媒体文件（上传、换源、恢复、删除都归它） | `upload` / `file` |
  | `watch-later` | 稍后再看（不可数，不加 s） | `watchlater` |

  ★ **`signIn` vs `login` 是本次最险的一处同名冲突**：旧 `/coin/signIn` 是**签到**，
  而"sign in"在通用语义里就是登录 —— 两个概念在同一份契约里都必须有名字，故拆成
  `check-in`（签到）与 `session`（登录）。

  ★ **`folder` 词条的适用范围（`T58` 收尾交叉审查澄清）**：「不要叫 `folder`」约束的是**给收藏夹这个资源命名**
  （独立寻址的集合资源必须叫 `favorite-folders`，见 §2.3 资源清单）。`PUT /api/v1/watch-later/{id}/folder`
  末段的 `folder` 是**稍后再看条目的目标归属**（域上下文由 `watch-later/{id}` 自带），不在该词条约束面内，
  且已随 `T58-4` 冻结（登记簿 / 权重表 / 测试三处一致）**不改**；出现第三个 `folder` 段才重新裁决（rule of three）。
