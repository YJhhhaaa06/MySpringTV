# 缓存与数据一致性

> 定位（先读这一句）：本仓缓存是**显式封装层**（各域自持三态机 + 共享引擎 `CacheAside`），**不用** `@Cacheable`。
> **本篇只讲缓存口径**：三态语义 / key 命名 / 空标记与 `partial:` 窗口 / 写后失效 / 各域缓存清单。
> **熔断 · 单飞 · 冷却退避 · 降级**不在本篇，去向见文末 [§边界与去向](#边界与去向机制外链)。
> 各域业务语义（如 feed 的 fanout）见 [feed 域架构](../domain/feed.md)；模块边界见 [模块边界与依赖](./模块边界与依赖.md)。

---

## 一、为什么是显式封装层，而不是 `@Cacheable`

`@Cacheable` 只能表达"命中即返回"。本仓缓存真正的语义**主体**它一个都表达不了：

| 需要表达的语义 | `@Cacheable` | 本仓 |
|---|---|---|
| 空标记防穿透（hit-empty 不回源） | ✗ | ✓ `empty:{dataKey}` |
| 读 miss 回源 + 回填 | 部分（无防穿透） | ✓ loader 契约 |
| 写后失效（而非写后更新） | ✗ | ✓ `invalidate` / 各域 DEL |
| Redis 失败降级、DB 失败上抛（**两种失败可区分**） | ✗ | ✓ `CacheUnavailableException` |
| 条件写防残缺缓存（集合/计数增量写） | ✗ | ✓ 各域 Lua |

**分工（三层，各写各的）：**

- **共享引擎 `CacheAside`**（`common.cache`）：JSON 值版通用三态机（单 key `get` + 批量 `getBatch`）。
  **它只服务 content 域**——其余域的数据结构不同，各持三态机。
- **各域自持的三态机**：`ContentCache` / `FollowCache` / `LikeCache` / `CommentCache` / `FeedCache`。
  它们**有意未抽公共框架**（Set / ZSet / LIST+HASH 各异，公共层只会长出分支）。
- **共享协议基类 `RedisOps`（抽象类，非 bean）** + 每域 `*RedisOps`：
  只管"把命令发出去 + 把 Redis 异常归一化"，不含任何缓存语义。

**横切件（一次性、唯一源）：**

| 件 | 职责 |
|---|---|
| `CacheKeys` | 键命名唯一源（数据 key + `empty:` + `partial:` 的字符串拼装） |
| `JsonCodec` | 缓存值 JSON 编解码；**编解码失败 = 缓存不可信**（包成 `CacheUnavailableException`，不 500） |
| `CacheUnavailableException` | Redis 失败的类型化出口（与 DB 的 `DataAccessException` 区分） |
| `CacheMetrics` | 六事件打点；**只接在 `CacheAside`**（content 域），覆盖边界见 §七 |

> `RedisOps` 是**抽象类**而非 `@Component`：若标 `@Component`，按类型注入 `RedisOps` 会立刻
> `NoUniqueBeanDefinitionException`（各域子类各自 `@Component`，注入点写具体类型）。

## 二、共享引擎 `CacheAside`

### 2.1 三态语义（单 key）

| 态 | 触发条件 | 行为 |
|---|---|---|
| `hit_data` | 数据 key 命中**且反序列化成功** | 返回值，并滑动续期（脏 JSON 归 `degrade`，不吞成命中） |
| `hit_empty` | `empty:{dataKey}` 命中 | 返回 `null`，**不回源 DB**（防穿透） |
| `miss` | 两者皆无 | 回源 `loader` → 回填 |
| `degrade` | Redis 命令失败 / 值不可信 | 只调 `loader` 返回，**不写回**（下次 miss 自愈） |

数据 key 的续期带 **±10% TTL 抖动**（`JITTER_RATIO`，保底 1 秒）；**空标记从不续期**。

### 2.2 回填口径（loader 的契约即回填规则）

`loader` 的返回值语义决定回填动作，这是全仓的**同一套口径**：

```
loader() 返回 非 null  → writeOrInvalidate(dataKey, value, ttl)   // 写数据 key（并同步清空标记）
loader() 返回 null     → markEmpty(dataKey)                       // 写空标记（已确认无数据）
loader() 抛异常        → 原样上抛，不写空标记、不 DEL 数据 key      // 加载失败 ≠ 确认无数据
```

- **两种失败必须区分**：本引擎**只 catch `CacheUnavailableException`**；`loader` 抛出的
  `DataAccessException`（DB 失败）原样上抛（全局 500）。把"读不到"降级成"没有"是更坏的语义。
- **写入即清空标记**：`writeOrInvalidate` 写数据 key 时**同步 `DEL empty:`**，防止此前写下的空标记
  把真数据固化成"假空"窗口。
- **空标记有存在守卫**：`markEmpty` 仅在数据 key **不存在**时才写（宁可少写、多查一次 DB，绝不误写）。
- 并发 miss 的回源去重、以及降级/熔断的收口**不在本篇**——见 [韧性](./韧性.md)。

### 2.3 批量读 `getBatch`

- 一趟 pipeline 探测**全部** key 的三态（`EXISTS empty:` + `GET` + `EXPIRE` 续期），语义与单 key 一致。
- miss 子集与**整批降级**子集各走一次 `batchLoader`（常量趟数，而非逐 key 各查一次 DB）。
- **批量 loader 契约**：必须为每个请求 key 给出条目（无数据给 `null`）。**漏 key 视为契约违规**，
  按"加载失败"处理（不写假空标记）。
- 内容列表（`/start` / `/search` / `/profile`）靠它把"页成本 ∝ 条数"降为"常量往返"。

### 2.4 `init()` 预热**不做**（永不实现）

`ContentCache` **不搬**启动全量重建 `init()`。理由（可复算）：

1. 它的两条产物**都已有自愈路径**：内容 key → `CacheAside` 的 miss 回填；类型分区索引 → `ensureIndex` 懒重建。
   **`init()` 只是预热，不是正确性来源**；
2. 代价是启动期一次**无上限全表查询**（`findAllContent`），换到的只是"首批请求不 miss"。

> 索引懒重建失败后的**进程内冷却退避**（`video.cache.content-index-rebuild-cooldown`，默认 `10s`）属韧性机制，
> 见 [韧性](./韧性.md)；它只影响"重建频率"，不改缓存口径。

## 三、键空间与命名（`CacheKeys`）

**键字符串是冻结契约**（测试里硬编码了形状，让"改名"这种静默缓存失联无法悄悄发生）——
所有域经由 `CacheKeys` 拼装，**不得在域内散写字面量**。

### 3.1 数据 key + `empty:` 两件套

- 数据 key：各域形态见 §五。
- **空标记**：`empty:{dataKey}`（String，值固定 `"1"`），TTL **60 秒**
  （`CacheKeys.EMPTY_MARKER_TTL_SECONDS`），承载"**已确认无数据**"。
  它同时服务防穿透与**写路径判定**（集合类的条件写要知道"这一侧是'已加载的空'而非'没加载'"）。
- **失效集 = 两件套**：凡 DEL 数据 key，必须**一并 DEL 其 `empty:`**，否则残留空标记会让后续读"假空"。

### 3.2 `partial:` 的取舍（前缀窗口标记）

`partial:{dataKey}`（TTL **与数据 key 同步**）断言集合的**完整性**：

```
无 partial  → 数据 key（若存在）就是全集
有 partial  → 数据 key 只是 DB 按序的前缀 [0, W)，W = ZCARD
```

**谁用、谁刻意不用：**

| 域 | 用 `partial:`？ | 理由（代码取证） |
|---|---|---|
| follow | **用** | 唯一有"按序分页读大集合"的域；miss 只装 `[0, offset+count)`，装载量 ∝ 位次而非列表总量 |
| content | 不用 | 单条详情 + 索引 LIST，不产生"前缀态" |
| comment | 不用 | 前缀用 **LIST 水位 `LLEN`** 表达（窗口追加），不是 `partial:` 标记 |
| like | 不用 | Set 无偏移语义，不存在前缀/全集之分 |
| feed | **刻意不用** | 收件箱键的**写者只有读路径**（fanout/重建只 DEL 不写）⇒ 永不产生前缀态；保留 `partial:` 反而制造"残留标记把完整集误判成前缀"的风险 |

**`partial:` 的配套四处特判必须同时存在**，缺一处是**静默错答案**（不是性能退化）：

1. **判定**（`isFollowing` / `batchIsFollowing`）在部分态下**未命中必须回落 DB**（前缀里查不到 ≠ 不是成员）；
2. **全量读**（`getFollowingIds`）遇部分态**必须先补齐**（返回前缀会静默漏人）；
3. **写路径**任一侧部分态 ⇒ **整体失效**（`ZREM` 会在前缀里留洞、`ZADD` 会插入非前缀成员，都破坏偏移语义）；
4. 部分态 / 降级态的 **`total` 走域级计数口径**（`ZCARD` 只是已知前缀大小，会低估）。

## 四、读写口径

**总则一句话：单写 DB 真相 + 写后失效 + 读 miss 回源回填。**

### 4.1 读路径

- 三态读（§二.1）；命中即滑动续期。
- **Redis 失败 → 降级直查 DB**（不影响结果）；**降级不写回**（写回交给下次 miss 自愈）。
- **DB 失败 → 上抛**（500），**不吞成 `null`**。降级成空会把"读不到"伪装成"没有"。
- 实现上靠**只 catch 自己的异常类型**保证：`CacheUnavailableException` 只从 `*RedisOps` 冒出，DB 异常不经它。

**几处刻意的例外**（须逐个识别，非疏忽）：

| 位置 | DB 失败时 | 判据 |
|---|---|---|
| content 索引懒重建装载 | 记日志**跳过重建、保留旧索引** | 不把 DB 瞬时故障放大成"全站索引归零" |
| comment 楼中楼（children 预览） | **降级为空数组** | 预览子集，缺席可如实表达（`children: []` + 顶层 `replyCount` 仍在） |
| feed 大V发件箱腿 | **fail-open 按空处理** | 追加的一路，缺席退化为"少一批大V内容"，不 500 |

### 4.2 写路径

- **先落 DB，事务提交后才碰缓存**（由各域 `*ChangedListener` 的 `AFTER_COMMIT` 保证；事件范式见
  [领域事件与解耦](./领域事件与解耦.md)，事务载体见 [事务边界](./事务边界.md)）。
- **写后失效，而非写后更新**：DB 改完不写缓存，直接 `DEL`（数据 key + 空标记，follow 另加 `partial:`）
  让读自愈回填。feed 的 fanout **只 DEL、从不写 Redis**。
- **条件写防残缺缓存**：集合/计数的增量写**只在 key 已加载时**才执行（各域 Lua 原子完成）。
  冷 key（未加载）时**不写入半套数据**（否则读命中一个"看起来对、其实缺项"的缓存），改走整体失效让读回源。
- **写失败 ⇒ 失效让读自愈，不抛出**：Redis 写失败时 `DEL` 相关 key（含空标记），而不是"留着旧缓存"。

## 五、各域缓存清单

| 域 | key 形态 | 缓存内容 | TTL / 配置项（默认） | 失效触发方 |
|---|---|---|---|---|
| content（详情） | `content:{id}`（JSON） | 内容详情 DTO（含媒体装配后 URL） | `video.cache.content-ttl`（**30m**）；`empty:` 60s | `ContentCacheChangedListener`；点赞/评论监听器经 `invalidateContent` |
| content（索引） | `content:index:{type}:{cid}`（LIST，一条 4 键） | 类型/分区索引 id（`-1`=通配维度） | **无 TTL**（`ensureIndex` 懒重建） | 写后 `refreshContent` / `removeContent`；写失败自愈 `DEL` 触发懒重建 |
| comment | `content:comments:{id}:roots`（LIST）/`:replies`（HASH）/`:count`（String int） | 主楼窗口 / 楼中楼（每主楼前 K=2，`PREVIEW_REPLIES_PER_ROOT`）/ 真实主楼总数 | `video.cache.comment-ttl`（**10m**）；`empty:` 挂在 `:roots`，60s | `CommentCacheChangedListener`（增删主楼/回复）、`LikeChangedListener`（评论点赞） |
| like（成员） | `user:likeSet:{id}` / `user:commentLikeSet:{id}`（Set） | 我点赞过的内容 / 评论 id | `video.cache.like-ttl`（**15m**）；`empty:` 60s | `LikeChangedListener`（提交后条件写） |
| like（计数） | `content:likeCount:{id}` / `comment:likeCount:{id}`（String int） | 点赞数 | `like-ttl`（15m）；**无空标记** | `LikeChangedListener`；内容删除经 `invalidateContentLikeCount` |
| follow（关系） | `user:following:{id}` / `user:follower:{id}`（**ZSet**，score=成员 id） | 关注集 / 粉丝集 | `video.cache.follow-ttl`（**30m**）；`empty:` 60s；`partial:` 同数据 key | `FollowChangedListener`（提交后条件双写） |
| follow（计数） | `user:followCount:{id}` / `user:followerCount:{id}`（String int） | 关注数 / 粉丝数 | `follow-ttl`（30m）；**无空标记** | `FollowChangedListener`（条件 `INCRBY`） |
| feed | `feed:inbox:{id}` / `feed:outbox:{authorId}`（**ZSet**，score=contentId） | 收件箱窗口 / 大V发件箱窗口（最近 N 条） | `video.feed.inbox-ttl` / `video.feed.outbox-ttl`（均 **60m**）；`empty:` 60s | fanout（**只 DEL**，两端两件套）；重建（DEL 收件箱）；发布（outbox **无条件**失效） |
| feed（锁） | `feed:rebuild:lock:{id}`（String token） | 重建去重锁（**非缓存**，`SET NX EX`） | 60s（`FeedCache.REBUILD_LOCK_TTL`） | 重建流程取/放（`Lua CAS`） |

> `content-ttl` / `comment-ttl` / `follow-ttl` / `like-ttl` 在**绑定期**校验（非正数 ⇒ 启动即拒）；
> 所有 `Duration` 属性**必须带单位后缀**（裸数字会被解析成秒级，不报错只行为诡异）。

## 六、空标记与 `partial` 窗口装载：什么时候才用，代价是什么

### 6.1 空标记（negative cache）

**才用的条件**：当"**确认无数据**"是一个**高频可复现**的读——
从未点赞的用户、无关注的用户、无评论的内容、空收件箱——写空标记可挡住对 DB 的穿透。

**代价：**

- **短 TTL 的"假空"窗口**：写路径**必须**清空标记（点赞脚本先 `DEL`、回填非空集合同步 `DEL`），
  否则真数据被空标记挡在 60 秒假否定之后；
- **残余竞态**（如实登记、未消除）：`markEmpty` 的守卫只查数据 key，与"并发写已提交"之间存在
  毫秒级窗口 ⇒ 空标记可能盖在刚提交的写之上，表现为最长 60s 假否定。

**计数 key 刻意不用空标记**：`0` 是**合法值**，必须与"key 不存在"靠 `GET` 返回 `null` / `"0"` 区分——
写空标记会让"0 个赞"与"未知"混淆。

### 6.2 `partial` 前缀窗口装载

**才用的条件**：**大集合 + 按序分页读**（follow 的百万粉丝）。它把"任何一页都装载全量"降为
"装载量 ∝ 位次"。

**代价：**

- **集合不变量的复杂度上台阶**：§三.2 的**四处特判**必须同时存在，缺一处即为静默错答案；
- **失效集升为三件套**（数据 key + `empty:` + `partial:`）：残留 `partial:` 会让新装的完整集被误读为前缀；
- **只在 follow 域**（其余域见 §三.2 表格的理由）。

## 七、一致性的有意取舍（各带代价）

| # | 取舍 | 代价 |
|---|---|---|
| 1 | **缓存只作加速器**：Redis 失败一律降级走 DB、接口不 500 | 降级期 DB 承担全量读（惊群），靠单飞/熔断削峰（→ [韧性](./韧性.md)） |
| 2 | **DB 失败上抛**（一般纪律），只有"缺席可如实表达"的附加腿例外（feed 大V腿 / comment 楼中楼） | 例外需逐个判据，读者必须能在代码里读到"为什么它不同" |
| 3 | **写后失效而非写后更新** | 紧随写之后的一次读会 miss 回源（一次读放大） |
| 4 | **空标记短 TTL**（60s） | 写路径必须清空标记；毫秒级残余竞态（§六.1） |
| 5 | **共享引擎只服务 content，各域自持三态机** | 三态/回填逻辑在各域重复；打点 `CacheMetrics` **只覆盖 content**，like/follow/comment/feed 未接线（观测边界，非正确性） |
| 6 | **`partial:` 只 follow 用** | follow 是四域里唯一携带"前缀态"语义的域，判定分支与失效集最复杂 |

## 八、新代码检查清单

1. **选层**：content 走 `CacheAside`；其余域自持 `*Cache` + `*RedisOps`。键一律经 `CacheKeys`。
2. **要不要空标记**？"确认无数据"是否高频可复现？计数（`0` 合法）不写空标记。
3. **会不会产生"前缀态"**？若会，必须上 `partial:` 且 §三.2 的**四处特判齐备**；否则不引入。
4. **写路径**：DB 提交后才碰缓存（`AFTER_COMMIT`）；用写后失效；Redis 写失败 ⇒ 失效自愈、不抛出；
   条件写只在 key 已加载时执行。
5. **读路径**：DB 失败上抛，**不吞成 `null`**；Redis 失败降级、**不写回**。
6. **横切机制不在本篇展开**：熔断 / 单飞 / 冷却退避 / 降级 → [韧性](./韧性.md)；
   事件监听 → [领域事件与解耦](./领域事件与解耦.md)；提交后失效的事务载体 → [事务边界](./事务边界.md)；
   打点与指标 → [可观测](./可观测.md)；包结构与依赖方向 → [模块边界与依赖](./模块边界与依赖.md)。
