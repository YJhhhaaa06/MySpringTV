# 领域事件与解耦

> 定位（先读这一句）：**每个域只声明"自己发生了什么"，需要响应的人自己订阅。**
> 本篇只讲这条范式、本仓的事件清单、以及"谁发/谁订/何时订"的纪律；
> 事务切分与载体 bean 去 [事务边界](./事务边界.md)、异步投递去 [MQ 与投递可靠性](./MQ与投递可靠性.md)、
> 缓存失效口径去 [缓存与数据一致性](./缓存与数据一致性.md)。
> 文末 [§七 边界与去向](#七边界与去向机制外链) 列全部外链。

## 一、范式：两条

### 1.1 每个域只声明"自己发生了什么"

事件的**类型与发布点都归属于"事实发生地"**：

- 类型放在自己的 `event` 包（如 `content.event.ContentPublishedEvent`）；
- 发布点在自己的 Service 事务方法**内**（如 `ContentService.addVideo` 发 `ContentPublishedEvent`）。

事件的载荷只带**业务身份**（`contentId` / `userId`），**不带别域的实现细节**。
`ContentCacheChangedEvent` 的类注释写明这条："刻意不把'要失效哪个 key'写进事件——key 形状是缓存层的实现细节。"

### 1.2 需要响应的人自己订阅

想对某个事实做反应，就**在自己的 `event` 包里订阅**，动作作用于**自己的**资源：

```
        content 域                          feed 域
  ContentService.addVideo
    事务内 ── publish ──►  ContentPublishedEvent  ──►  feed.event.ContentPublishedFeedListener
                                                        （AFTER_COMMIT → 投写扩散消息）
```

### 1.3 为什么（消环 + 包结构上"谁依赖谁"可见）

**消环**：若 content 直接调 feed 的 notifier，就是 `content → feed` 编译期依赖；而 feed 本就依赖
content 的 DAO/Service（读内容），于是成 `content ⇄ feed` 双向环。事件把其中一条边改成
"content 声明事实、feed 订阅"，依赖方向变成单向：

```
   事件（单向） ──►
   content ⇄⇄⇄⇄⇄⇄⇄⇄⇄  feed
   ◄── Service 契约 / DAO 薄依赖
```

`ContentPublishedEvent` 与 `ContentPublishedFeedListener` 的类注释都记了同一句话：
"**content 不再依赖 feed（消掉 TV 的 `content ⇄ feed` 环），且'谁依赖谁'在包结构上可见**。"

**可见**：依赖边不再藏在 `service` 方法体里，而是"谁 import 了谁的 `event` 类型"——
一眼可数（连同 §四 的落点约束）。

## 二、事件清单

逐个核对源码后的**全部**领域事件（7 个）。"时机"一列均为
`@TransactionalEventListener(phase = AFTER_COMMIT)`，**同步**执行（无 `@Async`）。

| 事件（类型） | 发布方 | 订阅方 | 时机 | 一句话语义 |
|---|---|---|---|---|
| `ContentPublishedEvent(contentId, authorId)` | `content`（`ContentService.addVideo` / `addPost`） | `feed`（`feed.event.ContentPublishedFeedListener`） | AFTER_COMMIT | 新内容已发布 ⇒ feed 投写扩散消息 |
| `ContentCacheChangedEvent(contentId, op)` | `content`（`ContentService` 多处：评论开关 `invalidate`、改信息/换媒体 `refresh`、删除 `remove`、下架 `remove`、恢复 `refresh`） | ① `content`（`ContentCacheChangedListener`）；② `comment`（`ContentRemovedCommentListener`，**仅 `REMOVE`**）；③ `like`（`ContentRemovedLikeListener`，**仅 `REMOVE`**） | AFTER_COMMIT | 内容 key 现处于某状态：失效 / 重载 / 剔除 |
| `ContentMilestoneEvent(contentId, action)` | `content`（`ContentService.addVideo` / `addPost` / `deleteContent`） | `content`（`ContentMilestoneListener`） | AFTER_COMMIT | 要记一条内容里程碑日志（观测事实） |
| `CommentCacheChangedEvent(contentId, rootId, op)` | `comment`（`CommentService.addComment` / 删评论） | ① `comment`（`CommentCacheChangedListener`）；② `content`（`CommentCacheChangedContentListener`，**任意 op**） | AFTER_COMMIT | 评论两键组要变：失效主楼序列 / 定向失效某主楼 replies |
| `LikeChangedEvent(userId, targetId, target, liked)` | `like`（`LikeService`：点/取消内容或评论） | ① `like`（`LikeChangedListener`）；② `content`（`LikeChangedContentListener`，**仅 `CONTENT`**）；③ `comment`（`LikeChangedCommentListener`，**仅 `COMMENT`**） | AFTER_COMMIT | 点赞状态变了 ⇒ 各缓存订正自己的计数 |
| `FollowChangedEvent(userId, followedUserId, follow, transition)` | `follow`（`FollowService.follow` / `unfollow`） | ① `follow`（`FollowChangedListener`）；② `feed`（`FollowChangedFeedListener`） | AFTER_COMMIT | 关注关系变了，附带本次的大V状态迁移 `transition` |
| `UserRenamedEvent(userId, newUsername)` | `user`（`UserService.changeUserName`） | `content`（`ContentCacheChangedListener.onUserRenamed`） | AFTER_COMMIT | 有人的名字变了 ⇒ 作者冗余名的内容缓存需失效 |

**读表要点**：

- **一个事件可有多个订阅方，且跨域**：`ContentCacheChangedEvent` 有 3 个订阅方（含 2 个跨域），
  `LikeChangedEvent` 有 3 个。三者都在**同一次提交后**被同步调用，**互不依赖、顺序无所谓**
  （`LikeChangedListener` 类注释："发起点赞的那个域不再决定别人的失效顺序——这是有意的"）。
- **订阅方多按 op/target 早退**：`ContentRemovedCommentListener` / `ContentRemovedLikeListener`
  只在 `op == REMOVE` 时动作；`LikeChangedContentListener` / `LikeChangedCommentListener` 各自
  只在 `target` 匹配时动作。**一个域订阅了事件，不代表它对每种载荷都响应**。
- **`transition` 是"跨提交边界的值传递"**：大V状态迁移在事务内算出（与计数同生共死），
  事件里带出来、监听器里消费，避免监听器重算（重算会读到已提交的新状态、edge 可能不同）。
- **内容里程碑是"观测事实"而非"业务语义"**：`ContentMilestoneEvent` 与 `ContentPublishedEvent`
  **刻意分开**——"把两者合并会让 feed 的投递语义与日志需求纠缠在一起"。

## 三、禁止替别的域发事件

**反面模式**：A 域伸手去改 B 域的缓存 key，或干脆**替 B 域发它的事件**。
两者都让"依赖方向"从包结构上消失，并加深编译期耦合。正解一律是
**"各方订阅同一事件、失效自己的缓存"**。

### 例 1：点赞域曾伸手改内容/评论缓存（S6-B2b）

`LikeChangedListener` 原先**直接驱动** `content.cache.ContentCache` 与
`comment.cache.CommentCache`（`notifyLikeCountChanged` / `notifyCommentLikeChanged`）——
点赞域的编译期依赖里出现了**别人的缓存实现**，`content ⇄ like`、`comment ⇄ like` 两个环闭得更死。

改为各方订阅 `LikeChangedEvent`：

```
  改前： like.event.LikeChangedListener ──► content.cache.ContentCache    ❌ 跨域碰别人的缓存
                                        └─► comment.cache.CommentCache    ❌

  改后： LikeService ──发 LikeChangedEvent──┬─► like.event.LikeChangedListener     （点赞域自己的 LikeCache）
                                            ├─► content.event.LikeChangedContentListener（失效内容 key）
                                            └─► comment.event.LikeChangedCommentListener（失效评论树 field）
```

`LikeChangedListener` 类注释原话："**各方订阅同一个事件、各自失效自己的缓存**"，
依赖方向由"like → 别人的缓存"变成"content/comment → like 的事件"。

### 例 2：评论域曾替内容域发事件（S5 → S6-B2d）

`CommentService` 原先在评论写事务里直接
`events.publishEvent(ContentCacheChangedEvent.invalidate(contentId))`——**评论域去发内容域的事件**，
只为了失效内容的 `comment_count`。评论域被迫 import 内容域的事件类型。

改为：评论域只声明 `CommentCacheChangedEvent`，由
`content.event.CommentCacheChangedContentListener` 订阅并失效**自己的**内容 key
（任何 op 都要失效——楼中楼回复同样计入 `content.comment_count`）。

**同向的另一半**：`ContentService.deleteContent` 原先把两件别人的事都做了
（`commentCache.invalidateComments` + `likeService.deleteContentLike`）。现在它只发一次
`ContentCacheChangedEvent.remove(contentId)`，由 `comment` 与 `like` **各自订阅、各自失效自己的缓存**
（即上表里两个"仅 `REMOVE`"订阅方）。

> 两条纪律：**① 发事件的人只发"自己发生了什么"**；**② 想失效别人的缓存，别伸手——订阅事件。**

### 3.1 附带红线：AFTER_COMMIT 回调里**不得转发事件**

`ContentCacheChangedListener` 类注释专门留了一条"不能做的事"：
**不要在 AFTER_COMMIT 监听器里 `publishEvent(...)` 来"转发"别的域的失效**——
回调执行时**事务已经结束**，此时发布的事件不会被其它 `AFTER_COMMIT` 监听器收到
（`fallbackExecution` 默认 `false`，见 §五）⇒ **转发会被静默丢弃**。
正解仍是"让需要的人自己订阅**事务内发布的那个事件**"。

## 四、订阅方的落点约束（ArchUnit 规则 3）

跨域事件的消费**只能写在自己的 `event` 包**里——这是**会失败的测试**，不是文档约定。

规则（`ArchitectureTests.跨域事件只能由自己的event包消费`）：

```
noClasses()
  .that().resideInAPackage("..videoweb.<X>..")
  .and().resideOutsideOfPackage("..videoweb.<X>.event..")
  .should().dependOnClassesThat().resideInAPackage("..videoweb.<Y>.event..")
```

对全部业务域 `X ≠ Y` 两两断言（域集合 = `user / content / comment / like / follow / coupon / upload / admin / feed`）。
含义：`X` 想响应 `Y` 的事件，那个 import **必须写在 `X.event`**（监听器），
不能写在 `X.service` / `X.controller`。

**由来**：S5 时 `CommentService`（service 包）直接 `publishEvent(ContentCacheChangedEvent…)`，
从包结构上完全看不出这条依赖。规则把这个"藏在方法体里的边"赶到 `event` 包，使其**可见**。

**推论（写作时必须遵守）**：任何"订阅别的域的事件"的类，落点双约束——
① 位于订阅方自己的 `event` 包；② 若同时"伸向别域缓存"则会撞上规则 2（见 [模块边界与依赖](./模块边界与依赖.md)）。
故监听器只调**自己域**的缓存/服务。

## 五、提交后副作用：`@TransactionalEventListener(phase = AFTER_COMMIT)`

本仓所有监听器（§二 表中全部订阅方）统一标注：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

语义（框架保证）：事件在**事务内**发布，监听器**只在事务成功提交后**才被调用；
**事务回滚 ⇒ 完全不调用**。于是"回滚却留下副作用"从"靠行序 + 注释维系"变成**类型保证**。

### 5.1 为什么必须提交后

**回滚会留下指向不存在内容的副作用。** 以 `ContentPublishedFeedListener` 为例，
其类注释写明："投递必须发生在**内容行提交之后**——否则事务回滚会留下一条指向不存在内容的收件箱消息。"
同类理由覆盖全部副作用：缓存失效（回滚后缓存已改 = 污染）、里程碑日志（回滚后留下假成功行）。

**存在证明（关键测试，勿删）**：本项目用"让事务内后续调用抛异常 ⇒ 断言副作用未发生"来
证明该时序。若有人把副作用改回"写在事务方法体末尾"或"事务内更新"，用例立刻变红：

| 机制 | 存在证明测试 |
|---|---|
| 点赞缓存 | `LikeCacheTests.事务回滚后缓存未被污染` |
| 关注缓存 | `FollowCacheTests.事务回滚后缓存未被污染` |
| 评论缓存 | `CommentReadTests.事务回滚后评论缓存未被污染` |
| 内容缓存 | `ContentCacheTests.事务回滚后缓存未被污染` |
| 内容里程碑 | `observability/MilestoneLogTests` |

> "只会写'正常点赞后缓存被更新'的测试**不足以**证明时序正确"——那种测试在两种实现下都会过。

### 5.2 为什么 `fallbackExecution` 保持默认 `false`

默认 `false` ⇒ **无事务时事件不被投递给 AFTER_COMMIT 监听器**。本仓保留默认，理由在多个监听器
类注释里逐字一致：**本项目的写操作一律在 `@Transactional` 方法内发布事件**，
不存在"无事务时也要失效缓存/投递"的场景；若将来出现，**必须显式打开并在此说明理由**（而不是默默打开）。

这条默认值同时是 §3.1 那条红线成立的机制前提：正因为 `false`，
AFTER_COMMIT 回调（事务已结束）里再发事件才会**静默丢弃**。

### 5.3 为什么不用 `@Async`

同步执行的理由（监听器类注释一致）：TV 的副作用就在**提交线程**同步执行，语义一致；
异步会引入"提交后缓存短暂未更新"的**新窗口**，且丢 MDC（reqId 断链）、让测试需要等待。
故**不用** `@Async`。

## 六、新代码检查清单（"我要让某域响应某事件，该怎么做"）

1. **先确认事件存在**。要响应的事实若已有事件类型（§二表），直接订阅；
   没有才新建，且**类型放在"事实发生地"的 `event` 包**（见 §1.1）。
2. **落点 = 自己域的 `event` 包**。新建 `XxxListener` 放在 `X.event`，
   否则 ArchUnit 规则 3 失败（§四）。
3. **标 `@TransactionalEventListener(phase = AFTER_COMMIT)`**，`fallbackExecution` 保持默认 `false`（§五）。
4. **只作用于自己的资源**。监听器里调**本域**的缓存/服务；**不要 import 别域的 `cache` 包**
   （ArchUnit 规则 2），也不要替别域做失效（§三）。
5. **按载荷早退**。若事件带 `op` / `target` 等区分，只在关心的取值上动作（§二"读表要点"）。
6. **不要转发**。别在 AFTER_COMMIT 回调里 `publishEvent` 转发（§3.1）。
7. **发布方纪律**：事件必须在 `@Transactional` 方法**内**发布；只带业务身份，不带 key 形状（§1.1）。
8. **补一条"回滚未发生副作用"的测试**（§5.1）——只测"正常路径生效"不足以证明时序正确。

**新增/改动后的自检**：`.\mvnw.cmd -B test -Dtest=ArchitectureTests`（规则 2/3/4 会立刻拦下越界落点）。

| 不在本篇的内容 | 去向 | 本篇只保留的边界 |

| 日志/指标/审计的形态 | [可观测](./可观测.md) | 里程碑日志作为事件的一例 |

> `FollowChangedFeedListener` **只负责在提交后把消息交给 notifier**，投递可靠性不在本篇。
