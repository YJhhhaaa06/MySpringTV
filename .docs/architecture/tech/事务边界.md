# 事务边界

> 定位（先读这一句）：`@Transactional` 在本仓**只回答一个问题——哪些写必须同生共死**，
> 既不承担"取连接"，也不承担"约定俗成"。
> **本篇只讲**切分原则、事务边界载体为什么独立成 bean、`readOnly` 的语义与去事务判据、典型模式与检查清单；
> **提交后副作用的机制语义**在 [领域事件与解耦](./领域事件与解耦.md)，**逐处调用点明细不在此篇**——
> 本篇给可复用的原则，明细随代码可复算。

---

## 一、三条总原则

| # | 原则 | 判据 |
|---|---|---|
| 1 | **写路径保持单事务** | 同一请求内的多条写必须同进同退：记录 + 计数、扣库存 + 插订单、整窗替换 + 同步状态 |
| 2 | **纯读去事务** | 纯 SELECT、无原子性需求 ⇒ **不加** `@Transactional` |
| 3 | **只读快照用 `readOnly`** | 多条读**必须看到同一 read view** ⇒ `@Transactional(readOnly = true)` |

### 1.1 取证分布

`src/main/java` 内**独占一行**的 `@Transactional` / `@Transactional(readOnly = true)` 声明：

| 域 | 写（`@Transactional`） | 只读（`readOnly = true`） | 载体类 |
|---|---|---|---|
| content | 9 | 0 | `ContentService` |
| like | 4 | 0 | `LikeService` |
| feed | 3 | 2 | 写：`FeedWindowWriter` / `FeedInboxBatchWriter`；只读：`FeedPullReader` / `FeedBigVRouter` |
| user | 3 | 2 | `UserService` |
| comment | 3 | 0 | `CommentService` |
| admin | 2 | 0 | `MediaAuditService` |
| follow | 2 | 0 | `FollowService` |
| coupon | 1 | 0 | `CouponService` |
| **合计** | **27** | **4** | |

> 只统计**声明行**；不含 `@TransactionalEventListener`（那是事件机制，见 §六）。
> 复算：`grep -rn '^\s*@Transactional' src/main/java`。

## 二、为什么"事务边界载体必须独立成 bean"

**结论**：Spring 的 `@Transactional` 由**代理**拦截。**同类自调用**（`this.xxx()`）不走代理
⇒ 事务**静默失效**（不报错、难察觉）。因此：

- 承载注解的方法，若被**同一个类**里的方法自调用，事务不生效，而代码看上去"有事务"；
- 正确做法：把**承载注解的方法挪到另一个 bean**，由编排方**跨 bean 调用**。

三类真实的「编排（无事务）→ 载体（独立 bean，有事务）」对：

| 编排（无事务） | 事务边界载体（独立 bean） | 边界语义 |
|---|---|---|
| `FeedRebuildService.rebuildInbox` | `FeedWindowWriter.replaceWindow` | 单事务「替换窗口 + 写同步状态」 |
| `FeedService.getFeed` / `purePull` | `FeedPullReader.pullForPage` | 单只读事务「命中总数 + 当页 id」 |
| `FeedInboxWriter.fanout` | `FeedInboxBatchWriter.insertBatch` / `insertBackfillBatch` | **每批各自事务**（逐批提交，非整段大事务） |

要点：

- `FeedRebuildService.rebuildInbox` 自身**无** `@Transactional`：取锁 → 读关注集 → 排除大V →
  调 `windowWriter.replaceWindow(...)` → 失效缓存 → 释放锁，只有"替换窗口"这一步在事务内。
  若把它写成同类私有方法再自调用，事务会**静默失效**；抽成 `FeedWindowWriter` 后跨 bean 调用，事务真实生效。
- `FeedService.getFeed` **无事务**：纯拉里"total 与当页 id 两条查询"被抽到 `FeedPullReader`（见 §三）。
- `FeedInboxWriter.fanout` **无事务**：循环里调 `FeedInboxBatchWriter` 的 public 方法 ⇒ 每批落库都在
  **自己的一次事务**里（等价于"逐批借还连接"），借此避免大 fanout 的长事务持锁，重试可幂等重放。

**同类自调用"不生效但无害"的实例**：`FeedBigVRouter.isBigV` 委派 `isBigVBatch`，属同类自调用
⇒ `isBigVBatch` 上的 `@Transactional(readOnly = true)` 经此路径**不生效**。**无害**：单作者只有一块 SQL，
没有"跨块 read view"问题（那正是批量入口要事务的唯一理由）。批量入口被 fanout / 重建 / 读**经代理**调用，事务生效。

**私有方法只写业务、注解标在 public 入口**：`CommentService` 把 `@Transactional` 标在
`deleteCommentByUser` / `deleteCommentByAdmin` 两个**公开入口**，私有 `doDeleteComment` 只写业务、
运行在调用方事务里——同一陷阱的另一种规避形态。

## 三、`readOnly = true` 的"语义"用途与"作废用法"

`readOnly = true` 在本仓**不是**"读操作的装饰"，只有两种正当形态。

### 3.1 语义用途：多条读必须同源快照

| 载体 | 为什么必须同一 read view |
|---|---|
| `FeedPullReader.pullForPage` | 「命中总数 + 当页 id」两条查询**同源**；否则会出现"页里有第 11 条但 `total=10`"这类**自相矛盾的信封** |
| `FeedBigVRouter.isBigVBatch` | IN 列表长度 ∝ 关注数（无上限）⇒ 按 `bigv-query-batch` 切多条 SQL；切分发生在**同一只读事务**内（一次连接借还 + 同一 read view）⇒ **跨块无时序偏差** |

即：它把"**这几次读要看到同一个瞬间**"表达出来——**不是**"我想借个连接"。

### 3.2 作废用法：为"取连接"而套的事务 ⇒ 整体去掉

旧实现里大量存在"纯读却套一层事务"。判据：**若事务里只有一条 SELECT，事务的唯一作用就是取连接
⇒ 直接去掉**，**不改成 `readOnly`**。本仓按此口径去掉的读路径（代表性）：

- `CommentService.getRepliesForRoot`（两条纯读，无原子性需求）
- `ContentService.search` / `listContentForAdmin`（纯读）
- `FollowService.loadUserList`（单条 SELECT）
- `FeedRebuildService.loadFollowedUserIds`（单条 SELECT）
- `UserService.doLogin`（纯读无写）
- `CouponService` 的列表 / 详情读路径

### 3.3 单条查询上的 `readOnly`（纯读声明）

`UserService.getProfile` / `isAdmin` 是**单条查询**上的 `@Transactional(readOnly = true)`——
此处不承载"同源快照"语义，只是**声明这是纯读**。判断一个 `readOnly` 是否"有语义"，看它**是否包住多条查询**：
多条 ⇒ §3.1；单条 ⇒ §3.3。

## 四、纯读去事务的判据

| 读的形态 | 事务 | 依据 |
|---|---|---|
| **单条 SELECT** | **去事务** | 无原子性需求，事务只是"取连接的手段" |
| **多条读，但各自独立、不需同一瞬间**（例如"DB 装载"与"判关注态"来自不同数据源） | **去事务** | 合并进一个事务只会把两次 DB 查询捆进同一快照（`FollowService.loadUserList` 有意分两段） |
| **多条读，必须同一 read view** | **保留** `readOnly = true` | 见 §3.1 |

> 反直觉点：**不是"读多就必须包事务"**。只有"**这几次读必须在同一瞬间**"才保留；
> 其余一律去事务——事务越少，连接占用与快照耦合越少。

## 五、典型模式库

| 场景 | 事务形态 | 为什么 | 真实类名 |
|---|---|---|---|
| 记录 + 计数同进同退 | `@Transactional` | 落一条记录与改一处计数必须原子，否则计数漂移 | `LikeService.likeContent` / `removeLikeContent`（内容 / 评论共 4 个写方法） |
| 关系行 + 双方计数 | `@Transactional` | 关注行与 follow / follower 计数必须原子；大V滞回判定在**同事务同连接**内（fail-atomic） | `FollowService.follow` / `unfollow` |
| 扣库存 + 插订单 | `@Transactional` | 白扣 / 超发都不可接受；唯一键撞键回滚即"库存只扣一次" | `CouponService.grabCoupon` |
| 插入 + 多处计数联动 | `@Transactional` | "评论在但计数没加"是静默脏数据 | `CommentService.addComment` |
| 校验占用 + 插入 | `@Transactional` | 先查后插必须原子 | `UserService.registerAsUser` |
| 整窗替换 + 写同步状态 | `@Transactional`（独立 bean） | 窗口与"已同步"标记必须同事务，否则读侧闸门误信陈旧窗口 | `FeedWindowWriter.replaceWindow` |
| 每批各自事务（大 fanout） | `@Transactional`（独立 bean，循环外调） | 逐批提交避免长事务持锁；重试可幂等重放 | `FeedInboxBatchWriter.insertBatch` / `insertBackfillBatch` |
| 编排自身无事务 | 无 | 编排跨多个 bean，事务落在**被调用的载体**里 | `FeedRebuildService.rebuildInbox`、`FeedInboxWriter.fanout`、`FeedService.getFeed` |
| 整表快照写入（一次扫描） | `@Transactional` | 每行一条 UPDATE，是一次"世界快照"的写入，须同进同退；中途失败不留"半轮扫描" | `MediaAuditService.scanAll` |
| 多条读需同源快照 | `@Transactional(readOnly = true)` | 信封的 `total` 与页内容同源 | `FeedPullReader.pullForPage` |
| 分块读需同一 read view | `@Transactional(readOnly = true)` | 跨块无时序偏差 | `FeedBigVRouter.isBigVBatch` |
| 单条读 / 独立多读 | 无事务 | 无原子性需求 | `CommentService.getRepliesForRoot`、`ContentService.search`、`FollowService.loadUserList` |
| 提交后副作用（缓存失效 / 投递） | `@TransactionalEventListener(AFTER_COMMIT)` | 见 §六 | `LikeService` → `LikeChangedListener` 等 |

## 六、提交后副作用

**唯一正确时机 = 事务提交之后。** 在事务内做缓存失效 / 消息投递的窗口里：并发读者可能按旧值回填缓存，
或事务回滚却已产生副作用。

本仓的统一手法：**在事务方法内 `publishEvent`，监听器标 `@TransactionalEventListener(phase = AFTER_COMMIT)`**
——事务提交才触发，回滚则**完全不触发**；`fallbackExecution` 保持默认 `false`（写路径一律在事务内发事件，
没有"无事务也要执行"的场景）。feed 域的两个实例（**只做指针**）：

- `ContentPublishedFeedListener`：订阅 `ContentPublishedEvent`，提交后投 `feed.push.content`（写扩散）。
- `FollowChangedFeedListener`：订阅 `FollowChangedEvent`，提交后投重建 / 降级补推。

> **机制语义（"谁声明、谁订阅"、`AFTER_COMMIT` 的精确语义、可见性上界、失败面）不在本篇，
> 见 [领域事件与解耦](./领域事件与解耦.md)。**

## 七、新代码检查清单

### 7.1 我要写一个"写操作"

1. **是不是"多条写必须同进同退"？** 是 ⇒ 加 `@Transactional`（单事务）。
2. **是不是"逐批 / 逐段各自提交"？** 是 ⇒ 把每批落库做成**独立 bean 的 public 方法**（跨 bean 调），
   不要在同类的循环里自调用。
3. **注解标在哪？** 标在**被跨 bean 调用的 public 入口**；若调用方与本方法**同类**，事务会静默失效——
   把载体抽出去。
4. **有没有提交后的副作用（缓存失效 / 投递 / 里程碑日志）？** 有 ⇒ **不直接调用**，改为在事务内
   `publishEvent` + 监听器 `AFTER_COMMIT`。
5. **方向**：缺原子性需求就别加事务；加了就说明"哪几条写必须一起成败"。

### 7.2 我要写一个"多查询读"

1. **这几次读必须在同一瞬间吗？**
   - 是（如 `total` 与页内容、分块 IN 列表）⇒ `@Transactional(readOnly = true)`，且**载体独立成 bean**。
   - 否 ⇒ **不加事务**。
2. **就一条 SELECT？** ⇒ 不加事务（不为"取连接"套事务）。
3. **读路径不写、不发事件**；缓存 miss 回源走各域 `Cache` 的既有口径（见 [缓存与数据一致性](./缓存与数据一致性.md)）。
