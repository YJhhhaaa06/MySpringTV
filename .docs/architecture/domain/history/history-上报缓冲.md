# 播放记录 —— 上报缓冲（服务端设计）

> 定位（先读这一句）：本篇是 `/report` **上报缓冲**这套机制的**唯一事实源** —— 为什么放 Redis、
> 键与原子性、落库与剪枝、失败姿态、读路径的新鲜度、已知代价。
> **不写**：域的基础结构（表 / 端点全集 / 时长 / 播放量）→ [history](./history.md)；
> 用户看到什么 → [history-需求](./history-需求.md)；客户端该怎么配合 → [history-客户端契约](./history-客户端契约.md)。
> 页面与词（播放页 / 观看会话 / 标签页）→ [history-术语表](./history-术语表.md)。
>
> **一句话**：`/report` 只写 Redis；**正常退出**（`/flush`）立即落库；**轮询只兜"没正常上报退出"的会话**。
> ★ **它不是降频手段** —— 请求数一条不减（鉴权 / 限流 / 内容校验照旧），挡掉的是 **DB 写**。
> 收益的准确表述 = **每次观看会话 1 次写库**（而不是每条心跳 1 次）。
>
> ★ **为什么独立成篇**：这一节自成一套机制（缓冲 / 落库 / 剪枝 / 故障姿态），与域的静态结构
> （表、端点、时长）耦合很松；而它自己被代码引用的密度最高，独立后引用能一指到底。

---

## 一、为什么缓冲在 Redis 而不是内存

`feed/mq/FeedDeliveryBuffer` 是**内存**态，应用重启即丢。本方案的缓冲必须跨"用户退出"活到
"轮询捡起"，用内存会让**每次重启丢掉全部崩溃会话的进度** ⇒ Redis。副产品：**应用重启不丢缓冲**。

## 二、两个 key（`CacheKeys` 自持，字符串冻结）

| key | 类型 | 内容 |
|---|---|---|
| `history:report:{userId}` | HASH | field = `contentId`，value = `"{progress}:{serverReceiveTs}"`（秒:毫秒） |
| `history:dirty` | ZSET | member = `userId`，score = 该用户**最后一次上报**的 `serverReceiveTs` |

- **`ZADD` 的 score 与 hash 里的 ts 必须同一时钟**（都取 App 侧 `serverReceiveTs`）；用 Redis `TIME`
  去比 App 时间戳会因漂移把"刚上报"判成"空闲"⇒ 提前落库（不致命）或永不落库（致命）。
- `history:report:{userId}` 的 **TTL = 30 分钟**（> 闲置阈值 60s + 轮询周期 15s + 最大滞留 10min）。
- ★ **为什么用 ZSET 而不是"扫 hash 判 mtime"**：`HTTL` 拿不到"最后一次写"，`HGETALL` 全库扫是 O(用户数)。
  ZSET 一条 `ZRANGEBYSCORE ... -inf now-W LIMIT n` 就同时回答了"谁脏"和"谁够闲"。
- ★ **`history:dirty` 刻意不带 TTL** —— 理由见 §4.1（"成员过期"不能靠 key 过期表达）。

## 三、三条写路径

```
① /report  ──(一次 Lua: HSET + EXPIRE + ZADD)──> Redis
② /flush   ──(HGETALL)──> 批量 ODKU ──> 条件删（Lua）   ← 退出信号，同步
③ 轮询     ──(ZRANGEBYSCORE now-W)──> 同一段②，但按批处理 ← 兜底，W=60s
```

- ★ **① 必须一条 Lua**：`HSET` 成功而 `ZADD` 失败（连接中途断）⇒ 数据在 hash 里但**不在 dirty 里**
  ⇒ 永远不会被轮询捡到，只能等 TTL 静默消失。反向（dirty 有、hash 空）是良性的（轮询空跑一次）。
- **②③ 共用同一段落库逻辑**（同一个方法），只是触发者不同 —— 否则两条路径的语义会漂移。

## 四、落库：**读 → 写 → 条件删**（不是"弹出 + 失败放回"）

```
1. HGETALL history:report:{uid}          // 不删
2. 批量 ODKU（显式 SET update_time = 缓冲里的 ts） // 一批一事务
3. 条件删（一次 Lua）：对每个 field，值**仍是**我们写出去的那个 ⇒ HDEL；hash 空 ⇒ DEL key + ZREM dirty
```

★ **为什么不"原子弹出 + 失败放回"**：弹出后到写库之间崩溃 ⇒ 数据**已经没了**，放回代码根本执行不到。
条件删则是**至少一次 + 幂等**（重复写的 ODKU 结果完全相同，因为 `update_time` 来自缓冲而非
`CURRENT_TIMESTAMP`）⇒ **崩溃只会重写，不会丢**。它还顺带解决了"放回覆盖新值"的问题：
期间有新上报 ⇒ 值已变 ⇒ **不删**，下一轮写新值。

★ **空快照也必须走一趟条件删**：脏成员可能对应一个**已经过期 / 被淘汰**的 hash（典型场景 = 应用停机
超过 `bufferTtl`，Redis 里的 TTL 照走，ZSET 却没有 TTL）。这种"僵尸成员"不清掉，会因 score 最老而
**每一轮都占满 `ZRANGEBYSCORE LIMIT` 的名额** ⇒ 真正待落库的用户永远取不到，兜底整体失效。

**失败分流**（照 `DeliveryOutcome` 三态的形状，不按失败次数判）：

| 类型 | 处置 |
|---|---|
| `TransientDataAccessException` / 超时 / 死锁 1213 / 连接类 | **不删**（自然留缓冲），下一轮重试 |
| `DataIntegrityViolationException` / `BadSqlGrammarException` | 整批失败后**逐条重试**，把该条摘出、记 ERROR 丢弃（真脏） |
| 滞留超过"最大滞留时长" | 丢弃 + WARN（防永久占内存） |

⚠️ **不许用批量 `INSERT IGNORE` 绕过整批失败**：单条 `IGNORE` 已记过这个坑（把列截断 / CHECK 失败也
降级成 warning ⇒ 静默丢弃，`history.md` §十 #12）—— 批量里用只是把坑放大 N 倍。
⚠️ **flush 的 SQL 只能改 `progress_seconds` + `update_time`，绝对不碰播放量账本 `content_play_dedup`**（`/play` 的唯一职责；`V10` 起 `watch_history` 已没有 `play_counted` 列）。
⚠️ **解析不了的值也必须进确认清单**：只丢弃不确认 ⇒ 那个 field 永远留在 hash 里 ⇒ `HLEN > 0`
⇒ 脏成员永远摘不掉（与"僵尸成员"同族，一个是 hash 侧、一个是 field 侧）。

### 4.1 剪枝：成员级 TTL（**不是**给 ZSET 加 EXPIRE）

轮询每轮先执行：

```sql
ZREMRANGEBYSCORE history:dirty -inf (now - bufferTtl)
```

★ **阈值可证，不是拍脑袋**：写入时 hash 的 `EXPIRE bufferTtl` 与 `score = ts` 是**同一次 Lua、同一个 ts**
⇒ **hash 的过期时刻 = score + bufferTtl**。所以"score 早于 `now - bufferTtl`"严格等价于"这条 hash 已经过期"
⇒ 剪掉的一定是**值已不在**的成员，不会误删还活着的进度。

★ **为什么不能改成"给 `history:dirty` 加 TTL"**：它是**全局单键** ——
① 每次 `ZADD` 续期 ⇒ 只要有一个活跃用户，key 就永不过期，僵尸成员照样留着（"看起来有 TTL"的假象比没有更糟）；
② 固定不续期 ⇒ 到期删掉**整个集合**，连活跃成员一起，周期性大面积丢数据。
"成员过期"与"key 过期"不是一回事，全局集合表达不了前者。

★ 它与 §四 的"条件删"是**两道防线**，不是重复：
- 条件删（正面）：僵尸被轮询**取到**时清掉；
- 剪枝（时间兜底）：不等被取到，按时间清掉 —— 防"轮询线程没起来 / 名额被挤占"，并省掉无用的 `HGETALL`。

★ **成本口径**：每 `pollInterval`（15s）一次 `ZREMRANGEBYSCORE`，O(log N + M)、N = 脏用户数
（本仓通常个位数）⇒ 约 **0.07 QPS**，且**不在请求路径上**。它在"僵尸少"时是纯支出（僵尸 score 最老，
下一轮必被取到、取到即清），换的是**停机 > `bufferTtl` 且僵尸数 > `idleBatchSize` 时**"60 轮 / 15 分钟盲跑"
→ **一条命令清完**（否则兜底静默停摆）。删除判据：Redis 成为瓶颈 / `pollInterval` 降到秒级以下 /
ZSET 成员数达十万级。

## 五、失败姿态

| 场景 | 行为 |
|---|---|
| Redis 熔断打开 / 不可达 | `/report` ⇒ **503 + `Retry-After`**；★ **熔断判定先于内容校验**（否则每个 503 先付一次 `loadContentVOs` 降级查库，正好违反"不碰 DB"） |
| `/flush` 落库失败 | **200**（数据还在缓冲，轮询兜底）；不返 5xx —— 客户端重试无益且放大流量 |
| 应用重启 | 缓冲在 Redis、不丢；轮询线程起来后照常接手 |
| Redis 进程重启（无持久化） | 缓冲全丢 = 这些会话回退到上次落库的进度（§七 #3） |

★ **部署前提**：缓冲与缓存**共用同一 Redis**，且该实例**不得设 `maxmemory` / 必须 `noeviction`**。
淘汰策略会**静默**杀掉缓冲（缓存丢了能重建，缓冲丢了是数据丢失）。代码看不见这件事，故启动时
`CONFIG GET maxmemory-policy` 自检：非 `noeviction` ⇒ WARN + 把策略打进启动日志
（托管 Redis 可能禁用该命令，容忍失败）。

## 六、读路径

| 端点 | 口径 |
|---|---|
| `/position` | **只点查 DB**。理由：`/flush` 成功后确认脚本的 `HLEN == 0` 分支会 `DEL` 该用户 hash ⇒ **正常路径读缓冲必然 miss**，等于白付一趟 `HGET`；崩溃续播改由客户端本地 `history:pending:{contentId}` 承担（初始化取 `max(服务端值, 本地值)` ⇒ [客户端契约](./history-客户端契约.md) §6.2） |
| `/list` | **不合并缓冲**。合并会打崩分页语义（`total` 算不算？排序键混用 ts 与 `update_time`）⇒ 崩溃会话刚看的新视频最多滞后 W 才进列表；★ **活跃会话（一直播不 flush）则一直不出现**（见 §七「跨设备可见性」） |

## 七、已知代价

| # | 代价 | 边界 / 推翻条件 |
|---|---|---|
| 1 | **崩溃 / 断网的会话**最多回退"闲置阈值 + 一次心跳间隔"的进度 | 只有这一条用户可见；正常退出延迟为 0。推翻 = 客户端能在本地持久化进度并重进补报（已写进客户端契约 §六） |
| 2 | 列表对崩溃会话最多滞后 W（60s） | 续播不依赖缓冲（`/position` 只读库）⇒ 崩溃会话的续播靠客户端本地 pending 补（[客户端契约](./history-客户端契约.md) §6.2）；**活跃会话不进列表**，见下方「跨设备可见性」 |
| 3 | **Redis 停机（无持久化）⇒ 缓冲全丢**；而**不做缓冲时同样故障下进度是落库的** ⇒ 故障期数据安全性**变差** | 这是本方案最硬的代价。缓解：`/flush` 已把"正常退出"摘出缓冲；只有"崩溃 + 同时 Redis 停机"才丢。推翻 = 换 Redis 持久化 / 独立实例 |
| 4 | 缓冲与缓存同实例，若配 `maxmemory` + `allkeys-lru` ⇒ 静默淘汰 | 启动自检只能告警，不能阻止；真要保证需独立实例 |
| 5 | DB 与缓冲存在**落后窗口**（两条读路径都看不到缓冲） | 崩溃续播靠**客户端本地 pending**（每秒更新的当前进度）补齐。★ **跨设备**：只有 `/flush`（暂停 / 退出 / 切页）才让 DB 变新 —— 见下方「跨设备可见性」，别把它写成"等 75s 就好" |
| 6 | `/flush` 是新非 GET 端点 ⇒ 限流权重表 +1、`SecurityContractTests` +1 | 加端点时必须同 commit 改（`history.md` §十一 迁移锚点段） |
| 7 | ★ **多设备 + 双方都未正常退出**时，设备 B 补报的旧值可能覆盖缓冲里设备 A 的新值（B 的补报基线取的是**落后**的库值 ⇒ `本地值 > 库值` 误判成立）⇒ 该会话进度**倒退** | 需同时满足：B 的本地 pending 未过期（30min）、A 的进度只在缓冲里（A 也没正常退出）。★ 本地 pending 是**每秒更新的当前进度**（不是上次上报值）⇒ 误判窗口从"一个上报间隔"收窄到"B 崩后到它重开之间 A 又看的那段"。单设备崩溃重开**不受影响**（本地就是最新值，且比 B站 更准 —— B站 实测杀进程后重开是从 0s）。推翻 = 出现跨设备续播的真实需求 ⇒ 恢复读缓冲并给 LWW 加单调守卫 |
| 8 | **每心跳一趟内容校验读**：`/report` 仍要走 `loadContentVOs` 判 404/400 + 取时长 clamp（1 趟 pipeline = 3 命令，缓存 miss 才查库） | 设计代价。去掉 = 改 404/400 契约；并入缓冲 Lua = 触碰他域 cache（ArchUnit 规则 2）⇒ **当前无合法省法**。推翻 = 出现真实上报 QPS 基线且 content 缓存命中率低 |

### 跨设备可见性（★ 别再把"活跃会话"算进兜底）

| 原设备状态 | 另一台设备何时看到最新进度 |
|---|---|
| 暂停 / 退出 / 切页（发了 `/flush`） | **立即** |
| ★ **一直在播、一直 `/report`、从没 flush** | **看不到**（不是"等 75s"）。缓冲里一直有新值，而每次上报都会把 `history:dirty` 里该用户的 score 刷成"刚刚" ⇒ **永远不满足"闲置 > `idleThreshold`"** ⇒ 轮询不捡他 ⇒ 另一台设备读到的是**上次落库的值**，可能落后整个会话。B站 实测约 **30s** 可见 ⇒ **本仓这一点弱于 B站**，是刻意的（对齐它要客户端定期 flush） |
| 崩溃 / 断网 / 关页但没发 flush（**停止上报**） | 约 **75s**（idle 60s + 轮询 15s）—— **这才是轮询兜的场景** |

★ 关键区别：轮询的判据是"该用户**停止上报**超过 `idleThreshold`"（`ZRANGEBYSCORE -inf now-60s`），
**不是**"缓冲里有数据"。持续上报会不断刷新 score ⇒ 活跃会话永远不会被兜底线程碰到。

★ 推翻 = 要让"正常播放中"的进度跨设备可见 ⇒ 客户端**定期 flush**（每 30~60s 一次；代价 = 每次会话
从 1 次 DB 写变成 N 次，抵消本方案的一半收益），或把落库触发从"闲置"改成"按时间轮转"（同样回到高频写）。
