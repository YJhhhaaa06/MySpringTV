# 播放记录 —— 客户端契约

> 定位（先读这一句）：本篇只规定**客户端（播放器）必须怎么做**，是前端接入播放历史时的**唯一事实源**。
> **不写**服务端怎么实现（→ [history](./history.md)）、**不写**用户看到什么（→ [history-需求](./history-需求.md)）。
> 页面与词的准确说法（播放页 / 历史记录页 / 标签页 / 观看会话）→ [history-术语表](./history-术语表.md)。
> ★ **状态：已实现（2026-10-25/26 前端重制第二窗口）** —— 新前端（`frontend/`）的播放页已接入本契约；
> 实现口径、代价与验证矩阵见 [客户端静默机制](../../frontend/客户端静默机制.md) §3.1~§3.4。
> 本篇仍是**唯一事实源**（数值与判据只在这里改）；旧 SPA（`static/`）已冻结、不参与。
>
> 读法：接入直接看 **§二（五个端点）+ §三（上报节奏）+ §四（退出信号）**；
> §六 是崩溃补偿（**最容易漏、后果最重**）；§九 / §十 是排错与自测。

## 一、为什么需要一份独立的客户端契约

服务端把"上报"与"落库"拆成了两条路径（`/report` 只进 Redis 缓冲、`/flush` 才落库、轮询兜崩溃会话）。
这个设计的成立**依赖客户端做对两件事**：什么时候上报、什么时候 flush。做错的后果是**不对称的**：

> ★ 本篇只用两个时间单位，别混：**一次观看会话** = 从打开播放页到关闭 / 切走（本篇所有节奏都按它算）；
> **一次播放** = 播放量口径里的"一人一次"，与打开几次无关（`/play` 幂等）。

| 客户端少做了什么 | 后果 |
|---|---|
| 不发 `/flush` | 进度**不丢**（还在缓冲里），但**不会被主动落库**：一直播就一直不落库；只有**停止上报**（崩溃 / 断网 / 关页）之后约 75s 才被兜底捡起 |
| 只发 `/flush`、从不发 `/report` | `/flush` 空转，**进度直接丢**（缓冲里什么都没有） |
| 用 `sendBeacon` 发退出信号 | **401**（带不了 `Authorization`）⇒ 静默丢 |
| 在 `timeupdate` 里上报 | 每秒几十次请求，被限流（权重 1，但仍会 429） |
| 503 不退避 | 服务端已经判定后端不可用，客户端还按原频率打 ⇒ 放大故障 |

**结论**：这些不是"实现细节"，是契约。所以本篇独立成文，并对每条给出**判据**（怎么判断做对了）。

## 二、客户端只用五个端点

| 端点 | 何时调 | 语义（对客户端） |
|---|---|---|
| `POST /api/v1/contents/{id}/play` | **开始播放时一次** | 播放量去重计数；幂等，重复调不报错 |
| `PUT /api/v1/contents/{id}/progress`（body `{"progress": N}`） | **播放中定期**（§三） | 只进缓冲；`progress` 单位**秒**，整数 |
| `POST /api/v1/history/flush` | **暂停 / 退出 / 切页**（§四） | 把**本用户全部**缓冲同步落库；无参数 |
| `GET /api/v1/contents/{id}/progress` | **播放器初始化** | `{progress}`；无记录返回 `0`，不 404 |
| `GET /api/v1/history?page=&pageSize=` | **历史记录页** | 分页；`pageSize` 默认 20、上限 100 |

- 写端点收 **JSON body**（`T59` 起）：只有 `PUT …/progress` 有字段 `{"progress": N}`，`/play`、`/flush` 无入参；
  token 一律走 `Authorization` 头。
- 全部端点**需要登录**（类级 `@RequiresLogin`）；未登录 ⇒ 401，不要拿 401 当"没有记录"。
- ⚠️ `/flush` **没有 `contentId` 参数**：它写的是该用户缓冲里的**全部**内容。所以"退出时要落库最后一段进度"
  必须先 `/report` 再 `/flush`（§四.2 的顺序问题）。

## 三、上报节奏

| 项 | 取值 | 依据 |
|---|---|---|
| 间隔 | **30~60s** | 与缓冲的兜底窗口（默认 60s）同量级；更密没有收益（DB 写已被缓冲挡住）；更疏只让"服务端 / 其它设备"看到得更旧，**不影响本机崩溃续播**（那条由 §6.1 的本地每秒进度兜住） |
| 触发点 | 定时 + **暂停** + **进度跳变**（拖动进度条） | 暂停与拖动是"用户主动停在这里"，值得立刻报 |
| 单位 | 秒（整数） | 服务端 `progress_seconds` |
| 上限 | 超过时长会被服务端 clamp，**不报错** | 客户端不必自己做边界判断 |

★ **不要**在 `timeupdate` 里逐帧上报 —— 那是每秒几十次。`timeupdate` 只用来更新 UI 与本地缓存。

★ **与服务端缓冲是叠乘关系**：客户端每 60s 一条 ⇒ 服务端 60s 内 N 个用户各 1 条（Redis 写），
DB 只在 flush / 兜底时写一次。所以客户端**不需要**为了"省数据库"而调更稀。

## 四、退出信号（最容易写错的一段）

### 4.1 用 `fetch keepalive`，**不是** `sendBeacon`

```js
fetch('/api/v1/history/flush', {
  method: 'POST',
  keepalive: true,                        // ★ 页面卸载后仍会把请求发完
  headers: { 'Authorization': 'Bearer ' + token }
});
```

- ⚠️ **`navigator.sendBeacon` 带不了 `Authorization` 头**（它只支持简单请求），而本仓 token 只走该头
  ⇒ 用它必然 401 ⇒ 退出信号静默丢失。这是本篇最重要的一条。
- `keepalive` 的约束：请求体 ≤ 64KB（本端点无 body，无所谓）、必须 `POST`。

### 4.2 顺序：先 `report` 再 `flush`（否则最后一段进度要等兜底）

`/flush` 只写"缓冲里已有的值"。若最后 30s 的进度只在客户端、还没 `/report`，直接 flush 会漏掉它。

```js
// 推荐：在页面还活着的时候做（visibilitychange → hidden）
async function onHidden(finalProgress) {
  try { await report(finalProgress); } catch (e) { /* 忽略：下面 flush 仍会写缓冲里的旧值 */ }
  fetch('/api/v1/history/flush', { method: 'POST', keepalive: true, headers: authHeader });
}
```

- **为什么用 `visibilitychange(hidden)` 而不是 `pagehide`/`beforeunload`**：`await` 在页面真正卸载时不可靠；
  `visibilitychange → hidden` 时页面还在，第一次请求通常能完成，第二次用 `keepalive` 兜底。
- ⚠️ **两个 `keepalive` 请求之间的顺序没有保证**。若 flush 先到、report 后到：
  flush 写的是旧值，report 留下一条新脏数据 ⇒ 该用户被重新标脏 ⇒ **兜底窗口后落库**。
  **最终一致，但"退出即落库"退化成"最多延迟一个兜底窗口"**（§八 #2）。
- ★ 若将来要消除这个竞态，最小改动是让 `/flush` 接受可选的 `contentId` + `progress`（先写缓冲再 flush）。
  **当前契约没有这个参数**，所以客户端应按 4.2 的顺序发、并接受上述退化。

## 五、503 退避与恢复

服务端在 Redis 不可用时对 `/report` 返回 **503 + `Retry-After: <秒>`**（不降级直写库）。

```js
// 建议的客户端状态机
let interval = 45_000;          // 正常节奏
let degraded = false;

async function tick() {
  const resp = await report(progress);
  if (resp.status === 503) {
    degraded = true;
    const wait = Number(resp.headers.get('Retry-After') || 30) * 1000;
    interval = Math.max(wait, 30_000);       // 按服务端给的节奏退避
  } else if (resp.ok && degraded) {
    degraded = false;
    interval = 45_000;                       // ★ 必须有恢复条件
  }
}
```

- ★ **必须有恢复条件**：只降不升 ⇒ 后端恢复了客户端还在按 5 分钟一次上报，进度长期落后。
- **不要自己叠指数退避**：`Retry-After` 已经是服务端"自己多久重试一次"的节奏，客户端跟随它即可。
- **不要放弃上报**：503 期间的进度仍在本地；恢复后正常上报会覆盖。放弃 = 永久丢失（§八 #3）。
- 503 **不是**"内容不存在"：不要跳转到错误页，静默降级即可。

## 六、崩溃补偿（本地标记）

进程被强杀 / 断电时，`visibilitychange` 来不及执行 ⇒ 最后一段进度只在本地。

### 6.1 写什么

```js
// per-content，不是一个全局 flag：多个标签页、多个视频并存
// ★ 由 timeupdate 驱动：**每秒最多写一次**（不要每帧），值 = 播放器当前秒数
localStorage.setItem(`history:pending:${contentId}`, JSON.stringify({ progress, ts: Date.now() }));
```

- ★ 它存的是**本地当前进度**（每秒更新），**不是"最后一次上报的进度"** —— 与 `/report` 的节奏解耦：
  `/report` 成功既不改变它、也不删除它。
- 在 `/flush` 返回 200 后删除（此时服务端已拿到至少这个值）。`ts` 是**最后一次更新**的时刻；
  过期（> `bufferTtl`，默认 30m）说明该会话早已结束，丢弃即可。
- ★ **为什么每秒写、而不是只在上报时写**：崩溃丢失的窗口从"一个上报间隔（30~60s）"缩到 **≤1s**，
  且重开时的定位基线是"崩溃瞬间的真实位置"而不是"30s 前上报的那个值"。
  `localStorage` 是同步 API，每秒一次远低于它的可用频率 —— 但**仍然不要**放进 `timeupdate` 的每帧路径（节流到 1s）。

### 6.2 重进时怎么补

```js
// 播放器初始化：先定位播放头，再补报（R-20：服务端只读库 ⇒ 必须由本地 pending 补齐）
async function resume(contentId) {
  const server = await position(contentId);               // 只认已落库的值
  const local  = readPending(contentId);                  // 本地**当前**进度（每秒更新，最多落后 1s）；>30min 丢弃
  const start  = Math.max(server, local?.progress ?? 0);  // ★ 本地更新就用本地

  if (local && local.progress > server) {                 // 本地更新 ⇒ 补报落库（补的是**本地最新**，不是上次上报值）
    await report(local.progress);
    await flush();
  }
  if (local) localStorage.removeItem(`history:pending:${contentId}`);   // 补报失败会抛错跳过这行
  return start;                                           // 播放头从这里定位，补报后不必再 seek
}
```

★ **为什么不能只用 `/position` 定位**：`R-20`（2026-10-22）起它**只读 DB**（不读上报缓冲）。
崩溃 / 没发 flush 的会话，新进度还在本地 ⇒ 直接拿 `position` 的返回值定位会**退到旧位置**。
本地 `pending` 是"每秒更新的当前进度"，取 `max` 即可补齐，且不依赖服务端缓冲。

★ **为什么比较的是"本地最新"而不是"上次上报值"**：上报每 30~60s 才一次，拿上报值当基线会把
"最后 30~60s 看的这段"整段算丢（例如崩溃在 640s、上次上报是 600s ⇒ 只能补到 600）。
用每秒更新的本地值 ⇒ 补到 640，误差 ≤1s。

★ **为什么 `start` 必须在补报之前算好**：补报**不会**回头改已经定位的播放头。
顺序写成"补报完再定位"也能得到同样的 `start`，但多等两个请求；写成"定位后不再 seek"最省。

★ **为什么要与服务端值比较**：多设备场景下本地可能是旧值（在另一台设备看到更后面）。
不比较就补报会**把别处的新进度覆盖成旧的**（服务端是"后到即新"，不做进度单调守卫）。
这是本仓刻意的 LWW 口径（`history-需求.md` §六），客户端必须自己让路。

> ⚠️ `R-20` 之后这道比较的基线是**库值**（而不是缓冲值）⇒ "多设备 + 双方都未正常退出"时仍可能误判
> （见 [history-上报缓冲](./history-上报缓冲.md) §七 #7）。单设备崩溃重开不受影响。

★ **续播位置什么时候是精确的**（回答"用户会不会看到倒退"）：

| 场景 | 重开 / 续播拿到的位置 | 差多少 |
|---|---|---|
| 正常播放，客户端没崩 | **本地最新值**（`max` 取本地） | ≤1s |
| 单设备崩溃 + 补报成功 | **本地最新值** | ≤1s |
| 崩溃 + 补报失败（503 / 断网） | 已落库的值 | 最多一个兜底窗口（约 75s） |
| 换一台设备（本地无 pending） | 已落库的值 | 取决于原设备是否 flush 过 |
| 两台设备都在播同一视频 | 以**最后上报**的为准（LWW） | 可能互相拉回 |

> ★ 参考：B站 实测"电脑播几秒 → 任务管理器杀 Chrome → 重开"也是**从 0s 开始**
> ⇒ 崩溃会话的续播精确度不是行业硬指标，本仓（本地每秒更新 + 补报）实际**比它更准**。

★ **为什么补 `report + flush` 而不是只补 `flush`**：缓冲的 TTL 是 30 分钟。超过后服务端缓冲已经没了，
只发 flush 是空转；而"用本地进度重报 + flush"两种情况下都正确，且幂等。

## 七、读路径预期（客户端可以假设什么）

| 场景 | 客户端能期望的 |
|---|---|
| 打开播放器读 `/position` | **已落库的值**（`R-20` 起不读缓冲）。崩溃 / 未 flush 的会话要靠 §6.2 的 `max(服务端, 本地)` 才拿得到最新进度 —— **这是客户端义务，不是服务端保证** |
| 刚上报的条目出现在 `/list` | **正常退出立即**（flush）；★ **一直在播就一直是旧值**（未落库，列表不合并缓冲）；崩溃 / 断网后约 **75s** |
| 崩溃后重进同一个浏览器 | 若做了 §6.2 的定位 + 补偿 ⇒ **精确（≤1s）**；没做 ⇒ 已落库的值（最多滞后约 75s） |
| **另一台设备**查同一个视频的进度 | 原设备**暂停 / 退出 / 切页** ⇒ 立即（`/flush`）。★ **一直播不暂停 ⇒ 看不到** —— 轮询只兜"**停止上报**"的会话，持续上报会一直把这些用户挡在 `idleThreshold` 之外（[上报缓冲](./history-上报缓冲.md) §七「跨设备可见性」）；只有原设备**崩溃 / 断网 / 关页没发 flush** 才在约 **75s** 后可见。B站 实测约 **30s** 可见 ⇒ 本仓这点弱于它 |
| 崩溃 + Redis 停机 | 该会话进度**可能回退**到上次落库的位置（[history-上报缓冲](./history-上报缓冲.md) §七 #3） |
| 同一浏览器的**两个标签页**同看一个视频 | 列表里**只有一行**；进度以**最后上报的那个标签页**为准（LWW） |

★ **初始化顺序建议**：`resume()`（§6.2：`position` + 本地 pending 取 `max` + 必要的补报）→ 定位播放头
→ `play`（首播计数）→ 开始定时 `report`。
`play` 与 `position` 谁先都行，但 `play` **不要**放在"播放了几秒之后"（那会漏计只看一眼就退出的播放量）。

## 八、错误码处理表

| 状态 | 客户端应该做什么 | **不要**做什么 |
|---|---|---|
| 200 | 正常路径；`/flush` 时清除本地 pending 标记（若仍在播，§6.1 会在下一秒重新写入 —— 那是新的未落库进度） | — |
| 400「播放进度不能为负数」 | 修 bug（进度计算错误） | 重试 |
| 400「只能记录视频的播放进度」 | 停止对该内容上报（图文没有进度） | 循环重试 |
| 401 | 视为未登录（token 过期 ⇒ 走刷新/登录） | 当成"没有记录" |
| 404「内容不存在」 | 停止上报该内容 | 重试 |
| 429 | 按常规退避（限流，见 `限流.md`） | 立即重试 |
| 503 | 按 `Retry-After` 降频（§五），**恢复条件 = 收到 200** | 降级成"不再上报" / 跳错误页 |

★ 400 / 404 都是**不该重试**的（重试必然同样失败）；503 / 429 才是可重试的。

## 九、做错会怎样（不对称后果，按严重度）

| # | 错误 | 可见后果 | 是否可自愈 |
|---|---|---|---|
| 1 | `sendBeacon` 当退出信号 | 401 静默丢 ⇒ 关页即"停止上报" ⇒ 约 75s 后被兜底捡起 | 部分（兜底） |
| 2 | 只发 `flush` 不发 `report` | 退出时缓冲为空 ⇒ **最后一段进度丢** | 否 |
| 3 | 503 后放弃上报 | 故障期进度**永久丢** | 否 |
| 4 | 崩溃补报不看 `position` | 覆盖别处更新的进度 | 否（用户会看到"进度跳回"） |
| 5 | `timeupdate` 逐帧上报 | 请求风暴 + 429 | 是（改代码） |
| 6 | 不发 `flush` | 进度**不进列表**（一直播就一直不落库）；停止上报后约 75s 才被兜底捡起 | 是（兜底，但要等停止上报） |

★ **#2 / #3 / #4 是"永久丢"**，其余都是延迟或可修。排在前面的三个值得在实现时专门测。

## 十、前端自测清单（实现后逐条跑）

1. 播放 5 分钟：`/report` 约 5~10 次，**DB 里 0 行**（缓冲生效）。
2. 点暂停 / 关标签页：一次 `/flush`，DB 有行，`progress` 等于最后看到的秒数。
3. 强杀进程（任务管理器）：等待一个兜底窗口后 DB 有行。
4. **强杀进程后立刻重开**：播放头从崩溃前的位置继续（误差 ≤1s），**不是从 0s、也不是从上次上报值** ——
   验 §6.1 的每秒本地进度 + §6.2 的 `max`。（B站 实测是 0s，本仓的目标比它高。）
5. 关掉本机 Redis：`/report` 连续 503 且带 `Retry-After`；客户端间隔变大；Redis 起来后**回到原间隔**。
6. 同一浏览器的两个标签页同看一个视频：`/list` 只有一行。
7. 断网 2 分钟再恢复：进度不倒退（本地 pending 生效）。
8. 换一台设备看到更后面，再回到旧设备：**旧设备的补报不能覆盖新进度**（§6.2 的 `position` 判断）。
9. **另一台设备趁这边在播时查同一个视频**：这边暂停/切页后另一台立即看到；如果这边**一直在播、从没 flush**，另一台**看不到**（§七「跨设备可见性」）。
