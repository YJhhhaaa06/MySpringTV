## ① ［一致性］历史不可删 / 不可清空 —— **已推翻**（来源：`F-27`①，2026-10-21 接受，2026-10-30 转台账，2026-10-31 由 `R-26` 推翻）

- **What（当时牺牲了什么）**：用户不能管理自己的观看记录。根源是**播放量计数与历史行共用一张表**：
  `/play` 判首播靠 `watch_history.play_counted` 置 1，而播放量要求
  `content.play_count == COUNT(watch_history WHERE play_counted = 1)` 可复算 ⇒ 删掉一行，计数与人次就对不上。
- **Why（当时为什么接受）**：B站 删历史**不减**播放量，所以"删行 + 扣播放量"是错的方向；
  要正确删除，必须先把"计过数的人次"挪出历史行 —— 那是一张新表 + 一次口径重定，值不当期做。
- **推翻（2026-10-31）**：`R-26` 把去重证据搬进账本 `content_play_dedup`（`V10`），顺带把口径改成
  "每人·每内容·每自然日一次"（原口径一行只能存一个标记，本身就是"每天一次"的障碍）。
  于是 `DELETE /api/v1/history` 只删 `watch_history`、**碰不到账本** ⇒ 删历史不减播放量、也不重复计。
- **残留**：`R-26` 的用法与残留代价（不回填 / 无清理 / 并发复活）在下面 ②③④ 三条。

## ［容量与成本］`watch_history` 与账本都无容量上限、无旧行清理（来源：`F-27`④，2026-10-21 拍板，2026-10-30 转台账）

- **What**：牺牲了"存储与行数的硬边界"。`watch_history` 一人一内容一行，只增不减（用户删才减）；
  `content_play_dedup` 一人·一内容·**一天**一行，增长比前者更快（∝ 活跃天数）。两者都没有 TTL / 淘汰 / 保留最近 N 条。
- **Impact**：影响面：表体量与列表翻页深度。直观现象：老用户的历史能一直翻到底（B站 行为）。
  红线提示：账本**只有"今天"的行有约束力**，更早的行按语义永远无用 ⇒ 将来清理**不改语义**；
  但一旦清理，`play_count == COUNT(账本)` 就只能对"清理之后"成立。
- **When**：常态存在，增长上限 = 用户 × 内容 ×（历史：1；账本：活跃天数）。本仓无真实流量 ⇒ 目前只是理论成本。
- **Why & Mitigation**：放弃"按时间清历史"（会删掉用户的"看过"证据，且与 `total` 语义耦合）与
  "按条数清"（要新增计数列 / 定时任务）。账本清理**留了后路**：`idx_date` 只服务
  `WHERE play_date < ?`，真要做按 `tools/devclean/` 的一次性运维脚本形态做，**不引入常驻定时任务**。

## ［一致性］「记录开关」只由客户端遵守，服务端写路径不校验（来源：`R-25`，2026-10-31 拍板）

- **What**：牺牲了"这个承诺有服务端兜底"。`users.history_recording` 只被 `GET /users/me` 读、被 `PUT /users/me/history-recording` 写；`/play`、`/report`、`/flush`、轮询兜底**一个都不看它**。用户 2026-10-31 在 Chrome 重放上报请求实测：**B站 是服务端强制的** ⇒ 本条是**刻意偏离**，不是"没做到"。
- **Impact**：影响面：任何绕过前端的调用（curl / 缓存里的旧前端 / 将来的第二客户端）仍会写历史并计播放量。直观现象：本仓唯一客户端遵守 ⇒ 界面上承诺成立。红线提示：**别把它当漏做去补**——服务端要拦**四个落库口**（`/play` / `/report` / `/flush` / 轮询兜底），其中轮询兜底**没有用户请求可拦**，漏一个就静默破功。
- **When**：只在"绕过前端的调用方"真的出现时疼；本仓当前为零。
- **Why & Mitigation**：收益为 0（没有第二客户端）而成本是持续的：`/report` 是设计上最高频的写，每次多读一次开关（DB 点查，或为极低频的写建一条热路径缓存）。推翻条件写死：**出现第二个客户端或公开 API ⇒ 必须改成服务端校验**；届时的最小改法是"读一次开关 + 四个口子逐个加守卫"，并补"轮询兜底"的用例。

## ［一致性］关闭开关期间不计播放量（来源：`R-25`，2026-10-31 拍板）

- **What**：牺牲了"播放量只由内容侧决定"。关闭期间客户端**连 `/play` 也不发** ⇒ 这段观看不产生任何播放量。
- **Impact**：影响面：`content.play_count` 与全站排行口径；个人设置会影响公共统计（每人每内容最多少计 1）。直观现象：无 —— 用户看到的是"开关说什么就做什么"。图文不受影响（本来就没有 `/play` 路径）。
- **When**：有人在关着开关看长尾内容时才明显；本仓无真实流量 ⇒ 纯理论。
- **Why & Mitigation**：播放量的去重证据当时**只长在 `watch_history` 那一行上**（`uk_user_content`），不建行就没有去重载体；而"偷偷建一行 0 秒"会让开关变成谎话（用户能在列表里看见）。
  ★ 2026-10-31（`R-26`）后账本已存在，技术上可以"只记播放量、不建历史行" —— 但**没有这么做**：
  关闭开关的语义是"不记录"，而播放量是公共统计，改它属于产品口径变更（不是技术顺手）。
  推翻条件：产品决定"关掉记录也照常计播放量" ⇒ 客户端恢复发 `/play`、服务端只写账本不建行。

## ② ［一致性］播放量口径变更后**存量与新值不可比**（来源：`R-26`，2026-10-31 拍板）

- **What**：`content.play_count` 的历史值是"一人一次"口径、`V10` 之后是"每自然日一次"口径，
  而账本**不回填** ⇒ 同一个数字在跨版本对比里**含义不同**。也不再有"绝对可复算"：
  `play_count == COUNT(账本)` 只对 `V10` 之后**新建**的内容成立，存量内容多出一个"历史余额"。
- **Impact**：影响面：排行 / 卡片播放量角标的时间序列对比、以及"播放量是否虚高"的直觉。
  直观现象：无 —— 单看一个数字看不出来。红线提示：**别拿它做跨版本报表**；
  `HistoryWriteTests` 之类的新用例只对"夹具新建内容"用绝对等式，老内容用增量等式。
- **When**：有人跨版本比对播放量、或要求"账本必须能精确复算历史值"时。
- **Why & Mitigation**：回填 `DATE(watch_history.update_time)` 可行但**写的是假日期**
  （`update_time` 是"最后上报时间"，不是"计数的那个自然日"），而账本一旦掺假，
  "计过数的人次"这个唯一用途就不可信了。代价换来的收益是：账本每一行都**真**是某天计过数。
  推翻条件：出现"必须跨版本精确复算"的硬需求 ⇒ 先决定是接受假日期回填，还是接受口径断层写进报表。

## ③ ［一致性］删除与上报并发时，那条可能"复活"（来源：`R-26`，2026-10-31 拍板）

- **What**：删除的顺序是"先删库、再清缓冲"。两个窗口都会让那条重新出现：
  ① 删除期间到达的 `/report`（心跳）会写回缓冲 ⇒ 下一次 flush 落库；
  ② 正在播放的另一个标签页，下一次开播（`/play`）也会无条件重建历史行（这是**有意**的：页面在播、列表里却没有它才是 bug）。
- **Impact**：影响面：历史页的"删除"按钮。直观现象：删完几十秒后又出来（很窄，需要同设备另开标签在播）。
  红线提示：**别把它当缺陷去加分布式锁**——要彻底堵，得给内容记"删除墓碑"（用户级 + 内容级 + 时间窗），
  代价远大于收益。
- **When**：只在"一边删、一边还有会话在播同一个视频"时。单标签正常使用不会遇到（历史页与播放页不同时开）。
- **Why & Mitigation**：与 B站 一致（它也是"再看一次就回来"），而且语义上站得住：历史的本义是"最近看过"。
  对冲：删除后前端**同时清本地 `history:pending:{contentId}`**，避免"重进播放页 → 从旧位置续播 → 立刻重建"。

## ④ ［容量与成本］账本行数无界（见上方"容量与成本"条，这里只留一句）

- `content_play_dedup` 一行 = 某人某天给某内容计过一次数；**只有"今天"的行有约束力**
  ⇒ 清理是纯容量优化，漏跑不改语义。本仓不清理（`R-26`③），真要做走 `tools/devclean/` 运维脚本。
