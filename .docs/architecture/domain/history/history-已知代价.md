## ［一致性］历史不可删 / 不可清空（来源：`F-27`①，2026-10-21 拍板，2026-10-30 转台账）

- **What**：牺牲了"用户能管理自己的观看记录"这个能力。根源是**播放量计数与历史行共用一张表**：`/play` 判首播靠 `watch_history.play_counted` 置 1（`UPDATE … WHERE play_counted = 0`），播放量则要求 `content.play_count == COUNT(watch_history WHERE play_counted = 1)` 可复算 —— 删掉一行，计数与人次就对不上。
- **Impact**：影响面：历史页（不渲染删除 / 清空按钮，见 GAP-19）、`/play` 的判首播语义。直观现象：用户找不到"删一条 / 清空"的入口；已删除内容的行仍留在列表里做失效占位。红线提示：若要做删除，**必须先**把"计过数的人次"从 `watch_history` 里解耦（独立计数表或计数列），否则同一内容再播会被判"首播"、播放量重复 +1。
- **When**：常态存在（能力缺口，不是偶发）。真要做时，复杂度不在 `DELETE` 本身，而在"删完还要保证播放量只增且可复算"。
- **Why & Mitigation**：放弃"删行 + 同时扣播放量"（B 站是删历史不减播放量，扣了反而与它的口径不一致）。对冲方案：内容被删时行仍保留（失效占位，`R-18` 口径"历史不可删"）；清空需求若真出现，届时先补"计过数人次"的独立载体，再开放删除 —— **不要**在 `watch_history` 上直接 `DELETE`。

## ［容量与成本］`watch_history` 无容量上限、无旧行清理（来源：`F-27`④，2026-10-21 拍板，2026-10-30 转台账）

- **What**：牺牲了"存储与行数的硬边界"。一人一内容一行，行数增长 ∝ 用户 × 看过的内容，只增不减；没有 TTL、没有淘汰、没有"只保留最近 N 条"。
- **Impact**：影响面：`watch_history` 表体量与 `/history` 列表的翻页深度。直观现象：老用户的历史能一直翻到底（这是 B 站的行为，也是本域的刻意对齐）；磁盘随观看量线性增长。红线提示：若出现真实规模（单表行数让 `/history` 的 `total` 或翻页成本变成问题），本条须先被推翻。
- **When**：常态存在，但**增长有界**（用户数 × 内容数，且内容总量本身有界）；本仓无真实流量 ⇒ 目前只是理论成本。
- **Why & Mitigation**：放弃两种清理方式 —— **按时间**清理会删掉用户的"看过"证据（也就要连带解决上一条的播放量解耦）、**按条数**清理要新增计数列 / 定时任务，并与列表 `total` 的语义耦合（"第 501 条开始看不见" 是产品决定，不是技术决定）。对冲方案：读路径靠 V8 覆盖索引 + 分页（`T50`：5k 行 3.15→0.10 ms）；真要清理时按 `tools/devclean/` 的一次性工具形态做，**不要**引入常驻定时任务。

## ［一致性］「记录开关」只由客户端遵守，服务端写路径不校验（来源：`R-25`，2026-10-31 拍板）

- **What**：牺牲了"这个承诺有服务端兜底"。`users.history_recording` 只被 `GET /users/me` 读、被 `PUT /users/me/history-recording` 写；`/play`、`/report`、`/flush`、轮询兜底**一个都不看它**。用户 2026-10-31 在 Chrome 重放上报请求实测：**B站 是服务端强制的** ⇒ 本条是**刻意偏离**，不是"没做到"。
- **Impact**：影响面：任何绕过前端的调用（curl / 缓存里的旧前端 / 将来的第二客户端）仍会写历史并计播放量。直观现象：本仓唯一客户端遵守 ⇒ 界面上承诺成立。红线提示：**别把它当漏做去补**——服务端要拦四个口子，其中轮询兜底**没有用户请求可拦**，漏一个就静默破功。
- **When**：只在"绕过前端的调用方"真的出现时疼；本仓当前为零。
- **Why & Mitigation**：收益为 0（没有第二客户端）而成本是持续的：`/report` 是设计上最高频的写，每次多读一次开关（DB 点查，或为极低频的写建一条热路径缓存）。推翻条件写死：**出现第二个客户端或公开 API ⇒ 必须改成服务端校验**；届时的最小改法是"读一次开关 + 四个口子逐个加守卫"，并补"轮询兜底"的用例。

## ［一致性］关闭开关期间不计播放量（来源：`R-25`，2026-10-31 拍板）

- **What**：牺牲了"播放量只由内容侧决定"。关闭期间客户端**连 `/play` 也不发** ⇒ 这段观看不产生任何播放量。
- **Impact**：影响面：`content.play_count` 与全站排行口径；个人设置会影响公共统计（每人每内容最多少计 1）。直观现象：无 —— 用户看到的是"开关说什么就做什么"。图文不受影响（本来就没有 `/play` 路径）。
- **When**：有人在关着开关看长尾内容时才明显；本仓无真实流量 ⇒ 纯理论。
- **Why & Mitigation**：播放量的去重标记 `play_counted` **就长在 `watch_history` 那一行上**（`uk_user_content`），不建行就没有去重载体；而"偷偷建一行 0 秒"会让开关变成谎话（用户能在列表里看见）。备选方案（为"计过数的人次"建独立载体）与[历史删除](./history-已知代价.md)的前置条件是**同一件事** ⇒ 等真要开放删除时一起做，不在本窗为它加表。
