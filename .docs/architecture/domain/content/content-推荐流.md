# 内容推荐流（首页无限加载）

> 定位（先读这一句）：本仓的「推荐」**不建画像、不算热度、不做召回排序** —— 它是一个
> **按会话随机、可稳定翻页的内容流**。本篇只讲它的**序、游标、失败口径与代价**。
> 缓存三态 / 降级 / 熔断 / 单飞等横切机制不在本篇（→ [缓存与数据一致性](../../tech/cache/缓存与数据一致性.md)、[韧性](../../tech/resilience/韧性.md)）；
> 分页与载荷的契约规则见 [接口契约](../../tech/api/接口契约.md) §2.6。需求号 `R-28`。

---

## 一、口径与边界

一句话：**把全站内容按"一次会话的一个随机排列"切成页，翻页不重不漏，翻完即止。**

**是**：

- 序 = `rank(seed, contentId)` 降序；`seed` 在每次"会话"随机生成一次；
- 翻页用**游标**（上页末条 id），不用页码、不返回总数；
- 候选池 = 内容域既有的类型 / 分区索引（Redis LIST），**不新建池**。

**不是**（刻意不做）：

| 不做 | 理由 |
|---|---|
| 用户画像 / 协同过滤 | 没有行为数据规模，做出来也是假的；"随机"至少是真的随机 |
| 热度加权 / 排行榜 | 需要热度计算与窗口口径，是另一个能力；本机制的输入只有 id |
| 给新内容加权曝光 | 要加权就得把 `create_time` 放进池子、并把它冻结进游标（否则两页之间内容"变新鲜"会重排）；见 §四 代价 2 |
| 启动时全量预热池子 | 池子有懒重建自愈（[缓存与数据一致性](../../tech/cache/缓存与数据一致性.md) §2.4 已把"启动全量预热"定为永不实现）；预热不是正确性来源 |
| 每用户私有队列 | §三 |

内容类型：推荐流**同时含视频与图文**（与 B站 移动端一致）。视频页侧栏"只放视频"是**前端**的过滤，服务端不为此加特例。

## 二、机制

### 2.1 池子：复用既有索引

候选池就是内容域的类型 / 分区索引，键为 `content:index:{type}:{cid}`（`-1` = 通配维度）；
一条内容进 **4 个** key，其中 `content:index:-1:-1` 是全量 id。维护已有两条路径，本功能**不新增任何写入**：

- 发布 / 编辑：`ContentCache#refreshContent` → `pushFront`（LREM 去重后 LPUSH）；
- 删除 / 下架：`ContentCache#removeContent` → `removeIdFromAllIndexes`（LREM）。

索引缺失时由 `ContentCache#ensureIndex` 懒重建（单飞 + 冷却退避），本功能直接复用。
`type` / `categoryId` 参数只是换一个 key，不改变算法。

### 2.2 排序函数

```
rank(seed, id) = mix64(seed ^ mix64(id))

mix64(z):                                  // splitmix64 finalizer
  z = (z ^ (z >>> 30)) * 0xbf58476d1ce4e5b9L
  z = (z ^ (z >>> 27)) * 0x94d049bb133111ebL
  return z ^ (z >>> 31)
```

三个性质（都是可验证的，不是"应该"）：

1. **纯算术**：只依赖 `long` 运算 ⇒ 跨 JVM、跨进程、跨版本一致。**不用** `Object.hashCode` /
   `Random` / `ThreadLocalRandom` 做排序键 —— 它们的实现细节不构成契约。
2. **`mix64` 是 64 位双射**（异或右移可逆、乘数为奇数）⇒ `id ↦ rank` 单射 ⇒ **同一池内不会并列**，
   不需要 id 兜底排序。
3. 换 seed 即换排列；同 seed 同池 ⇒ **同一个序**（与"这一页恰好返回哪几条"无关 —— 那还取决于哪些内容还有效）。

### 2.3 游标：为什么不是页码

格式：`v1.<seed>.<lastId>`，三段十进制，`<lastId>` = 上一页**最后一条返回项**的 id。

| 段 | 含义 | 作用 |
|---|---|---|
| `v1` | 格式版本 | 换排序算法时递增；旧游标**自动降级为第一页**（不会给出错序） |
| `seed` | 本次会话的随机种子（31 位正整数） | 重建同一个排列 |
| `lastId` | 上页末条 id | 下一页从 `rank < rank(seed, lastId)` 开始 |

**页码（offset）在这里不成立**，两条独立的理由：

1. **随机序没有"第 2 页"**。若每次请求重新随机（而不是用 seed 复算同一排列），两页就是两个独立排列，
   重叠条数的期望 = `k² / N`（k = 每页条数，N = 池子大小）—— N=30、k=12 时是 **4.8 条**。
2. **即使固定 seed，offset 也会漂**。池子增删会让位次整体位移 ⇒ 翻页重复 / 漏项；
   而游标锚在 **id** 上，`rank` 只依赖 id 本身，与"池子里还有没有它"无关。

由此得到一条关键性质：**上页末条即使已被删除，游标照样精确** —— 服务端不需要那条内容存在。

三条纪律：

- **不透明**：客户端只回传，不解析、不拼装；服务端不校验签名。
- **伪造无害**：改成任意值最多得到"另一个随机序的某个位置"——不越权、不泄露、成本与普通请求相同。
- **非法即缺省**：少段 / 非数字 / 版本不认识 ⇒ 当作没传游标（返回第一页）。这是**静默归一**口径
  （与 `PageParams#normalizeCursor` 同一纪律：分页参数错只是少几条，不返 400）；但游标是字符串，
  解码在本功能自己的纯函数里，不复用那个只认 `Long` 的方法。

### 2.4 取页

```
1. 解游标：无 → seed = random(31 位), lastId = 0；有 → 取 seed / lastId（非法 → 按无处理）
2. 读池 + 去重 → 候选 id 集（N 条）
3. 过滤：lastId != 0 时只留 rank(seed, id) < rank(seed, lastId)
4. 按 rank 降序遍历，**分块**批量读内容（如 32 条/块），跳过"确认无数据"的 id，凑满 pageSize+1 或候选耗尽
5. nextCursor：取满 pageSize+1 → 截到 pageSize，游标 = v1.<seed>.<本页末条 id>；取不满 → null
```

四条不变量（测试就钉这四条）：

| # | 不变量 |
|---|---|
| 1 | **`nextCursor == null` ⇔ 候选已耗尽**（短页也意味着到底）。前端只在 `null` 时停止 |
| 2 | **同一游标 + 池子未变 ⇒ 同一个序**（纯函数）⇒ 重试安全；池子变了只会"少几条 / 多几条"，不会错位 |
| 3 | **"还有没有下一页"靠多取一条判定**：能取到 `pageSize+1` 条有效内容 ⇒ 有下一页；取不满 ⇒ 到底。不靠"本页不满"去猜 |
| 4 | 空页**只可能**出现在候选耗尽时（第 4 步会继续扫，不会因为一块全是脏 id 就返回空） |

删除与新增在会话中的表现：

| 事件 | 对序的影响 | 对游标的影响 |
|---|---|---|
| 内容被删（池子已 LREM） | 其余 id 的 rank 不变 | 无（游标不依赖它存在） |
| 内容被删（LREM 失败留脏 id） | 同上 | 无；第 4 步跳过该 id |
| 新内容发布 | 新 id 的 rank 随机 | 落在游标之后 → 本次可见；之前 → 本次不可见。**永不重复** |

### 2.5 参数与响应

| 参数 | 缺省 | 上限 | 说明 |
|---|---|---|---|
| `cursor` | 无 = 新会话 | — | 上页返回的 `nextCursor` 原样回传 |
| `pageSize` | **20** | **50** | `PageParams#normalizePageSize` 归一；非数字 / ≤0 静默回落 |
| `type` | 无 = 不过滤 | — | **数字** 1=视频 2=图文（既有口径） |
| `categoryId` | 无 = 不过滤 | — | 0..9；语义越界仍 400（既有口径） |

响应是**信封**（形状只此一种，不带参数也是它；Java 侧 = 新 VO
`RecommendPageVO { List<ContentVO> list; String nextCursor; }`，即 `data` 节点）：

```json
{ "list": [ { "id": 1042, "type": 1, "title": "…" } ], "nextCursor": "v1.739201.1042" }
```

- `list` 与 `PageResult` / `CursorResult` 同名，前端不需要第三套读法；
- **不返回 `total`**：随机流的"总数"没有业务含义，给了就是假精确；
- `limit` **不是**本端点的参数（传了不生效），分页一律用 `pageSize`。

### 2.6 失败口径

| 失败 | 表现 | 依据 |
|---|---|---|
| 池读失败（`CacheUnavailableException`） | `{list: [], nextCursor: null}`，**200** | 索引读失败降级为空推荐（既有口径） |
| 内容读 Redis 失败 | `CacheAside` 内部降级直查 DB，结果照常 | [缓存与数据一致性](../../tech/cache/缓存与数据一致性.md) §4.1 |
| DB 失败 | 上抛 500，**不吞成空页** | 同上：读不到 ≠ 没有 |
| 游标非法 | 当作没传，返回第一页 | §2.3 |
| `type` / `categoryId` 语义越界 | 400 + 原文案 | 既有口径 |

★ **空列表只可能来自三处**：池子真的空、池子里的 id 全部失效（删除时 LREM 失败且内容已全没）、
池读失败。三者在客户端都表现为 `nextCursor: null`（前端停止）—— 这是有意的：
**不把基础设施故障暴露成可区分的 UI 状态**，与"翻到底"同一个收尾动作。

## 三、与"每用户私有队列"的取舍

| 维度 | A 每用户私有队列 | B 随机函数序（**本文档**） | C 每日固定 seed |
|---|---|---|---|
| 服务端状态 | 每活跃用户一条 LIST + TTL | **无** | 无 |
| 跨页不重复 | 队列存活期间成立 | **恒成立**（rank 单调） | 当日成立 |
| Redis 重启 / evict / 过期 | 游标（下标）失效 ⇒ **重复** | 无影响 | 无影响 |
| 匿名用户 | 需先有稳定的匿名身份 | **不需要身份** | 不需要身份 |
| 两个标签页 | 互相踩（队列被另一页重建） | 各自独立 | 各自独立 |
| 新内容可见性 | TTL 内为 **0**（不在队列里） | 按剩余比例随机插入 | 次日 |
| 「换一换」 | 重建队列 | 换 seed | **不可用** |
| 每页成本 | O(pageSize) | O(N) | O(N) |

**不采用 A 的三条理由**（不是"它做不到"，是"代价与收益不成比例"）：

1. **顺序进了 TTL 缓存**：队列一旦被重建，游标指向另一套排列 ⇒ 跨页重复。
   这撞 [缓存与数据一致性](../../tech/cache/缓存与数据一致性.md) §七 取舍 1「缓存只作加速器」——
   排序是**正确性**，缓存是**加速器**，两者不能混。
2. **匿名要额外一套身份**。A 并非不能服务匿名：服务端可以签发匿名 id（cookie / 设备 id）当队列 key。
   代价是要多一套**签发 / 过期 / 清缓存即丢 / 跨设备不认**的身份体系，只为给"翻页"找个 key；
    B 从根上不需要任何身份。
3. **建队列的并发**：两个标签页同时首屏会各自建、互相覆盖；想同时满足"刷新要看到新内容"与
   "多标签不互踩"，只能"每标签页一条队列"⇒ 要给每个标签页发会话 id（连登录用户也要），
   与第 2 条是同一类代价：**为了翻页引入一个身份域**。

**A 该被重新考虑的条件**（这是它的适用面，不是排期）：**顺序必须被冻结** —— 运营插位、
A/B 分组、跨设备"这次不重复"。三者都不在本机制的输入里；真出现时应该新开一个"编排层"，
而不是把随机序改造成队列。

**C 是退路**：`seed = 天数`，零新参数、游标只需一个 id。代价是「换一换」失效、所有人同一序、跨日游标失效。

## 四、已知代价与推翻条件

| # | 代价 | 什么时候疼 | 推翻条件 / 正确动作 |
|---|---|---|---|
| 1 | **每页 O(N)**：一次 `LRANGE 0 -1` + O(N) 算 rank + O(N log N) 全排序（N 小时比 Top-K 更不容易写错） | 池子到 10⁴ 起开始可测；10⁵ 不可接受 | 池子 > 5×10⁴ 或 P99 > 20 ms ⇒ 改**预排序分桶**（不是改每用户队列：那是 O(用户×N) 内存）；排序本身可先换 Top-K |
| 2 | **新内容不保曝光**：与其它内容同权随机 | 发布者期待"发完就能在首页看到" | 若"发布后 X 分钟内首页可见"成为硬需求 ⇒ 首屏拼一段"最新"（按 `create_time` 倒序，**独立区块**），并把时间水位冻结进游标；不要混进随机序 |
| 3 | **刷新 / 换标签页 = 新序**：会话不跨刷新保留 | 用户回退后想接着看 | 需要"回退保序"⇒ 前端把 `list + nextCursor` 存进模块级 store（不涉及服务端） |
| 4 | 游标可伪造 | 无 | 不处理：伪造只换一个随机序，不越权不泄露 |
| 5 | **无 `total` / 无页码** | 想显示"共 N 个"或跳页 | 不做：随机流没有稳定总数，页码在随机序里无意义 |
| 6 | 换排序算法必须升 `v1`，旧游标回第一页 | 发版那一刻 | 一次性"回到开头"，写进发版说明；比"静默错序"好 |
| 7 | **脏 id 多时一页要扫很深**：为凑满 `pageSize+1`，可能连续读穿多块（32 条/块） | 删除时 LREM 长期失败 / Redis 故障期 | 脏 id 占比长期偏高 ⇒ 先修删除路径（`removeContent` 的自愈 DEL），而不是加大块大小 |

## 五、契约

| 项 | 口径 |
|---|---|
| 端点 | `GET /api/v1/contents/recommended` —— **改造既有路由，不新增端点** |
| 入参 | `cursor`（可选）/ `pageSize`（缺省 20、上限 50）/ `type` / `categoryId` |
| 出参 | `data = { list, nextCursor }` |
| 分页形状 | 游标信封；[接口契约](../../tech/api/接口契约.md) §2.6 的判据是"**offset 不可靠**（顺序不稳定或深翻成本高）"，不限于深翻 |
| 类型 / 分区 | 数字口径（1=视频 2=图文 / 0..9）保持不变；语义越界仍 400 |
| 鉴权 | 公开；带 token 时按面填充互动态（`{关注}`），匿名 `interaction: null` |

**第二个消费方：视频页侧栏（相关推荐）**。它取**第一页**、排除当前视频、只留视频、取 6 条，
**不传游标** ⇒ 每次进页面都是新随机序。这条规则意味着"相关推荐其实是随机"——
要真正相关（同分区优先、服务端排除自己）应新开 `GET /api/v1/contents/{id}/related?limit=`，
那是另一个产品语义、另一条契约，不要把它塞进本端点。

## 六、验证锚点

**纯函数（不起 Spring）**

| 用例 | 判据 |
|---|---|
| 同 `(seed, id)` 反复调用 rank 相同 | 纯函数 |
| 10⁵ 个连续 id 的 rank **两两不同** | 双射 ⇒ 无并列 |
| 不同 seed 的排列不同 | 换 seed 有效 |

**HTTP（真实入口）**

| 用例 | 期望（业务口径推导，不抄实现） |
|---|---|
| **翻完全部页** | 收集到的 id 集合 == 池子集合，且**无重复**（独立 oracle：直接读索引 key 比对） |
| 相邻两页 | 交集为空 |
| 游标指向**已删**内容 | 下一页不重不漏（先记下游标，再删该内容，再请求） |
| 池中有**脏 id**（索引里留着、内容已无） | 该 id 不出现，且本页仍**填满** pageSize |
| 空池 | `{list: [], nextCursor: null}`，200 |
| 池读失败（打桩 `readIds` 抛 `CacheUnavailableException`） | 200 + 空，不 500 |
| `pageSize` 归一 | 缺省 20 / 上限 50 / 非数字回落；`limit` **不识别**（仍按 `pageSize`） |
| 非法游标 | 返回第一页（与不带游标同集合，顺序可不同） |
| 同游标请求两次（池子不变） | 结果逐字节一致 |
| 池子恰为 `k × pageSize` | 最后一页**恰好** `pageSize` 条且 `nextCursor == null`（不多给一个空页） |

**判别力来自反向验证**（三条都实测，`RecommendFeedTests` 10 例 + `RecommendOrderTests` 4 例）：

| 注入 | 实测结果 |
|---|---|
| 去掉 §2.4 第 3 步的游标过滤 | **5 红**：翻完全部页 / 相邻两页 / 整除边界 / 脏 id / 游标删除 |
| 把 `pageSize + 1` 退化成 `pageSize` | **6 红**：以上 5 条 + 同游标两次一致（游标永远为 null ⇒ 两次请求各自新 seed） |
| 把 rank 换成 `mix64(id)`（不看 seed） | **3 红**：`RecommendOrderTests` 的基准值与「换 seed 换排列」+「不带游标换一换」 |

⚠️ **两条容易误以为能抓、其实抓不到的注入**（别把它们写进验收）：
`id.hashCode()` 在 `1..10⁵` 上仍然两两不同（该区间 `hashCode == id`），"两两不同"抓不到它；
同理"同一表达式调两次"对纯函数几乎没有判别力。要抓"排序键不看 seed"，只有「换 seed 换排列」；
要抓"rank 被收窄成 32 位"，才用大样本的"两两不同"（生日问题，10⁵ 样本期望约 1 次碰撞）。
