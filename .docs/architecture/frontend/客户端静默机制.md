# 客户端静默机制（用户看不见、浏览器一直在跑）

> **定位**：本篇记录**没有界面、但一直在跑**的客户端行为 —— 播放进度上报与自动重试、
> 退出信号、崩溃补偿、乐观更新与对齐、幂等键、登录态时序、限流感知、本地存储边界。
> 每条给**四要素**：触发 / 做了什么 / 代价 / 怎么验（判据能变红吗）。
> **不写**：播放进度的节奏与退避**数值**（唯一事实源 = [history-客户端契约](../domain/history/history-客户端契约.md)
> §二~§九）、限流算法（→ [限流](../tech/rate-limit/限流.md)）、幂等算法（→ [写接口幂等](../tech/idempotency/写接口幂等.md)）、
> 页面形态与端点矩阵（→ [前端](./前端.md)）。
> **状态**：2026-10-25/26 前端重制第二窗口落地；本篇是这批行为的**实现口径与代价台账**，
> 契约类数值仍以各自事实源为准。

---

## 一、为什么这些行为要单独成篇

它们有一模一样的性质：**界面上没有任何地方能证明它做对了**。三类失败，用户都先"看不出"：

| 失败类别 | 例子 | 用户多久才会发现 |
|---|---|---|
| **静默丢数据** | 只在 `timeupdate` 里上报、退出不发 `flush` ⇒ 最后一段进度丢 | 下次打开时"怎么退回 30 秒前" |
| **静默多写** | 每次请求新生成幂等键 ⇒ 超时重试发出两条评论 | 刷新后才看到重复 |
| **静默吃额度** | 401 也照常上报、503 不退避 ⇒ 自己的令牌桶被打空 ⇒ 别的操作 429 | 表现为"这破站老提示太频繁" |

所以它们的**唯一有效防线**是：契约写死数值（→ history-客户端契约）、纯逻辑单测钉住规则、
真浏览器 E2E 钉住"真接口下行为成立"。截图与人工点按**验不了**这一类。

> ★ 一条通用判据：**这条行为去掉之后，界面会变吗？**
> 不会 ⇒ 它必须进本篇，并且必须在 §五 的验证矩阵里有归属（有覆盖，或**明写没覆盖**）。

## 三、逐条

### 3.1 播放进度上报：事件 → 动作的**唯一**接线表

| DOM 事件 / 时机 | 做什么 | **不**做什么 |
|---|---|---|
| `loadedmetadata` | 有续播位置就 `currentTime = start`，提示一次 | 不在此刻上报 |
| `play`（首次） | `POST /contents/{id}/play` **一次** + 启动 45s 定时器 | 不重复发 `/play`（后端去重，但前端也不该打） |
| 定时器 45s | `PUT /contents/{id}/progress` | 不与 `timeupdate` 挂钩 |
| `pause` | **立刻** `PUT` 一次 + `POST /history/flush` | 播完触发的 `pause` 交给 `ended` 处理（否则 flush 两次） |
| `seeked` | 立刻 `PUT` 一次（"用户主动停在这里"） | 不在 `seeking` 里发（拖动中会连发） |
| `timeupdate` | **只**写 `localStorage`（节流 1s/次） | ★ **绝不**发请求（契约 §三 的红线：每秒几十次） |
| `ended` | 最后一次 `PUT` + `flush` + 清本地标记 + 停定时器 | — |
| `visibilitychange → hidden` | `PUT`（页面还活着，能 await）→ `finally` 里 keepalive `flush` | 不用 `sendBeacon` |
| 组件卸载 / 切内容 | 若在播：`PUT` + keepalive `flush`，然后摘监听 | 不 await（页面正在走） |

**代价**：进度最多落后 45s 才落库（缓冲 TTL 30m 兜底）；每次装载多 1 个 `GET /progress`（未登录则 0 个）。
**怎么验**：契约数值在 [history-客户端契约](../domain/history/history-客户端契约.md) §十 有自测清单；
本仓实现由 `player/progressReporter.test.ts`（18 例）+ `.tmp/progress-e2e.mjs` 覆盖。

### 3.2 退出信号：`fetch(keepalive)`，不是 `sendBeacon`

`navigator.sendBeacon` **带不了 `Authorization` 头**（只支持简单请求），而本仓 token 只走该头
⇒ 用它必然 401 ⇒ 退出信号静默丢失。这是契约 §4.1 点名的头号坑。

- 顺序：**先 `PUT` 再 `flush`** —— `flush` 只写"缓冲里已有的值"，最后 30s 只活在客户端时直接 flush 会漏。
- 两个 keepalive 请求**之间顺序无保证**（Web 平台不保证），所以最坏退化成"最多晚一个兜底窗口"——**接受**。
- 该路径走**裸 `fetch`**，不走 `api/http.ts`：那层带 15s `AbortController`，在卸载路径上会把请求 abort 掉。

**怎么验**：`.tmp/progress-e2e.mjs` 覆盖"暂停即落库"（正常退出），`visibilitychange` 路径为**代码形式保证**，
headless 下难以断言"请求真的发出去了"——**明写没自动覆盖**（§五.3）。

### 3.3 崩溃补偿与续播基线

- 每秒写 `history:pending:{contentId} = {progress, ts}`（**不是**"上次上报的值"）⇒ 崩溃丢失窗口从 45s 缩到 ≤1s。
- 装载时 `start = max(已落库, 本地最新)`；**本地更旧时不许补报**（服务端 LWW，会把别处的新进度覆盖成旧的）。
- 本地比服务端新 ⇒ 先 `PUT` + `flush`，**成功后**才删标记（失败就留着，下次再补）。
- 标记 30 分钟过期（= 缓冲 TTL）：过期说明会话早已结束，丢弃。

**代价**：`localStorage` 同步写，每秒一次（远低于可用频率，但**不能**放进每帧路径）；多标签同看同一视频时
两个标签抢写同一个 key（后写赢，最终一致）。

**怎么验**：`progressReporter.test.ts` 的 `planResume` / 本地标记两条；E2E 验"重开定位到 00:05"。

### 3.4 自动重试：全仓**只有**进度上报持有它

| 输入 | 行为 | 理由 |
|---|---|---|
| `503` / `429` + `Retry-After: N` | 下一次间隔 = `max(N × 1000, 30s)`，并提示"降频" | `Retry-After` 就是服务端"多久后再来"的节奏；**不自己叠指数退避** |
| `503` / `429` **无** `Retry-After` | 保持原节奏 | 不瞎猜一个数 |
| 网络失败（status 0）/ 5xx | 保持原节奏 | 进度还在本地，恢复后覆盖 |
| **收到 200** | ★ 立刻回到 45s 并清降级 | **只降不升 = 进度长期落后**（契约 §五 明确要求有恢复条件） |
| `400` / `401` / `403` / `404` | **停止上报** | 重试必然同样失败；继续打只会把 429 也刷出来 |

**代价**：降频期间进度更旧（但仍在本地）；`30s` 下限是刻意的（服务端说 5s 不等于我们该 5s 一次）。
**怎么验**：`progressReporter.test.ts` 用假定时器钉住"45s→503→30s→200→45s"与"404 停报"；
**E2E 未覆盖**（要停本机 Redis，会污染其它用例的前提）。

### 3.5 写入动作为什么**不**自动重试

点赞 / 投币 / 收藏 / 关注 / 发评论**都不带重试循环**，失败就回滚 + 说人话。判据三条：

1. **不知道服务端做没做**：网络超时时请求可能已生效（NATURAL 端点重试安全，但响应丢了下一次点击就是
   "用户的新意图"，不是"重试"）；
2. **重试会变成"程序在连点"**：`409 IDEMPOTENCY_IN_PROGRESS` 带 `Retry-After: 1`，但自动重试会把
   "用户手快"静默升级为持续的请求风暴；
3. **用户在场**：写按钮是用户主动点下去的，失败提示 + 一次回滚足够；进度上报不同——它没有用户在场盯着。

**代价**：网络抖动时用户要自己再点一次。
**怎么验**：无正面测试（"没有重试"很难断言），靠代码审查 + E2E 里的失败分支（本金不足 / 限流）。

### 3.6 幂等键的两种生命周期（**刻意不同**）

| 端点 | 键的生命周期 | 依据 |
|---|---|---|
| `POST /comments` | **草稿级**：按下发表时取，**同一草稿的重试复用**；草稿一改就作废 | 失败后果**无界**（重复评论没有上限），必须让服务端能认出"同一次意图" |
| `POST /contents/{id}/coins` | **调用级**：每次调用新键 | 失败后果**有界**（同一条内容最多两枚，超出后端 `COIN_ALREADY_FULL`）⇒ 不值得为它维护意图级状态 |

**已接受的代价**：投币在"其实成功了但客户端没收到"的场景下重试会多投一枚（上限两枚）。
**不做**：把键生成放进请求层自动加 —— 那会掩盖"这个端点要不要幂等"这个业务判断（4 条 `KEYED` 之外带键无意义）。

**怎么验**：评论的"草稿级"复用**没有自动化覆盖**（组件内状态机，E2E 也没造"超时后重试"场景）——
§五.3 明写。

### 3.7 乐观更新三段式（少一段就出"假状态"）

1. **乐观**：先改本地（按钮立刻亮、计数 ±1）——否则每次点击都要等一个 RTT；
2. **回滚**：失败把本地改回去（且回滚到"这次动作之前"，不是"取反"）；
3. **对齐**：写成功后**重读服务端权威值**（详情 / 资料 / 列表页），因为登录瞬间、另一台设备、
   别人同时点赞都会让本地值过期。

★ 真实踩坑：**登录那一刻页面会并行重读一次资料**（读到的是"关注前"的状态）。只做 1+2 的实现在
E2E 里表现为"点击关注成功了，按钮却还写关注"（服务端 `isFollowed=true`）。必须在成功路径补第 3 段。

**代价**：每个写操作多 1 个读请求（限流令牌 +1）。
**怎么验**：`.tmp/space-e2e.mjs` STEP2 断言"服务端 `isFollowed=true` 且按钮=已关注"；互动/收藏同理。

### 3.8 登录态恢复的时序（"我是谁"必须先落定）

- `restoreSession()` **单飞**：并发调用复用同一个请求。入口文件与页面组件都会调它，
  不合并不等于"多打一次 `/users/me`"，而是**白花一枚限流令牌**，每次进应用。
- ★ **凡是用到"我是谁"的装载，必须 `await restoreSession()` 再发**：
  `isSelf`（空间页）、`canDelete`（评论）、`isFollowed`（关注按钮）都依赖它。
  抢在它之前装载的真实后果：看自己的空间被画成"关注自己"（点了后端回 `FOLLOW_SELF`）、
  自己的评论没有删除按钮。
- **token 过期**（401/403）⇒ 清 token 退化为匿名，并把 `interaction` / `followed` 置回 `null`（三态），
  **不**保留"看起来登录了"的假状态。

**怎么验**：E2E 覆盖了"登录后空间页无关注按钮"与"自己的评论可删"；
`restoreSession` 的**单飞**没有单测（§五.3）。

### 3.9 限流感知：说清"等多久"，而不是假装没发生

本仓限流**曾经**咬到正常操作：2026-10-25 本窗口 E2E 实测"首屏 + 连续三个写操作就 429"（当时登录桶 `20 枚 / 2 枚每秒`）；
2026-10-26 用户把登录桶提到 `200 / 10`、匿名 `600 / 30`（**数值以 `application.yaml` 的 `video.rate-limit.user.*` 为准**，
本篇不复制配置）。结论不变：**429 是正常路径上会发生的事**（缓存 miss `×3` 放大单次成本、突发连点仍会撞），
所以前端必须能说清"等多久"，而不是假设它不会发生。

- 429 文案吃 `Retry-After`：`操作太频繁了，N 秒后再试`（通用错误映射在 `http.ts#describeError`）。
- 页面级错误态给「重试」按钮（429 / 网络 / 5xx 都是**瞬态**），不给"回首页"了事。
- **不**自动重试（§3.5）；**不**在降级时静默（降频提示会弹一次）。

**代价**：用户会看到频率提示（这是真实约束，藏起来只会让人以为坏了）。
**怎么验**：E2E 里"撞限流→等 8s 重试"是真实路径；文案出现在互动 / 评论 / 空间三处。

### 3.10 本地存储只有两个 key（**故意的**）

| key | 归属 | 为什么必须存在 |
|---|---|---|
| `myspringtv.token` | `auth/token.ts`（唯一落点） | 后端是 `Authorization: Bearer`，不是 Cookie；刷新后要能不重新登录 |
| `history:pending:{contentId}` | `player/progressReporter.ts` | 崩溃补偿：强杀进程时最后 ≤1s 的进度只在本地 |

**不加第三个**：列表 / 详情 / 评论 / 收藏夹**一律不做本地缓存**。理由是它们都有服务端缓存与
`ETag` 级别的成本控制，前端再存一份只会引入"两份数据不一致"与"清理时机"两个新问题
（本仓无真实流量，收益为 0，代价是 bug 面）。

> ⚠️ 别把它当"轻量离线方案"：没有 Service Worker、没有请求排队、没有后台同步（§六）。

## 四、失败模式对照表（这些机制坏掉时，界面**不会**立刻告诉你）

| 坏掉的地方 | 界面上的表现 | 真实后果 | 谁会发现 |
|---|---|---|---|
| 不发 `/play` | 无 | 播放量不涨 | 看计数的人（半可见） |
| 只 `flush` 不 `report` | 无 | 最后一段进度**永久丢** | 用户下次续播"倒退" |
| `sendBeacon` 当退出信号 | 无 | 退出信号 401 静默丢 ⇒ 晚 ≈75s 才落库 | 换设备看历史 |
| 503 不退避 | 无 | 故障期请求风暴，放大后端故障 | 后端日志 |
| 退避无恢复条件 | 无 | 进度长期落后（界面不报错） | 跨设备可见性变差 |
| 本地 pending 不清/不清对 | 无 | 每次重开都"补报"旧进度，可能覆盖别处新进度 | 多设备用户 |
| 三态 `null` 归一成 `false` | 按钮显示"关注"（看起来**正常**） | 点一下反而可能取消关注 / 后端 409 | 用户迷惑，极难复现 |
| 幂等键每请求新生成 | 无 | 超时重试多发评论 | 刷新后看到重复 |
| 登录态没先落定 | 短暂显示"关注自己" | 后端 `FOLLOW_SELF` 报错 / 自己的评论不能删 | 眼尖的用户 |
| 429 只说"请求失败" | 报错 | 用户反复点，越点越糟 | 用户投诉"这站老出错" |

| 脚本 | 覆盖的静默行为 |
|---|---|
| `progress-e2e.mjs` | 真播 → 暂停即 report+flush → 库里 progress/playCount 变化 → 重开定位 → 播放中每秒写 pending |

### 5.3 ★ 目前**没有**自动化覆盖（下个窗口可补，别当成已验）

1. **幂等键"同一草稿重试复用"**（组件内状态机；E2E 没造"超时后重试"场景）。
2. **`restoreSession` 单飞**（并发调用只打一次 `/users/me`）。
3. **`visibilitychange` 退出信号真的把请求发出去了**（headless 下请求可发，但"卸载后仍发完"难断言）。
4. **组件卸载时的收尾上报**（`teardown(finalize)` 路径）。
5. **"写操作不自动重试"**（这是个"没有"的断言，只能靠审查 + 失败分支 E2E 间接看）。

> 补法建议：1/2/4 可以不做 DOM 测试 —— 把状态机再抽一层纯函数即可（键生命周期、单飞计数、收尾上报的决策），
> 3 用 CDP 的 `Network.requestWillBeSent` 观察卸载后是否发出。

## 六、已知边界与"刻意不做"

| 不做 | 为什么 | 若要推翻 |
|---|---|---|
| Service Worker / 离线队列 | 本仓无真实流量；离线补偿会引入版本化、清理与调试成本，收益为 0 | 有真实弱网用户数据 |
| 跨标签页协调（同一视频两个标签） | 现状是 `localStorage` 后写赢、服务端 LWW；契约 §七 已登记"列表只有一行" | 有"多标签同看"的真实需求 |
| 后台自动重试写操作 | §3.5 的三条判据 | 出现"弱网下写失败率高"的数据，且能接受重复写 |
| 前端本地缓存列表/详情 | §3.10 | 服务端缓存失效导致明显卡顿 |
| 把静默行为暴露成 UI（e.g. "同步中"角标） | 与 B 站一致：这些不该占界面 | 用户明确要求可见 |
