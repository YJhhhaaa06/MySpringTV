## 二、为什么不复用 `favorite_folder` 放"稍后再看"

稍后再看与收藏**是两个语义**（B 站 也是两个独立入口、两个按钮）。一旦共表（哪怕加一个 `folder_type` 列）：

- `/favorite/status`（`isFavorited`）、`/favorite/count`、`/favorite/folder/list`、`/favorite/folder/public`
  **全部**要加"排除稍后再看"这一条过滤；
- **漏一处即静默错答案** —— 那正是"**收藏按钮状态异常**"的来源（本仓已有 F-04 ~ F-09 一整批"冗余/口径不一致"的债，别再主动再造一个同类）。

⇒ **独立表后收藏侧一行不改**，污染在结构上不可能发生。

## 三、容量上限（口径 = **配置常量**，不进 schema）

| 项 | 值 | 说明 |
|---|---|---|
| 默认夹内容上限 | **5000** 条 | 每用户至多一个默认夹 |
| 自建夹内容上限 | **500** 条 | |
| 自建夹**个数**上限 | **20** 个 | 默认夹不计入 |

- 落在 `video.favorite.*`（`@ConfigurationProperties`，与本项目既有配置类同款，见 `FavoriteLimitProperties`）。
  三个键是**扁平键**（`default-folder-max-items` / `custom-folder-max-items` / `custom-folder-max-count`），
  且**必须为正**：键名/前缀写错时原生 `int` 绑定**不报错、只给 0**，而 0 会把每次新增都判 400
  ⇒ 构造器**故意让它响亮失败**（上下文起不来），不留"看着在跑、其实全 400"的静默态。
- ⚠️ **"多少条"数的是 `favorite_item` 行**（**含已失效条目**）—— 与 `FavoriteFolderVO#itemCount`
  及 `/favorite/list` 的 `total` **同一口径**；别一个口径数"内容"、一个口径数"行"
  （那会得到两个都"对"但互相矛盾的数）。
- ⚠️ 数字是**刻意砍小的演示值**：B 站 实测为 默认夹 5 万 / 单夹 1000 / 自建夹 99，且**官方未公示**
  （需求篇 §六 早写明"别直接照抄"）。
- 超限 ⇒ **400**（与"改名空 / 格式非法 → 400"同族）。**判定点**：`createFolder`（个数）·
  `addItem`（目标夹）· `moveItem`（**目标夹** —— 漏它就能"绕道 move 把夹撑爆"）；
  `remove` / `deleteFolder` / `updateFolder` 不在判定面上。
  ⚠️ **默认夹的懒建不在判定面上**：个数只数自建夹、条数只看目标夹。若 20 上限误拦懒建，
  该用户会**再也收藏不了任何东西**且**不自愈**（唯一出路是删一个自建夹），并重演 I-08 那个
  "前端占位行永远建不出来"的互锁 ⇒ 已由用例钉住（满 20 个自建夹的新用户不选夹收藏仍 200）。
- ★ **重名 = 允许**（B 站实测确认）：**刻意不加** `(user_id, name)` 唯一键，同名夹是合法状态
  ⇒ 这也是 `FURTHER_ISSUES.md` **F-11** 里"是否拒重名"那个问号的答案；T16 只补契约测试钉住它
  （结构侧由 `FavoriteSchemaTests` 的"索引全集"断言守着：加键即红）。

### 三.1 超限 400 与 403/404 的先后：**按类型分家**（2026-10-14 拍板）

- **参数型 400**（夹名空 / 超长 / `isPrivate` 格式非法）**先于** 403/404 —— 既有惯例，
  理由两条：参数校验**不碰库**；且"非法输入 ⇒ 400"不随资源状态漂移。
- **状态型 400**（**容量超限**）**后于** 403/404 —— 容量是**资源状态**（必须查库，且要知道是哪个夹），
  若提前判，别人的**已满**夹 ⇒ 400、别人的**未满**夹 ⇒ 403 ⇒ 就成了"**可区分他人夹满/未满**"
  的探测口（私密夹的夹内尺寸一并被侧面暴露），而且要对**非本人**的夹发计数查询
  —— 与本仓"归属先校验、再按 id 写"的既定纪律相反。
- ⇒ 两类各按自己的理由排序，**不是**把"400"当成一个整体去排名次。
  用例钉住：往**他人已满的夹** add ⇒ **403（不是 400）**。

### 三.2 它是**软上限**（用户 2026-10-14 拍板）

- 判定是 `COUNT → INSERT` 两步、**非原子** ⇒ **真并发**下会越界：越界量 ≤ **并发通过检查的请求数**
  （19 个夹 + 8 并发 ⇒ 最多 27 个），且**越界后自限**（此后所有新增/新建一律 400，不会再涨）；
  **顺序重试不会越界**（每次都重新 COUNT）。危害 = 软上限被瞬时突破并长期停在越界态（只能删夹回落），
  **不是数据损坏，也不能被放大**。
- ★ **读路径不因"越界"做任何隐藏或限制**：越界的夹照常出现在列表里、照常打得开
  —— "软"体现在**写入侧不管死**，**不**体现在读取侧撒谎。
- ⚠️ **为什么不加锁**（完整论证在 `FavoriteLimitProperties` 类注释）：
  ① **RR 快照陷阱** —— 快照建立在事务内**第一条普通读**上，锁若晚于它，其后的 COUNT 仍读旧快照，
  即"**锁在、但不生效**"且**无任何报错**，后人一挪位就**静默重开**窗口；
  ② **本域没有可锁的常驻行** —— `favorite_folder` 在"0 个夹"时无行可锁，在 `uk_user_default` 上锁
  不存在的行 = gap lock（正是本仓**明文排除** `FOR UPDATE` 的那个死锁来源），唯一干净的对象
  `users` 是**别域的表**；
  ③ 要覆盖**全部**写点才有意义，且 `createFolder` 现在**没有事务**（上锁必须连带给它加上）。
- 未结账 ⇒ `FURTHER_ISSUES.md` **F-23**（推翻条件 = 出现真实流量 / 上限要被当**权益或计费**用
  ⇒ 届时走**计数列 + 原子条件 `UPDATE`**，**不要**上用户行锁）。

### 三.3 为什么不给 `favorite_folder` 加 `item_count` 计数列（2026-10-14 议过，**本期不加**）

- 加它的**真正动机不是"省一次 COUNT"**：现在的 COUNT 走 `uk_folder_content` /
  `idx_folder_time` 的**前导列**（覆盖索引扫描，量级 ∝ 夹内条数且**被上限本身封顶**）。
  真正值钱的是另外两条：① **把软上限变硬**（`UPDATE … SET item_count = item_count + 1
  WHERE id = ? AND item_count < limit` —— coupon 域 `stock` 那种"**判定与扣减不可分割**"，
  实测先例 `CouponConcurrencyTests`）；② 列表端少一次聚合。
- 代价是**动 schema**（V4 会被占用 ⇒ T17 的 `watch_later` 顺延 V5，连带三处文档）+ **5 个写点维护**
  （`add` / `remove` / `move`×2 / `deleteFolder`）+ 回填 + **一条新不变量**（列 = `COUNT(*)`，
  与 F-04 ~ F-07 那族"冗余列 vs 明细"同类）。
- ⇒ 与 T16 红线④「上限不进 schema」冲突 ⇒ 属**独立一题**（"计数类约束的原子化"）。
  ★ 本期顺手产出它的**对照面 = 那条 COUNT 的访问计划**（`EXPLAIN` 落在
  `FavoriteItemDao.countByFolderId` 注释里）—— ⚠️ **只有计划形态、没有耗时**（夹具只证明功能、未计时）
  ⇒ 将来按 `CURRENT_NEEDS.md` **C-6** 决策时**必须先补耗时基线**，本处不预先宣告它是"性能结论"。

## 四、稍后再看（独立表 + 独立端点）

```sql
CREATE TABLE IF NOT EXISTS `watch_later` (
  `id`          bigint NOT NULL AUTO_INCREMENT,
  `user_id`     bigint NOT NULL,
  `content_id`  bigint NOT NULL,
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_content` (`user_id`,`content_id`),   -- 幂等靠唯一键：重复 add 撞它 ⇒ 只更新时间（移到最前）
  KEY `idx_user_time` (`user_id`,`create_time`)            -- 倒序分页
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- ⚠️ 结构变更走 **V4**（V1 / V2 / V3 已应用 ⇒ **逐字节冻结、连注释都不能改**，
  见 `architecture/tech/数据与Schema演进.md` §2.4）。
- 列表**复用同一条装载契约**（`ContentService.loadContentVOs`）⇒ 失效占位口径
  （`收藏功能-分期与设计.md` **§3.5**）**自动一致**；**不得**自持第二份封面 / URL 实现（一期 I-07 的教训）。
- **域归属 = 留在 `favorite` 域内**（`favorite/{controller,service,dao,model}` + `mapper/WatchLaterMapper.xml`），
  **不新开域** —— 它要复用本域的装载契约与失效口径；新开域只会多出一条跨域边 + 一次
  `ArchitectureTests.DOMAINS` 登记。
- **"挪进普通夹"** = 一次"加入目标夹 + 从稍后再看移除"；⚠️ 它不是 `favorite` 的 `move`
  （两个列表不同源），语义与失败面要单独定（见下 §四.2）。

### 四.1 三条实测语义（用户 2026-10-14 拍板；需求篇 §六 是用户视角事实源）

| 语义 | 落地口径 |
|---|---|
| **只能加视频** | `add`（与 `move`）要求内容 **`type = 1` 且未软删**：不存在 / 已软删 ⇒ **404**；存在但非视频（`type = 2` 图文）⇒ **400**「只能添加视频」。⇒ 表里**只有视频行**，列表 VO 不必带 `type` |
| **重复添加 ⇒ 移到最前** | `add` 用 `INSERT … ON DUPLICATE KEY UPDATE create_time = CURRENT_TIMESTAMP`（撞 `uk_user_content`）：**不新增行、不改 `id`、只把时间刷成现在** ⇒ 按 `create_time DESC` 重排即到最前。排序 `create_time DESC, id DESC`（同 `favorite_item` 的 tie-breaker 口径） |
| **除清单外无状态显示** | ★ **红线**：**不新增** `/watchlater/status`、**不**把"是否在稍后再看"塞进 `interaction` / `/favorite/status` / 任何 `Content*VO`。⇒ 唯一可见处是 `/watchlater/list` 本身 |

### 四.2 `add` / `remove` / `move` 的口径与失败面

- **`add` 容量（100，配置常量）**：★ 判据用 `COUNT(*) WHERE user_id = ? AND content_id <> ?`（**排除自身**）——
  这样"**已在池中的内容再次加入**"（移到最前）在**已满时仍成功**，只有"加**新**内容且已满"才 **400**。
  与 T16 同族：**状态型 400、软上限**（`COUNT → INSERT` 非原子），档位仍是配置常量（不进 schema）。
- **`add` 幂等**：不"先查后插"——重复由唯一键 + `ON DUPLICATE KEY UPDATE` 兜（同 `uk_folder_content` 的做法）。
- **`remove` = 批量**（`contentIds` 列表）：★ 同 **G11** 的理由 —— **不校验内容存在性**（失效条目必须删得掉）、幂等（0 行不算错）；空集 ⇒ 400。
- **`move`**：`contentId` + **`folderId` 缺省 = 默认夹（懒建）**（同 `/favorite/add` 的 `folderId` 语义）。
  实现 = **同事务**内"加入目标夹 + 从稍后再看删行"；"加入目标夹"**复用 `FavoriteService.addItem`**
  （它已含内容存在性 / 归属 / 容量 / `favorite_count` 重算 / 缓存失效四件事，别重写）。
  失败面：**非视频 400 / 内容不存在或失效 404**（R-07「失效不可移入」）→ **目标夹不存在 404 / 非我 403 /
  目标夹已满 400**（T16）→ **目标夹已有同内容 409**（撞 `uk_folder_content`，稍后再看**保留**）。
- **不做缓存**：与"我的夹列表 / 夹内列表刻意不缓存"一致 —— 稍后再看是**低频私有读**，无热路径需求。

### 四.3 端点与鉴权

**端点草图**（沿用**逐端点** `@RequiresLogin`，**绝不**加类级）：

| 端点 | 鉴权 | 说明 |
|---|---|---|
| `GET /watchlater/list` | 登录 | 分页信封 `PageResult<WatchLaterItemVO>`，按 `create_time` 倒序；出参**新 VO**（D3） |
| `POST /watchlater/add` | 登录 | form：`contentId`（**只视频**；重复 ⇒ 移到最前） |
| `POST /watchlater/remove` | 登录 | form：`contentIds`（批量；**不校验存在性**、幂等） |
| `POST /watchlater/move` | 登录 | form：`contentId` + `folderId`（**缺省=默认夹**）⇒ 挪进普通夹 |

- **列表 VO** = 新建 `WatchLaterItemVO`（D3，2026-10-14 拍板）：键集 = `{contentId, addedTime, invalid, title,
  coverUrl, authorName}` —— 与 `FavoriteItemVO` **同形但用 `addedTime`**（不借收藏语义的字段名）；
  **不含** `id`（移出按 `contentId`、渲染按 `contentId` 定位，`uk_user_content` 保证其唯一）。
- **鉴权机制级**锚点：`SecurityContractTests` 补一组"四端点判为需登录"（该域**不得**用类级注解）。

## 五、他人公开夹"点开看内容"（⚠️ 破公开面键集）

- `PublicFavoriteFolderVO` **加 `id`** ⇒ ★ **必须同步改 `FavoritePrivacyTests` 的键集断言** ——
  那个类的注释里那句"**将来若真要做'打开他人公开夹'，届时加 id 时必须同步改键集断言**"就是为这一刻写的。
- 新端点 `GET /favorite/folder/items?folderId=X`：
  - **匿名可访问**（同 `/favorite/folder/public`，**逐端点**声明；⚠️ **绝不加类级 `@RequiresLogin`**，

- 前端：他人主页的公开夹从"只列名称 + 数量"改为**可点开**（涉及 `static/static/js/views/user.js` 与 `api.js` 端点清单注释）。
