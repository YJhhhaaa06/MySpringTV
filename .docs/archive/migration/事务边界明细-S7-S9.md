| `MediaAuditService:167` | `restoreMedia` | ✅ **保持单事务** | `@Transactional` 包「找媒体行（404）+ 路径/扩展名校验（400）+ 写文件 + 两条 `updateFileExists`」。⚠️ **写文件在事务内、与 DB 提交无法原子**（TV 原样）：DB 回滚时**已写文件会残留**——与 S7 的"落盘/提交无法原子"同族，**保持旧口径不改进** |

**配套四行**：

1. **`hideContent` 的三条提交后失效 = 复用既有订阅方（零新代码）**。TV 下架后依次调
   `contentCache.removeContent` + `commentCache.invalidateComments` + `likeService.deleteContentLike`；
   S6-B2 起这三件事已由「内容域发 `REMOVE`、评论域与点赞域各自订阅」承接
   （`ContentRemovedCommentListener` / `ContentRemovedLikeListener`）。故 `hideContent` 只发一次
   `remove(contentId)`，**效果与 TV 逐条等价**（A10 闭合）。
2. **`unhideContent` 只发 `refresh`**（TV 只调 `contentCache.refreshContent`，不碰评论/点赞缓存）——
   逐字对齐。
3. **鉴权零改动**：`/api/admin` 前缀的 `role==1` 判定已在 `JwtAuthFilter.isAdminPath`（S6-B1 走
   `AdminChecker` 端口）。本切片只在三个控制器上加**类级** `@RequiresLogin`——这一步**不能省**：
   缺它时匿名请求会掉进第 3 段判成 **403**（TV 是 401），与旧契约不符。
4. **`AdminContentVO` 落 content 域**（`content/model/vo`）而非 `admin/model/vo`：`ContentDao`
   是它的生产方，放 admin 域会让 `content ⇄ admin` 成环（与 S6 消环的纪律冲突）。TV 原在
   `admin/model/vo`，此处**有意迁移位置**（《决策留痕表》C-6）。

**C 保真度提问**：本切片要搬某块基建吗？→ **是：MQ**。结论（《决策留痕表》C-7）：

- **交 Spring AMQP 原生**：拓扑（`Declarables` + `RabbitAdmin`）、连接/自动恢复（`CachingConnectionFactory`）、
  消费有限重试（`listener.simple.retry.*`）+ DLQ（`default-requeue-rejected=false` + 队列 DLX 参数）、预取（`prefetch=1`）。
- **原样搬（JDK 零依赖）**：`InboxRebuildDebouncer`（per-user 尾沿去抖）——这是**语义合并**机制，不在 MQ 职责内。
- **登记为 B 类裁剪（无 owner）**：`MqDeliveryDispatcher`（异步投递线程池）与 `MqDeliveryBuffer`（内存补偿缓冲）。
  RT 解耦改用"**发布不等 publisher-confirm**"（TV 建 dispatcher 的唯一理由就是"等 confirm 阻塞 Web 线程"；
  不等 confirm ⇒ 天然不阻塞）。影响与补回位置见《遗留台账》B8/B9。

**配套四行**：

1. **提交后副作用（模式 A）**：`FeedInboxWriter.fanout` 的"落库后失效缓存"与旧"按代码行序 + 注释"
   同构，但**不必再用 AFTER_COMMIT**——本链**本身就在 MQ 消费线程**里（非事务上下文），
   "先 DB 真相、后缓存失效"的三步顺序是**方法体内的行序**，与 TV 逐字一致。⚠️ 这一条与 S3~S8 的
   "副作用改事件"**刻意不同**：那些是 Web 线程事务后的副作用，本链没有外层事务可挂。
2. **重建红线顺序（保持）**：`replaceWindow` 事务内**先 `DELETE` 后重查、其后不得再删**，窗口写入用
   `INSERT IGNORE`（幂等、不删）⇒ 并发 fanout 增量只会**并集**进来（"只多不丢"）。挪动顺序=丢消息。
3. **重建读关注集走 DB 真值**（`getAllFollowedUserIds`），**不读 `FollowCache`**——与"核对 oracle 同源"，
   且窗口成本 ∝ 关注数 × K，缓存窗口读会引入与"当前快照"不同的时序。
4. **`FeedBigVRouter` 的判定输入**：① 名单（`BigVProperties.userIds`）② `auto_bigv` 状态表（**滞回产物**）
   ③ `users.follower_count >= 阈值`（**冷启动 / 历史数据未入状态表的兜底**，不可省——否则已达标作者
   会因"没有状态行"被突然降级）。**三路并集**，与 TV 逐字一致。
