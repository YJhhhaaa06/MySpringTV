## 二、T7-0：反面盘点（**独立工具任务**）

> 与第三批 T1 同性质：**纯工具，不含任何业务代码**，且是后续任务的判据来源。
> 老项目已有正范式可参考：`tools/endpoint_matrix.py`（正则启发式 + 明确声明局限）。

### 它要回答什么

> **老项目 `src/main` 的每一个资产，在本仓的"去向"是什么？**

范围（实测口径，别按印象写）：`old-project/TVhomework1/src/main` 下
**160 个 `.java`** + **20 个 `webapp/` 文件** + **1 个 `app.properties`** + **1 个 `pom.xml`**（依赖清单）。

### ★ 做法：按行为域分组，**不要**做"文件 × 文件"对照表

这是本任务最容易被做错的地方。台账自己登记过这条教训（《遗留台账》B2 段）：

> 那张表数的是"源码里字面量 `markEmpty` 的出现次数"……当能力被抽到共享层之后，
> 前者会自动失真——**而且失真方向是"看起来问题更大"**。

⇒ 若按文件/符号对，会产出大量**伪缺口**（150 行手写 IoC 在 Spring 里本就无对应物）
和大量**伪闭合**（同名类 ≠ 同行为）。

**正确形态**：按域分组，判据落到**可观察行为**，每组一行，行数少且每条能验证：

| 域 | 老侧证据 | 判定问题 | 输出类型 |
|---|---|---|---|
| 端点 | servlet + `switch-case` 路由 | 已有（腿 1） | 指针 → 《端点对照表》 |
| 业务行为 | pytest 210 例的用例名 | 每条 ↔ 新测试 | 指针 |
| SQL / DAO | `old-project` 的 mapper XML 语句数 | 语句数 + 表列引用一致性 | **计数 + 一致性** |
| 缓存 | 各域 TTL 键 | TTL 值与失效矩阵 | **逐键对照** |
| MQ | 拓扑 + 三队列 + DLQ TTL | 队列名 / 参数 | 逐项对照 |
| **配置** | `app.properties` **逐键** | 新 `application.yaml` 每个键都有对应，**且值一致** | ★**逐键对照** |
| 过滤器 / 监听器 | `filter/` 5 个 + `AppShutDownListener` | 每个的**能力**是否有人承担 | 逐项对照 |
| 工具 / 异常 / ioc | `util/` 13 + `exception/` 20 + `ioc/` 8 | 替代物 | 指针 |
| 前端 | `webapp/` 20 文件 | 已有（台账 D28） | 指针 |
| 启动期守卫 | `AppShutDownListener.validateUploadPath` | 硬校验是否继承 | 逐项对照 |

> ★ **"配置逐键对照"是最可能翻出真账的一格**：新 yaml 某个键若在 `app.properties`
> 有对应而**值不同**，它**不会让任何测试变红**（正是 B 类同族问题），
> 但会静默改变 TTL / 上限 / 窗口行为。

### `tools/flyway_parity.py`（腿 4 固化）

**背景**：`flyway.baseline-version=0` + `CREATE TABLE IF NOT EXISTS` 的组合意味着
**V1 在已有库上是 no-op** ⇒ "Flyway success"只证明它**没报错**，**不证明两边结构相同**。
而 318 例测试全跑在**由 V1 现建的 Testcontainers** 上 ⇒ 若 V1 与活库有偏差，
就是"测一套结构、跑另一套"。

**2026-10-05 已手工实测通过**（结论见 §六），本任务把它**固化成命令**并纳入常规复算。

- 读 `information_schema` 取活库的表/列集 + 活库 `flyway_schema_history`；
- 与 `V1__baseline_tv_schema.sql` 的建表/列声明做**集合比对**（表名、列名、列数）；
- 输出差异清单；差异非空即 `exit != 0`。

### 交付物与验收

- **交付**：`tools/migration_matrix.py`、`tools/flyway_parity.py`（遵守 `tools/README.md` §三：
  UTF-8 强制 / 路径从仓库根解析 / `--help` / 默认只预演）；`tools/README.md` 补两行。
- **验收**：
  1. `python tools/migration_matrix.py` → 输出**未表态 = 0**（或列出未表态项并 `exit != 0`）；
  2. `python tools/flyway_parity.py` → `exit 0`，且**故意改一处**（如把某个列名改错）能变红；
  3. 两个脚本都 `--help` 自证用法（**不要把用法只写在文档里**）；
  4. 局限必须在脚本头部声明（同 `endpoint_matrix.py`：正则启发式 ≠ 人核）。

### ★ 前置：**老项目已停用，新项目成为唯一写方**

**已确认前提（2026-10-05，用户拍板）**：`old-project/TVhomework1` **已停用，只读留存作行为规格**。

这条前提解锁了本仓此前**做不到**的事，也必须先写下来（已登记《决策留痕表》**K-1**）：

1. **新项目是 `TVDatabase` 与 `stone` 的唯一写方** ⇒ 一次性对账/重算是**安全的**，
   不会出现"两个代码库互相破坏对方不变量"；
2. **共库共媒体根**在这里从负债变成资产：老库**就是**老项目真实语义的对照组
   （老 e2e 当年跑在它上面），不必靠 Testcontainers 重建；
3. ⚠️ **代价**：老库 `flyway_schema_history` 是**两边共享的 Flyway 状态**
   ⇒ 本仓从此**不能随意改 V1**（改了 V1 的库与活库会分叉，且 baseline 行不会重算）。

### ★ 双趟探针：**基线那一遍必须在任何写操作之前**

单跑一遍探针**什么都证明不了**——同一份发现，可能是"迁移引入的回归"，也可能是
"老库本来就烂"，而**没有任何东西能区分这两者**。方法：

```
① 备份 TVDatabase  +  保全 stone 的目录/文件清单（媒体侧基线同等重要）
② 探针对着【备份】跑  → baseline.json      ← ★ 唯一一次机会
③ 探针对着【活库】跑  → now.json
④ 做差 → 三张清单（见下）
```

| 集合关系 | 结论 | 归属 |
|---|---|---|
| 发现 ∈ baseline | **存量脏数据**，不是迁移引入 | 《遗留台账》**E 类** |
| 发现 ∈ now \ baseline | ★ **新项目引入的** | **迁移缺口，T7 内必须处置** |
| ∈ 两者 ∩，但新代码读它不出错 | 存量脏数据且已被容错 | E 类，登记即可 |

> ⚠️ **② 必须在 ③ 之前，且只有一次机会。** 新项目一旦开始写库（T6 走查已留下
> `users.id=227` 与一条券订单），"老项目自证的那份数据"就**永久拿不回来了**。

### 探针输出的**形态**：三张清单，不是"问题数"

异常清单**每条若只登记成台账一行是太粗的**——必须**分类**，因为三类的出口完全不同：

| 清单 | 判据 | 出口 | 影响结项？ |
|---|---|---|---|
| **① 代码缺口** | 探针跑出的 500 / 400 / 解析失败 / 空指针 | **T7 内修代码** + 补一条测试钉住 | ✅ **是**（必须清零） |
| **② 存量脏数据** | baseline 有、不致命 | 《遗留台账》**E 类**，分"可对账 / 不可对账" | ❌ 否，但**每条都要表态** |
| **③ 口径未定** | 探针**无法判断对错**的 | 《决策留痕表》→ 定口径 → 权威实现重算 | ❌ 否 |

**①为什么必须最先清零**：在"会 500 的状态"上跑对账，等于在一个不确定的地基上做修复。

### 逐项检查清单（由 T7-0 的域清单导出）

| # | 检查 | 为什么只有真数据能暴露 |
|---|------|---------------------|
| 1 | 存量行是否违反新代码假设（NULL 进非空、`type`/`sort` 越界、时间倒挂） | 容器数据是**现造**的，天然合法 |
| 2 | `content_media.url` → `stone` 磁盘文件的匹配率 | 存量孤儿/缺失的**分布**只在真数据上存在（正是 `MediaAuditService` 要处理的场景） |
| 3 | 计数列 vs 明细表实际行数（`content.comment_count`/`like_count`、`users.follow_count`/`follower_count`、`comment.like_count`） | 老项目是直改库测试的，明细/计数**可能本就不一致** |
| 4 | `feed_inbox` / `feed_inbox_sync` 孤儿行 | 读侧假设"有同步行就得有窗口" |
| 5 | **读接口对全部存量 id 不 500**（`/start`、`/search/IdSearch`、`/search/keywordSearch`、`/profile`、`/comment/show`、`/feed`） | 这才是"存量数据能被业务规则读出" |

### ★★ 计数列的一个真实隐患（**必须在任何写操作之前处理**）

2026-10-05 实测（`information_schema` + `sql_mode`）：

| 列 | 类型 | `+ delta` 下溢后果 |
|---|---|---|
| `content.like_count` / `content.comment_count` | **`int unsigned`** | ★ **500**（`sql_mode` 含 `STRICT_TRANS_TABLES`） |
| `users.follow_count` / `users.follower_count` | **`int unsigned`** | ★ **500** |
| `comment.like_count` | `int`（**有符号**） | 静默变负数 |

而所有 `update … = col + delta` 语句都是**一字未改、没有防负守卫**
（`ContentMapper.xml` / `UserMapper.xml` 的注释均明确写了这一点）。

> **⇒ 若存量里存在 `like_count=0` 但明细有赞的内容行，用户点一次"取消赞"会 500。**
> 老项目同代码，**所以这大概率是继承的债**——但它现在**变成我们的了**：
> 新项目是唯一写方之后，"谁来回滚这个不一致"的答案是**我们**。

**处置**：探针检查 #3 必须**在任何写操作之前**跑，因为它决定了能不能安全地接受用户写操作。

### 存量数据的**逐列分级**（E 类的处置口径）

| 子类 | 处置 |
|---|---|
| **计数列不一致** | ✅ **可对账**（老项目停用 ⇒ 新项目唯一写方 ⇒ 对账后长期自洽）。⚠️ **必须先定口径**——"计数含不含软删行"（`CommentMapper.xml` 那条"先软删会把楼内回复也置 1"的注释证明这里真有过坑）；口径不定就对账 = 白干 |
| **`file_exists` / `last_verify_time`** | ✅ **不用修数据**：它是**可重算的缓存**，`MediaAuditService.scanAll()`（`POST /api/admin/media/scan`）本来就重算并回写 |
| **孤儿媒体行**（`content_id` 不在 `content` 里） | ❌ **不可对账**：没有内容行可回填聚合。只能登记（它们本就不参与聚合，是 `orphanMediaIds` 的**合法输出**） |
| **Redis 里与 DB 不一致的 key** | ❌ 不算账：缓存本就允许陈旧（有 TTL / 失效机制） |

> ★ **按列类型分，不要按行分**——这一格的结论对全部同类行一次性成立。

## 五、为什么**不做**"复用老 210 条 e2e"

第三批收尾后曾考虑"把老 pytest 套件改路径后复用来做端到端验证"。**结论：不做**，理由已实测：

| 判据 | 实测事实 |
|---|---|
| 断言改动量 | **比看上去轻**：老套件断言写的是 `body.get("code") == 400`，而新契约 D-14 是"HTTP status = code，**body 仍带 `{code,msg}`**" ⇒ **取到的值不变**，断言基本不用改（`["code"]` 直取写法全仓仅 2 处、`status_code==200` 仅 3 处） |
| 适配改动量 | **不轻**：`headers={"token": …}` **148 处内联、分布 20 个文件**（`Authorization` 出现 **0** 次）；登录 `{account}` 15 处 / 6 文件 |
| ★ **不可脚本化的阻断** | `conftest.py` 的测试装置**绑死"老项目固件"**：`STONE_DIR` 默认 `.stage8-target/media-test`、`ACCESS_LOG_DIR` 默认老实例日志目录、`EXPIRED_COUPON_ID = 6`（硬编码"测试库重建自某份 db.sql"）、`SEED_*_PREFIX`（依赖 `init_test_db.py` 种子）⇒ **照跑会连到错的地方** |
| ★ **方向性冲突** | 《测试策略》§6.2 已定：**e2e 是行为规格、单测是实现细节规格，同一行为不必映射两次**。老 210 条的**行为规格已被翻译进新 318 例**；再跑一遍，查的是"同一行为规格 × **老数据**"——而"老数据"这一面**恰恰由 T7-1 的探针覆盖**，且探针秒级、只读、不产生第二套测试事实源 |

> **净结论**：复用买到的东西（老数据面上的验证）**已被 T7-1 以更低成本覆盖**；
> 而它要的代价是一个 **20+ 文件的适配层 + 第二套会漂移的测试事实源**。
> 本批**明确表态不做**，记在此处以免下次重新论证。
