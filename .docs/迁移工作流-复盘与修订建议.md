# 迁移工作流复盘（S1–S3 实测）与修订建议

> 生成时间：2026-10-02
> 用途：**新窗口开工前先读本文，再读《迁移工作流-切片SOP.md》**。
> 本文只写"流程真的有问题的地方"与"最小修订"，不复述 SOP 已有的内容。
> 证据来源：S1(coupon) / S2(comment 写路径) / S3(like) 三次完整切片，九步全部走完。
> 基调：SOP 的主体（迁移口径 + 坑清单）是这三片里最值钱的东西，**不要改**。
> 问题集中在**两处门禁**——开工前的"填决策表"与收尾的"DoD 六条"。

---

## 〇、一句话结论

**SOP 的两个门禁都在检查最便宜的东西：**

| 门禁 | 检查什么 | 三片实测结果 |
|------|---------|------------|
| 开工前 | 事务边界（要"逐条表态、无 🔴"） | 14 处里**真正需要拍板的 0 处**（7 处 ✅保持、5 处去事务——全是模式套用；2 处是范围划转） |
| 收尾 | 反模式 grep 必须零命中 | 三片累计命中 36 次，**全是 Javadoc 注释行**；从未抓到过东西 |

**而三次真正阻塞/改变计划的事，两件都不在这两个门禁的检查范围里：**

| 切片 | 真正需要拍板的事 | 现有门禁是否覆盖 |
|------|----------------|----------------|
| S1 | 无（计划里的 3 条预判全中） | — |
| S2 | **切片范围**：`/comment/show` 的实现在**另一个模块的 Service** 里，comment 必须缩窄 | ❌ 不在事务表字段内 |
| S3 | **保真度尺度**：缓存基建搬多少（TV `cache` 包 2,528 行 vs 自建 250 行） | ❌ 同上 |
| S2 / S3 | **两个"声明了但没生效"的机制**（`@Transactional` 自调用、`@RequiresLogin`） | ❌ DoD 无此项 |

S2/S3 各**中途打断一次**去向用户提问——两次都是因为上述问题在执行期才浮现。

---

## 一、问题清单（按"真的很有问题"排序）

### 问题 1（最严重）：开工前门禁查错了维度

**事务边界是低风险项，范围与保真度才是高风险项。**

14 处事务边界的实际决策：`✅保持`（写操作要原子——这几乎不需要决策）×7、`⚠️去事务`（纯读，
模式 C 早已定调）×5、`划归后续切片`×2。**没有一处需要"拍板"。**

而版本库里的**真决策**（缓存层大幅精简、缓存失效裁剪、评论区开关改读 DB、重复抢券 msg 变化、
`couponId` 校验改 400、读路径划归 S5…）**几乎都不是事务边界**。

> 根因：决策表的字段是"旧行为 / 决策 / 新实现"，天生装不下「**这个切片该覆盖到哪**」
> 和「**保真到什么程度**」这两个维度。

**后果**：这两件事每次都被推到执行中途才浮现 → 只能中途打断去问（S2/S3 各一次）。
若在规划期就做，成本更低、可选项更多（那时还没有代码和测试要调整）。

### 问题 2：切片计划的规模估法（文件数/行数/事务数）与实际工作量几乎无关

- S2 计划估 **930 行** → 真实需要 **3000+ 行**（因为端点在别人 Service 里，会拖进 8 处事务的缓存类）
- S1 计划估 **231 行** → 实际 7 个实现文件 + 3 个测试类（方向相反，但同样偏）
- 真正决定工作量的三个量是：**端点调用链深度 / 依赖模块是否已就位 / 保真尺度**。
  三者都不在估算口径里。

**修订**：计划里每个切片加一张「**端点 → 实现入口 → 依赖模块**」三列清单。
S2/S3 都是新窗口自己现做这张表才发现问题的——**做一次只要几分钟，能省掉中途返工。**

### 问题 3：DoD 缺一条 —— 没有任何一项要求证明「声明式机制真的生效」

三片里两次发现坏掉的机制，**都不是 SOP 查出来的**，而是"为了别的目的写测试"时偶然撞上的：

| 机制 | 怎么坏的 | 为什么 DoD 全绿却没发现 |
|------|---------|----------------------|
| `@Transactional`（slice 0） | 同类自调用绕过代理 | 测试直调了 service（走代理的那条路），线上走自调用 |
| `@RequiresLogin`（切片 0 起） | 拿到 `HandlerExecutionChain` 却按 `HandlerMethod` 判断 | 断言"无 token → 401"通过了——**401 来自 `@CurrentUserId` 解析器，不是鉴权机制** |

两者都能**六条 DoD 全绿地交付**。这是结构性缺口：
**DoD 查"旧模式有没有残留"（面向过去），不查"新机制有没有在工作"（面向现在）。**

### 问题 4：反模式 grep 是一条"永远绿"的仪式

三片命中 7 / 12 / 17 处，**全部是 Javadoc 注释行**，零真实命中，从未抓到东西。
原因很简单：**新代码不可能再写 `Connection conn`**——这条检查在验收阶段没有发现能力。

它真正的价值在**写作阶段**（提醒你别写旧模式），不在验收阶段。
现在把它摆在 DoD 里，会造成"我们已经排除旧模式了"的错觉，而它什么都排除不了。

### 问题 5：「环境隔离验证」对不依赖该依赖的切片是空验

S1/S2 停掉宿主 `redis`/`rabbitmq`——那两片**根本不碰 Redis**，停不停都会绿，**零信息量**。
直到 S3 才让这条真正有分量。但 SOP 把它写成通用 DoD 项，很容易被当成"已验证"。

**修订**：DoD 每条都标注「本切片是否有信息量」，无信息量的写 `—`，不许一律打勾。

### 问题 6：SOP 假设"老项目是可靠规格书"，但实测它有明确的错与不一致，而 SOP 没给判断标准

三片实测到的规格缺陷：

- `CommandConverter.commentToCommand` 对 `contentId == 0` 抛的是「未指定被**点赞**内容」
  ——评论接口里混进了点赞域的复制粘贴错文案
- **守卫不一致**：`comment.reply_count` 有防负守卫（`reply_count + ? >= 0`），
  而 `content.comment_count` / `content.like_count` / `comment.like_count` **都没有**
- **类型不一致**：`content.like_count` 是 `int unsigned`（0 时再 −1 会报错 → 500），
  `comment.like_count` 是有符号 `int`（同场景静默变 −1）
- **文案不一致**：取消未点赞，内容侧「无法取消」/ 评论侧「不可取消」

SOP 的判定顺序只覆盖「**不明确** → 挂起问人」，**没覆盖「明确是错的、但属于既有行为」**
——而这一类比"不明确"更常见。

> 三片采用的处置标准（**有效，建议写进 SOP**）：**原样保留 + 文档记明 + 不修**。
> 理由：修它就是行为改动，需单独立项，且必须让 DoD 明确"这是改进不是回归"。

### 问题 7：决策表的名字与用途不匹配——重要决策无处安放

表名叫"**事务边界**决策表"，实际被当作"**所有需要留痕的决策**"在用。
结果：真正需要追溯的决策大部分塞进了提交信息——**提交信息可读但不可检索**，
而这张可检索的表又装不下它们。

**修订（低成本）**：另立一份并列的「**非事务决策表**」（或把现表升格为"决策留痕表"，
事务只是其中一个分组），把问题 1 里那类决策（范围 / 保真度 / 契约差异）放进去。

## 二、最小修订（新窗口直接照做，**不必重写 SOP**）

### A. 开工前门禁改造（先做这三件，**再**填事务表）

1. **端点清单**：`端点 → controller 方法 → service 实现所在模块`
   （专治"实现在别人 Service 里"，S2 就是靠它发现 `/comment/show` 的实际入口）
2. **依赖清单**：每个外部依赖标注「已就位 / 本切片一并交 / 划归哪个切片」
3. **保真度提问**：本切片要不要搬某块基建？若要，先回答「**它能不能开箱即用**」
   ——做法是扫一遍它的 import 依赖面（S3 就是这么发现 `cache` 包有 10 类待改件的）。
   **结论必须落纸**，否则下一个切片会重新论证一遍。

> 顺序很重要：**范围定了，事务边界才有正确的边界。** 先填表＝在错的边界上做正确的事。

### B. DoD 增两条（原六条照旧）

**第 7 条：声明式机制生效证明。**
本切片用到的每个声明式机制（`@Transactional` / `@RequiresLogin` / `@TransactionalEventListener` /
校验注解…）**至少一条直接测机制的测试**。
判据是一个自问：「**这个断言的结果还可能由谁产生？**」若还有别的来源，就还没测到目标机制。
参考实现：
- 鉴权 → `SecurityContractTests`（直接对 `RequestMappingLookup` 求值）
- `AFTER_COMMIT` → `LikeCacheTests.事务回滚后缓存未被污染`（+ 必须有反向对照）
- 事务 → `CommentCounterTests.删除时计数失败则软删回滚`

**第 8 条：DoD 每条标注「本切片是否有信息量」。** 无信息量的写 `—`（治问题 5）。

### C. 降级两条（不是删，是改用法）

- **反模式 grep**：保留，但定位为"**写作期自查提示**"，从 DoD 的核心项降到附带项（问题 4）。
- **环境隔离验证**：只在切片**真的依赖**被停的那个依赖时才算 DoD（问题 5）。

## 三、这些别动（三片实测都成立）

- 「老项目是**行为规格书**，不是源码来源」+ 三层三套命运（SQL 复制 / 语义重写 / 管道删掉）
  ——三片下来完全成立，是这份 SOP 最值钱的部分
- **关键计数走独立 oracle**（直接查列 / `COUNT(*)`，不信接口回显）——真的挡住过"测试迎合"
- **不搬无主代码**（S1 的 `findById`、S2 的读路径方法、S3 的 `deleteByContentId` 全都没搬）
- **提交信息记录 diff 看不见的决策**
- **坑清单（§二）**：三片新增 6 条（10–15），**全部是"不报错"类**，全部值得留
- 反模式清单的**写作期**提醒作用（见 §二 C）

---

## 四、给新窗口的三条操作性建议

1. **先读本文 §二，再读 SOP**；§二 A 做完再动代码。
2. **依赖与保真度结论做完就落纸**（写进决策表或计划），别只放脑子里
   ——S3 的 `cache` 包结论若不落纸，S5（要搬 `ContentCache` 5 处 + `CommentCache` 8 处事务）
   会把同一场论证重做一遍。
3. **写测试时先想"要证明什么机制"，再想"覆盖哪些分支"。**
   三片里真正发现问题的测试全是前者的写法；纯分支枚举型测试**一次都没发现过缺陷**。

## 五、一句诚实的自我评价

三次切片里，SOP 帮我避免的是**环境与技术类**问题——坑清单极有效；
**没**帮我避免**判断类**问题（范围、保真度、机制生效）——那三次都是靠"停下来自己去查 / 去问"
解决的，不是靠流程给的保障。

所以这份 SOP 的性质是：**一份很好的"操作手册" + 一份偏弱的"决策框架"**。

新窗口如果只照 SOP §一（标准流程）走，会重复我三次的中途打断；
把本文 §二 A / B 补上，打断次数应该能降到 0–1 次。
