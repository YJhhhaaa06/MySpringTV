## 〇、本批范围与设计决策

### 关键设计决策：content 必须拆成「薄」与「全」

实测 `content` 是 23 文件 / 3,806 行 / 11 处事务的巨模块。而下游 `comment` 与 `like`
**只需要它的 3 个方法**（`isContentExist` / `updateLikeCount` / `updateCommentCount`），
其余 21 个方法（feed 窗口、关键词搜索、admin 列表、文件校验）属读路径与管理面。

若不拆分，`content` 会成为所有下游切片的阻塞源。故：

- **content-thin**：只搬存在性检查 + 计数增减（约 3 个 DAO 方法）→ 解锁 comment / like
- **content-full**：读路径 + 搜索 + admin → 留到本批之后（它自己就是大切片）

⚠️ **content-thin 不单独成切片**：它没有对外端点，无法独立验收。
把它并入 S2（comment），作为"为交付 comment 所必需的薄依赖"。

### 依赖关系（实测）

```
coupon ──── 独立，零跨模块依赖
             │
content-thin ┤（只搬 3 个方法）
             ├──► comment（需 content 存在性检查）
             │        │
             │        └──► like（需 comment + content）
             │
user（已完成）├──► follow（需 user，已就位）
```

## 一、S1：coupon 切片

**规模**：4 文件 / 231 行 / 3 处事务 · **跨模块依赖：无** · **状态**：可立即开工

### 为什么排第一
唯一**零跨模块依赖**的模块，且能演练 user 切片没有的新模式（并发安全 + 唯一键竞态）。

### 事务边界（开工前先填表确认）

| 方法 | 旧行为 | 预判决策 |
|------|--------|---------|
| `grabCoupon` | 单事务包住"扣库存 + 插订单" | ✅ 保持，`@Transactional` |
| `listAvailableCoupons` | 用事务只为取连接，纯读 | ⚠️ 去掉事务（同 U-3/U-4） |
| `listMyCoupons` | 同上，纯读 | ⚠️ 去掉事务 |

### 必须保真的并发语义（**本切片的重点**）

1. **扣库存靠单条原子 SQL**，不是"先查再扣"：

   ```sql
   UPDATE coupon SET stock = stock - 1
   WHERE id = ? AND stock > 0 AND begin_time <= NOW() AND end_time >= NOW()
   ```
   `rows == 0` ⇒ 抛 `ConflictException("库存不足或活动未开始/已结束")`。
   **活动时间窗判断也在 SQL 里**，不要挪到 Java（否则引入 TOCTOU 窗口）。

2. **重复领取靠唯一键兜底**：旧代码手工判 `e.getErrorCode() == 1062` 抛
   `ConflictException("您已抢过该优惠券")`。
   新写法**删掉错误码判断**——Spring 把 1062 翻译成 `DuplicateKeyException`
   （`DataAccessException` 子类），由异常出口统一映射为 409。
   《事务边界决策表》U-2 补注已预告过这个映射点。

3. **券码生成**：`UUID` 去横线取前 16 位转大写（旧实现原样保留）。

### 验收要点
- 抢券成功：`coupon_order` 新增一行、`coupon.stock` 减 1、返回 16 位券码
- 库存为 0：409，且**不产生订单行**、库存不为负
- 活动未开始 / 已结束：409（时间窗判定在 SQL 内）
- 同一用户重复抢：409 + "已抢过"，且库存**只扣一次**（关键：验证事务回滚）
- 我的优惠券 / 可用优惠券列表：形状与旧版一致
- **并发用例**：N 个线程抢库存 1 的券 → 恰好 1 成功、库存为 0、订单 1 行
  （这是本切片最有价值的测试，务必写）

### 新增需要的能力
无（Redis / MQ / 新依赖都不需要）

## 二、S2：comment 切片（内含 content-thin）

**规模**：comment 5 文件 / 820 行 / 4 处事务 + content-thin 约 3 个 DAO 方法
**跨模块依赖**：content-thin（本切片一并交付） · **状态**：S1 完成后可开工

### content-thin 的范围（只搬这些，不要多搬）

| 方法 | SQL 口径 |
|------|---------|
| `isContentExist` | 存在性检查（注意 `is_deleted` 口径，需读旧代码确认，**不要想当然**） |
| `updateLikeCount` | `like_count = like_count + ?` |
| `updateCommentCount` | `comment_count = comment_count + ?` |

⚠️ 搬 `isContentExist` 时**必须**确认旧 SQL 是否带 `is_deleted = 0` 条件——
这决定了"给已删除内容评论/点赞"是否被拒。读旧代码，不要推断。

### 本切片要演练的新模式
- **软删除**：`comment.is_deleted` 口径贯穿所有查询
- **楼中楼**：`parent_id` / `reply_to_user_id` / `reply_count` 三者一致性
- **计数联动**：发/删评论要同步 `content.comment_count`（跨表，同一事务）

### 验收要点
- 发评论：`comment` 新增行 + `content.comment_count` +1（同事务，独立 oracle 复算）
- 楼中楼回复：`parent_id` / `reply_to_user_id` 正确，主楼 `reply_count` +1
- 删除评论：软删除（`is_deleted=1`），`comment_count` 相应减少
- 对不存在/已删除内容评论：按旧口径拒绝（**以旧实现为准**）
- 未登录发评论：401（`@RequiresLogin`）
- 评论区开关（`content.comment_enabled`）：是否属本切片需先查 `CommentService` 调用面

### 事务边界
4 处（`CommentService.java:102/115/179/240`），开工前逐条填表。

## 三、S3：like 切片

**规模**：5 文件 / 888 行 / 4 处事务（`LikeService`）+ 3 处（`LikeCacheService`）
**跨模块依赖**：comment（S2）、content（S2 的 content-thin） · **状态**：S2 完成后可开工

### 本切片要演练的新模式
- **首次接入 Redis 缓存语义**（决策⑤的显式封装层，**不用** `@Cacheable`）
- **"提交后副作用"**：旧的缓存更新写在事务 lambda **之后**，靠注释维系
  （`LikeService.java:72` "缓存更新放在事务提交后"）。新写法用
  `@TransactionalEventListener(phase = AFTER_COMMIT)` —— 这是《迁移参照系》§2.4 的落地。
- **计数器 + 记录双写**：`content_like`/`comment_like` 与 `like_count` 同事务

### 验收要点
- 点赞：记录 +1、`like_count` +1、缓存更新**发生在提交后**
  （断言方式：让事务回滚 → 缓存**不得**被更新）
- 重复点赞：409（靠唯一键 `uk_user_content`）
- 取消未点赞的赞：409
- 批量查询点赞状态（`findLikedContentIds` 的 `IN` → `<foreach>`）
- 未登录点赞：401

### ⚠️ 关键测试
**"事务回滚后缓存未被污染"** —— 这是旧代码靠注释纪律维系、最易写错的地方，
必须有测试钉住。可用 `@MockitoSpyBean` 让事务失败，断言缓存未被改动。

## 四、S4：follow 切片（薄版）

**规模**：9 文件 / 1,446 行 / 3 处事务（`FollowService`）+ 4 处（`FollowCache`）
**跨模块依赖**：user（**已完成**）/ content-thin（S2 的） · **状态**：S2 完成后可开工

### 范围裁剪（重要）

`FollowService` 注入 7 个依赖，其中 3 个属 **feed 域**，本批**不搬**：

| 依赖 | 处置 |
|------|------|
| `FollowDao` | ✅ 搬 |
| `UserDao` | ✅ 已就位（需补搬 2 个方法：`updateFollowCount`/`updateFollowerCount`） |
| `FollowCache` | ✅ 搬（539 行，本切片主体） |
| `AutoBigVStateService` | ⚠️ **待定**——它是状态迁移（`auto_bigv` 表写），不是通知。见下方风险 |
| `InboxRebuildNotifier` | ❌ 留后（feed 域） |
| `AuthorBackfillNotifier` | ❌ 留后（feed 域） |
| `InboxRebuildDebouncer` | ❌ 留后（feed 域） |

**交付**：关注 / 取关 / 关注列表 / 粉丝列表 / 计数。

### ⚠️ 必须显式记录的裁剪风险

不搬 notifier ⇒ **关注关系变化不会触达 feed 重建**。
当前无 feed，所以可接受；但**必须在《事务边界决策表》和提交信息里写明这是有意裁剪**，
并指出补回位置（feed 切片时）。否则将来做 feed 会找不到"为什么关注后时间线不更新"的原因。

`AutoBigVStateService` 的取舍：它写 `auto_bigv` 表（滞回判定状态）。
若 `follow` 的计数变更需要同步维护该状态，则应搬；否则留后。
**开工前读 `FollowService.follow()` 实际调用点再定**，不要预设。

### 验收要点
- 关注：`follow` 新增行、双方计数各 ±1（同事务）
- 不能关注自己（若旧实现有此校验，以旧为准）
- 重复关注：409
- 取关未关注：409
- 关注/粉丝列表：顺序口径（旧实现有 `ORDER BY id` 的明确注释，**必须保留**）
- 未登录：401

## 五、S5：content 读路径切片（本批最后、最大）

**规模**：content 剩余部分（约 21 个 DAO 方法 + `ContentService` 11 处事务 + `ContentCache` 5 处）
**跨模块依赖**：user、follow（列表要显示关注状态） · **状态**：S4 完成后可开工

### 为什么放最后
它最复杂（3,806 行），且依赖前面切片的产出（关注状态、点赞状态、评论数）。
先做前面的能让它的测试有真实数据可用。

### 范围
- 内容详情（含作者信息、点赞/关注状态、媒体列表）
- 用户作品列表 / 分页
- 关键词搜索（`FULLTEXT ... WITH PARSER ngram`）
- 文件校验状态（`file_exists` / `last_verify_time`）

### 特别注意
- `ContentCache` 有 **5 处事务**——它是 cache-aside 回填（未命中回源 DB 并可能写库），
  按《迁移参照系》§一 的警告，**不是**纯缓存层
- 分页参数口径：旧实现的分页归一化曾**反复重构四轮**（踩坑清单 §7），
  新写法直接用 Spring 的绑定 + `Pageable` 思路，**不要**复刻旧的归一化逻辑
